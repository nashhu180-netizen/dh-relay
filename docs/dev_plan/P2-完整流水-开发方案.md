## 1. 概述

- **交付什么 / 不含什么**：交付 dh-relay P2 的完整流水：一批 2～3 张已授权标准档任务卡，在无常驻 AI 主控的情况下，从授权、落户、施工、机器闸、两轮代码复核、需求与一致性复核、教训复核、集成协作、收口、逐卡 verify 到 run 归档完整接力；不含 A 立项、B 拆计划、P3 能力、任何 deploy、master/main 远端 push 或跨仓 run。
- **承接设计**：[P2 完整流水产品设计与验收](../design/02-完整流水-产品设计与验收.md) · B1～B18 / H3～H5；[P1 产品设计与验收](../design/01-产品设计与验收.md) · A1～A8 / H1～H2 只作为已实现基线与兼容约束，本计划不重复拆卡。
- **实施策略一句话**：先把隔离守卫立在最前，再并行改造 v1 契约与宿主基础债；随后按协议、宿主、权限主体、收口写者逐层接线，最后把 run 归档写者、宿主外 oracle 和真实批次人验拆成三个独立验收单元。
- **任务前缀 / 模块 slug**：DHR_ / dh-relay，verify scope=dh-relay；任务 ID 从 DHR_04 连续发到 DHR_21。
- **实际卡数说明**：本稿拆为 18 张，比设计估算 14～16 张多 2 张。原因不是扩大范围，而是 DHR-A-05 新增的 run 级 archive 写者不能与“不 import relay 代码”的宿主外 oracle 合并；真实 H3/H4 自举又不能与 oracle 能力建设合并。若压回 16 张，会重新出现“归档写者 + oracle + 真实自举”同卡或把 B9 后移的旧问题。
- **待用户决定**：自举使用哪 2～3 张真实标准档卡、条件适用时使用哪个测试仓与哪份限权凭据，均保持 {待用户定}；选卡原则见 DHR_21，任何任务卡不得替用户预选。

### 3.2 任务卡

#### DHR_04

- **目标**：在任何 P2 生产实现之前，建立一个可独立执行的 fail-closed 守卫，同时约束 dh-relay 自身开发改动、relay 在业务仓的内容写入和宿主外副作用登记。
- **非目标**：不生成 authority snapshot；不实现最终收口 oracle；不替业务仓修改 .gitignore；不把预存同名目录或合法 relay 模块误判为本次违规。
- **验收口径**：
  - **机器证**：[产品设计与验收 B9](../design/02-完整流水-产品设计与验收.md#61-ai-自动验收栏)：以变更前后路径集和回归命令证明 P2 生产代码只改 tools/，dh-crew 代码与 active state 零改动，dh-crew run-all 行为不受影响。
  - **机器证**：[产品设计与验收 B9](../design/02-完整流水-产品设计与验收.md#61-ai-自动验收栏)：用合成 authority snapshot、受限写环境、前后快照、git diff/status 与独立检查结果共同证明业务仓内容写入是允许集合的子集；卡授权的业务代码路径必须可写，未授权路径必须拒绝。
  - **机器证**：[产品设计与验收 B9](../design/02-完整流水-产品设计与验收.md#61-ai-自动验收栏)：本次 run 在 `docs/modules/<模块>/relay/`、`workspace/<卡>/relay/` 等模块下新建带 relay archive/runtime schema 或 marker 的文件夹即失败，legacy 根新写亦失败；分别用“run 前已存在的同名目录”和“合法模块 `docs/modules/relay/`”两条反例证明不得误杀；Git、用户级目录、CLI 与 psmux 副作用分账可观察。
- **变更范围**：tools/policy/、tools/tests/；本卡 workspace。
- **档位**：标准（全程隔离与路径所有权红线）。
- **实施提示**：
  - 守卫默认拒绝，允许集只能从固定根和 authority fixture 推导。
  - 后续每张卡的任务级证据命令都必须包含本守卫，不在后卡重写另一套策略。
  - 业务仓策略先做成只消费正式设计字段的纯守卫，用合成 snapshot 验收；DHR_12 后续只接入宿主生成的真实 snapshot，不得改写策略。
