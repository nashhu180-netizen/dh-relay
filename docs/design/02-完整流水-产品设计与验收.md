## 1. 人话版目标

### 1.1 我们在做什么

我理解你要的是：P1 已经证明"没有常驻 AI 主控，靠文件状态也能接棒"，IHSR_05 也证明一张真实业务卡能在 relay 上跑完六棒。但那一趟还是靠主控会话手写计划、拼包装、盯窗口、亲跑 oracle、亲做收口。**P2 要把主控还在干的活搬进 relay 本身**：

- **relay 只管"已经立项、已经拆好计划、你在对话里授权开工的任务卡"**——立项（A）与拆计划（B）不在 relay 里，仍由你和主会话按 dev-harness 走。
- **你不敲命令行**（用户 2026-08-16 拍板 D14）：你在主会话对话里说"用 relay 跑这几张卡"，主会话先落一份**授权工件**（哪几张卡、什么时候、基于哪个版本的 DevPlan、各卡目标/验收/变更范围快照），再代你在**该仓**把 relay 拉起来；之后从建工作区、施工、机器闸、两轮代码复核、集成与端到端、需求/一致性复核、教训复核，到收口销户，全程由确定性 Runner 按接力计划接棒，每张卡各自 verify 销户。
- 你只在**agent 弹出的窗口里说话**：落户确认、偶尔的决策、真机端到端协作、收口确认、异常时的诊断问答；不敲命令行、不依赖飞书。
- 终端全关、隔天再来：磁盘上的接力计划和进度都在，主会话代你续（或双击快捷方式打开 `relay` 控制台按编号选一个 run），断掉的棒由诊断 agent 带你接上。

一句话：**P2 交付"一批已授权任务卡从落户到销户的无常驻 AI 主控接力"，可从任意仓发起、可跨天接续，并用真实卡自举跑通。**

> 措辞约定（审核 U2）："无常驻 AI 主控"不等于没有控制面——Runner/宿主、接力计划生成 agent、汇合 agent、诊断 agent 与 finalizer 脚本仍构成控制面，只是不再由一个常驻 AI 会话承担。

### 1.3 关键决策（动这些要重新讨论）

1. **relay 的边界 = 已授权任务卡；"授权"是一份可审计的工件，不是命令行参数**（用户拍板 D14）：用户在主会话对话里授权后，主会话落一份不可变 **authority snapshot**（授权时刻、卡号集合、各卡的 DevPlan 行与目标/验收/变更范围、所依据的 DevPlan 与 design 文件的 Git blob 哈希、授权证据指针），relay 只消费它；传入不在 snapshot 内的卡一律拒绝。**run 跑到一半你正当地改了某卡的 DevPlan 口径 → 只冻结那张卡「及依赖它的卡」并由诊断 agent 在窗口问你（重新授权 / 回滚 / 取消），无关卡照常；snapshot 工件本身被篡改则全 run 停**（D17；R9 审 S4 补依赖闭包与安全停点：冻结判定在**每次 launch 前、远端 push 前、finalizer 最终 CAS 前**各重验一次；已在跑的 worker 不强杀，其结果按失效隔离；若该卡已 push 远端 test，先走 B16 补偿路径再冻结；`finalizing` 中途命中失配 → 走 `closeout_blocked` 而非中断 CAS）。不做立项/拆计划；不改 DevPlan 任务的目标/验收（只回填状态与 SHA）。命令行入口 `relay start -Task …` 仍存在，但只作为脚本/调试通道，**产品路径不要求用户敲命令**。
2. **流水就是 dev-harness 节点表的接力版**：S0～S3（落户）→ 施工 → E2 代码复核（两轮换人）→ 集成/需求境证据 → E4 需求复核 → E6 教训复核 → E5～E10 备料 → E11 用户确认 → E12～E13 verify/销户。relay 不发明第二套流程；`review.md`/`progress.md`/证据账本仍是 dev-harness 工件，由对应棒写。
3. **Runner 仍不判质量**：汇合 agent 写 `verdict`（`approve / rework / escalate`），Runner 只按枚举分支，并强制"缺任一复核棒结果不放行、返工轮次有界"。
4. **脚本节点是机器事实的唯一来源**：dh check、测试、e2e 脚本、finalizer 以脚本节点跑；宿主脚本执行器扮演该 attempt 的 worker（receipt backend=script），只写宿主私有 candidate，Runner 照常校验晋级；结果带 `gate_outcome=pass|fail|error`；**不新增 result_status**（审核 S1）。
5. **返工默认 fresh fix worker**（用户拍板 D1'）；原会话恢复留目标形态。
6. **确认闸 = agent 窗口作答**（用户 2026-08-16 对话拍板，推翻审核推荐的一次性回执 CLI）：落户确认、决策、收口确认都在对应 agent 的窗口里明文回答，agent 把回答原文写进 result/review.md 确认记录，Runner 不读回答。**登记为已接受的弱信任**（输入者身份不可机器验证；IHSR_05 F-006 有误点/代答先例），配三道**由宿主持有**的护栏（审核 R4-04）：① agent 必须先写 `decision_required` checkpoint 挂起；Runner 摄入该 checkpoint 时记 `decision_checkpoint_event_id`，收口 result 引用的 event_id 须存在于事件账且早于 result 摄入，否则拒；② 收口确认要求用户输入固定短语「认可执行本地收口」原文（agent 抄录，弱信任）；③ **截图由宿主拍**——摄入 decision checkpoint 时与摄入确认 result 时各自动拍一张该 launch 绑定的 RELAY 窗口截图，宿主写哈希与 `evidence_refs` 进事件账，agent 不能自填。不再有 `relay approve` 命令、不再要求飞书。
7. **收口执行 = 收口 agent 前台 + finalizer 脚本后台，且 finalizer 只由宿主启动**（用户拍板 D2 折中；xhigh 审 S3）：收口 agent 备料、写交付汇报、在窗口拿到确认后只提交 `succeeded + next_action=finalize` 的 final result（含确认记录字段）；Runner 校验三护栏与 manifest 后**自己签发 finalizer 的 script receipt 并由宿主执行**，agent 不得直接调用 finalizer 脚本、不持任何 Git 收口权限。finalizer 按 closure journal 逐步幂等执行——**全部在从 master HEAD 新建的暂存分支上完成，最后一次 CAS 快进**（用户拍板 D6）：审计（预期 master HEAD、index 干净、路径所有权无重叠）→ squash → 合入态复验（机器闸复跑）→ 准备并校验销户回填 → 原子 verify 提交（含回填）→ 回读一致性 → master 仍为预期 HEAD 才快进 → 清树与暂存分支。崩溃从最后完成步续跑，master 永无"已合入未 verify"中间态；失败进 `closeout_blocked` 由诊断 agent 带你处置。永不 deploy；finalizer 永不 push（test 受控 push 只属 7a 集成棒，见决策 13）。
8. **三路复核显式成棒、代码复核顺序两轮**（用户拍板 D3 + 对话补充）：代码复核 R1 → fresh R2（读已落账 R1）→ fresh 汇合；需求与一致性复核 agent（fresh）；教训复核 agent；三者账号可同、会话必不同、启动命令不得含 resume/continue。返工复审 = 同节点新 attempt；复核工件按 attempt 不可变 `review-<node>-<attempt>.md`，canonical `review.md` 只由汇合/收口 agent 以 expected-hash CAS 写。
9. **计划只引用注册表条目**（审核 S2）：RelayPlan 只写 `profile_id / script_spec_id / 开关`；命令模板（含冻结 hash）、允许参数白名单、工作目录根、账号配置目录路径、fallback 关系、push 目标白名单放**用户级**注册表 `~/.dh-relay/registry/*.psd1`（只含路径/别名、零凭据）；**P2 不支持仓级覆盖**（用户拍板 D9，防仓内文件被改后接管账号映射；留 P3）；计划内不得出现任意 CLI 参数。
10. **运行现场归目标仓**：经 canonical runtime resolver 解析该仓 dh-relay 模块命名空间（默认 `<repo>/.dh-runtime/relay/<run_id>/`，不进 git，不写死路径）；用户级 `~/.dh-relay/runs.json` 只做索引（repo 路径 + run_id + 摘要 + 更新时间，不含 config_dir 等路径），写入用临时文件 + 原子改名 + 文件锁；run_id 含仓 slug 前缀避免跨仓冲突。
11. **一 run 一批卡（2～3 张试验）与基线刷新**（用户拍板 D8、D11、D12）：卡间按 DevPlan 依赖串行/并行；接力计划生成时按 DevPlan 变更范围做**静态路径重叠检查，重叠卡强制串行**；每卡在棒 1 开工时刻从当时 master HEAD 建树；**同一仓同一时刻只允许一个 finalizer 在跑**。**基线落后**（前卡已快进）：finalizer 在暂存分支先 rebase 候选到新 master → 生成新 candidate generation（新 `base_sha + candidate_tree_sha + diff_hash`）→ 若 **patch 哈希不变**且机器闸复跑通过 → 旧复核工件仍有效，但旧 manifest/确认失效，**重新弹一次收口窗口重新确认**（新 manifest）；若 **patch 变了**（冲突解决或内容漂移）→ 自动重跑受影响证据（机器闸 → R1′→R2′→lead′，开关的 e2e）后再重新确认；只有 master 未漂移才是"一次确认"。rebase 冲突 → `closeout_blocked` → 诊断 agent 可拉修复 agent 解冲突后重走。**多卡下的重编排**（xhigh 审 S2，用户 2026-08-16 定）：保持 run 全局 generation（P1 身份链不改）；某卡 `dependency_blocked` 触发的重编排只允许在**该卡内**新增前置棒（不改其它卡、不加卡）；重编排 agent 计算期间其它卡照常；新计划生效那一刻 Runner 判影响面——**不受影响的卡**（节点未变、不依赖该卡）手上在跑的棒先交完再切换届次（不重做、不丢），切换后下一棒 fresh 继续；**受影响的卡**（依赖该卡）干完手上一棒后按 P1 依赖冻结等待。卡级 generation 留 P3。多卡 DAG 通用调度器、跨仓 run 留 P3。
12. **诊断 agent 自动拉起、代发控制事件属 P2 对 P1 §2.2/§4.4 的明确放宽**：任一棒 `interrupted_unknown`/paused/`closeout_blocked`/quota 无 fallback/续跑发现断棒 → Runner 拉一次性只读诊断 agent；它读现场、写诊断事件，在窗口问你"续跑 / 换账号重试 / 重来 / 放弃 / 丢弃暂存分支"，按你的回答代发**预定义子类型**控制事件（`actor=diagnoser:<node_id>`、`on_behalf_of=user`、`user_reply_verbatim`、绑定 launch/session）；Runner 消费控制事件改状态，诊断 agent 本身仍不直接写 active state、不施工。此代发同属弱信任，与确认闸一并登记。
13. **test 分支受控 push = 跟着项目走的条件分支**（用户拍板 D10；2026-08-16 用户澄清"push 远端这个动作是跟着项目的，项目有就做没有就不做"；xhigh 审 S8 收紧）。**两类前提必须分开记账（R9 审 S5：否则漏配授权/ACL 会被记成 N/A，等于给权限红线开新口子）**：
    - **① 项目适用性谓词（只有它不成立才可记「前提不成立·本次不适用」）**：授权冻结时刻，目标仓**确无可用远端**（`git remote -v` 为空或无 eligible remote）。此时该棒退化为"合到本地 `test` 分支 + 窗口协作"，B16 的 push 分支与 H5 按 **N/A** 登记——N/A 不进本次放行证据包、不算未验证、更不算风险放行。**实测 `dh-crew` 与 `infohub-vps-services` 当前 `git remote -v` 均为空。**
    - **② 安全前置条件（不成立一律记「未授权 / 未验证」并禁止 push，绝不可记 N/A）**：仓**有**远端但缺注册表白名单、缺 `integration=true`、缺 run 级 `-AllowTestPush`、缺 ACL 机器证据或缺 H5。此时 push 被拒、该项进未验证账，按红线处理（`AGENTS`/dev-harness G12 权限安全不可豁免），不得以"没配所以不适用"的说法绕过。
    - **表述红线**：B16 整项写"通过"必须以真实 Git 服务上跑通为前提；只在本地/裸远端验过机械链时，远端 provider 能力只能写"未在真实 Git 服务上验证"。
    - **P2 实际收口口径（用户拍板 D20）**：P2 **不专门搭真实测试 Git 服务**；B16 只在本地临时仓 + 裸远端上把机械链（白名单硬拒、指纹冻结、lease 冲突、force-with-lease 回滚、cancel-after-push 补偿、串行锁）验到位，**"真实 Git 服务的 ACL 能否锁死到 `refs/heads/test`"诚实标为未验证**，H5 在无真实远端时记 N/A；交付表述不得写"B16 通过"，只能写"机械链已证、真实服务器能力未验证"。将来接入带远端的项目时按该未验证项补证（不另立 A，属同一验收 ID 的证据补齐）。以下为适用时的约束——仅在上述谓词全成立时，7a 集成脚本节点可把候选合入并推到远端 **`test` 一个分支**——注册表 push 白名单冻结 `remote URL 指纹 + refs/heads/test`，脚本硬拒其它 remote/ref（master/main 永不）；**权限边界在远端**：目标 Git 服务侧须把 relay 使用的凭据 ACL 限制到该仓 `refs/heads/test`（不可由 relay 自证；`DHR-A-04` 后按验收二分原子拆分：机器项=B16 检查器校验脱敏 ACL 回读工件的存在/格式/覆盖范围/remote 指纹一致，人判项=H5 由你判断该回读的来源与时效；工件缺失即未验证、权限属红线不得风险放行）；推前 journal 冻结 remote URL 指纹、远端 test 原 HEAD、source SHA、完整 refspec；e2e 失败或用户在窗口说"回滚"时以 `--force-with-lease=test:<原HEAD>` 精确回退；lease 冲突（外部人员改过 test）或补偿失败 → `closeout_blocked`，不得宣称已回滚/run done；`cancel_card` 发生在 push 之后必须先走同一补偿路径；同仓 test 推送持宿主锁串行；部署到测试服务器仍由用户在窗口协作中亲手执行（agent 只给命令）。
14. **不改 dh-crew**：新代码落 `tools/relay/`；dh-crew 的 dispatch/loop/notify 不动、不被 relay 读状态；飞书通知 adapter、登录自启降 P3（用户拍板 D9）。

### 1.4 范围与分期

**P2（本设计；用户拍板 D4 分卡逐层冻结，预计 14～16 张标准卡，具体由 B 拆）**：

1. v2 契约与兼容：新增角色、`script` 节点、`gate_outcome`、`verdict`、`rework`（re-ready 新 attempt）、profile/script 引用、按 attempt 不可变复核工件、release manifest、控制事件子类型（resume/retry/reset/cancel/abort）、run 生命周期、多卡 run 结构；P1 业务状态机与合法边不变，旧 run 可读。
2. 宿主基础债：RB-1 截图/通知非致命、F-019 决策态快照、F-023 三条（consumed 轮转 / spawner 异步 / Runner 提交临时名）。
3. 任意仓发起 + 用户级注册表 + run 索引 + `relay` 控制台（start/resume/status/propose/cancel）+ 现场经 resolver 归目标仓；codex-ninth 实棒（非秘密身份回执 + expected_identity 比对）。
4. 脚本节点（机器闸、e2e/集成脚本、finalizer 承载）。
5. 三路复核 + 汇合 + 有界返工/补证回路 + 集成/端到端可选棒（多轮协作 + test 受控 push/回滚）。
6. 收口 agent + finalizer 脚本（暂存分支一次快进 + 基线落后 rebase 重过闸）+ 宿主持有的确认闸护栏 + release manifest。
7. 诊断 agent 自动拉起 + 接续（先摄入未消费结果、再判断棒、控制台续跑）+ quota 高置信识别/预登记 fallback。
8. 多卡调度（依赖/静态重叠检查/finalizer 与 test 推送串行锁）。
9. 真实自举（一批 2～3 张与 relay 实现无关的真实卡）+ H3/H4/H5。
10. **授权工件与授权边界**（`DHR-A-04`，见 B14）：主会话落不可变 authority snapshot（含 DevPlan/design 的 Git blob 哈希）；relay 只消费它；不在 snapshot 内的卡、状态不可开工的卡一律拒绝；接力计划生成 agent 只按模板填槽位，Runner 晋级前以 snapshot 语义等价复核，不得改卡的目标/验收/变更范围。
11. **棒完整性**（`DHR-A-04`，见 B17 与 B18）：落户棒真产出 8 件套且逐文件非占位（自带谓词，不挂靠 `dh` R15）；教训复核棒真被调度并区分成功/无候选/失败三终态，收口棒不得先于它 ready。
12. **诊断 agent 的可信只读承载**（`DHR-A-04`，见 B15）：注册表 profile 增能力位，宿主只以强制只读方式拉起诊断 agent；不支持强制只读的 CLI/profile 拒绝用于该角色。

（用户 D4 拍板"分 7 卡"时范围尚不含多卡/集成/诊断；v5 范围扩大后预计 8～10 张。**`DHR-A-04` 修订后**：机器验收项由 13 条增至 **18 条**（新增 B14/B15/B16/B17/B18，其中 B15/B16 由 B7/B13 原子化拆出），人判项增至 3 条（H3/H4/H5），故估算上调为 **14～16 张**——**这是估算不是闸**，最终以 B 拆的覆盖/颗粒度审计为准；硬约束只有一条：**每张卡只承载一个安全边界**。若 B 拆结果显著超出该区间且无法用颗粒度理由解释，才回 A 调整范围；任何情况下不得静默压缩验收。）

**P2 内降级实现**：quota 只做"高置信识别则换预登记 fallback，否则 paused→诊断"；接力计划生成 agent 只做模板实例化。

**不做（留 P3+）**：完整 quota 识别/恢复通道、计划内任意 CLI 参数、通用动态 planner、通用多卡 DAG 调度器与跨仓 run、仓级注册表覆盖、登录自启、飞书通知 adapter、原施工会话恢复返工、非 psmux 后端、跨机器、UI、自动决策、dh-crew 侧改窗口拥有会话（F-021）。

### 2.3 多卡调度

- 接力计划把每张卡实例化为一组节点（1～8'），卡间边来自 DevPlan 依赖列；无依赖卡可并行（受注册表 `max_parallel_cards`，默认 2）。
- 同一仓同一时刻只允许一个 finalizer 节点 running（宿主级锁）；后一张卡的 finalizer 以前一张快进后的 master HEAD 为预期 HEAD 重新审计。
- 任一卡 escalate/paused 只冻结依赖它的卡；其它卡照常。
- 某卡重编排（仅限本卡内加前置棒）：计算期间其它卡照常；生效时不受影响卡的在跑棒交完再切届次、下一棒 fresh 继续，受影响卡按依赖冻结（决策 11）。
- run 终态区分 `done-complete`（全部卡 finalizer succeeded）与 `done-partial-cancelled`（含被 cancel 的卡）；后者不得表述为"全部销户"；部分完成也留完整事件账。

### 2.4 任意仓发起与接续

- **产品路径（你不敲命令行，D14）**：你在主会话对话里授权 → 主会话在目标仓落 **`authorization-request`**（只是请求）→ 代你拉起宿主 → **宿主**校验该仓 AGENTS/DevPlan/模块 slug、request 内每张卡存在且状态可开工、树干净 → **在窗口把精确卡清单再展示一次给你核对**（主会话转录属弱信任，见 §3/§7）→ 通过后原子 `CreateNew` 建 `<run>` 并由宿主生成 `authority-snapshot.json`、锚定其哈希 → 写用户级索引 → 拉棒 0。任一校验失败 → `start_rejected`（含拒因枚举），**不建 run**。
- **relay 的进程归属与存活语义（用户拍板 D18=独立宿主后台跑）**：现役 `Invoke-RelayHost` 是**调用方进程内的有界 tick 循环**（`tools/relay/host/relay-host.ps1`，无 detached/service 形态），**P2 必须新增 detached 宿主形态**——主会话代起后宿主脱离主会话独立存活，主会话结束、终端全关都不影响它继续调度；只有你主动 `relay stop`（控制台菜单项）或系统重启才停。配套契约：宿主 **PID/lease 文件**（含 run_id、启动时刻、宿主可执行指纹）写进 `<run>/`；**同一 run 只允许一个活宿主**（重复启动被 lease 拒绝并提示已在跑）；宿主异常死亡后 lease 过期可被新宿主接管（走 §2.4 恢复锁流程）；`relay status` 能报"宿主活着/已死/lease 过期"。**H3 的"关掉全部终端一次再续"因此有两种可展示形态**：关终端但宿主仍活（继续跑）与连宿主一起停（走恢复），两者都要演示。
- **命令行入口仍在但非产品路径**：`relay start -Task A,B,C` 只作脚本/调试通道，同样必须消费 snapshot（无 snapshot 或卡不在其中 → 拒），不得成为绕过授权的旁路。
- `relay`（无参数）= 控制台，可由主会话代起或双击快捷方式打开：读 `~/.dh-relay/runs.json` 列出所有仓未完成 run（卡到第几棒、断了哪些），按编号选一个即 `resume`；`relay status [-RunId]` 只读。
- **续跑判定**（P2 对 P1 A6 的恢复边补充；xhigh 审 S7 补竞态屏障）：宿主启动时先取 **run 恢复锁**：冻结新 launch → 原子 claim 并摄入所有未消费的 tmp/result/ack/inbox → probe 各在册 session → 对"进程/会话已消失"的 attempt **再做一次 claim/双空扫描**（防 result 在首扫后、probe 前原子落盘）→ 仍无 final result 者才 CAS 记 `interrupted_unknown`（A6 fail-closed 起点，不自动推进业务）→ 释放锁 → 拉诊断 agent。日常 tick 同样对"非 launched 节点"的迟到合法 result 做摄入并按身份链判 stale/接受，不得因扫描器只看 launched 而永久拒收。"已交棒 attempt 不重跑"仅指不因重启机械重跑，其结果是否仍有效由后续机器闸/finalizer 审计兜底；工作树与工作区现状保留。
- 诊断 agent 的选项：续跑（fresh 新 attempt，带 handoff/工作树现状）、重来（丢弃工作树未提交改动后新 attempt）、换账号重试（预登记 fallback profile）、放弃这张卡（cancel 该卡节点组）、丢弃暂存分支（closeout_blocked 时）。
- 登录自启（计划任务 `relay resume --all`）留 P3，P2 不做。

## 3. 契约增量（`relay/v2`，v1 只读兼容）

- **节点角色**：沿用 `worker/reviewer/replanner`，新增 `planner / workspace / build / fix / review_lead / integration / requirement_review / lesson_review / closer / diagnoser / gate / finalizer`。
- **节点类型**：`agent`（默认）| `script`。script 节点只引用 `script_spec_id`；宿主脚本执行器扮演该 attempt 的 worker（receipt backend=`script`），只写宿主私有 candidate，Runner 按完整身份链 + script_spec hash + 矩阵校验后晋级 final；result = `succeeded` + `gate_outcome=pass|fail|error` + `exit_code` + 脱敏限长 `output_tail` + `duration_ms`；计划 `on_gate_fail: <fix_node_id>`；`error` 按 `interrupted_unknown` 兜底。
- **多卡结构**：plan 顶层 `cards[]`（card_id、DevPlan 引用、节点组、卡间 depends_on、开关 `integration/e2e`），节点 node_id 前缀 = card_id；Runner 调度以节点为单位、锁以卡/仓为单位。
- **授权两件套：request（agent 写）+ snapshot（宿主写）**（`DHR-A-04`；R9 审 S1/S3 收紧）：
  - **`authorization-request`**（主会话写，落 `<repo>/.dh-runtime/relay/requests/<request_id>.json`，run 尚未存在）：授权时刻、授权来源（对话指针）、卡号集合、目标仓与模块 slug、开关意图。它**只是请求，不是授权事实**；主会话的转录属**已登记的弱信任**（机器无法证明它忠实抄录了你的话），故宿主在建 run 前必须在窗口把**精确卡清单**再展示一次给你核对（与落户确认同一形态，见 §4）。
  - **`authority-snapshot.json`**（**宿主**在校验通过后原子 `CreateNew` 建 run 时生成，位于 `<run>/`，内容哈希由宿主锚定进 Runner 拥有的 authority/事件账）：在 request 基础上补齐**各卡 `{card_id, devplan_path, devplan_row, 目标, 验收口径引用, 变更范围, 状态}`** 与**两级哈希**——① 整文件 **Git blob 哈希**（来源证明）、② **每卡规范化片段哈希**（该卡的 DevPlan 行 + 其引用的验收 ID 正文，**影响面证明**；因为一份 DevPlan 常承载多卡，整文件 blob 判不出"只影响哪张卡"——`dev_plan/P1-最小接力PoC-开发方案.md` 一文件即承载 DHR_01～03）。
  - **agent 不得生成或改写 snapshot**；`relay start -Task` 只能消费既有 request/snapshot，**禁止凭 `-Task` 自造授权**（旁路反例）。
  - **失配三分（D17 精确化）**：① 宿主锚定的 `snapshot_hash` 不符=工件被篡改 → **全 run fail-closed**（先校验这一层，它是后两层的信任根）；② 某卡的**片段哈希**变化 → **只冻结该卡及其传递依赖闭包**（无关卡继续，见决策 1 与 B14）；③ 整文件 blob 变化但相关卡片段哈希未变 → 只记事件、不冻卡。`active-plan.json` 与每张 launch receipt 记 `authority_snapshot_hash`。Runner 以 snapshot 复核 planner 输出的语义等价（卡集合、验收引用不得变），不信任 proposal 自述。
- **profile 引用**：节点 `profile_id`；用户级注册表条目 `cli / config_dir / work_dir_root / model / fallback_profile_id / account_alias / expected_identity / capabilities`（只是路径、别名与能力位；`capabilities.readonly` 声明该 profile 能否被以强制只读方式拉起及其 CLI 实现，如 codex `--sandbox read-only`）；**diagnoser 角色只能绑定 `capabilities.readonly=true` 的 profile，宿主按该实现拉起并在 receipt 记配置哈希；不支持则拒绝拉起**（`DHR-A-04`）；receipt 记 `profile_id + account_alias + cli + config_fingerprint`；拉起后尽力取 CLI 返回的脱敏账号主体与 `expected_identity` 比对，不符即 `launch_failed`，取不到登记"账号身份不可机器验证"（B4 据此判）；fresh 由新 launch/session + 命令模板无 resume/continue/旧 session 参数证明。
- **verdict**：`review_lead` result 允许 `verdict ∈ {approve, rework, escalate}`；`requirement_review` result 允许 `verdict ∈ {pass, needs_evidence, escalate}`；其它角色携带即拒。
- **返工/补证回路**：计划 `rework: { fix_node_id, max_rounds: 3, re_review_node_ids[] }`、`evidence_rework: { target_node_ids[], max_rounds: 2 }`；触发时目标节点重新 ready 为新 attempt（round→node/attempt 映射记事件）；超上限由对应 agent 写 `decision_required`。
- **复核工件**：reviewer/lead/需求复核每个 attempt 写不可变 `review-<node>-<attempt>.md`；canonical `review.md` 各段只由 lead / 需求复核 / 教训复核 / 收口 agent 以 expected-hash 顺序 CAS 写。
- **人机多轮协作**（P1 §4.2 语义）：integration 等棒进入需人配合阶段写一次 `decision_required` checkpoint；其后多轮往返 Runner 不感知；写出后续 `working` checkpoint 或 final result 才恢复调度；依赖节点期间冻结。
- **确认记录**（xhigh 审 S5 补时序屏障）：agent 写 `decision_required` checkpoint → Runner 接受后**宿主立即对该 launch 绑定的唯一 RELAY 窗口精确截图**（按 handle/window_title 单窗口，零窗口或占位图=失败）并写 `decision_ack`（含 event_id、截图哈希）→ agent 只有读到 ACK 才可向用户展示确认问题；用户回答后 agent 提交 result（`user_reply_verbatim`（抄录）+ `decision_checkpoint_event_id`）→ Runner 摄入时再拍一次同窗口精确截图并核对：ACK 存在、event 顺序、launch/session/attempt 一致、收口时 `user_reply_verbatim == "认可执行本地收口"`；缺任一项 → 不签发 finalizer receipt。截图与哈希只由宿主写入事件账，agent 自填一律忽略。
- **release manifest**：收口 agent 备料终点生成规范化 `release-manifest.json`：候选 squash 目标 SHA、预期 master HEAD、精确路径集、各复核 attempt 工件哈希、gate/e2e 结果哈希、release_mode、Risk-Count/Refs、verify 文案哈希、动作范围；finalizer 与宿主外 oracle（B10）都以它为准。
- **quota**：`quota_exhausted` 枚举转正；识别规则表按 CLI/版本冻结正反样本（脱敏）于注册表；仅高置信匹配才写；fallback 只用注册表预登记条目；无 fallback → paused → 诊断。
- **控制事件子类型**（扩 P1 §3.4，字段仍为 actor/source/nonce + 身份链绑定；xhigh 审 S6 补目标绑定）：`action ∈ {resume, retry_with_profile, reset_attempt, cancel_card, cancel_run, abort_closeout, rollback_test}`；每条控制 candidate 必须带 `target = {run_id, card_id, node_id, attempt_id, launch_id, generation}` + `expected_state_hash`（目标当前状态快照哈希）+ 参数（如 profile_id）+ `option_id`；**`DHR-A-04` 收紧**——diagnoser 的 checkpoint 必须冻结**规范化 option 载荷** `{option_id, action, params, target}` 及其哈希，代发的控制 candidate 与该载荷**逐字段全等**才受理（`option_id` 合法但 action/params 被换即拒）；由诊断 agent（`actor=diagnoser:<node_id>`、`on_behalf_of=user`、`user_reply_verbatim`、绑定其 launch/session）通过宿主提供的**单次、目标绑定、载荷绑定的窄工具**发出；`relay` 控制台（`actor=console`）走**另一套「直接用户命令」schema**（不依赖 diagnoser 声明的选项，但仍须带完整 target + `expected_state_hash`），两条路径各自有正向用例；Runner 唯一消费者，重验目标与 expected_state 后执行；旧 generation/错 run/重复 nonce/非预定义 action/选项不在声明列表/状态哈希不符一律拒绝并留 `control_rejected`。弱信任仅限"输入者是谁"，不扩成"agent 可任选控制动作"。
- **run 生命周期**（控制面维度，与 P1 task overall state 分离）：`active → done`；`active → cancelled`；卡级 `finalizing → closeout_blocked → finalizing | aborted`；finalizing 中不接受 cancel。
- **运行现场、tracked 写入与所有权**（xhigh 审 S9）：运行现场经 resolver 落 `<repo>/.dh-runtime/relay/<run_id>/`（含 `closeout/<卡>/journal.json`）；`~/.dh-relay/runs.json` 只存 repo 路径 / run_id / 摘要 / 更新时间。**所有 tracked 写入（工作区 8 件套、review 工件、knowledge 候选、as-built、DevPlan 回填）统一落在任务树 `D:\wt\<卡>` 内、随该卡 squash 合入；主工作树对所有棒只读**（finalizer 除外，且只经暂存分支快进）；宿主持 `(canonical_repo, task_id)` 跨进程 claim lease，**一仓同卡同时只允许一个 active run**。

## 4. 固定流转补充

- **落户确认**：workspace 棒完成 8 件套后写 `decision_required`（档位/目标/范围/验收/落点摘要）；回答"确认"→ `succeeded`；回答"取消"→ 诊断 agent 路径 `cancel_card`。**8 件套齐备是该棒 `succeeded` 的前置机器条件**（缺件/占位则不得终结，见 B17）。
- **授权校验**：主会话只写 `authorization-request`（见 §2.4/§3）；**宿主**校验每张卡在 DevPlan 中存在、状态可开工、且在 request 内，通过后原子建 run 并由宿主生成不可变 `authority-snapshot.json`（agent 不得自造 snapshot）；接力计划生成 agent 的 proposal 只填模板槽位，Runner 晋级前以 snapshot 复核，不符即拒（见 B14）。
- **教训复核**：每卡必调度 `lesson_review` 棒并在事件账留 launch/result；它写 knowledge 候选与 review.md 教训段，不阻断放行，但收口棒不得在它终结前 ready（见 **B18**）。
- **机器闸失败**：`gate_outcome=fail` → 修复 agent（fresh）→ 回闸；连续 ≥3 次由修复 agent写 decision。
- **代码复核**：R1/R2 只读、fresh；汇合规则写在 brief（P0/P1=0 且 findings 归档 → approve；有 P0/P1 → rework；争议/超轮 → escalate）。
- **集成与端到端**：仓约定有 test 分支/需真机验证时开启；集成脚本节点管本地/远端 test 的合入、push（仅 `-AllowTestPush` 且白名单 `test`）、回滚；agent 只给命令、你执行并回贴（含部署测试服务器）；结果作需求境证据进账本。
- **需求与一致性复核**：按 brief 验收口径逐条要证据；缺则 `needs_evidence` 回目标棒（只重跑该棒及下游机器闸；改代码则走 rework 全套）；一致性表覆盖 brief/DevPlan/证据。
- **收口**：收口 agent 走 E5～E10 备料清单、产出 manifest 与 verify 文案，窗口问确认；拿到固定短语后调 finalizer；finalizer 在暂存分支执行授权包（squash / 复验 / 回填 / verify）后一次快进 master 并清树；不 push、不 deploy。
- **恢复**：`relay`/`relay resume` 同 RunId 续跑；断棒 → 诊断 agent；finalizer 崩溃从 journal 最后完成步续跑，master 未动；`closeout_blocked` 由诊断 agent 带你重试或丢弃暂存分支。

## 5. 操作剧本（自举）

1. 你在对话里授权一批 2～3 张**与 relay 实现无关**的真实标准档卡（B 阶段与你定）；主会话在该仓落 authority snapshot 并代你拉起 relay，之后主控不再介入（你不敲命令行）。
2. 棒 0 出计划；每张卡按依赖依次/并行走 1～8'；你只在窗口里：落户确认、（如有）决策、真机协作、收口确认。
3. 途中关掉全部终端一次，隔一段时间 `relay` 控制台续跑，诊断 agent 带你接上断棒。
4. 全部卡 verify 销户后 run done；宿主外 oracle 核对主干 commit/verify trailer/DevPlan/树。

## 7. 边界

- **不做**：立项/拆计划、通用多卡 DAG 调度器、跨仓 run、仓级注册表覆盖、登录自启、通知 adapter、原会话恢复返工、非 psmux 后端、跨机器、UI、自动决策、任何 deploy、除 `test` 外的任何 push（master/main 永不）、完整 quota 恢复通道、通用动态 planner。
- **禁改**：dh-crew controller/loop/dispatch/notify 代码与 active state；DevPlan/workspace 只由对应棒或 finalizer 按 dev-harness 规矩写；DevPlan 任务的目标/验收不由 relay 改。
- **凭据**：注册表只存路径/别名；事件、计划、manifest、tail、通知零凭据。
- **信任登记**（`DHR-A-04` 起，每项各有独占验收 ID，B 拆时不得与相邻能力合并成一张卡）：
  - 窗口作答（落户/决策/协作/收口/诊断）的输入者身份不可机器验证，登记为用户接受的弱信任；收口另有宿主持有的三护栏（先挂起且事件可核、固定短语、宿主拍前后精确单窗口截图）→ **B8**。
  - 诊断 agent 代发控制事件同属弱信任，但能力被目标绑定 + 选项绑定 + 单次授权收窄 → **B15**。
  - test 分支 push 是 P1 "永不 push" 的唯一受控例外，且**只在项目真有远端时才适用**（run 级授权 + remote 指纹白名单 + 可回滚 + 补偿）→ **B16**；其远端 ACL 属外部事实，机器项只验回读工件（B16），主观来源与时效判断归 **H5**，两者共享 `acl_evidence_id`、结论独立、合取才放行首次 push；谓词不成立时登记"本次不适用"（不是未验证，也不是风险放行）。
  - 授权真源是**宿主**据主会话 request 生成并锚定的 authority snapshot（两级哈希）、planner 只能语义等价实例化 → **B14**；**主会话对你原话的转录属已登记弱信任**（机器无法证明忠实），故宿主建 run 前在窗口再展示一次精确卡清单请你核对；落户 8 件套完整性 → **B17**；教训复核棒真实执行与三终态 → **B18**。
  - 集成端到端棒产出的是**人验证据**：每个需人判 E-ID 必须留你的原文 verdict，agent 与需求复核棒均不得代判 → **B13**；最终业务结论在 E10/E11 放行证据包由你确认。
  - 诊断 agent 的"只读"不靠 prompt 而靠注册表能力位 + 宿主拉起方式 → **B15**（现役以 `--dangerously-skip-permissions`/`--yolo` 拉起，是本项要消灭的反面基线）。
- **表述**：P2 通过只能称"一批任务卡完整接力自举通过"，不宣称通用多卡生产编排。
