## 候选 L-7601 · 清理完成必须由 close 与 kill 结果共同证明

触发场景：给 Windows 子进程探针设置超时并清理 root child 及其后代 · 建议分类：编码陷阱 · 来源：`review-code1.md` F-76-C1-01（原 P1）
疑似重复：无；候选-51/69/73分别覆盖常驻对象的停止钩子、`t.after` 清理顺序和等待预算，不覆盖本条的清理完成判据
- 现象：原实现宽限到期就 `finish` 并 `unref()`，没有等 root child 发出 `close`，也没有确认 `taskkill /T /F` 成功，因而可能把仍有后代的清理宣称为完成。
- 反思：探针业务超时、清理请求发出、清理已完成是三个不同终态；宽限耗尽或解除引用只说明不再等待，不能证明进程树已消失。
- 建议后续动作：把 child close、后代 kill 退出码和清理宽限分别建成状态；只有 close 已发生且 kill 成功才返回普通失败结果，其他情况显式失败，并为 child 不 close、kill 非零和正常 close 各留负例。
状态：待裁决

## 候选 L-7602 · 异步化要保持逐项校验的首错顺序

触发场景：把已有同步 registry/profile 校验改成异步探针，同时要求维持现役错误面和兼容入口 · 建议分类：编码陷阱 · 来源：`review-code1.md` F-76-C1-02（原 P2）
疑似重复：无；候选-11约束同类目标覆盖面，候选-33约束对称实现路径，候选-66约束实现与冻结契约的横向比对，均不等于首错优先级兼容
- 现象：异步实现初版先扫完整表的 config，再做 alias 探针；多个 profile 同时损坏时，它会先报与同步入口不同的 profile/错误类别，虽然外层错误包装仍相同。
- 反思：异步化保持返回类型或外层 reason 不足以保持兼容；调用方和证据可能依赖按 profile 顺序、按 config→alias 的确定性首错。
- 建议后续动作：异步入口复用同步的结构检查和逐 profile 检查顺序；用 profile[0] alias 与 profile[1] config 同时损坏的独立夹具逐项比较 sync/async 首错，不允许为并发便利而重排验证。
状态：待裁决
