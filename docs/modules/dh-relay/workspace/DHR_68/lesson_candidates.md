## 候选 L-6801 · 外部 CLI 的测试替身，返回形态必须逐命令对真、否则「全绿」是假的

- **触发信号**：新增或修改某个外部 CLI 的 fake / stub；或某条验收依赖该 CLI 的**成功输出形态**或关键失败形态。
- **检查动作**：先用**真实 CLI** 逐命令 probe 一遍，记录每个动词的 `exit code`、`stdout 是否 JSON`、`是否为空`、必要的顶层字段；再让**测试机读这份对照表去比对 fake**。没有对照表的命令，不得用 fake 支撑该命令的验收。
- **现象**：DHR_67 的 fake 给 `pane run` 返回 `{ok:true,value:{}}`，而真实 `herdr pane run` 成功时是 **exit 0 + stdout 全空**；adapter 以 `json:true` 调用，于是 Claude 路径在真实宿主上 **100% `json-parse` 失败**——但 fake 全绿，卡被记为已完成。同类还有 `agent prompt`：真实返回 `{agent:{…},type}`，本卡第一版 fake 误按 `{type:'ok'}` 写（复核轮 1 抓到）。
- **反思**：fake 的"覆盖率"只证明代码在**你想象的形态**下能跑。形态本身是外部依赖的事实，必须取证，不能靠记忆或类比（`send-keys`/`pane close` 确实只返回 `{type:'ok'}`，一类比就把 `prompt` 归错了类）。
- **与既有候选的边界**（教训复核 C-68-01 要求显式标注）：
  - [候选-6] 讲"断言可能根本不咬"；本条讲"断言咬对了，但**被测替身**从一开始就不是真实形态"。
  - [候选-36] 讲"被测对象和验收对象不是同一个东西"（仓内副本 vs 真产物）；本条是它在**测试替身**这一层的具体化：对象对了，**接口形态**没对。
  - 本条的独立价值在于给出可执行的检查动作（probe 对照表 + 机器比对），而不只是原则。
- **本卡的落实**：`scripts/probe-command-shapes.mjs` + `evidence/real-herdr-command-shapes.json` + `DHR_68/D` 测试（读对照表当 oracle，fake 再漂就直接红）。
- 状态：待裁决

## 候选 L-6802 · Windows 上 `spawnSync` 超时走 `error.code === 'ETIMEDOUT'`，不投递信号

- **触发信号**：在 Windows 上给 `spawnSync` 加超时，或把子进程失败映射成"超时"语义位。
- **检查动作**：fixture 必须同时覆盖 `child.error.code === 'ETIMEDOUT'` 与 `child.signal` 两条路径，并断言二者产生**同一个** `timedOut` 语义位。
- **现象**：现役 `herdr-cli.mjs` 只在 `child.signal` 为真时判超时；DHR_35 实测的真实失败串却是 `spawn:ETIMEDOUT`（走 `if (child.error)`）。只按信号实现，本卡的超时对账分支**永远不会触发**——修了等于没修。
- **反思**：跨平台的进程 API 在失败通道上的差异，容易被"看起来对"的分支掩盖；判据要按**实测到的失败串**写，不按文档记忆写。
- 出处：`progress.md` E-6800/E-6805；`findings.md` F-6801。
- 状态：待裁决

## 候选 L-6803 · 给「自带等待窗口」的 CLI 动词设外层超时，先读它自己的 timeout 默认值

- **触发信号**：adapter/wrapper 要给某个外部 CLI 动词设置调用超时，而该动词本身是**阻塞等待型**（等就绪、等连接、等收敛）。
- **检查动作**：先读该动词 `--help` 的默认/最大 timeout；断言外层上限**不短于**它的正常默认等待窗口；不要用"改 argv 传个更小的 timeout"来代替边界设计（会改变对外契约）。
- **现象**：`herdr agent start` 自带 `--timeout` **默认 30 000 ms（max 300 000）**，而 adapter 的通用上限是 10 000 ms——外层比依赖自己的合法等待窗口还短，属于**结构性砍断**，不是"偶尔慢"。更糟的是砍断时 agent 往往已经建成，adapter 却当失败关掉 pane，**泄漏一个活着的 agent 进程**。
- **反思**：本卡起初把依据写成"实测 max 29482 ms"，那只是经验数字，说服力和可维护性都弱；读到依赖自己的合同后，60 秒才有了"给依赖默认窗口留一倍余量"的可证依据。**先读依赖的合同，再定自己的边界。**
- 出处：`progress.md` E-6802；`findings.md` F-6803。
- 状态：待裁决

## 候选 L-6804 · 对**已提交**交付物做卫生/格式验收，必须显式指定基线到 HEAD 的提交范围

- **触发信号**：要下"改动干净 / 格式合规"这类结论，而检查工具默认只看工作区（`git diff --check`、lint、格式化器的默认调用）。
- **检查动作**：写成 `git diff --check <基线>..HEAD`（或等价的范围形式），并在**每次重新生成证据文件之后**重跑一遍；不要把某一时刻的工作区干净当成全范围干净。
- **现象**：本卡在这条上**栽了两次**。第一次（轮 1 F-68-R1-02）：progress 写了"`git diff --check` 干净"，但那次只查了未暂存工作区，已提交的证据文件里有尾随空白。第二次（整改复验 F-68-RV-01）：修好之后又**重跑了一次绿测覆盖证据文件**，尾随空白随新输出回来了，"持续闭合"再次不成立。
- **反思**：卫生检查的**范围**和**时点**都是结论的一部分。范围不写清就是在报一个更弱的命题；证据文件被重新生成就等于检查作废——**凡是会被重新生成的证据，卫生检查必须排在生成之后**。
- 出处：`progress.md` E-6810 / E-6813 / E-6814；`findings.md` F-68-R1-02、F-68-RV-01。
- **与 [候选-49] 的边界**（miner 指出）：候选-49 约束的是"变异证据须以最终提交为基线"；本条约束的是**所有提交范围的卫生检查**，更宽。
- 状态：待裁决

## 候选 L-6805 · 「延后动作」的恢复条件若语义是「离开某状态」，就写成排除该状态，不要用有限白名单

- **触发信号**：为某个动作设"先扣住、条件满足后再做"的延后逻辑，而触发条件的自然语言是"当它**不再**处于 X 状态时"。
- **检查动作**：把条件写成 `status !== X`，而不是 `['A','B'].includes(status)`；并逐一列出该状态机的**全部合法出边**，确认白名单没有漏掉直跳终态的那条。
- **现象**：本卡的 `instructionPending` 补发判据初版写成白名单 `['working','idle']`，漏掉 `blocked → done` 这条合法转换——信任确认后 agent 若很快转 `done`，提交指令整条不发，随后进 `waitForExecutorResult` 空等，最终误落 `E_EXECUTOR_RESULT_MISSING`。由复核轮 2 抓出（F-68-R2-01）。
- **反思**：白名单枚举的是"我想到的出边"，排除式表达的才是"语义本身"。语义是否定式的时候，用肯定式白名单去近似，必然随状态机演进而漏。
- **与 [候选-1] 的边界**（miner 指出）：候选-1 要求"每个分支/原因码都有断言"；本条约束的是**状态迁移的完备性**，二者不互相替代。
- 出处：`progress.md` E-6821；`findings.md` F-68-R2-01。
- 状态：待裁决
