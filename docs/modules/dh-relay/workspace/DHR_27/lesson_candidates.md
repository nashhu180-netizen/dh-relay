- 反例代价：本卡 F-001——CM6a 审计扫出 `src/dsh-host/` 等桌面轨文件、当时 dh-relay 还无 workspace/DHR_26，若当场定性为「污染/越界」并顺手清理或上报 P0，会误伤正在收口的 DHR_26（同日 15:59 已 verify `c90cf88` 用户签、16:01 销户 `b64757b`）；反过来若默认「肯定是并行轨」直接放过，真污染也会漏。本卡的处置：范围外命中只记 finding、查 git log + 对方 workspace 落户情况确认性质、明确「不代改」（连 DevPlan 里 DHR_26 状态行未刷也留给对方轨收尾）。
- 建议落点：教训库（行为流程）。可附带考虑：dh 体检/审计类输出遇「失败数陡增/范围外命中」时，标准动作清单第一条就是「查同仓并行轨」。

### L-002 · 对证分语义层与字节层——内嵌 provenance 哈希时字节必不等

- 反例代价：本卡 F-003——task_plan 步 10 预期写「两路投影应全等」，实跑字节级必不等（plan 文件被授权改写→哈希异→source_refs 异）；若不懂分层，这里要么误报「冻结不忠实」返工，要么为凑全等偷偷去掉 provenance 字段。正确做法已验证：语义级（除 source_refs 外全字段）对证 IDENTICAL + 字节差异逐项归因到 manifest 里留痕的授权改写。

- 状态：ready-for-review

### L-003 · 真实历史数据进 testdata 的 fail-closed 冻结范式
- 触发情境：要把真实运行现场（含主机绝对路径、可能含敏感信息）的文件冻结进仓内 testdata 当 fixture。
- 反例代价：不走范式的话，两头都容易翻车：绝对路径/凭据混进仓（宪章#6 红线），或事后无法证明「冻结全程对源零写入、改写只有登记过的那几处」。本卡已验证的完整范式：①只冻结投影消费的最小文件集（3/41，排除文件记原因）；②输出内容全量扫绝对路径，fail-closed——扫出即 exit 非 0、不落盘；③manifest 记 run 目录全部 41 文件原始 sha256 作零写入对证基线；④唯一改写点（brief_ref）逐字段留痕含原值哈希；⑤冻结脚本对源目录只有 read 调用，事后重哈希对证 IDENTICAL。
- 建议落点：skill/dev-harness 参考层（可复用施工范式，`scripts/freeze-v1-run.mjs` + `test/freeze.test.mjs` 可当模板指过去）；教训库放一句话索引即可。
- 状态：ready-for-review
