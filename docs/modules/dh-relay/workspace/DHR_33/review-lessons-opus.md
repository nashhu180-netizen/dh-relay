## 三、本卡新增候选（10 条 · 现象 / 根因 / 回流建议）

### 候选-46 · 护栏用例必须能区分"对"与"错"两种实现——两条分支可观测结果相同的断言是零护栏
- **触发场景**：为"必须走 A 不能走 B"这类分叉/优先级/顺序规则补测试；尤其 A、B 两条路在测试构造下都"什么都不做"时。
- **现象**：轮 2 的 N2 变异（让 herdr 抢在 process 之前）17/17 全绿，定性为"零测试保护"，rework-2 B13 要求补一条双候选节点用例。返工 2 补了（`agent-node.test.mjs:227-244`），断言是 `paneSplits === 0` 且 `events === ['run_created']`。我重做同一变异：**7/7 全绿，与补测之前一模一样**。原因是 process 候选用了不可解析的 `missing-step.mjs`（走 process 则提前 return、零事件），herdr 候选用了注册表里查无的 `herdr.codex.test`（走 herdr 则 F-007 提前 return、零事件）——**两条路的可观测输出完全相同，断言无从区分**。
- **根因**：补护栏时人的注意力在"我加了一条断言"，而护栏的有效性取决于"错误实现下这条断言会不会取到不同的值"。当被比较的两条路径在测试构造下都走"提前返回"的短路时，任何观测量都相同，断言必然全绿。这与候选-6（断言可能根本不咬）不同：**这里断言在咬，只是两边咬出来一样**。
- **回流建议**：①凡"必须走 A 不走 B"的护栏，构造上要让 **A 产生独有的可观测事实**（本例：process 候选换成可解析的 step ref，让走 process 时真的开 Attempt、落 `attempt_started`），再断言该事实存在 + B 的特征事实不存在（双向）；②该类护栏**必须**当场做一次反向变异（把优先级调过来）证明会红，不做不算完成；③返工清单里"补护栏"类条目的完成判据直接写成"变异 X 后必红"，而不是"新增一条用例"。

### 候选-47 · 返工清单的每个分组都要在 progress 有逐项落地行——门槛句只点名部分分组，未点名的那组会整段蒸发
- **触发场景**：把复核结论拆成分组返工清单（代码 / 测试 / 文档 / findings），并用"逐项落地表"当完成门槛。
- **现象**：`rework-2.md` 分 A（运行时 11 项）/ B（测试 7 项）/ C（文档 3 项）/ D（背景说明），门槛句写的是「本清单 **A/B** 逐项在 progress 落地状态表」。返工 2 的 progress 果然只有 A 表和 B 表，**C 段三项没有任何落地行**——其中两项（C19 数字更正、C20 progress 自评合并）**一个字没做**，没人核对。返工 1 也同形：D-20（progress DONE 重写）漏做，轮 2 才逮到。**两轮返工，文档组各漏一次。**
- **根因**：门槛句里的分组名是人手写的，写的时候按"重要的是代码和测试"删减；被门槛放行的那一组就没有任何机器或流程动作会去看它。文档修正天生是"不影响测试绿"的一类，最容易被这样漏掉。
- **回流建议**：①返工清单的完成门槛统一写成「**本清单全部分组逐项落表**」，不点名分组；②生成清单时给每项一个稳定编号，progress 状态表用同一套编号（本卡 rework-2 是 1~21 连续编号，progress 却重编成 A1~A11/B12~B16 并做了合并，追溯要靠人对）；③文档类返工项的完成判据写成可 grep 的形态（如"progress 中不再出现字符串 `205（+5）`"），让核对不依赖阅读。

### 候选-48 · "环境干扰 / 环境假红"是要证明的结论，且证明需要多次等价复跑——单次绿会把真抖动盖过去
- **触发场景**：worker 报测试挂死/失败，主控在另一环境复跑一次通过，据此裁"环境干扰、非代码缺陷"。
- **现象**：返工 2 中 worker 三次全量 `npm test` 未得终态 → 裁定为"会话内残留测试子进程的环境干扰" → 主控干净环境**一次** 212/212 exit 0 → A-0 硬门槛判过。我独立并跑同一批文件（`herdr-adapter` + `agent-node`，`npm test` 也包含它们）**6 次红 2 次**，失败点与代码轮 2 报告的 P2-4 **逐字相同**（`✖ DHR_33 driver #3/#5…` / `Error: timeout:done attention`）。也就是说：**"环境干扰"的裁定是对的那一半（挂死确实与残留进程有关），但它顺带把一个仍然存在的真抖动一起赦免了。**
- **根因**：挂死与偶发红是两种失败，被合并成一个"环境"结论；而复跑一次通过对偶发红（本卡红率约 1/3）几乎没有证伪力——单次绿的概率本来就有 2/3。候选-17 的判据②"无沙箱等价复跑不复现"没有写次数，就默认成了一次。
- **回流建议**：①裁"环境"前先把失败**按签名分类**（挂死 / 断言红 / 超时红），逐类给结论，不合并；②等价复跑的次数要能证伪观察到的红率（原始 2/4 红，复跑至少 5~6 次全绿才谈"不复现"），**次数与红率写进账本**；③硬门槛（如本卡 A-0）的通过判据直接写成"连续 N 次 exit 0"，别写"跑通一次"。

### 候选-49 · 有效单测的变异证据必须以最终提交为基线——中间态取的变异证据会被后续返工作废
- **触发场景**：heavy 卡由复核实例选定变异点、做红→还原→绿三段取证，之后**还有返工**。
- **现象**：本卡 E-3306 的 8 个有效变异是在 `5ecd4b0`（返工 1）上取的，review.md 据此在返工 2 之前就把 E-3306 判成"达成"。随后返工 2（`4d68163`）改动了 `workflow-driver.mjs` **108 行**——正是 8 个变异点里 5 个所在的文件。验收表的证据指针仍指向轮 2 报告。我在 HEAD 上复算了其中 5 个点，全部仍红（结论未被推翻），**但这是复算出来的，不是原证据自动成立的**。
- **根因**：变异证据是"某一版代码 + 某一版测试"的联合属性，任何一边变了都要重算；而验收表的"达成"是一次性写入的状态位，不带基线信息，也没有机制在后续提交时把它置回"待复算"。
- **回流建议**：①变异表的每一行必须记 **基线 commit sha**，验收表的结论列同样写基线；②只要目标文件在后续提交里被改动，该条验收自动回到"待复算"；③heavy 卡的收口顺序改成"最后一次返工之后再取变异证据"，或在最终提交上做一次抽样复算并留痕（本卡 5/8 抽样复算可作范式）。

### 候选-50 · 测试对用户级/家目录配置的隐式依赖——外部配置路径一律强制注入，缺省即失败
- **触发场景**：被测代码有"默认读 `~/.xxx/config.json`"这类回退，测试没显式注入路径。
- **现象**：`agent-node.test.mjs` 新增的双候选用例 `startWorkflowDriver({ repoRoot, runId, actor, herdrCli: fake.cli })` **没传 `herdrRegistryPath`**，默认落到本机 `~/.dh-relay/executor-profiles.json`（实测存在、3142 字节、无 `herdr.codex.test`）。当前恰好走不到（process 分支先返回），但这正是它零判别力的成因之一；一旦按候选-46 改成强断言，测试结论就会随本机注册表内容漂移。同文件的 `herdr-adapter.test.mjs` 的 `runtimeFixture` 反而做对了（注入临时 registry）。
- **根因**：生产代码的"默认路径"回退是给运行时的便利，测试继承了这个便利就等于把机器状态引进了断言。同一个仓里两个测试文件一个注入一个不注入，说明这不是规范而是习惯。
- **回流建议**：①凡读仓外配置的加载器，给一个"测试模式必须显式传路径、缺省抛错"的开关（或在测试 setup 里统一注入指向临时目录的环境变量）；②复核清单加一条机械检查：新测试里出现被测组件的**默认路径回退**且未注入 → 直接记 finding；③与候选-36 互补——候选-36 说"至少有一条机器证要跑真产物"，本条说"其余所有测试都不许碰真产物"。

### 候选-51 · 挂死 ≠ 失败：起常驻轮询对象的测试 fixture 必须注册停止钩子，套件门槛要记 exit code 与 wall-clock
- **触发场景**：测试里启动"自带轮询循环、靠条件自终止"的常驻对象（driver / watcher / service）。
- **现象**：本卡 driver 的 herdr 分支是 `while (!stopping)` 轮询；返工 1 前 `idle` 恒态**没有任何生命周期出口**（每秒 spawn 两个 herdr 子进程、永不停），而 `runtimeFixture` 当时**没有 `t.after(driver.stop())`**，靠 driver 自终止。后果一路蔓延：需求轮时全量 `npm test` 两次挂死被强杀（含孤儿 service 进程）；轮 2 的 V3 变异下测试进程 120s 未退出（exit=124）；返工 2 时 worker 三次未得终态。返工 2 补了 `t.after(driver.stop())` + idle 有界后，我复跑同一个 V3′ 变异**正常 exit=1**——治理确实见效。
- **根因**：`node --test` 里一个不终止的异步循环不会报错，只会把整个套件拖到 runner 超时；"测试红"有人看，"测试不返回"没人看，甚至会被当成机器慢。而 fixture 的清理责任经常被"这个对象会自己停"的假设跳过。
- **回流建议**：①凡在测试里 `start` 出一个带内部循环的对象，**同一行下面就写 `t.after(() => obj.stop())`**，不假设它自终止；②产品侧配套：任何轮询循环都要有"所有非活跃状态"的有界出口（本卡返工 2 把上限从"仅 done"改挂"非 working/非 blocked 的静默期"就是这个）；③套件门槛的记录格式从"pass/fail 数"改成"**exit code + wall-clock + pass/fail**"——本卡两次"全量绿"记录都没写耗时，挂死史全靠账本散文追溯。

### 候选-52 · 派活层事故不落任何工件——progress 需要一类"工具链/派活事故"条目
- **触发场景**：主控经 Herdr / 插件 / 网关派活给 worker 或复核实例，过程中出现终端层、模型层、命令层的事故。
- **现象**：本卡过程中至少发生过：复核实例的模型身份三/四证矛盾（这条进了 review 抬头，因为候选-40 要求）、codex 提示词卡在输入框、Edit 工具改写行尾（这条进了 review-code2 §三留痕）。**其中只有被某条已有教训点名要求登记的那两条留下了痕迹，其余（如 prompt 卡输入框）在 progress / findings / review 里零记录**——我这轮是从主控的派活说明里得知的，仓内无从核实。
- **根因**：progress 的条目类型默认是"施工/复核的业务进展"，工具链事故既不属于代码变更也不属于验收证据，没有它的位置；而它恰恰是最容易复发、也最不容易被下一个人预料到的一类。
- **回流建议**：①progress 增设一类条目前缀（如 `- [工具链]`），主控与 worker 遇到派活层事故当场追加一行（现象 + 绕过方式），不判定不展开；②收口时教训 miner 专扫这一类；③仓内已有 `knowledge/herdr-派活操作.md` 收纳规程，事故现象可回流到那里，但**先要有账**。

### 候选-53 · 只读复核做字节级变异不能用"会重写全文"的编辑工具；向 CRLF 文件写 LF 新行会留下 git 不可复原的混合行尾
- **触发场景**：Windows + `core.autocrlf=true` 的仓库；复核实例做临时变异；worker 用 agent 工具编辑既有文件。
- **现象**：代码轮 2 第一次变异误用 Edit 工具，它把文件全文规范化成统一 CRLF——而该文件当时是**混合行尾**（worker 写入的新行是 LF、原文件是 CRLF），于是 sha256 无法往返还原。用 `git checkout --` 只能归位到"仓库规范形态"（`git hash-object` 与 HEAD 一致、内容零变化），**混合行尾的原始字节永久丢失**（autocrlf=true 下 blob 是纯 LF，git 里根本没存过那份混合字节）。轮 2 此后改用字节级替换，全部 sha256 往返成功。rework-2 加了"行尾纪律"条款，返工 2 实测已统一（我核了 8 个文件，全部 100% CRLF）。
- **根因**：两层——①agent 的编辑工具以"读全文 → 改 → 写全文"实现，天然会规范化行尾，与"字节级不变"的复核要求冲突；②worker 侧的行尾混合是无声的，`git diff` 因 autocrlf 看不见，只有对文件做 sha256 才暴露。
- **回流建议**：①复核实例做临时变异一律用**字节级替换**（读 bytes → replace → 写 bytes），并在报告里贴变异态与还原态双 sha256；②worker 编辑既有文件时保持仓库规范行尾，收口前跑一次"混合行尾扫描"（每个改动文件的 `\r\n` 行数 == 总行数）；③`git checkout` 能"修复"这类问题这一点要写清楚——它恢复的是**规范形态**不是**原始字节**，不能当作"没动过"的证据。

### 候选-54 · 派工前的 fresh 只读预审（审 brief / task_plan 本身）是投入产出比最高的一道闸
- **触发场景**：heavy / 高危卡，主控冻结架构裁决后、派工前。
- **现象**：本卡在派工前多加了一路"开工预审"（fresh 实例只读审 brief + task_plan），产出 19 条（P1×6 / P2×8 / P3×5）。**六条 P1 全部是主控冻结裁决里的代码事实错误**：`relay.event/v2` 没有 payload 字段、`emitEvent` 会静默丢弃多余键、host-observation v0 装不下版本/能力 hash、`inspectRun` 的 detail 视图不含事件、reason code 错用了 pi-agent 专属的 `E_EXECUTOR_ADAPTER_LOST`、profile 两套结构之间没有桥。这六条**任何一条被施工者照做，都会产出一份"形状对、跑不起来"的交付**，返工成本远高于一次只读预审。
- **根因**：主控冻结架构裁决时依据的是自己的只读侦察记忆，而侦察与冻结之间隔着"把观察写成裁决"这一步——这一步会把"我看到 X"悄悄变成"X 是这样"。预审实例读的是**同一份 brief + 同一份代码**，但没有那份记忆，只能去核。
- **回流建议**：①heavy 卡的 Recipe 增加"开工预审"为必做路径（本卡是临时加的，不在冻结的五路里）；②预审的输入固定为 brief + task_plan + 它们引用的源文件，输出只报"裁决里的事实断言哪条与代码不符"，不做方案评审；③预审 P1 的处置固定为"改 brief 再派工"，不允许"派工时口头交代"。

### 候选-55 · task_plan 里冻结引用的既有教训会被 worker 自建 helper 悄悄绕开，且历轮复核都不核它
- **触发场景**：task_plan / brief 里写「按候选-NN 做」「一律用 `xxx` helper」这类对既有教训或既有工具的冻结引用。
- **现象**：task_plan `:17` 逐字写着「等待一律用 `test/helpers/settled-state.mjs` 的 `settledState`（**等不变量，候选-35**）」。交付的 `herdr-adapter.test.mjs` **没有 import `settled-state.mjs`**，自建了 `runtimeUntil(check, label, timeoutMs)`，等的正是"我要断言的那个事件出现"——恰好是候选-35 点名的反模式。此后 **代码轮 1、需求轮、代码轮 2 三路复核都没有核这条冻结引用**（轮 2 只是从抖动现象反推到 fixture 构造，没追到这条规定）。
- **根因**：冻结引用写在 task_plan 的 Context Packet / 步骤说明里，是散文而不是验收项；复核的注意力在 brief 的完成条件与 rework 清单上，没有一条流程动作会去核"task_plan 里点名要用的东西用了没有"。
- **回流建议**：①task_plan 里凡出现"一律用 X / 按候选-NN 做"，就在验收表或复核清单里给它一行（可 grep 的判据，如"新测试文件必须 import `settled-state.mjs`"）；②这类冻结引用尽量做成**机器闸**（本仓已有 `control-plane-imports.test.mjs` 这类 import 纪律测试的范式，完全可以加一条"测试文件不得自建 wait helper"）；③复核 worker 的核对清单固定加一问：「task_plan 点名要用的既有工具/教训，代码里用了吗？」
