## 7. 教训候选备料（供主控搬进 `lesson_candidates.md` 再走 miner 归并）

> 按 `教训库-候选.md` 的字段格式预写。本轮不直接写入候选库（只读范围外）。

### 新候选提案 1 · finding 的提出者不宜裁决自己 finding 的整改是否闭合——「fresh」是按轮次失效的属性

- **触发场景**：复核轮报出 finding → 施工方整改 → 需要判定是否闭合 · **建议分类**：行为流程 · **来源**：DHR_61（`review-code1-opus.md:245` 同一 reviewer 复验自己提出的 14 项并全判 CLOSED）；对照 DHR_33（返工 1 由换人 fresh 的代码轮 2 复验，当场逮出返工 1 **新引入**的 P1-2）
- **疑似重复**：**候选-26 的镜像面**（那条讲「主控驳回复核发现也是待审对象」，本条讲「复核者对自己 finding 的整改判 CLOSED 也是待审对象」）；两者同一根因——裁决与被裁决同源。裁决时可考虑合并为一条通用条目「任何一方对自己论断的复审都需要外部一支」
- **现象**：DHR_61 代码轮 1 报 14 条，整改后由同一实例复验并全判 CLOSED，P0/P1 归零。复验质量本身很高（每项三重证据、未闭项如实标 OPEN、拒绝以主控口径代替自身未复现的观察），但复验路径**沿用的是提出者上一轮自己设计的探针**（如 P0-1 只重跑 V-007/V-008 两条原崩路径），结构上很难命中「整改新引入」这一类别——恰是 DHR_33 换人复验一次就抓到的类别。
- **反思**：「fresh」不是实例的固有属性，是**相对某个论断**的属性。一个实例在提出 finding 的那一刻起，对「这条该怎么修才算修好」就有了先验；复验时它验证的是自己的预期是否被满足，而不是「还有没有别的没修好」。
- **建议后续动作**：① 整改闭合的裁决默认交给**下一路 fresh 实例**（heavy 卡天然有代码轮 2 承接）；② 若因排期必须由原 reviewer 复验，则其 CLOSED 裁决在下一路 brief 里**必须标为「待独立复核」并明示允许推翻**；③ 复验轮的探针清单要求至少一条**不同于上一轮的构造角度**。

### 新候选提案 2 · 整改轮必须在主账本落账——reviewer 的私有 review 文件不是账本

- **触发场景**：复核发现 → 施工方整改 → 整改结果只写在 review 文件的「复验」章节 · **建议分类**：行为流程 · **来源**：DHR_61（14 项整改闭合全部只存在于 `review-code1-opus.md` §7；`progress.md:14` 止于整改前一天、`findings.md:11-12` 两条已被推翻的 finding 仍 open、`review.md:10` 代码轮 1 仍写「待派」、无 `rework-*.md`）
- **疑似重复**：**候选-47 的前一步**（那条讲返工清单的门槛句漏点某个分组，本条讲返工清单**根本不存在**）；与 **候选-41** 同族（findings 是给收口流程读的清单）但方向相反——41 讲该升的没升，本条讲该改的没改
- **现象**：整改真实发生且被独立探针证实（32 条终态证据），但收口三件套（progress / findings / review）一个字都没动。读账本的主控会看到一个比实际严重得多的状态：F-003 的四项「仍未完成」其实全已实现，代码轮 1「待派」其实已出两轮结论。
- **反思**：与 DHR_33 的「打了 ✓ 但没做」形态相反、后果同构——账本与事实脱节，收口者拿到的不是事实。而这次更隐蔽：因为**代码是对的、复核是扎实的**，唯一的破绽在文档，最容易被判为「小事收口时补」，但收口恰恰就是读这些文档的时刻。
- **建议后续动作**：① 整改轮的完成判据固定包含「`progress.md` 追加日志条 + 证据条」与「`rework-N.md` 按候选-47 全部分组逐项落表」；② 被复核推翻的 findings 按候选-10 追加纠错条、原句保留；③ 可做成机器闸：`review-*.md` 出现「复验 / rework / CLOSED」字样而同期 `progress.md` 无新增条目 → 记 finding。

### 新候选提案 3（正面样本） · 注册期的容量/边界证明要用 schema 上界构造，使其成为运行期实际载荷的上界

- **触发场景**：契约规定「某载荷不得超过 N 字节」，而载荷由多个受 schema 约束的字段拼成 · **建议分类**：编码陷阱 · **来源**：DHR_61 P1-1 的整改（`profiles/validate-profiles.mjs:67-93`）+ 代码轮 1 的独立复算（V-014/V-015/V-016）
- **疑似重复**：**候选-36 的正面形态**（那条讲机器证要跑真产物，本条讲**注册期证明不能跑真产物**——必须跑 schema 上界）；两条互补，裁决时宜并列而非合并
- **现象**：初版实现只在 pause 落账那一刻做 4096 兜底——恰是设计明令禁止的时点（「不能在 quota 发生时才因尺寸失败」）；且用 schema 合法上界实测，一个**完全合法**的 registry 算出 4301 字节，会在最需要它的时刻落不了账。整改改为在注册时用「`identifier`='R'×128 + hash 64 位 + 最长合法毫秒时间戳 `9999-12-31T23:59:59.999+23:59` + 6 个 snapshot」构造 JCS payload 求证，使注册期证明成为运行期实际载荷的**严格上界**，不留「注册通过但落账超限」的缝；运行期兜底保留为第二道闸。
- **反思**：容量类约束天然是「所有合法输入」的全称命题，拿手头的真实配置去量只证明了一个样本；而它的失效时刻恰恰是最坏情况发生时——也就是最不能失败的时刻。同时这条依赖时间戳精度这类**非 schema 约束**时会漏（P3-5：`(\.[0-9]+)?` 小数秒无上界），必须把论证用到的每个上界都在 schema 层背书。
- **建议后续动作**：① 容量/边界证明一律以 schema 合法上界构造，并证明它是运行期载荷的上界；② 论证中用到的每个「最大合法代表」都要有 schema 层背书，没有就先收窄 schema（本卡新增 `$defs/millisecondTimestamp` 即此做法）；③ 用独立模型复算一遍边界分档（本卡 V-015 的 n=0..6 扫描），不复用被测实现。
