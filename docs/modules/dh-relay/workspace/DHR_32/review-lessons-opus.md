### L-3 · Windows 入口解析要两级 → **需改写（拆二）**

**独立复算**：三段事实全部成立。
- `claude-grok` 是 PowerShell Function，`where.exe claude-grok` 不命中（BLOCKED-1 属实）；
- 裸 `Get-Command` 过宽实测确认：`pwsh -NoLogo -Command "Get-Command -Name Get-ChildItem -ErrorAction Stop"` **exit 0**。也就是说把 `command_alias` 写成 `Get-ChildItem`（或任何 cmdlet 名）都能通过 `E_UNRESOLVED_ALIAS`；
- 基线 `0269981` 时**修法尚未落实**：`validate-profiles.mjs:55-63` 用的是裸 `Get-Command -Name $env:DHR_PROFILE_ALIAS -ErrorAction Stop`，无 `-CommandType` 限定。
- **fadd742 后已落实**：兜底改为 `Get-Command -Name … -CommandType Application,Function,Alias,ExternalScript -ErrorAction Stop`，并新增 `negative-unresolved-alias` fixture。②这一项现在是「已修」而非「待修」。

**为什么要拆**：现在这一条塞了三件不同性质的东西——

| 内容 | 性质 | 该去哪 |
|---|---|---|
| ① `where.exe` 只认 PATH 可执行文件，Function/Alias 要 `pwsh Get-Command` 兜底 | Windows/PowerShell 平台事实 | `knowledge/`（+ DHR_33 输入） |
| ② 兜底必须限 `-CommandType Application,Function,Alias,ExternalScript`，排 Cmdlet 防过宽 | 本仓当前缺陷的修法 | findings / DHR_33 输入，**不是教训** |
| ③ 此类入口不可被直接 spawn、只能经 shell 拉起 | **可迁移原则** | 教训库 |

③ 才是有迁移价值的那条，而且它在本卡被两路独立命中（BLOCKED-1 的解析形态登记 + 需求轮 P2-2「evidence 没登记『因此不可直接 spawn』这个可执行性约束」）。混在一条里，将来读者只会记住「Windows 上要两级解析」这个实现细节，而漏掉真正会咬人的那句。

**另需注意（写作纪律）**：miner 备料时把 ② 写成了祈使句（「必须 `-CommandType ...`」），而当时代码并未这么做——读者会误以为已落实。虽然 `fadd742` 事后把它修了，但**备料写下的那一刻它是一条假的「已知已解决」**。教训条目描述修法时必须标注落实状态（已修 / 待修 / 建议），否则条目会在时间轴上说谎。这一点并入漏-A 的建议动作。

**改写建议（③ 的成稿）**：

> ### 候选-N · 「名字能解析」≠「能执行」≠「能被非交互 spawn」——入口探测必须分这三层，且要登记该入口的拉起方式约束
> 触发场景：给 CLI 入口 / 命令别名做可用性探测并写进注册表、契约或调度器；尤其是入口可能是 shim / 函数 / 别名 / 包装脚本的场景 · 建议分类：领域知识 + 编码陷阱 · 来源：DHR_32 BLOCKED-1（`claude-grok` = PowerShell Function，`where.exe` 必败）+ 需求轮 P2-2；`claude5` 入口名可解析但目标 CLI 文件不存在
> 疑似重复：无
> - 现象：同一张注册表里三种形态各踩一层——`claude-grok` 是 PowerShell Function，名字解析得了但**不能被 `spawn('claude-grok')` 直接拉起，只能经 shell**；`claude5` 的入口名解析得了、目标可执行文件却根本不存在，校验器照样放行；而校验器的兜底解析裸用 `Get-Command`，连 `Get-ChildItem` 这种 cmdlet 名都判「可解析」。三个洞都在「解析成功 = 可用」这一个假设上。
> - 反思：探测命令返回 0 只回答了「这个名字在某个命名空间里有定义」，它不回答「它指向的东西还在不在」，更不回答「调用方那种拉起方式能不能拉起它」。而调度器/Adapter 恰恰是用第三种语义在消费这个结论。
> - 建议后续动作：① 入口探测分三层各自出结论并分别登记：名字可解析 / 目标可执行文件存在 / 可被目标拉起方式启动；② 注册表或 evidence 里为每个入口登记**解析形态**（executable / cmd-shim / ps1-shim / function / alias）**与拉起方式约束**（可直接 spawn / 必须经 shell / 必须经特定宿主命令），消费方按此选拉起方式；③ 平台细节（Windows 上 `where.exe` vs `Get-Command -CommandType ...` 的分工）归 knowledge，不写进教训条目正文。

### 漏-A · 需求项在文档逐级复制中静默丢失 —— **本轮最该补的一条**

**事实**（需求轮 P2-1，全仓可复算）：

- `design/02` B4 原文：「注册表条目解析到真实 `cli/config_dir/`**`work_dir_root`** 并被实际使用」；
- DevPlan §3.2 DHR_32 **目标**段：「逐一核对实际命令、**配置来源与工作目录规则**、账号身份可观测信号 ……」；
- DevPlan §3.2 同一张卡的**验收口径**段：只剩「注册表条目解析到真实 cli/config_dir」——`work_dir_root` 在这一步被摘掉了；

- 于是 task_plan 的 evidence 模板没有这一节、§2.3 字段闭集没有这个字段、五份 evidence 零出现、注册表零出现。

全仓检索 `work_dir` / `工作目录`：**只在 DevPlan:123 那一处命中**。

**为什么这是教训而不只是本卡缺陷**：「brief 逐字复制验收口径」这个机制是**为了防漂移**才设的（brief 抬头明写「本文件是只读副本；口径冲突以 DevPlan 为准」）。结果它反过来把上游的一次摘录遗漏**固化并放大**了——因为逐字复制不会去核对上游的上游。这是一个防护机制自身产生的失效模式，很值得记。miner 完全没抽到它，可能正因为它不是任何一次失败或返工的产物：**它没有引发任何红灯，只是安静地少了一项。**

**成稿建议**：

> ### 候选-N · 任务卡「目标」段与「验收口径」段必须互相核对，逐字复制的 brief 会把上游的摘录遗漏固化成永久丢失
> 触发场景：验收口径从上游设计文档摘录进任务卡，再被 brief / task_plan 逐字复制下发；尤其是「目标」与「验收口径」分两段写的卡 · 建议分类：行为流程 · 来源：DHR_32 需求轮 P2-1（`work_dir_root` / 「工作目录规则」全链丢失）
> 疑似重复：与候选-4（内部引用悬空）、候选-14（声称与上游一致要读源文件）同属「文档传导」家族，但触发形不同——候选-4 是引用目标不存在（会 blocked），候选-14 是声称一致但没核（会被复核逮），本条是**逐级复制中少了一项且不产生任何红灯**
> - 现象：design/02 B4 要求解析到 `cli/config_dir/work_dir_root`，DevPlan 任务卡的「目标」段还留着「配置来源与工作目录规则」，但同卡「验收口径」段已把 `work_dir_root` 摘掉；brief 逐字复制验收口径，于是 evidence 模板、字段闭集、注册表、五份 evidence 全链零出现。全仓检索该词只剩 DevPlan 一处。施工与两轮复核都不会因此报错——它只是不见了。
> - 反思：「逐字复制」是防漂移机制，但它只保证**副本与母本一致**，不保证**母本与母本的母本一致**；一旦摘录环节漏项，逐字复制会把漏项忠实地传播下去并盖上「已对齐」的印章。同一张卡里「目标」段和「验收口径」段本来互为冗余校验，却没人拿它们对过。
> - 建议后续动作：① 派活前对任务卡跑一次「目标 ↔ 验收口径」互查：目标里点名的每一项，验收口径里要么有承接、要么有显式的「本卡不承接，归 XX 卡」声明，两者都无即视为漏项；② brief 的完成条件段除逐字复制外，追加一行「上游 Oracle 原文差异说明」（本次摘录相对 design 原文删了什么、为什么）；③ 这条可做成 dh-check 静态规则（抽取目标段名词短语 → 在验收口径段做存在性匹配 → 未命中的列出待人确认）。

### 漏-B · 机读清单必须能表达「这条当前不可用」，否则必失败条目与正常条目外观相同

**事实**（需求轮 P1-3）：注册表五条里 `herdr.codex.ninth`（账号未登录）与 `herdr.claude.account5`（目标 CLI 文件不存在）派下去必然失败，但 `codex-ninth` 的六项能力位全标 `supported`、与三条可用 Profile 外观完全一致，校验器对 golden 判 `ok:true`。`claude5` 只能靠「`product:unverified` + 全 `unproven`」隐含表达，这是约定不是契约。而 P6-M2 的原文限定词是「每个**启用** Profile ……」——字段闭集里根本没有「启用/停用」的表达手段。

**可迁移原则**：**「能力」与「当前可用性」是两个正交维度。** 能力位回答「这东西设计上能做什么」（从 `--help` 就能读出来，未登录的账号照样列得出全部开关），可用性回答「现在派下去会不会成」。字段闭集只冻结了前者时，消费者拿不到后者，只能自己发明规则或者去读人写的 markdown——而这恰恰是本卡要消灭的「靠猜」。

去重：候选-32（字段缺口先查消费者是否已降级）方向相反（那条是劝阻扩协议），本条是**指出缺了一个维度**，不重复。

### 漏-C · 布尔字段会把「未证」吞成「否」——审计类产物里「不知道」必须有独立表达

**事实**（需求轮 P2-8）：`claude5` 的 `capabilities.headless = "unproven"`，但同一条 entry 的 `headless_supported = false`。三值枚举里的「未证」被布尔字段压成了「不支持」。

**可迁移原则**：「不支持」和「不知道」的下游动作不同——前者是永久排除，后者是待补证。二值字段无法承载三态，一旦并存就必然有一边在说谎。这条是 dh-relay 反复强调的「不可证要如实标『不可证』而非猜」这个价值观在**数据结构层**的延伸：文字上守住了不可证，字段上却守不住。附带一个结构性问题：`headless_supported` 与 `capabilities.headless` 本身语义重复，重复字段是这类失真的温床。

**fadd742 后：这条不但没修，反而被固化了。** 返工给校验器加了一条一致性检查：

```js
if (profile.headless_supported !== (profile.capabilities.headless === 'supported')) → E_SCHEMA
```

它把「`unproven` → `headless_supported:false`」从一个疏忽**升级成了强制规则**——现在任何「未证」的入口都**必须**在布尔字段上声明 `false`，否则校验不过。一致性是有了，但「不知道」被永久编码成了「不支持」，且消费者再无从分辨。

这让本条的价值不降反升：**为二值字段与三值字段加一致性检查，会把二值那边的表达力缺陷锁死**。正确做法是先问「这个布尔字段是否还有存在必要」（它与 `capabilities.headless` 语义重复），而不是让三值去迁就二值。原本价值中等，现在建议**优先入库**，并把返工这一步作为反面示例写进现象段。

### 漏-D · 变异点选在有冗余保护的分支上，变异后照样红——红的不是地方

**事实**（需求轮 P2-6）：本卡的有效单测变异点选在 `validate-profiles.mjs` 的 `E_CREDENTIAL_FIELD` 黑名单分支。`progress.md:17` 的记录很诚实地写出了变异后发生了什么：**「目标反例由预期 `E_CREDENTIAL_FIELD` 退化为 `E_SCHEMA`，因此红」**。

也就是说：把凭据黑名单**整个短路掉**，那份 negative fixture 依然被拒——只是拒绝它的换成了 schema 的 `additionalProperties:false`。原因是两份凭据 fixture 都打在**顶层**（`{"api_key":"fixture-only","profiles":[]}`），而顶层本来就是闭集。**变异证明的是「error code 会变」，不是「零凭据红线会破」。** 红线的独立有效性零证明。

**可迁移原则**（候选-6 的下一层）：候选-6 说「要做变异对照」，本卡做了；本条说**变异点必须选在「该保护唯一负责的场景」上**。若变异后仍然红，要先确认红的原因是目标断言失效，而不是另一层防护接住了——后者说明这个变异点选错了，换一个真正只有它守得住的输入。判据：变异 + 构造一个「只有被变异的那层能拦」的输入（本卡就是「凭据值出现在合法 entry 的自由字符串字段值里」，如 `account_alias: "sk-ant-api03-…"`，schema 的 `minLength:1` 拦不住，只有 `CREDENTIAL_VALUE` 正则拦得住）。

这条含金量不低，而且有点讽刺：miner 引用了 progress 那段变异记录去给 L-1 当旁证，说明它读到了这段文字，却没看出这段文字自己承认了变异没证明什么。

**fadd742 后（半修）**：两份凭据 fixture 都从顶层改到了合法 entry 内部。`negative-credential-value` 现在把 `sk-ant-api03-…` 放进 `quota_detector_id`（闭集内的合法字段），**只有 `CREDENTIAL_VALUE` 正则拦得住**——这条已经是干净的隔离变异点了，正是我需求轮 P2-6 建议的做法。但 `negative-credential-field` 仍用 `api_key`，而 entry 级 `additionalProperties:false` 照样拦得住它，**冗余保护依旧存在**，变异该分支后红的原因仍可能是 schema 而非黑名单。教训成立且仍有未闭合的一半，建议入库时把这个「一半修好、一半没修」的对照写进现象段——它把「隔离变异点」这件事讲得比任何抽象说明都清楚。
