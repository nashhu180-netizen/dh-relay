• 部分成立

  ① 候选-35只针对“快照滞后”——部分。其触发场景确实是“先事件账、后快照”的非原子写序；DHR_33/
  DHR_61 等的是内存 store.events，DHR_68 等的是已读出的派生状态，不能直接套用“事件到账但快照
  旧”的原始故障链。
  但候选-35的反思又明确规定：等待条件与断言目标是同一件事时，轮询会自证。因此不能把候选-35缩
  窄成只管快照滞后，并以此完全驳回 LES-01。

  ② 等待后的断言均为独立性质——部分。DHR_61 等到 checkpoint_recorded 后核的是 Receipt 协议、
  主/回退身份与不含投影值，属独立性质；DHR_68 除重复核对 waiting_human 外，还核 Attention 数
  量、detail、HOST_LOST 缺失、零发送/零关 pane，亦有独立性质。
  但 DHR_33 在等待 checkpoint_recorded 后又断言同一事件存在，确属候选-35所说的重复证明；将其
  称为“冗余而非缺陷”站不稳。该用例已 skip 且断言冻结，只说明本卡不能整改，不改变该断言的证明
  力问题。另，提出者称“两条 agent-node 用例”都直接重断言同一事件并不准确：DHR_61没有该重复断
  言。

  ③ 改为独立不变量超出冻结口径——部分。task_plan.md 第4、5、8步明确冻结等待
  checkpoint_recorded / waiting_human，所以不得由施工者自行改写为另一套屏障，主控在“不可擅改
  冻结实现”上站得住。
  但允许范围本身就是这些用例的“等待逻辑”，且 C-005 同时要求新等待工具遵循 settled-state.mjs
  的“等不变量、不等断言值”口径，brief 红线也禁止“等出我要的值”。冻结文本内部存在张力。因此不
  能据此断言独立不变量天然越出本卡允许路径；至多可说它偏离了已写明的具体等待目标，需在卡外澄
  清后才可变更。

  结论：主控对“DHR_61、DHR_68并非纯自证”以及“不能在本卡内擅自改写冻结步骤”的驳回有依据；但把
  候选-35限缩为快照问题、并将DHR_33的重复断言排除为非缺陷，依据不足。
