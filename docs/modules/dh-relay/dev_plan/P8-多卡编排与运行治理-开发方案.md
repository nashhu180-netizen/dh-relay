## 0. 定位

P8 在单卡闭环稳定后增加运行治理能力：多卡调度、重编排、诊断、跨项目 Action、run 级归档和宿主外 Oracle。

P8 不建设任意 DAG。卡间边只来自 DevPlan 依赖、冻结的路径重叠规则和发布版 Workflow Contract。

## 1. 前置条件

- P7 Gate 通过；
- 至少一张真实标准档卡已完整 verify；
- 单卡恢复、E11、Finalizer 和 DevHarness Gate 已稳定；
- 用户明确放行 P8；
- 用户在开工阶段选择 2~3 张代表性真实卡。

## 2. 交付范围

交付：

1. 一 Run 2~3 卡的依赖、并行和路径重叠调度。
2. 同仓 Finalizer 串行与基线刷新。
3. 卡内最小重编排和计划 Revision。
4. 只读诊断 Agent、持久 Attention 和受控选项。
5. Hook、Action Registry 和 durable Outbox。
6. 周报进行中与完成后写入场景。
7. run 级 `docs/relay/` 归档。
8. 不 import Relay Core 的宿主外 Oracle。

不交付：

- 任意 DAG 编辑器；
- 跨仓 Run；
- 自动修改 DevPlan 目标和验收；
- 模型任意控制事件；
- 外部消息队列；
- 远端部署；
- Linux 最终定型。

### DHR_41：多卡调度

目标：

- 一 Run 实例化 2~3 张授权卡。
- 卡间边来自 DevPlan 依赖。
- 静态变更范围重叠的卡强制串行。
- 无依赖且无重叠的卡按 `max_parallel_cards` 并行。
- 同仓同一时刻只有一个 Finalizer。

基线刷新：

- 前卡快进后，后卡候选在暂存分支 rebase。
- patch 不变时机器闸复跑并重新确认。
- patch 变化时重跑受影响机器闸和两轮复核后重新确认。
- 冲突进入 `closeout_blocked`。

### DHR_42：卡内重编排

触发：

```text
dependency_blocked
```

流程：

```text
Relay 创建 replan request
  -> 启动 replanner profile
  -> Agent 只读 Authority、Contract、当前计划和证据
  -> 提交 proposal
  -> Compiler 校验
  -> DSH 展示节点/边 Diff 和影响面
  -> 用户批准或拒绝
  -> Relay 保存 receipt 并发布新 revision
```

边界：

- 只允许在当前卡内新增合法前置节点。
- 不加卡、不换卡、不删硬节点。
- 不修改目标、验收和外部 effect。
- 不受影响卡完成手上节点后继续。
- 依赖闭包在安全点冻结。

### DHR_43：诊断与 Attention

触发包括：

```text
interrupted_unknown
paused
closeout_blocked
quota 无 fallback
恢复发现断棒
authority 或 gate 冲突
```

诊断分两段：

1. 只读 Diagnoser 输出 report、evidence 和 option set，然后退出。
2. Relay 持久化 Attention，DSH 展示，用户可以隔天选择。

每个选项冻结：

```text
option_id
action
params
target
expected_state_hash
nonce
expires_at
```

Diagnoser 只能使用 `capabilities.readonly=true` 且机器可证明只读的 Profile。Prompt 声明不能替代权限实现。

### DHR_44：Hook、Action 与 Outbox

首批事件：

```text
run.started
node.succeeded
card.succeeded
card.failed
attention.opened
run.finished
```

首个真实 Action：

```text
project-status.weekly-report.append@1
```

场景：

- S3 某批完成后写进行中周报。
- 卡片完成后写完成周报。

规则：

- Action 必须已注册并带版本和 content hash。
- 计划内禁止内联 shell 和任意脚本路径。
- request 不可变并携带 idempotency key。
- 状态至少为 pending、running、succeeded、failed、dead_letter。
- 默认 best_effort，不把周报结果冒充源卡验收。
- 目标项目拥有业务写入程序和检查器。

### DHR_45：归档、Oracle 和三卡实战

归档：

```text
<repo>/docs/relay/README.md
<repo>/docs/relay/runs/<run_id>/
```

run 级 Archive 节点作为单写者：

- 自建暂存分支。
- 持同仓 Finalizer 锁与 Archive lease。
- README 按 run_id 幂等 upsert。
- 生成 archive-manifest。
- CAS 快进后清理暂存分支。

宿主外 Oracle 不 import Relay 生产代码，独立重算：

- 每卡 verify、Risk-Count、manifest 与 candidate；
- DevPlan 状态和 SHA；
- review attempt hash；
- worktree 和暂存分支清理；
- Run 时间线、终态和 docs/relay 一致性；
- Outbox 幂等和 dead-letter；
- 重编排 revision 与用户 receipt。

真实实战至少包含：

- 一对可并行卡；
- 一对依赖或路径重叠卡；
- 一次 replan；
- 一次 diagnoser Attention；
- 一次进行中周报与一次完成周报；
- 一次基线刷新或受控冲突注入。

## 4. P8 阶段闸

### 机器闸 P8-M

| ID | 命题 |
|---|---|
| P8-M1 | 2~3 卡按依赖和重叠正确串并行 |
| P8-M2 | Finalizer 串行与基线刷新行为正确 |
| P8-M3 | Replanner 只能提交合法卡内 Proposal，越权被拒 |
| P8-M4 | Diagnoser 强制只读，Attention 可跨 DSH 重启处理 |
| P8-M5 | 周报 Action 幂等，失败和 dead-letter 可见 |
| P8-M6 | docs/relay 归档单写、幂等且与事件账一致 |
| P8-M7 | 外部 Oracle 对真实三卡 Run 独立重算通过 |

### 人类闸 P8-H

用户判断：

- 多卡并行是否真正减少等待；
- 重编排图 Diff 是否能理解；
- 诊断选项是否能帮助处理异常；
- 周报自动写入是否符合实际工作习惯；
- 工作台是否已经具备日常替代手动多终端管理的价值。

### 解锁规则

P8-M 全部通过、P8-H 明确、用户同意进入 P9 后，P9 才解除阻塞。
