## 0. B 方案审核与理解确认

### 0.1 白话说明：这个阶段做啥、解决啥、做完得到啥

- **要解决的问题**：前面各阶段是在 Windows 主力机上一路搭起来的。P9 要把它定型成可长期使用的产品：Windows 上 DSH 与命令行两条控制面并行可切换、Linux 笔记本只靠 SSH 也是完整正式路径、可以升级和重复发布、老代码有明确归宿，最后由你亲自 Dogfood 三条路径后拍板架构。

| 任务 | 用大白话说在做啥 | 解决什么问题 |
|---|---|---|
| DHR_46 | 把 Linux 无桌面环境的完整链路补齐：SSH 进去启动内核、用 Herdr 派活、断线重连、命令行处理提醒和批准；输出两平台能力矩阵，缺强证据的地方明确拒绝而不是糊弄 | Linux SSH 是正式路径，不是降级演示 |
| DHR_47 | 验证升级与发布：DSH 跨版本升级不影响既有运行（判否则验证卸载不影响）、Pi 若采用也固定版本；内核 / 命令行 / DSH 插件 / Linux 脚本都能可重复发布；老的 v1 现场、psmux、P2/P3 有明确归档说明 | 以后升级不心惊肉跳，老东西不再拖累 |
| DHR_48 | 你亲自跑三条真实路径：①Windows 用 DSH 全程；②任务跑一半关掉 DSH、切到命令行接着干；③Linux SSH 全程。据此出架构定型 ADR、两份手册、agent-console 处置 | 最终形态由真实体验和维护成本决定，不按沉没成本 |

- **完成后你手里有什么**：
  1. 一套在 Windows（DSH ↔ 命令行可切换）和 Linux（SSH）上都能正式使用的接力系统。
  2. 可重复的发布 / 升级方式。
  3. 架构定型 ADR + Windows 工作台手册 + Linux SSH 手册。
  4. 老代码、老现场、旧计划的最终处置结论；P4~P9 文件是否改名也在此收口。

## 1. 概述

- **交付什么 / 不含什么**：
  - 交付：①Windows 与 Linux 的 Runtime、IPC、Herdr、Git、权限与进程行为对齐；②Windows 的 DSH 工作台与 Relay CLI 两条并行、可配置替换的控制面；③Linux 仅 SSH、无 GUI 的完整操作路径；④Pi 作为可选 TUI Client / Native Agent Executor 的最终定位；⑤至少跨一个 DSH 版本的兼容升级验证（DSH 判否则验证卸载后 CLI 主线不受影响）；⑥DSH Bundle、Pi Extension（若采用）、Relay Runtime 与 CLI 的可重复发布方式；⑦v1/P1 历史现场与新 v2 Run 的发现与只读策略；⑧psmux legacy、旧 PowerShell Core、P2/P3 的最终归档说明；⑨agent-console 最终处置；⑩架构定型 ADR、Windows 工作台手册与 Linux SSH 手册。
  - 不含：多机分布式调度、云端 Relay 服务、任意 DAG 市场、自动安装未知第三方插件、deploy 与生产环境控制、跨仓 Run、Windows DSH 直接远控 Linux Runtime、每种客户端一份独立状态机。
- **最终产品形态**：Windows 主力机 = DSH Web Workbench 与必备 Relay CLI 并行可配置替换 + 可选 Pi TUI；Linux Headless 笔记本 = SSH + Relay CLI + 可选 Pi TUI + Herdr 远程持久终端。两边同一 Relay 协议、Workflow Contract、Run Store 语义与 Approval 合同。
- **承接设计**（拆计划输入 = `design/README.md` 白名单）：
  - [design/06](../design/06-多控制面与Headless-SSH运行-设计补充.md) · 「验收命题」节 **H1 ~ H12 全部**（P9 是最终定型，全量回验）+ §2「任意 CLI 终端」的准确含义、§5 Linux Headless 与 SSH 拓扑、§7 证据模型与无 GUI 场景、§9 Fallback 规则、§10「P9」。
  - [design/05](../design/05-DeepSeek-Harness插件化与专属工作台-可行性评估.md) · §3.3 DSH 仍处于快速迭代期、「与既有设计和计划的关系」节、§18 风险和停止条件、§19 最终完成形态、§20 官方资料基线。
  - [design/02](../design/02-完整流水-产品设计与验收.md) · **B1**（v1 只读兼容、双根 discovery、legacy 根零新写）、**B10**（宿主外 Oracle）——作为 legacy 与 Oracle 契约来源。
- **前置条件**：P8 Gate 通过；真实多卡 Run、重编排、诊断、Outbox、归档已完成；DSH 关闭状态下单卡与多卡控制路径已通过；用户确认 Relay 主线具日常使用价值；用户明确放行 P9。
- **实施策略一句话**：不追求两台机器同一界面，只追求同一协议与真相；先补齐 Linux Headless 全链与能力矩阵，再做升级 / 发布 / legacy 隔离，最后用三条真实 Dogfood 路径出架构 ADR——按实际体验与维护成本裁决，不按沉没成本。
- **任务前缀 / 模块 slug**：`DHR_` / `dh-relay`。
- **批次**：批次 1=`DHR_46`（Linux 全链 + 能力矩阵，本阶段第一个端到端 demo）；批次 2=`DHR_47`（升级 / 发布 / legacy）；批次 3=`DHR_48`（三路径 Dogfood + ADR）。

### 2.2 复用与禁改边界

| 路径 | 禁改 / 扩展 / 新建 | 说明 |
|---|---|---|
| Runtime 平台层、`capabilities/`、`legacy/`、`release/` | 扩展 / 新建 | 在 P8 Runtime 上补平台对齐与发布 |
| Relay 协议、Run Store、业务仓真相 | 禁随客户端升级变化 | 不得被 DSH / Pi 私有类型或客户端更新污染；客户端更新不能自动迁移 Relay Store |

| `.dh-relay` 文件 | 客户端禁直接编辑 | 所有客户端经 Relay Runtime 读写 |

### 2.3 阶段专属约束

- **最终客户端矩阵**：Relay CLI（必须；所有平台查询 / 恢复 / Attention / Approval 的独立正式控制面，与 DSH 并行可配置替换；窄控制合同）；DSH Bridge/UI（Windows 首选、可选；Web 图 / 项目导航 / 配置 / 证据 / 审批；窄控制合同）；Pi TUI/Extension（可选；终端工作台 / 规划 / 复核 / SSH；窄控制合同 + 可选 Agent Executor）；Herdr CLI/TUI（执行宿主必需；宿主控制，不写 Relay 真相）；agent-console（待裁决；启动器 / 托盘 / WebView 或只读启动器；不持有独立真相）。
- **Linux 操作路径**：`ssh <host>` → `relay status / events --follow / attention list / attention answer / approve` → `herdr` / `herdr agent attach <name>`。
- **Windows/Linux 对证**：相同 Protocol 与 Contract；状态枚举与 reason code 一致；路径 / Shell / 文件权限 / 截图 Provider 可以不同；最终验收语义、Approval Receipt 与 Verify 一致。
- **agent-console 候选处置**：①停止开发并归档；②缩成启动器 / 托盘 / WebView 壳；③保留 DSH 故障时的本地只读界面，控制仍走 Relay RPC。按实际体验与维护成本选，不按沉没成本。
- **架构 ADR 必答**：DSH 是否继续作 Windows 默认工作台；Relay CLI 长期参考客户端地位；Pi 是正式客户端 / 正式 Executor / 实验能力；Runtime 最终语言与发布形态；Herdr 长期主宿主地位；psmux legacy 保留期限；agent-console 处置。

### 3.2 任务卡

#### DHR_46

- **目标**：Linux 不装桌面环境即可运行 Relay Runtime（Unix Domain Socket + Relay CLI），经普通 SSH 启动 / 断开 / 重连，用 Herdr 启动 / detach / reattach / 附着 Agent，验证 Process、Git、路径、文件权限、进程树清理，跑一条 basic-agent-task 与一条代表性 DevHarness 路径，完成一次 CLI Attention 与一次 CLI E11 Approval；产出覆盖 §2.1 全部条目的两平台能力矩阵，强证据缺失时明确拒绝 / 路由 / 带外取证 Attention，不静默降级。
- **非目标**：不做 Linux 完整发布物（DHR_47）；不做 Windows DSH 直接远控 Linux；不做多机调度。
- **验收口径**：
  - **机器证**：[design/06 H9](../design/06-多控制面与Headless-SSH运行-设计补充.md#11-验收命题) · 本计划 P9-M2：Linux 无 GUI、仅 SSH 时完成代表性工作流、Attention 与 Approval（真实 SSH 实录）。
  - **机器证**：[design/06 H10](../design/06-多控制面与Headless-SSH运行-设计补充.md#11-验收命题) · P9-M11：GUI 强证据缺失时 Workflow fail-closed / 路由 / 带外取证，不误报通过（反例：要求截图的节点在无 GUI 主机上不得静默通过）。
  - **机器证**：[design/06 H4](../design/06-多控制面与Headless-SSH运行-设计补充.md#11-验收命题) · P9-M5：SSH 断开 / 重连、Runtime 重启恢复、POSIX 权限证明、进程树清理均有证据。
  - **机器证**：[design/06 H3 / H8 / H11](../design/06-多控制面与Headless-SSH运行-设计补充.md#11-验收命题) · P9-M4：Windows 与 Linux 对同一 Protocol / Contract 的状态枚举、reason code、Approval Receipt 与 Verify 语义一致（对证表）。

### 4.2 人类闸 P9-H

用户最终判断（见 DHR_48 人判项）：DSH 是否成 Windows 日常默认入口；Relay CLI 是否足以作为与 DSH 并行的独立正式控制面及 Linux 日常入口；Pi 是否值得成正式 TUI 客户端或 Native Agent Executor；Windows 与 Linux 操作差异是否可接受；启动、升级与故障恢复是否够简单；agent-console 是否仍有独立存在价值。

### 4.3 完成定义

P9 完成后，项目主线只保留一套现役说明：Detached Relay Runtime（持久工作流真相）；Control Clients（Relay CLI 必备、DSH Windows 首选但可替换、Pi TUI 可选）；DevHarness Contract/Gate；Herdr Executor Profiles；业务仓 `.dh-relay` 与 `docs/relay`。design/04、旧 P2、旧 P3 与各 Pilot 文档保留为历史与证据，不再与现役架构并列。P4~P9 文件是否按最终责任重命名在此阶段一并处置。
