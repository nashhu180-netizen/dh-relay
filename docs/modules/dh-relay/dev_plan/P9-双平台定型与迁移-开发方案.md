## 0. 定位

P9 把已经证明可用的 Relay + DevHarness + Herdr 路线定型为 Windows 与 Linux 都可维护的个人工作台。

最终产品不要求两台机器使用相同的界面：

```text
Windows 主力机
  首选 DSH Web Workbench
  必备 Relay CLI 回退
  可选 Pi TUI

Linux Headless 笔记本
  SSH + Relay CLI
  可选 Pi TUI
  Herdr 远程持久终端
```

两边必须使用同一 Relay 协议、Workflow Contract、Run Store 语义和 Approval 合同。P9 处理跨平台差异、客户端替换、版本升级、安装发布、遗留数据、agent-console 决策和长期运行边界。

## 1. 前置条件

- P8 Gate 通过；
- 真实多卡 Run、重编排、诊断、Outbox 和归档已完成；
- DSH 关闭状态下的单卡和多卡控制路径已通过；
- 用户确认 Relay 主线具有日常使用价值；
- 用户明确放行 P9。

## 2. 交付范围

交付：

1. Windows 与 Linux 的 Runtime、IPC、Herdr、Git、权限和进程行为对齐。
2. Windows 的 DSH 首选工作台与 Relay CLI 回退。
3. Linux 仅 SSH、无 GUI 的完整操作路径。
4. Pi 作为可选 TUI Client / Native Agent Executor 的最终定位。
5. 至少跨一个 DSH 版本的兼容升级验证；DSH 判否时则验证卸载后 CLI 主线不受影响。
6. DSH Bundle、Pi Extension（若采用）、Relay Runtime 和 CLI 的可重复发布方式。
7. v1/P1 历史现场与新 v2 Run 的发现和只读策略。
8. psmuxlegacy、旧 PowerShell Core、P2/P3 的最终归档说明。
9. agent-console 的最终处置。
10. 一份架构定型 ADR、Windows 工作台手册和 Linux SSH 手册。

不交付：

- 多机分布式调度；
- 云端 Relay 服务；
- 任意 DAG 市场；
- 自动安装未知第三方插件；
- deploy 和生产环境控制；
- 跨仓 Run；
- Windows DSH 直接远控 Linux Runtime；
- 每种客户端一份独立状态机。

## 3. 最终客户端矩阵

| 客户端 | 必需程度 | 主要场景 | 权限 |
|---|---|---|---|
| Relay CLI | 必须 | 所有平台的查询、恢复、Attention、Approval 和应急控制 | 窄控制合同 |
| DSH Bridge/UI | Windows 首选，可选 | Web 图、项目导航、配置、证据和审批 | 窄控制合同 |
| Pi TUI/Extension | 可选 | 终端工作台、规划、复核和 SSH 使用 | 窄控制合同 + 可选 Agent Executor |
| Herdr CLI/TUI | 执行宿主必需 | Codex/Claude Code pane、交互和附着 | 宿主控制，不写 Relay 真相 |
| agent-console | 待裁决 | 启动器、托盘、WebView 或应急只读 | 不持有独立真相 |

所有客户端通过 Relay Runtime 读写。禁止客户端直接编辑 `.dh-relay` 文件。

### DHR_46：Linux Headless 全链与能力矩阵

目标：

- Linux 不安装桌面环境也能运行 Relay Runtime。
- 使用 Unix Domain Socket 和 Relay CLI。
- 通过普通 SSH 启动、断开和重新连接。
- 使用 Herdr 启动、detach、reattach 和附着 Agent。
- 验证 Process、Git、路径、文件权限和进程树清理。
- 跑一条 basic-agent-task 和一条代表性 DevHarness 路径。
- 完成一次 CLI Attention 和一次 CLI E11 Approval。

Linux 操作路径：

```text
ssh <host>
relay status <run_id>
relay events <run_id> --follow
relay attention list
relay attention answer ...
relay approve ...
herdr
herdr agent attach <name>
```

能力矩阵至少覆盖：

```text
Relay Runtime 与 CLI
Unix Domain Socket
SSH 断开/重连
Herdr launch/observe/attach/stop
Codex/Claude Code/Pi 可用入口
Git worktree/finalizer/archive
终端转录、Receipt 和 Artifact Hash
GUI/截图能力是否存在
POSIX 权限证明
进程树清理
Runtime 重启恢复
```

强证据能力缺失时必须明确拒绝相应 Workflow、路由到具备能力的环境或生成带外取证 Attention，不能静默降级。

Windows/Linux 对证关注：

- 相同 Protocol 和 Contract；
- 状态枚举和 reason code 一致；
- 路径、Shell、文件权限和截图 Provider 可以不同；
- 最终验收语义、Approval Receipt 和 Verify 一致。

### DHR_47：升级、发布与 legacy

DSH 路径：

- 从 Pilot 锁定版本升级到一个后续版本。
- 记录 Bridge 兼容层改动。
- Relay 协议和 Run Store 不随 DSH 私有类型变化。
- 升级失败可以回滚或卸载 DSH Profile，不影响既有 Run。

Pi 路径（条件采用）：

- 固定 Pi 版本和 Extension 来源。
- 验证 TUI Client 与 Agent Executor 使用不同权限配置。
- Pi 退出后 Relay CLI 继续工作。

发布方式：

```text
Relay Runtime 可校验发布物
Relay CLI
Windows 初始化与 DSH Bundle（若采用）
Linux Headless 初始化脚本
Pi Extension/Package（若采用）
版本清单、checksum 与回滚说明
```

供应链规则：

- 不允许模型自动批准未知 Git 包的 prepare/install。
- 插件和 Extension 来源固定版本或 commit。
- 凭据与业务仓内容不进入发布物。
- DSH、Pi 或其他客户端更新不能自动迁移 Relay Store。

legacy 策略：

- `.dh-runtime/relay/` v1 只读发现和归档，不 resume。
- 旧 PowerShell P1 工具保留到新 Runtime 双平台 Dogfood 通过。
- psmuxlegacy 只作为受控回退，不被新 Run 默认选择。
- P2/P3 保持冻结说明，旧任务不复活。

### DHR_48：Dogfood 与架构定型

至少完成三条真实路径：

#### Windows 首选工作台路径

```text
DSH 可用
  -> DSH 展示和提交控制
  -> Relay Runtime
  -> Herdr 外部 Agent
  -> Attention / Approval
  -> verify / archive / Oracle
```

DSH Pilot 判否时，用 Pi TUI 或 Relay CLI 作为 Windows 日常客户端完成等价路径。

#### Windows DSH 故障回退路径

```text
已有 Run 正在执行
  -> 关闭或卸载 DSH
  -> Runtime 与 Herdr 继续
  -> Relay CLI 查看和处理 Attention
  -> 完成 Run
  -> 重新安装/启动 DSH 后只读重建
```

#### Linux Headless 路径

```text
SSH + Relay CLI/Pi TUI
  -> Relay Runtime
  -> Herdr Agent
  -> SSH 断开与重新连接
  -> CLI Approval
  -> verify / archive / Oracle
```

架构 ADR 最终确认：

```text
DSH 是否继续作为 Windows 默认工作台
Relay CLI 的长期参考客户端地位
Pi 是正式客户端、正式 Executor 还是实验能力
Relay Runtime 最终语言与发布形态
Herdr 的长期主宿主地位
psmuxlegacy 的保留期限
agent-console 的处置
```

agent-console 候选处置：

1. 停止开发并归档。
2. 缩成启动器、托盘和 WebView 壳。
3. 保留 DSH 故障时的本地只读界面，但所有控制仍走 Relay RPC。

选择依据是实际体验和维护成本，不按既有投入做沉没成本决策。

## 5. P9 最终闸

### 核心机器闸 P9-M

| ID | 命题 |
|---|---|
| P9-M1 | Windows 与 Linux 均能安装 Runtime、CLI、Herdr 并运行 |
| P9-M2 | Linux 无 GUI、仅 SSH 时可以完成代表性工作流、Attention 和 Approval |
| P9-M3 | DSH 完全不可用时，Windows Run 可以由 CLI 继续并完成 |
| P9-M4 | DSH、Pi、CLI 对同一 Run 的状态、请求和 Receipt 一致 |
| P9-M5 | 两平台的强制权限、进程清理和恢复行为有证据 |
| P9-M6 | 跨一个 DSH 版本后，改动集中在兼容层；或 DSH 判否后卸载不影响主线 |
| P9-M7 | Relay Store、协议和业务仓真相不受任何客户端升级污染 |
| P9-M8 | 发布物可重复构建并有版本、checksum 和回滚路径 |
| P9-M9 | legacy v1 和 psmux 路径不会被新 Run 误用 |
| P9-M10 | Windows 与 Linux 真实 Run 的外部 Oracle 均通过 |
| P9-M11 | GUI 强证据缺失时 Workflow fail-closed，不误报通过 |

### 人类闸 P9-H

用户最终判断：

- DSH 是否成为 Windows 日常默认入口；
- Relay CLI 是否足以承担长期应急和 Linux 日常入口；
- Pi 是否值得成为正式 TUI 客户端或 Native Agent Executor；
- Windows 与 Linux 的操作差异是否可接受；
- 启动、升级和故障恢复是否足够简单；
- agent-console 是否仍有独立存在价值。

## 6. 完成定义

```text
Detached Relay Runtime

  DSH Windows 首选但可替换
  Pi TUI 可选

DevHarness Contract/Gate
Herdr Executor Profiles
业务仓 .dh-relay 与 docs/relay
```

04、旧 P2、旧 P3 和各 Pilot 文档继续保留为历史与证据，不再与现役架构并列。
