## 1. 最终判断

本次建议确定五项方向：

1. **dh-relay 核心运行时使用 Go。** 项目基线建议固定为 `Go 1.26.x`，分别发布 Windows 与 Linux 单一可执行文件。
2. **Herdr 成为首选交互式 Agent 宿主。** Windows 与 Linux 均通过 Herdr 承载 Claude、Codex、Grok、Kimi 等交互会话。`process` executor 承载脚本、机器闸和无需交互的任务。
3. **psmux 只保留迁移期回退。** 它继续服务现有 Windows 基线和故障回退，停止扩展新的状态识别和编排能力。当前阶段不开发 tmux adapter；Linux 先完成 Herdr 真实 preflight 和 dogfood。
4. **编排采用受控图模型。** 引擎内部统一执行节点和边组成的 `ResolvedPlan`。V1 对外提供版本化流水、类型化扩展点、注册动作和本地 outbox。AI planner 不能即兴提交任意 DAG。
5. **agent-console 只消费稳定协议。** dh-relay 持有运行状态、编排真相和写权；agent-console 负责展示、配置、启动、提醒、终端聚焦和证据导航。

这里有一个必须单独写清的结论：

> **换成 Go 无法让 psmux 自动理解 Agent 正在工作、等待用户、已经停下或已经完成。**

Go 能改善类型安全、并发、进程监管、超时、跨平台文件和部署。psmux 缺少结构化 Agent 状态，这个信息缺口仍会存在。Herdr 提供 `idle / working / blocked / done / unknown`、状态变化序号和状态事件，解决的是宿主观测能力。两项选择需要同时成立。

## 2. 对上一版结论的修正

上一版把 Windows `psmux` 和 Linux `tmux` 写成主要交互后端，把 Herdr 放在未来候选位置。该结论需要修正，原因如下：

- 仓内 Herdr preflight 已验证状态枚举、状态变化序号、事件推送和精确 pane 句柄。
- 会话内确认问题能够被识别为 `blocked`，psmux 只能看到终端画面长期没有变化。
- Herdr 同时覆盖 Windows 与 Linux，能够减少两套交互宿主的长期维护面。
- psmux 的终端文本指纹仍有价值，可以作为迁移对证和回退手段；继续围绕它自建 Agent 语义识别的收益偏低。
- Herdr 仍有盲区。启动信任弹窗可能显示为 `idle`，退出事件和检测规则稳定性也需要补偿设计。因此 Herdr 提供观测事实，dh-relay 继续保留工作流权威。

修订后的分工为：

```text
Go              核心状态机、编排、授权、存储、回放、进程监管
Herdr           交互式 Agent 托管、状态观测、pane 定位、事件推送
process         脚本、测试、机器闸、后台非交互任务
psmux legacy    Windows 迁移对证和应急回退
fake            确定性测试和故障注入
agent-console   展示、配置、提醒、控制入口和导航
```

## 3. 当前方案评估

dh-relay 已经形成了可迁移的工程骨架：

- `contracts` 保存 schema、身份链、状态转换和脱敏规则；
- `runner` 保存唯一写者、原子落盘、事件账和确定性回放；
- `host` 负责摄入、tick、启动和证据收集；
- `adapters` 隔离外部宿主；
- `policy` 保存 fail-closed 守卫；
- fixtures 覆盖合法路径、拒绝路径、迟到结果、重放和策略边界。

换语言和换宿主时，最有价值的资产有四类：

1. 已冻结的 JSON 契约、状态转换和 reason code；
2. 现有 fixtures、回放签名和 DHR_04 的策略断言；
3. psmux 实战得到的启动、超时、截图、失联和失败分支经验；
4. Herdr preflight 得到的状态枚举、事件订阅、pane 句柄、资源成本和盲区证据。

PowerShell 代码适合作为行为参照。现有问题集中在动态类型、数组拆平、进程监管、平台专属命令和脚本间隐式约定。继续扩张 P2 后再迁移，会增加待重写面积。

## 4. 技术栈选择

### 4.1 AI 开发友好的评价标准

本项目所需的 AI 开发友好包含以下条件：

- 编译器能提前拦截类型、接口和控制流错误；
- 写法收敛，多名 Agent 轮流施工时风格差异较小；
- 格式化、静态检查和测试入口统一；
- 依赖少，Windows 与 Linux 部署步骤短；
- 进程、并发、文件原子性和错误传播有清晰原语；
- 代码结构易于定位，跨文件隐式状态尽量少。

### 4.2 候选对照

| 技术栈 | AI 开发友好 | 跨平台交付 | 进程与并发 | 类型兜底 | 与本项目匹配度 | 结论 |
|---|---|---|---|---|---|---|
| Go | 高 | 单文件、按平台构建 | 强，标准库直接 | 中高 | 很高 | **首选** |
| .NET / C# | 高 | 自包含发布可行 | 强 | 高 | 高 | 第二选择 |
| Rust | 中 | 单文件、按平台构建 | 很强 | 很高 | 中 | 暂不选 |
| TypeScript / Node.js | 很高 | 需要 Node 或打包层 | 较强 | 中 | 中 | 暂不选 |
| Python | 很高 | 运行时和打包需治理 | 中 | 低 | 中低 | 暂不选 |
| PowerShell 7 | 中 | 可跨平台安装 | 中低 | 低 | 低 | 核心退出 |

### 4.3 选择 Go 的原因

Go 对 dh-relay 的收益主要来自工程确定性：

- `go build`、`go test ./...`、`gofmt`、`go vet` 可以形成统一机器检查；
- goroutine、context 和 channel 适合非阻塞宿主事件、超时、取消和子进程监管；
- Windows 与 Linux 通过构建目标和少量平台文件隔离；
- 单一二进制适合加入 PATH，也适合被 agent-console 调用；
- 语言特性相对克制，AI 生成代码更容易保持一致；
- 外部 Agent CLI 才是主要时延来源，Go 已有充分性能余量。

Go 与 Herdr 的关系如下：

- Go 负责消费 Herdr 的结构化状态和事件；
- Go 负责断线重连、低频对账、超时和状态映射；
- Herdr 负责生成 Agent 观测信号；
- dh-relay 的任务完成判断仍依赖 receipt、checkpoint、result 和机器闸。

### 4.4 其余候选的处置

C# 是可信的第二选择，尤其适合 agent-console 的桌面技术路线。dh-relay 和 agent-console 通过协议解耦更稳妥，共用语言不会自动降低边界复杂度。

Rust 的正确性上限较高。dh-relay 当前仍处于产品规则快速演进期，Rust 会抬高 AI 施工和复核成本。未来出现长期常驻、高安全强度或深度嵌入需求时再评估。

TypeScript 与 Python 的原型速度快。对长期监管外部进程、要求 fail-closed、需要单机多平台分发的 Runner，它们会增加运行时和打包治理面。

PowerShell 可以保留为迁移期包装、基线工具和少量 Windows 专属探针，不再新增核心状态机、授权、调度和存储能力。

## 5. 建议的总体架构

```text
                            agent-console
                   展示 / 配置 / 提醒 / 窄控制
                                  |
                                  v
+------------------------------------------------------------------+
|                         relay CLI / API                           |
| start  resume  stop  list  status  inspect  validate  export      |
+-----------------------------+------------------------------------+
                              |
                              v
+------------------------------------------------------------------+
|                      Workflow Compiler                            |
| Pipeline / Playbook + Hooks + Authority Snapshot -> ResolvedPlan  |
+-----------------------------+------------------------------------+
                              |
                              v
+------------------------------------------------------------------+
|                      Deterministic Engine                         |
| Ready  Launch  Observe  Ingest  Transition  Retry  Pause          |
+---------------+-------------------------+------------------------+
                |                         |
                v                         v
+----------------------------+  +----------------------------------+
| Run Store                  |  | Executors / Host Adapters        |
| immutable artifacts        |  | process                          |
| atomic snapshots           |  | Herdr primary                    |
| append-only events         |  | psmux legacy                     |
| outbox                     |  | fake                             |
+----------------------------+  +----------------------------------+
                                              |
                                              v
                                   Claude / Codex / Grok / Kimi
```

核心约束保持不变：

- Runner 是运行状态、事件账、receipt 和 final result 的唯一写者；
- worker 只能通过 receipt 绑定的窄入口提交 checkpoint 与 result；
- Herdr adapter 只报告宿主能够证明的状态、事件和 pane 事实；
- 质量结论来自对应 Agent、机器闸和正式工件；
- agent-console 不直接写 run 现场文件；
- Herdr 的 `done` 不直接转换成工作流 `succeeded`。

## 7. 跨平台运行与 Herdr 状态模型

### 7.1 核心与宿主能力分离

核心层只依赖以下抽象能力：

- 原子文件创建、替换和追加；
- 子进程启动、等待、取消和退出码；
- 单调时钟与超时；
- 工作目录、环境变量和路径规范化；
- 交互会话 launch、observe、stop、capture、focus；
- 状态事件订阅和低频 snapshot；
- 可选的截图、权限证明和进程探测。

平台与宿主能力建议如下：

| 能力 | Windows | Linux |
|---|---|---|
| 非交互任务 | `process` executor | `process` executor |
| 交互式 Agent | **Herdr adapter** | **Herdr adapter** |
| 迁移回退 | `psmuxlegacy` | 当前无默认回退 |
| 测试回放 | `fake` | `fake` |
| 权限证明 | Windows ACL provider | POSIX mode / ACL provider |
| 进程对账 | Windows process provider | proc / process provider |

当前阶段不建设 tmux adapter。Linux Herdr preflight 出现明确阻塞后，再以独立任务评估 tmux 回退。

### 7.2 两套状态必须分开

Herdr 状态属于宿主观测：

```text
idle / working / blocked / done / unknown
```

dh-relay 状态属于工作流权威，例如：

```text
launching
running
attention_required
awaiting_result
succeeded
failed
interrupted_unknown
```

建议映射如下：

| Herdr 观测 | dh-relay 处理 |
|---|---|
| `working` | 节点保持 `running`，刷新宿主活性证据 |
| `blocked` | 创建或更新 Attention，节点进入 `attention_required` |
| `done` | 节点进入 `awaiting_result`；缺少合法 result 时禁止完成 |
| `idle` | 结合启动阶段、最近事件、pane 内容和 result 状态判断；不能单独判完成 |
| `unknown` | 触发低频 snapshot、进程对账和超时规则 |
| pane 或进程消失 | 缺少合法 result 时进入 `interrupted_unknown` |

合法 checkpoint 或 result 到达后，Engine 才执行正式状态转换。机器闸、两轮复核和 finalizer 仍按原设计验收。

### 7.3 事件快路与对账慢路

Herdr adapter 使用两条通道：

1. **事件快路**：订阅状态变化和 pane 事件，快速生成宿主观测事件。
2. **对账慢路**：周期性读取 snapshot、pane、进程和会话事实，修复断线、漏事件和宿主重启造成的漂移。

每个 run 启动时冻结并记录：

- Herdr 版本；
- API schema 或能力摘要；
- 可用事件类型；
- 支持的 Agent kind；
- 会话与 pane 句柄；
- 状态检测能力；
- 本次 run 的宿主能力 hash。

能力不足时，`relay validate` 应在创建 run 现场前拒绝。弱证据不能静默替代强验收。

### 7.4 已知盲区和补偿

Herdr 方案必须保留以下风险说明：

1. **启动信任弹窗盲区。** 实测中，启动信任弹窗可能显示为 `idle` 且 `interactive_ready=true`。工作树信任预置需要升级为前置任务；启动期还要设置专用超时和屏幕对账。
2. **退出事实需要兜底。** 宿主事件不能覆盖所有进程退出场景，Runner 仍需低频进程探测。
3. **检测规则可能变化。** run 需要记录 Herdr 版本和能力 hash；版本或能力变化时，旧 run 不能无提示切换判定语义。
4. **`done` 只表示宿主观察到 Agent 停止工作。** 它不能证明代码正确、任务验收通过或 result 已提交。
5. **Linux 机器证仍需补齐。** 当前仓内 preflight 以 Windows 实测为主，Go 迁移开工前应完成 Linux 的 launch、blocked、done、断线、重连和 result 闭环。

### 7.5 路径与配置

- 运行现场继续落在目标仓 `<repo>/.dh-relay/<run_id>/`；
- 用户级注册表继续落在 `~/.dh-relay/`；
- 持久路径使用规范字段，不能依赖固定盘符；
- 配置保存 profile、命令路径、能力位、工作根、宿主版本和冻结 hash；
- 配置不保存凭据值；
- 凭据继续由目标 Agent CLI 管理。

## 8. Codex 与 Grok 的争议，以及受控图模型

### 8.1 争议到底在讨论什么

讨论的核心问题是：

> AI planner 能否自由决定一张任务卡要经过哪些步骤、步骤如何连线，以及何时触发周报等外部动作。

当前固定流水大致可以简化成：

```text
立项 -> 拆计划 -> 开工 -> 代码复核 -> 教训复核 -> 收口确认 -> 完成
```

你希望增加的自由度类似：

```text
开工完成 -> 写一次周报 -> 继续代码复核
任务完成 -> 再写一次周报
以后 dev-harness 更新 -> 换一套新步骤
```

自由度需要保留，必经质量步骤也需要得到机器保证。

### 8.2 Codex 的判断

Codex 先审核过完全自由的 DAG 方案，并判定存在 P0 授权缺口。随后提出两层模型：

- 内层宏 `dev_harness_card@v1` 冻结一张卡的必经质量流程；
- 外层 DAG 负责组合卡宏、事件宏、归档宏和外部动作；
- 周报等跨项目动作进入 durable outbox。

这个方向解决了卡内步骤被随意改写的问题。planner 可以把一个经过审核的卡流程当成完整节点使用，未来 dev-harness 改版时发布 `@v2`。

### 8.3 Grok 的反对点

Grok 认可内层冻结、版本发布和 outbox，随后指出外层授权仍未闭合。

问题可以用一条坏计划说明：

用户授权了一张任务卡，也允许更新周报。planner 生成：

```text
写周报 -> 归档 -> 完成
```

或者生成：

```text
任务卡宏      写周报 -> 归档
   |               |
   +---- 两条互不依赖的支路
```

这种图只使用了允许的宏和允许的周报目的地，因此“有没有多做越权动作”的检查可能通过。代码复核、教训复核、收口确认却可能完全没有发生。省略步骤通常不会制造新的副作用，单纯检查副作用子集拦不住它。

Grok 的核心观点可以概括为：

> 宏在白名单里，只能证明每个已出现的节点合法；它无法证明所有必经节点都出现，也无法证明外部动作位于正确的质量闸之后。

因此，用户真正授权的对象需要包含完整拓扑，或包含一份已经审核过的 playbook 版本和 hash。

### 8.4 本文的最终选择

本文采用受控图模型，结构如下：

1. Engine 内部始终执行图，保留未来可视化和扩展能力。
2. AI planner 只能填参数、选择已允许的可选节点、绑定已注册动作。
3. 每张已授权任务卡必须被一个发布版 `dev_harness_card@vN` 覆盖。
4. 必经节点和必经边由 pipeline 或 playbook 冻结。
5. 外部动作只能挂到已声明的 hook，例如 `stage.succeeded` 或 `card.succeeded`。
6. 外部动作不能让主质量路径提前结束，也不能让某个终态在其 owner 卡通过约定质量闸前变为 ready。
7. authority snapshot 冻结 pipeline 或 playbook 的 `id + version + content_hash`，同时冻结参数和外部 effect。
8. Workflow Compiler 生成完整 `ResolvedPlan`，校验覆盖关系、必经闸、边、参数、effect 和能力后才允许启动。

这套模型保留了 Codex 的内部图和版本化宏，也补上了 Grok 指出的外层授权缺口。

### 8.5 周报例子

发布版流水：

```text
A 立项
  -> B 拆计划
  -> D 开工
  -> R1 代码复核
  -> R2 教训复核
  -> E 收口
  -> card.succeeded
```

允许两个 hook：

```text
D 开工成功 -> project-status.weekly-report.append
card.succeeded -> project-status.weekly-report.append
```

编译后的实际关系：

```text
A -> B -> D -> R1 -> R2 -> E -> card.succeeded
          |                         |
          +-> 周报进行中             +-> 周报完成
```

“周报进行中”默认使用 `best_effort`。它失败时留下 Attention 或 dead-letter，主质量路径继续。它不能替代 R1、R2 和 E，也不能把任务提前标记完成。

若 planner 提交以下图，编译器直接拒绝：

```text
A -> B -> D -> 周报 -> card.succeeded
```

拒绝原因是必经的 R1、R2、E 缺失。

### 8.6 三层产品能力

#### 第一层：版本化流水

`dev-harness-card@v1` 保存当前完整行为。未来调整复核位置、节点数量或收口拆分时发布 `dev-harness-card@v2`。旧 run 继续绑定旧版本和 content hash。

流水定义冻结：

- 必经节点和边；
- 可选节点与允许开关；
- 角色和执行器类型；
- checkpoint、result 和 gate；
- effect 声明；
- profile、script 和 action 引用范围；
- 完成、失败、取消和返工语义。

#### 第二层：类型化扩展点和注册动作

建议支持以下事件：

- `run.started`
- `card.started`
- `stage.succeeded`
- `card.succeeded`
- `card.failed`
- `run.finished`
- `attention.opened`

扩展点只接受已注册 `action_ref`。计划内禁止内联 shell、任意脚本路径和任意 prompt。

周报绑定示例：

```json
{
  "hook_id": "weekly-progress-after-build",
  "on": "stage.succeeded",
  "where": {
    "pipeline_id": "dev-harness-card",
    "stage_id": "build"
  },
  "action_ref": {
    "id": "project-status.weekly-report.append",
    "version": 1,
    "content_hash": "sha256:..."
  },
  "mode": "best_effort"
}
```

任务进行中的记录绑定明确 stage 或显式 checkpoint。heartbeat、终端静默和自然语言不承担完成判定。

#### 第三层：已发布 playbook

未来 agent-console 可提供：

- `card-only@v1`
- `card-with-progress-report@v1`
- `card-then-human-verify-then-report@v1`

每份 playbook 冻结流水版本、节点、边、参数 schema、hook、effect 和 content hash。用户在 agent-console 中选择或编辑草稿，发布后形成新版本；启动前展示完整图和效果摘要。

当前不开放 planner 任意组图。出现大量 hook 和 playbook 无法表达的实际需求后，再单独建设完整 invariant engine。

### 8.7 `ResolvedPlan` 是未来兼容点

Workflow Compiler 统一生成：

```json
{
  "protocol": "relay.resolved-plan/v1",
  "run_id": "R-...",
  "authority_hash": "sha256:...",
  "source": {
    "kind": "playbook",
    "id": "card-with-progress-report",
    "version": 1,
    "content_hash": "sha256:..."
  },
  "nodes": [],
  "edges": [],
  "effects": [],
  "required_capabilities": []
}
```

Engine 执行 ResolvedPlan，agent-console 渲染 ResolvedPlan。未来扩展 UI 编排时，Runner 和展示协议可以保持稳定。

## 9. Outbox 与跨项目动作

跨项目周报、通知和索引更新采用本机 durable outbox，不引入消息队列或数据库。

建议现场结构：

```text
<run>/
  outbox/
    requests/<action_request_id>.json
    attempts/<action_request_id>/<attempt>.json
    results/<action_request_id>.json
  action-state.json
```

规则：

- action request 为不可变文件；
- `action_request_id` 由 run、hook、来源事件和 occurrence 唯一确定；
- consumer 接收 idempotency key；
- 状态至少包含 `pending/running/succeeded/failed/dead_letter`；
- 默认 `best_effort` 不阻断源卡收口；
- 强依赖动作只能由已发布流水或 playbook 声明；
- 重试次数、退避和 dead-letter 可见；
- 目标项目拥有写入程序和检查器；
- relay 记录请求、尝试、结果和最终状态；
- 动作成功不能冒充源卡验收成功。

这足以支持周报场景，同时保持业务代码留在周报项目。

## 10. Run Store 与协议

继续使用文件型事件账，dh-relay 核心暂不引入 SQLite。

原因：

- 单个 run 使用唯一写者；
- receipt、result、proposal 和追加事件适合审计；
- fixture 易于复制、diff、回放和交给 AI 复核；
- agent-console 可以只读消费，无需共享数据库写锁；
- 跨平台迁移面较小。

建议保留并版本化：

- `relay.plan-proposal/v2`
- `relay.authority/v2`
- `relay.resolved-plan/v1`
- `relay.launch-receipt/v2`
- `relay.checkpoint/v2`
- `relay.result/v2`
- `relay.host-observation/v1`
- `relay.event/v2`
- `relay.run-state/v1`
- `relay.action-request/v1`
- `relay.action-result/v1`
- `relay.attention/v1`

`relay.host-observation/v1` 保存 Herdr 状态、状态变化序号、pane 句柄、宿主版本、能力 hash、观测时间和来源。它不能直接改写质量终态。

Go 重写先完整读取 `relay/v1`，新现场使用 v2。旧现场的续跑策略由兼容矩阵决定。

## 11. 与 agent-console 的边界

agent-console 继续作为薄壳，dh-relay 继续拥有编排和运行真相。

### 11.1 agent-console 可以做

- 发现本机 dh-relay 与 Herdr 的版本和能力；
- 列出 run，读取状态、事件、Attention 和动作失败；
- 展示 ResolvedPlan 的节点、边、当前节点和证据入口；
- 展示 Herdr 观测状态，例如正在工作、等待用户、已停下、宿主失联；
- 选择已发布 pipeline 或 playbook；
- 配置允许覆盖的 profile、hook 和可选开关；
- 发起 start、resume、stop、reply 等窄请求；
- 聚焦 Herdr pane 或打开证据；
- 提醒用户处理 Attention 和 dead-letter。

### 11.2 agent-console 不能做

- 直接修改 `relay-state.json`、events、receipt 或 result；
- 复制 dev-harness 节点表和质量判定；
- 把 Herdr `done` 解释成卡片验收成功；
- 绕过 authority snapshot 增删必经节点；
- 把未审 UI 图直接交给 Runner 执行；
- 管理 CLI 凭据值；
- 直接依赖 Herdr 作为工作流真相源。

### 11.3 V1 交互方式

先提供稳定 CLI 和 JSON：

```text
relay list --json
relay status <run_id> --json
relay inspect <run_id> --json
relay validate <request.json> --json
relay start --request <request.json>
relay control --request <control.json>
relay export <run_id> --output <dir>
```

agent-console 调用 CLI 或读取只读索引。当前不建设 HTTP 服务。

### 11.4 后续 IPC 兼容

实时体验需要提升时，可以在同一 JSON 契约上增加：

- Windows named pipe；
- Linux Unix domain socket；
- JSON Lines 请求、响应和事件订阅。

IPC 只承担传输，权限、状态和业务规则继续位于 dh-relay。

## 12. 迁移策略

建议暂停新增 PowerShell 核心能力，只处理阻塞缺陷。迁移分六批。

### 批次 0：冻结基线与宿主决策

- 固定 P1、DHR_04 契约、fixtures、reason code 和回放签名；
- 固定 psmux Windows 基线；
- 复用 design/03 与 evidence/03 的 Herdr 机器证；
- 补 Linux Herdr preflight；
- 定义 Herdr 版本和能力冻结规则；
- 修正根级文件守卫，为 Go 与 CI 开路。

### 批次 1：契约、存储和回放

- 建立 Go module；
- 实现 schema、identity、transition、redaction；
- 实现原子 store、事件账和 deterministic replay；
- 对同一 fixtures 比较 PowerShell 与 Go 结果；
- 保持 fake adapter 全绿。

### 批次 2：Engine、Host 和基础执行器

- 实现非阻塞 tick、context 取消、启动期限和进程 probe；
- 实现 process、fake executor；
- 实现 worker tool 的 Go CLI；
- 完成 Windows 与 Linux 的无终端回放。

### 批次 3：Herdr adapter

- 接入 Windows 与 Linux transport；
- 实现 capability discovery、snapshot、事件订阅和低频对账；
- 实现 host observation 到 workflow state 的映射；
- 覆盖 `working/blocked/done/idle/unknown`；
- 覆盖启动信任弹窗、宿主重启、漏事件、pane 消失和进程退出；
- 保留 psmuxlegacy 的基线回退。

### 批次 4：版本化流水、hook 和 outbox

- 发布 `dev-harness-card@v1`；
- 实现 Workflow Compiler 与 ResolvedPlan；
- 实现必经宏覆盖和外部动作支配关系校验；
- 实现注册动作、hook、outbox 和独立状态；
- 用进行中周报和完成后周报各跑一条真实夹具。

### 批次 5：agent-console 协议

- 输出 ResolvedPlan、RunState、HostObservation、Attention 和 ActionState；
- 实现只读查询和窄控制命令；
- 验证控制台可以画图、显示 Herdr 状态和打开对应 pane；
- 验证控制台不持有 Runner 写权。

### 批次 6：切换与清理

- 使用真实标准档任务完成 Windows 与 Linux dogfood；
- 新入口切换为 Go `relay`；
- Herdr 成为默认交互宿主；
- PowerShell 核心与 psmux adapter 冻结为 legacy；
- 更新 P2 剩余卡片的文件路径和测试命令；
- 保留原有行为验收，不重拆全部业务验收。

当前 P2 只完成 DHR_04，迁移窗口仍合适。建议先完成 Go 的 P1 与 DHR_04 行为等价和 Herdr adapter，再继续扩展 DHR_05 之后的能力。

## 13. 开发约束

建议把以下约束写进 Go 阶段的 AGENTS 和 CI：

- 所有持久协议先定义 schema、golden fixture 和拒绝用例；
- reason code 使用类型化常量；
- 时间、随机数、进程、文件系统和 adapter 可注入；
- 每个包保持单一职责；
- 业务状态转换只在 `contracts/engine`；
- 存储写入只在 `store`；
- 平台条件编译只在 `adapters/platform`；
- 所有 goroutine 具有 owner、context 和退出路径；
- Herdr 事件和 snapshot 必须能够重放；
- HostObservation 与 Result 使用不同 schema 和写入路径；
- 禁止计划内联 shell；
- 禁止 core 读取凭据值；
- `go test ./...` 是统一本地验收入口；
- Windows 与 Linux CI 同时通过后才允许合入核心运行时变更。

## 14. 当前明确不做

本次设计不要求立即实现：

- 任意 DAG 画布和完整 invariant engine；
- 插件市场或动态加载第三方二进制；
- SQLite、外部消息队列或服务端数据库；
- HTTP 服务、WebSocket 和远程控制；
- 多机分布式调度；
- dh-relay 与 agent-console 同进程嵌入；
- 将周报业务规则复制进 dh-relay；
- 同一 run 在不同 pipeline 版本之间热迁移；
- tmux adapter；
- 让 Herdr 独立决定任务成功；
- 继续扩展 psmux 的 Agent 语义识别。

## 15. 验收建议

### 15.1 语言迁移与 Herdr

| ID | 验收命题 |
|---|---|
| T1 | 同一组 v1 fixtures 在 PowerShell 基线和 Go 实现中得到相同 accept/reject、reason 和状态投影 |
| T2 | blocked、decision、stale、probe-lost 和 policy replay 的确定性签名保持一致 |
| T3 | `go test ./...` 在 Windows 与 Linux 通过 |
| T4 | Windows Herdr 与 Linux Herdr 各完成 launch、working、blocked、done、checkpoint、result、stop 的真实闭环 |
| T5 | Herdr 返回 `done` 且没有合法 result 时，节点保持 `awaiting_result` |
| T6 | 启动信任弹窗被阻塞时，Runner 在专用期限内进入 Attention 或启动失败，不能长期显示普通 idle |
| T7 | 事件订阅断开或漏事件后，snapshot 与进程对账恢复一致状态 |
| T8 | Herdr 版本或能力 hash 变化时，validate 给出明确拒绝或重新确认要求 |
| T9 | psmuxlegacy 只用于基线回退，不被新流水默认选择 |
| T10 | Go 进程崩溃和重启后，原子文件、不可变 result 和唯一写者约束仍成立 |

### 15.2 编排与外部动作

| ID | 验收命题 |
|---|---|
| O1 | `dev-harness-card@v1` 的必经节点不能通过 hook、参数或 planner 输出省略 |
| O2 | 每张 snapshot 卡都被一个允许版本的卡宏覆盖，取消豁免除外 |
| O3 | 未知 action、版本或 hash 不符、内联命令和未授权 effect 在编译阶段拒绝 |
| O4 | 外部 effect 在 owner 卡到达约定终态前不能变为 ready |
| O5 | `stage.succeeded` 与 `card.succeeded` 各能产生恰好一次周报 action request |
| O6 | 周报 action 失败时源卡按 `best_effort` 继续，失败、重试和 dead-letter 可见 |
| O7 | 重复事件、宿主重启和 consumer 重放不产生第二次周报写入 |
| O8 | playbook 缺卡宏、缺必经闸、边或参数被篡改时拒绝 |
| O9 | dev-harness 发布 v2 后，旧 run 继续绑定 v1，新 run 可选择 v2，二者互不污染 |

### 15.3 agent-console 兼容

| ID | 验收命题 |
|---|---|
| C1 | 控制台只凭 `resolved-plan/run-state/host-observation/event/attention` 即可画出步骤、边、状态和待处理项 |
| C2 | 控制台能够区分 Agent `done` 和任务 `succeeded` |
| C3 | 控制台直接改 run 文件、删必经节点或提交未授权 action 时全部拒绝 |
| C4 | CLI JSON 与后续 IPC 使用同一 schema，切换传输层不改变 workflow truth |
| C5 | dh-relay 或 Herdr 不可用时，控制台显示 unavailable，不能解析终端文本猜测质量终态 |

## 17. 决策摘要

| 议题 | 决策建议 |
|---|---|
| 核心语言 | Go 1.26.x |
