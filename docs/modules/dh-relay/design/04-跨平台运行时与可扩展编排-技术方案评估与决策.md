# DH Relay 跨平台运行时与可扩展编排：技术方案评估与决策建议

> 状态：独立技术评估结论，待用户确认。本文尚未进入 `design/README.md` 的 `designInputs[]` 白名单，不可直接作为 B 拆计划输入。
>
> 评估日期：2026-08-17
>
> 评估范围：`DHR-BL-7` 换实现语言、`DHR-BL-8` 流水步骤可扩展性，以及未来与 `agent-console` 的兼容边界。
>
> 现行正式设计仍以 [01-产品设计与验收](./01-产品设计与验收.md) 和 [02-完整流水-产品设计与验收](./02-完整流水-产品设计与验收.md) 为准。Codex、Grok 两轮评估与主会话裁决见 [evidence/04](./evidence/04-流水引擎化-两轮交叉审核记录.md)。

## 1. 最终判断

本次建议一次性确定四项方向：

1. **dh-relay 核心运行时改用 Go。** 当前技术基线建议锁定 `Go 1.26.x`，以单个可执行文件分别发布 Windows 与 Linux 构建。
2. **保留现有契约、Runner、宿主、适配器、策略守卫的分层。** 重写时迁移行为、契约和测试，不逐文件翻译 PowerShell。
3. **编排采用受控图模型。** 引擎内部统一使用节点和边组成的 `ResolvedPlan`；V1 对外提供版本化流水、类型化扩展点、注册动作和本地 outbox，不开放由 planner 即兴生成任意 DAG。
4. **为 agent-console 预留稳定协议边界。** dh-relay 继续拥有运行状态和编排真相；agent-console 通过版本化 JSON、只读查询和窄控制命令完成展示、配置、启动、提醒和导航。

这套方案吸收了 Codex 与 Grok 各自正确的部分：

- Codex 对两层抽象、流程版本化、外部效果声明和图模型的方向判断成立。
- Grok 对授权缺口的 P0 判断成立。只冻结宏集合无法证明必经质量流程没有被省略，当前阶段不能把自由组图权交给 planner。
- 最终方案让图存在于引擎内部，同时把用户可配置面收窄到已发布流水、已声明扩展点和已注册动作。未来需要更自由的 UI 编排时，再升级到已发布 playbook；任意 DAG 放到更晚阶段。

## 2. 当前方案评估

dh-relay 已经形成了较好的工程骨架：

- `contracts` 保存 schema、身份链、状态转换和脱敏规则；
- `runner` 保存唯一写者、原子落盘、事件账和确定性回放；
- `host` 负责摄入、tick、启动和证据收集；
- `adapters` 隔离终端宿主；
- `policy` 保存 fail-closed 守卫；
- 测试夹具覆盖合法路径、拒绝路径、迟到结果、重放和策略边界。

因此，换语言时最有价值的资产是以下三类：

1. 已冻结的 JSON 契约、状态转换和 reason code；
2. 现有测试夹具、回放签名和 DHR_04 的 85 条策略断言；
3. 真实 psmux 试验中得到的宿主语义、超时、截图卫生和失败分支经验。

PowerShell 实现本身适合作为行为参照。现有问题集中在动态类型、数组拆平、进程监管、平台专属命令和大量脚本间隐式约定。继续扩大 P2 后再迁移，会把这些问题复制到更多卡片和更多机器证中。

## 3. 技术栈选择

### 3.1 评价标准

这里把 AI 开发友好定义为：

- 编译器能够提前拦截类型、接口和控制流错误；
- 写法收敛，多个 Agent 轮流施工时风格差异有限；
- 格式化、静态检查和测试入口统一；
- 依赖少，Windows 与 Linux 部署步骤短；
- 进程、并发、文件原子性和错误传播具有清晰原语；
- 代码结构能够被 Agent 快速定位，减少跨文件隐式状态。

### 3.2 候选对照

| 技术栈 | AI 开发友好 | 跨平台交付 | 进程与并发 | 类型兜底 | 与本项目匹配度 | 结论 |
|---|---|---|---|---|---|---|
| Go | 高 | 单文件、按平台构建 | 强，标准库直接 | 中高 | 很高 | **首选** |
| .NET 10 / C# | 高 | 自包含发布可行 | 强 | 高 | 高 | 第二选择 |
| Rust | 中 | 单文件、按平台构建 | 很强 | 很高 | 中 | 暂不选 |
| TypeScript / Node.js | 很高 | 需要 Node 或打包层 | 较强 | 中 | 中 | 暂不选 |
| Python | 很高 | 运行时和打包需治理 | 中 | 低 | 中低 | 暂不选 |
| PowerShell 7 | 中 | 可跨平台安装 | 中低 | 低 | 低 | 核心退出 |

### 3.3 选择 Go 的原因

Go 对 dh-relay 的主要收益来自工程确定性：

- `go build`、`go test ./...`、`gofmt`、`go vet` 可以形成统一的第零轮检查；
- goroutine、context 和 channel 能直接表达非阻塞宿主 tick、超时、取消和子进程监管；
- Windows 与 Linux 通过构建目标和少量平台文件隔离；
- 单个二进制适合放入 PATH，也适合被 agent-console 作为外部本地服务调用；
- 语言特性相对克制，AI 生成代码更容易保持一致；
- 当前任务主要受外部 Agent CLI 时延影响，Go 已提供足够性能余量。

### 3.4 其余候选的处置

C# 是可信的第二选择，尤其适合 agent-console 的 WPF 与 SQLite 技术路线。当前仍建议 dh-relay 使用 Go，原因是两者应通过协议解耦。让控制台和 Runner 使用同一语言不会自动降低整体复杂度，反而可能诱导控制台直接引用业务核心。

Rust 的正确性上限很高，适合高强度系统组件。dh-relay 当前仍处于产品规则快速演进期，Rust 会增加 AI 施工和复核成本。只有未来必须深度嵌入 Rust 宿主，或安全边界升级到长期常驻服务时，再重新评估。

TypeScript 与 Python 的模型语料丰富，原型速度快。对一个长期监管外部进程、要求 fail-closed、需要单机多平台分发的 Runner，它们会把运行时、打包和动态错误留到更晚阶段。

PowerShell 可以保留为迁移期包装和 Windows 专属探针，但不再新增核心状态机、授权、调度和存储能力。

## 4. 建议的总体架构

```text
                         agent-console
                只读查询 / 配置请求 / 窄控制命令
                              |
                              v
+----------------------------------------------------------------+
|                         relay CLI / API                         |
| start  resume  stop  list  status  inspect  validate  export    |
+--------------------------+-------------------------------------+
                           |
                           v
+----------------------------------------------------------------+
|                    Workflow Compiler                            |
| Published Pipeline + Hook Bindings + Authority Snapshot         |
|                         -> ResolvedPlan                          |
+--------------------------+-------------------------------------+
                           |
                           v
+----------------------------------------------------------------+
|                    Deterministic Engine                         |
| Ready  Launch  Probe  Ingest  Transition  Retry  Pause          |
+------------+----------------------+-----------------------------+
             |                      |
             v                      v
+-------------------------+  +------------------------------------+
| Run Store               |  | Executors / Adapters               |
| immutable artifacts     |  | agent, script, process             |
| atomic snapshots        |  | psmux, tmux, fake                  |
| append-only events      |  | Windows/Linux evidence providers   |
| outbox                  |  +------------------------------------+
+-------------------------+
```

核心约束保持不变：

- Runner 仍是运行状态、事件账、receipt 和 final result 的唯一写者；
- worker 只能通过 receipt 绑定的窄入口提交 checkpoint 与 result；
- adapter 只报告可证明的运行事实；
- 质量结论来自对应 Agent 或机器闸，Engine 只执行结构化分支；
- agent-console 不直接写 run 现场文件。

## 5. Go 工程布局

建议采用标准 Go 布局，减少自定义目录规则：

```text
go.mod
go.sum
cmd/
  relay/
internal/
  contracts/
  engine/
  store/
  host/
  executor/
  adapters/
    fake/
    process/
    psmux/
    tmux/
  platform/
    windows/
    unix/
  policy/
  workflow/
  outbox/
  api/
schemas/
testdata/
tools/                 迁移期 PowerShell 基线，切换完成后冻结
```

包边界按职责划分。接口只放在 IO、时间、进程、文件系统、终端和外部动作边界，业务包之间优先使用具体类型。避免建立通用插件框架、依赖注入容器或深层泛型抽象。

现有 `DHR-BL-9` 需要同步解决：策略守卫增加根级文件白名单，并把 `go.mod`、`go.sum`、`cmd/`、`internal/`、`schemas/`、`testdata/` 和 CI 配置纳入明确生产边界。

## 6. 跨平台运行设计

### 6.1 核心与平台能力分离

核心层只依赖以下抽象能力：

- 原子文件创建、替换和追加；
- 子进程启动、等待、取消和退出码；
- 单调时钟与超时；
- 工作目录、环境变量和路径规范化；
- 终端会话的 launch、probe、stop、capture；
- 可选的截图、权限证明和窗口聚焦。

平台差异放入 adapter 或 provider：

| 能力 | Windows | Linux |
|---|---|---|
| 非交互进程 | `process` executor | `process` executor |
| 可见交互终端 | `psmux` adapter | `tmux` adapter |
| 测试回放 | `fake` adapter | `fake` adapter |
| 权限证明 | Windows ACL provider | POSIX mode / ACL provider |
| 窗口截图 | Windows window capture provider | 能力探测后选用对应 provider |
| 进程枚举 | Windows process provider | proc / process provider |

工作流在编译阶段声明所需能力。例如某节点要求真实窗口截图，而当前 Linux 后端只能提供 pane 文本，`relay validate` 必须在启动前拒绝或要求选择满足条件的后端。引擎不能用弱证据静默替代强验收。

### 6.2 终端后端策略

V1 建议同时支持三类执行：

1. `process`：脚本节点、机器闸、后台 Agent 和无需人工交互的任务。它是跨平台默认执行器。
2. `psmux`：Windows 可见交互 Agent，承接现有行为。
3. `tmux`：Linux 可见或可重连 Agent。

`fake` 始终保留，用于确定性回放和故障注入。

Herdr、Orca 或 agent-console 自己的宿主以后都通过同一 adapter 契约接入。核心不得感知窗口框架或 GUI 技术。

### 6.3 路径与配置

- 运行现场继续落在目标仓 `<repo>/.dh-relay/<run_id>/`；
- 用户级注册表继续落在 `~/.dh-relay/`；
- 所有持久路径存规范化 URI 风格或明确的 OS 原生路径字段，不能依赖 `D:\`；
- 配置只保存 profile、命令路径、能力位、工作根和冻结 hash，不保存凭据值；
- 凭据由目标 CLI 自己管理，relay 只继承或引用已声明身份。

## 7. 编排模型的最终选择

### 7.1 三层能力

建议把编排能力分为三层，并在当前版本实现前两层的基础契约。

#### 第一层：版本化流水

`dev-harness-card@v1` 保存当前 11 棒行为，用于兼容和迁移对证。未来调整 dev-harness 节点、复核位置或收口拆分时，发布 `dev-harness-card@v2`。旧 run 继续绑定旧版本和 content hash。

流水定义冻结：

- 必经节点和边；
- 可选节点及允许的开关；
- 每个节点的角色、执行器类型和输入 schema；
- checkpoint、result 和 gate；
- effect 声明；
- 允许的 profile 与 script/action 引用类型；
- 完成、失败、取消和返工语义。

#### 第二层：类型化扩展点和注册动作

流水可以在已声明的时机触发外部动作：

- `run.started`
- `card.started`
- `stage.succeeded`
- `card.succeeded`
- `card.failed`
- `run.finished`
- `attention.opened`

扩展点只接受已注册的 `action_ref`。计划中禁止内联 shell、任意脚本路径和任意 prompt。

周报场景可以表达为：

```json
{
  "hook_id": "weekly-progress-after-build",
  "on": "stage.succeeded",
  "where": {
    "pipeline_id": "dev-harness-card",
    "stage_id": "build"
  },
  "action_ref": {
    "id": "project-status.weekly-report.append",
    "version": 1,
    "content_hash": "sha256:..."
  },
  "mode": "best_effort"
}
```

任务完成后的记录使用 `card.succeeded`。任务进行中的记录绑定明确阶段或显式 checkpoint，避免从 heartbeat、终端静默或自然语言猜测进度。

动作由目标项目拥有。其注册信息声明入口、cwd、输入 schema、效果范围、幂等语义和检查器。relay 只在正确时机生成并调度动作请求，不复制周报业务逻辑。

#### 第三层：已发布 playbook

未来 agent-console 需要可视化配置多个节点时，引入 `playbook`：

- `card-only@v1`
- `card-with-progress-report@v1`
- `card-then-human-verify-then-report@v1`

每份 playbook 冻结流水版本、节点、边、参数 schema、hook、effect 和 content hash。用户在 agent-console 中选择或编辑草稿，保存后形成新版本；启动前展示完整图和效果摘要，确认后写入 authority snapshot。

当前不实现 planner 任意组图。以后确实出现大量未预见拼法，再单独设计完整图授权、覆盖闸、参数边界、动态失效和外部效果验证。

### 7.2 为什么不直接开放自由 DAG

自由 DAG 的问题集中在授权链：

- planner 可以省略质量宏，省略本身不会制造额外副作用；
- 宏集合合法无法证明边和触发顺序合法；
- 外部事件可以在卡片完成前变为 ready；
- 参数能够绕过宏内部固定规则；
- 用户确认摘要若不包含整图，无法证明用户批准了实际拓扑。

要安全开放自由 DAG，需要冻结完整节点、边、谓词、参数、effect 和所有覆盖关系，并实现省略闸、支配关系、变更失效传播和运行期复验。当前需求尚未证明这笔复杂度有收益。

### 7.3 `ResolvedPlan` 是未来兼容点

无论输入来自固定流水、hook 或 playbook，Workflow Compiler 都生成统一的 `resolved-plan.json`：

```json
{
  "protocol": "relay.resolved-plan/v1",
  "run_id": "R-...",
  "authority_hash": "sha256:...",
  "source": {
    "kind": "playbook",
    "id": "card-with-progress-report",
    "version": 1,
    "content_hash": "sha256:..."
  },
  "nodes": [],
  "edges": [],
  "effects": [],
  "required_capabilities": []
}
```

Engine 只执行 ResolvedPlan。agent-console 也只渲染 ResolvedPlan。这样未来扩展 UI 编排时，Runner 和展示协议无需推翻。

## 8. Outbox 与跨项目动作

跨项目周报、通知和索引更新采用本机 durable outbox，不引入消息队列或数据库。

建议现场结构：

```text
<run>/
  outbox/
    requests/<action_request_id>.json
    attempts/<action_request_id>/<attempt>.json
    results/<action_request_id>.json
  action-state.json
```

规则：

- action request 为不可变文件；
- `action_request_id` 由 run、hook、来源事件和 occurrence 唯一确定；
- consumer 必须接收 idempotency key；
- 状态至少包含 `pending/running/succeeded/failed/dead_letter`；
- 默认 `best_effort` 不阻断原卡收口；
- 强依赖动作必须由已发布流水或 playbook 明确声明，不能由普通 hook 临时升级；
- 重试次数、退避和 dead-letter 可见；
- 实际写入由目标项目检查器验证；
- relay 事件账记录请求、启动、结果和最终状态，不能把动作成功冒充源卡验收。

这已经足以支持周报记录，同时保持业务代码位于周报项目。

## 9. Run Store 与协议

继续使用文件型事件账，不在 dh-relay 核心引入 SQLite。

原因：

- 当前单个 run 已明确采用唯一写者；
- 不可变 receipt、result、proposal 和追加事件适合审计与 Git 外现场；
- fixture 易于复制、diff、回放和交给 AI 复核；
- agent-console 可以只读消费，无需与 Runner 共用数据库写锁；
- 跨平台迁移面较小。

建议保留并版本化以下协议：

- `relay.plan-proposal/v2`
- `relay.authority/v2`
- `relay.resolved-plan/v1`
- `relay.launch-receipt/v2`
- `relay.checkpoint/v2`
- `relay.result/v2`
- `relay.event/v2`
- `relay.run-state/v1`
- `relay.action-request/v1`
- `relay.action-result/v1`
- `relay.attention/v1`

Go 重写先完整读取 `relay/v1`，输出新现场时使用 v2。旧现场只读查看与归档，是否允许继续运行由兼容矩阵明确决定。

## 10. 与 agent-console 的边界

agent-console 继续作为薄壳，dh-relay 继续拥有业务编排和运行真相。

### 10.1 agent-console 可以做

- 发现本机 dh-relay 版本和能力；
- 列出 run、读取状态、事件、Attention 和动作失败；
- 展示 ResolvedPlan 的节点、边、当前节点和证据入口；
- 选择已发布 pipeline/playbook；
- 配置允许覆盖的 profile、hook 绑定和可选开关；
- 发起 start、resume、stop、reply 等窄请求；
- 聚焦对应终端或打开证据；
- 提醒用户处理 Attention 和 dead-letter。

### 10.2 agent-console 不能做

- 直接修改 `relay-state.json`、events、receipt 或 result；
- 复制 dev-harness 节点表和质量判定；
- 从终端文本猜任务完成；
- 绕过 authority snapshot 增删必经节点；
- 把 UI 画布保存为未审任意图并直接执行；
- 管理 CLI 凭据值。

### 10.3 V1 交互方式

先提供稳定 CLI 和 JSON 输出：

```text
relay list --json
relay status <run_id> --json
relay inspect <run_id> --json
relay validate <request.json> --json
relay start --request <request.json>
relay control --request <control.json>
relay export <run_id> --output <dir>
```

agent-console 调用 CLI 或读取只读索引。暂不建立 HTTP 服务。

### 10.4 后续 IPC 兼容

以后需要实时体验时，可以在同一 JSON 契约上增加：

- Windows named pipe；
- Linux Unix domain socket；
- JSON Lines 请求、响应和事件订阅。

IPC 只是传输层，权限、状态和业务规则仍在 dh-relay。当前只冻结消息 schema 与 request id，不实现常驻网络服务。

## 11. 迁移策略

建议暂停新增 PowerShell 核心功能，只处理阻塞性缺陷。迁移分五批完成。

### 批次 0：冻结基线

- 固定现有 P1、DHR_04 契约、fixtures、reason code 和回放签名；
- 生成 Windows 基线证据；
- 建立 Windows 与 Linux 能力矩阵；
- 决定 `relay/v1 -> v2` 兼容表；
- 修正根级文件守卫，为 Go 工程和 CI 开路。

### 批次 1：契约、存储和回放

- 建立 Go module；
- 实现 schema、identity、transition、redaction；
- 实现原子 store、事件账和 deterministic replay；
- 对同一 fixtures 比较 PowerShell 与 Go 结果；

## 12. 开发约束

为了让 AI 施工稳定，建议把以下约束写进 Go 阶段的 AGENTS 和 CI：

- 所有持久协议先定义 schema、golden fixture 和拒绝用例；
- reason code 使用类型化常量，禁止靠字符串拼接产生新码；
- 时间、随机数、进程、文件系统和 adapter 必须可注入；
- 每个包保持单一职责，跨包循环依赖为构建失败；
- 业务状态转换只在 `contracts/engine`；
- 存储写入只在 `store`；
- 平台条件编译只在 `adapters/platform`；
- 所有 goroutine 必须有 owner、context 和退出路径；
- 禁止计划内联 shell；
- 禁止 core 读取凭据值；
- `go test ./...` 是统一本地验收入口；
- Windows 和 Linux CI 同时通过后才允许合入核心运行时变更。

## 13. 当前明确不做

本次设计不要求立即实现以下能力：

- 任意 DAG 画布和完整策略引擎；
- 插件市场或动态加载第三方二进制；
- SQLite、外部消息队列或服务端数据库；
- HTTP 服务、WebSocket 和远程控制；
- 多机分布式调度；
- dh-relay 与 agent-console 同进程嵌入；
- 将周报业务规则复制进 dh-relay；
- 同一 run 在不同 pipeline 版本之间热迁移；
- 为 Herdr、Orca 或其他候选提前建立专属核心分支。

## 14. 验收建议

### 14.1 语言迁移

| ID | 验收命题 |
|---|---|
| T1 | 同一组 v1 fixtures 在 PowerShell 基线和 Go 实现中得到相同 accept/reject、reason 和状态投影 |
| T2 | blocked、decision、stale、probe-lost 和 policy replay 的确定性签名保持一致 |
| T3 | `go test ./...` 在 Windows 与 Linux 通过 |
| T4 | Windows psmux 与 Linux tmux 各完成 launch、probe、checkpoint、result、stop 的真实闭环 |
| T5 | 平台缺失强证据能力时，validate 在启动前拒绝，不产生 run 现场和用户级索引 |
| T6 | Go 进程退出、崩溃和重启后，原子文件、不可变 result 和唯一写者约束仍成立 |

### 14.2 编排与外部动作

| ID | 验收命题 |
|---|---|
| O1 | `dev-harness-card@v1` 的必经节点不能通过 hook、参数或 planner 输出省略 |
| O2 | 任意未知 action、版本/hash 不符、内联命令和未授权 effect 均在编译阶段拒绝 |
| O3 | `stage.succeeded` 与 `card.succeeded` 各能产生恰好一次周报 action request |
| O4 | 周报 action 失败时源卡按 `best_effort` 继续，失败状态、重试和 dead-letter 可见 |
| O5 | 重复事件、宿主重启和 consumer 重放不产生第二次周报写入 |
| O6 | playbook 缺卡宏、外部动作无终态支配关系、边或参数被篡改时拒绝 |
| O7 | dev-harness 发布 v2 后，旧 run 继续绑定 v1，新 run 可选择 v2，二者状态和工件互不污染 |

### 14.3 agent-console 兼容

| ID | 验收命题 |
|---|---|
| C1 | 控制台只凭 `resolved-plan/run-state/event/attention` 协议即可画出步骤、边、状态和待处理项 |
| C2 | 控制台直接改 run 文件、删必经节点或提交未授权 action 时全部拒绝 |
| C3 | CLI JSON 与后续 IPC 使用同一 schema，切换传输层不改变 workflow truth |
| C4 | dh-relay 不可用或协议不兼容时，控制台显示 unavailable，不能回退解析 DevPlan 或终端文本猜状态 |
