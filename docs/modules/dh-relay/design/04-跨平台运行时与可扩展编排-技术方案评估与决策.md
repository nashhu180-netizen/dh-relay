## 1. 最终判断

建议采用以下产品形状：

> **一个通用 Relay Core，两类扩展边界，以及一个外部控制台。**

两类扩展边界分别是：

1. **Workflow Contract**：描述某类工作怎样编译成可执行计划。DevHarness 是第一个、也是当前最重要的 Workflow Contract。
2. **Runtime Adapter**：描述节点在哪里运行、如何观察和控制。Herdr、process、fake、psmuxlegacy 都属于 Runtime Adapter。

外部控制台是 `agent-console`。它通过稳定协议读取和控制 dh-relay，不进入 Core，也不复制 DevHarness 规则。

本次建议确定八项方向：

1. **dh-relay 核心运行时使用 Go。** 项目基线建议固定为 `Go 1.26.x`，分别发布 Windows 与 Linux 单一可执行文件。
2. **Herdr 成为首选交互式 Agent 宿主。** Windows 与 Linux 均通过 Herdr 承载 Claude、Codex、Grok、Kimi 等交互会话。`process` executor 承载脚本、机器闸和无需交互的任务。
3. **psmux 只保留迁移期回退。** 它继续服务现有 Windows 基线和故障回退，停止扩展新的 Agent 语义识别。当前阶段不开发 tmux adapter；Linux 先完成 Herdr preflight 和 dogfood。
4. **Relay Core 保持领域无关。** Core 只认识 run、node、edge、gate、result、artifact、event、effect、approval、attention、capability 等通用概念。
5. **DevHarness 通过版本化 Workflow Contract 接入。** Core 不内置 A/B/D/E/R、任务卡、两轮复核、releasePacket、八件套等词义。
6. **编排采用受控图模型。** Workflow Compiler 将 Contract、运行参数、扩展绑定和 authority snapshot 编译成完整 `ResolvedPlan`。AI planner 不能即兴提交任意 DAG。
7. **DevHarness 的 Git 与结构化 Markdown继续承担领域权威。** Relay Store 保存运行、调度、receipt、事件和宿主观测。两者冲突时 fail-closed，并创建 Attention。
8. **agent-console 只消费稳定协议。** 它负责展示、配置、启动、提醒、终端聚焦和证据导航；dh-relay 保留运行写权，DevHarness 保留领域规则与工件权威。

还有一个需要单独固定的结论：

> **Go 无法让 psmux 自动理解 Agent 正在工作、等待用户、已经停下或已经提交合格结果。**

Go 改善类型安全、并发、进程监管、超时、跨平台文件和部署。Herdr 提供 `idle / working / blocked / done / unknown`、状态变化序号和状态事件。任务是否满足 Workflow Contract，仍由结构化 result、机器闸、工件和用户确认共同决定。

## 2. DevHarness 源码核对后的调整

### 2.1 原方向保留的部分

以下结论经源码核对后继续成立：

- Go 适合作为 dh-relay 的跨平台核心运行时；
- Herdr 适合作为交互式 Agent 的首选宿主；
- 文件型唯一写者、不可变工件、原子快照和追加事件适合 Relay Run Store；
- 受控图、版本化流程、hook、outbox 和后续 playbook 的方向成立；
- agent-console 应读取 ResolvedPlan 和 RunState，不应直接解析终端文本推断质量终态；
- DevHarness 规则不应被写入 Relay Core。

### 2.2 需要修正的部分

源码核对发现五项实质调整。

#### 调整一：DevHarness 是流程族，不是一条固定任务卡宏

DevHarness 的机读北极星由两级构成：

- `references/节点图.md#dh:node-graph`：A、B、D/E、R、汇报横切、维护旁路；
- `references/节点表.md#dh:nodes`：标准档任务的 S0~S3 与 E0~E13 子图。

因此，长期形态不应只有 `dev-harness-card@v1`。更准确的 Workflow Contract 族是：

```text
dev-harness/task-standard@1      当前 P2 主目标，映射 D/E 标准档
dev-harness/task-light@1         后续按真实需求接入
dev-harness/maintenance@1        后续映射维护旁路
dev-harness/planning-a@1         未来可选，当前不进入 P2
dev-harness/planning-b@1         未来可选，当前不进入 P2
dev-harness/restore@1            未来可选，当前由 resume + 工件对账覆盖
relay/basic-agent-task@1         与 DevHarness 无关的基础流程
```

当前正式 P2 已明确只接管已完成 A、B 且获得开工授权的任务卡，所以本期只实现 `dev-harness/task-standard@1` 和 `relay/basic-agent-task@1`。A、B 继续由主会话与用户按 Skill 完成。

#### 调整二：节点表中的派给和路径有可配置性

`references/节点表.md` 明确说明“派给”是默认建议，开工前用户可以逐节点改、换后端或关闭允许关闭的委托路径。D 动作还规定：

- 档位与施工说明书粒度是两条轴；
- 批次小审次数由实际施工批次产生；
- TDD 是强默认，部分任务不适用；
- worktree 需要按任务风险和用户选择分流；
- 判断节点、人闸和独立复核有角色约束。

所以 Contract 需要同时表达：

```text
固定终点和硬闸
允许调整的节点分派
已声明的可选路径
按运行输入展开的动态子图
禁止调整的独立性与收口约束
```

不能把 S0~E13 的每条边、每个执行者和每个实现细节全部写死成一条不可配置模板。

#### 调整三：DevHarness 已有机读锚点与机器工具

DevHarness 仓库已经有：

- `dh:node-graph` 与 `dh:nodes` 机读锚点；
- `dh-check.mjs`、`dh-core.mjs`、`dh-policy/*`、`dh-snapshot.mjs`、`dh-monitor.mjs` 等工具；
- 节点图、节点流、独立复核、releasePacket、H=0、策略和大量负例测试；
- Windows 与 Linux 安装入口。

因此，Go Relay Core 不应重新实现全部 G1~G14 和 DevHarness 文档解析。建议由 DevHarness 发布一份冻结的 Relay Contract 工件，dh-relay 只消费该工件，并通过 Gate Adapter 调用 DevHarness 已有的机器判断。

#### 调整四：两套真相需要明确分工

DevHarness 的程序化说明强调：`dh` 从 Git 与结构化 Markdown 派生状态，不另建一份领域状态账本。dh-relay 又必须保存跨天运行、attempt、receipt、宿主事件和恢复现场。

两者可以共存，边界如下：

| 真相类型 | 权威位置 | 内容 |
|---|---|---|
| 领域真相 | 目标业务仓的 DevPlan、workspace、review、Git、verify 提交 | 任务目标、验收、工件、质量闸、最终销户事实 |
| 运行真相 | `<repo>/.dh-relay/<run_id>/` | 节点调度、attempt、receipt、事件、Herdr 观测、超时、重试、outbox |
| 查询投影 | relay index、agent-console 读模型 | 可删除、可重建的展示数据 |

Relay 的 `node.succeeded` 只表示该节点已按 Contract 提交合法结果。DevHarness 的任务完成仍需 E0~E13 对应闸和仓内工件成立。

#### 调整五：Workflow Contract 需要冻结工具版本

当前 `dh` 可能指向用户机器上的可变工作区。如果 run 启动后 DevHarness 工具被更新，即使 Contract 文件没变，Gate 行为也可能变化。

每个 DevHarness run 需要冻结：

```text
source_repo
source_commit
contract_id
contract_version
contract_content_hash
gate_bundle_id
gate_bundle_digest
required_capabilities
```

启动、恢复和关键收口前都要校验工具 bundle。版本或 digest 不符时，暂停并要求重新验证，不能静默切换规则。

## 3. 总体架构

```text
                             agent-console
                    展示 / 配置 / 提醒 / 窄控制
                                   |
                                   v
+--------------------------------------------------------------------+
|                         relay CLI / API                             |
| start  resume  stop  list  status  inspect  validate  export        |
+------------------------------+-------------------------------------+
                               |
                               v
+--------------------------------------------------------------------+
|                       Workflow Compiler                             |
| Workflow Contract + Params + Extensions + Authority -> ResolvedPlan |
+------------------------------+-------------------------------------+
                               |
                               v
+--------------------------------------------------------------------+
|                         Relay Core                                  |
| Engine / Authority / Run Store / Replay / Attention / Outbox        |
+--------------+----------------------+------------------------------+
               |                      |
               v                      v
+----------------------------+  +------------------------------------+
| Workflow Gate Adapters     |  | Runtime Adapters                   |
| dev-harness gate bundle    |  | Herdr primary                      |
| basic task validators      |  | process                            |
| future workflow validators |  | fake                               |
+----------------------------+  | psmuxlegacy                        |
                                +------------------------------------+
                                             |
                                             v
                                  Claude / Codex / Grok / Kimi
```

依赖方向必须保持：

```text
DevHarness Workflow Contract ---> Relay Contract Interface <--- Relay Core
Runtime Adapter ----------------> Runtime Interface        <--- Relay Core
agent-console -------------------> Stable JSON Protocol     <--- dh-relay
```

Relay Core 不 import DevHarness 业务包。移除 DevHarness Contract 后，`relay/basic-agent-task@1` 仍应正常运行。

## 4. Relay Core 的职责边界

### 4.1 Core 认识的通用概念

```text
run
workflow_contract
resolved_plan
node
edge
attempt
receipt
checkpoint
result
gate
artifact
effect
action
approval
attention
capability
host_observation
```

通用节点状态建议为：

```text
pending
ready
launching
running
attention_required
awaiting_result
succeeded
failed
cancelled
interrupted_unknown
```

### 4.2 Core 不认识的 DevHarness 概念

以下词义由 DevHarness Contract 和 Gate Adapter持有：

```text
A 立项
B 拆计划
S0~S3
E0~E13
任务卡
DevPlan
标准档 / 轻档 / 高危
八件套
批次小审
两轮独立复核
需求复核
教训复核
releasePacket
verify(slug)
销户
H=0
风险放行
不可豁免红线
```

Core 可以保存这些概念的稳定标识、展示名称和证据引用，但不解释其业务含义。

### 4.3 Core 负责的事情

- 校验 Contract 身份、版本、hash 与能力；
- 把 Contract、参数、扩展绑定和授权编译成完整图；
- 按依赖、条件和状态决定哪个节点 ready；
- 为每次 launch 签发不可变 receipt；
- 摄入 checkpoint、result 和宿主观测；
- 实施唯一写者、原子落盘、追加事件和确定性回放；
- 管理超时、取消、重试、返工计数和中断恢复；
- 调用 Runtime Adapter 与 Workflow Gate Adapter；
- 管理 Attention、approval request 和 approval receipt；
- 管理跨项目动作的 durable outbox；
- 输出 ResolvedPlan、RunState、Event、Attention 和 HostObservation。

### 4.4 Core 不负责的事情

- 从 Skill 散文临时推断流程；
- 判断两轮复核在业务上是否合格；
- 解释数据口径是否正确；
- 生成或修改 DevHarness 正式目标和验收；
- 把 Herdr `done` 当成任务完成；
- 将 Relay Store 变成 DevPlan 或 review 的替代账本；
- 允许 agent-console 直接写 run 现场或业务工件。

## 5. Workflow Contract

### 5.1 Contract 的定位

Workflow Contract 是某类工作流面向 Relay 的版本化执行投影。它回答：

- 可以有哪些节点；
- 哪些节点和边必须存在；
- 哪些节点可以选配；
- 哪些节点可动态展开；
- 节点需要什么输入、结果和证据；
- 哪些角色必须独立；
- 哪些状态需要用户确认；
- 允许在哪些位置挂 hook 或插入扩展；
- 哪些外部 effect 需要额外授权；
- 哪个 Gate Adapter 负责领域校验。

### 5.2 建议的 Contract 结构

```json
{
  "protocol": "relay.workflow-contract/v1",
  "id": "dev-harness/task-standard",
  "version": 1,
  "content_hash": "sha256:...",
  "source": {
    "repo": "nashhu180-netizen/dev-harness",
    "commit": "c0bb93980f257a0aaa7df5b3a5fdc047598e48e3",
    "files": [
      "SKILL.md",
      "references/节点图.md",
      "references/节点表.md",
      "references/动作-D-开工.md",
      "references/动作-E-收口.md"
    ],
    "digest": "sha256:..."
  },
  "profiles": [],
  "nodes": [],
  "edges": [],
  "constraints": [],
  "extension_slots": [],
  "hooks": [],
  "gate_bundle": {
    "id": "dev-harness/gates",
    "digest": "sha256:..."
  }
}
```

这里的 `version` 是 Relay Contract 版本，独立于 Markdown 中的 `dh:v1` marker。`source.commit + source.digest + content_hash` 共同防止同名规则静默变化。

### 5.3 Contract 的生成方式

推荐关系：

```text
DevHarness Skill 与权威文档
       |
       | 由 dev-harness 仓内 exporter 读取机读锚点并补足复杂约束
       v
dev-harness/task-standard@1 contract
       |
       | dh-relay 校验版本、hash、能力和授权
       v
ResolvedPlan
       |
       v
Relay Core
```

V1 不建设动态插件市场。可以先在 DevHarness 仓库增加一个确定性导出命令，例如：

```text
dh relay-contract export --workflow task-standard --output <path>
```

导出器负责：

- 读取 `dh:node-graph` 与 `dh:nodes`；
- 绑定 D/E 动作细则和硬规则摘要；
- 生成节点、边、角色约束、approval、hook 和 gate bundle 引用；
- 计算 source digest 与 contract hash；
- 跑现有节点图、节点流、复核独立性、releasePacket、策略负例；
- 只有全部通过才发布 Contract。

在导出器落地前，可以维护一份人工编制、带 source digest 的 Contract fixture。它必须通过同一组 conformance tests，不能由 planner 在每次 run 前临时生成。

## 6. DevHarness 到 Relay 的映射

### 6.1 当前 P2 的映射范围

当前 P2 继续保持：A、B 在 Relay 外完成，Relay 从已授权任务卡的 D/E 生命周期开始。

| DevHarness 范围 | 当前处理 |
|---|---|
| A 立项 | 主会话与用户按 Skill 完成，Relay 只消费已冻结结果 |
| B 拆计划 | 主会话与用户按 Skill 完成，Relay 只消费 authority snapshot 与任务卡 |
| D/E 标准档 | 映射为 `dev-harness/task-standard@1` |
| R 恢复 | Relay 提供 run resume；DevHarness 工件恢复与 `dh status/gate` 对账作为 Gate Adapter 能力 |
| 汇报横切 | 映射为节点事件、report action 或 agent-console 展示 |
| 维护旁路 | 后续独立 `dev-harness/maintenance@1`，本期不混入标准档 |
| 轻档 | 后续独立 `dev-harness/task-light@1`，本期由 `basic-agent-task` 验证 Core 解耦 |

### 6.2 S0~E13 的通用映射

| DevHarness 节点 | Relay 节点类型 | 关键合同 |
|---|---|---|
| S0 建工作区 | script / gate | 生成工件骨架，绑定目标仓与工作区 |
| S1 brief | agent | 输出 `brief.md`，下游 Gate Adapter 校验 |
| S2 施工步骤 | agent | 输出 `task_plan.md`，保留判断角色约束 |
| S3 施工 | dynamic agent subgraph | 按批次展开 build、checkpoint、批次小审与修复 |
| E0 机器体检 | script gate | 机器事实，结构化 `gate_outcome` |
| E1 check 四道闸 | workflow gate | 调用 DevHarness Gate Adapter，缺项 fail-closed |
| E2 增量轮2 | independent review agent | fresh context、未参与实施、会话身份可证明 |
| E3 复核收敛 | aggregate / agent | 汇总轮1与轮2，不代替实际 review result |
| E4 需求复核 | review agent | 可并行，结果单独登记 |
| E5 教训复核 | review agent | 可并行，命中重蹈可触发返工 |
| E6 miner | agent / action | 候选备料，不直接晋级教训库 |
| E7 as-built | agent | 输出覆盖式快照，受工件 Gate 校验 |
| E8 AI 提交区 | agent / gate | 验收项逐条挂证据 |
| E9 交付汇报 | report action | 生成并展示，不代表人验通过 |
| E10 证据展示区 | report / approval preparation | 形成 releasePacket 和最后确认材料 |
| E11 用户确认 | approval gate | receipt 绑定 releasePacket hash 与允许效果集合 |
| E12 精确合入与 verify | privileged script | 只执行 E11 授权包中的本地效果 |
| E13 销户与清理 | finalizer script | 回填仓内真相、刷新状态、清理任务树 |

这张表只描述执行投影。节点的具体文档要求、风险规则、H=0、不可豁免项和 release_mode 继续由 DevHarness Gate Adapter 判断。

### 6.3 硬闸、默认和动态路径分开表达

Contract 中每个节点需要声明 `requiredness`：

```text
hard_required      缺失即拒绝编译或拒绝放行
default_enabled    默认存在，允许按 Contract 规则关闭
optional           用户或项目可选
dynamic            由任务内容在允许范围内展开
crosscut_action    不改变主质量路径的旁路动作
```

DevHarness 标准档的典型分类：

- E2 两轮复核完整性、E11 用户确认、E12 精确收口、不可豁免红线：`hard_required`；
- S1、E4、E5、E6、E7 的具体执行后端：可做 assignment override；
- integration、e2e 等项目条件分支：已声明 optional；
- S3 批次数与每批小审：dynamic；
- 汇报、周报、通知：crosscut action；
- TDD：Contract 元数据中的强默认和审核提示，不直接升级成所有任务的统一机器硬闸。

## 7. DevHarness 修改与特别节点插入

### 7.1 DevHarness 修改时

支持修改，规则如下：

1. 已发布 Contract 不可原地改写。
2. DevHarness 源文件变化后重新导出 Contract。
3. 导出器比较节点、边、Gate、角色、effect、approval 和参数 schema。
4. 影响执行语义时发布新 `contract_version`。
5. 旧 run 继续绑定旧 Contract、source commit 和 gate bundle。
6. 新 run 使用新版本前必须通过 conformance tests 和用户确认。
7. 运行中不热切换 Workflow Contract。

需要发布新版本的变化包括：

- 增删必经节点；
- 修改必经边或返工路径；
- 修改完成条件；
- 修改两轮复核与角色独立性；
- 修改 E11 授权包或 E12/E13 effect；
- 修改不可豁免规则；
- 新增可改变主路径的扩展槽；
- 修改节点输入、结果或工件 schema。

可以作为运行参数或 assignment override 的变化包括：

- 在允许集合内更换 Agent profile；
- 在允许集合内更换 Herdr、process 等后端；
- 调整 timeout 和 retry 上限；
- 选择已发布的 optional 节点；
- 绑定已注册的周报或通知 action；
- 填入 task_id、module_slug、workspace 等 authority 已允许参数。

### 7.2 DevHarness 不改，插入特别处理时

支持四种扩展形式，按影响从轻到重排列。

#### A. Assignment Override

同一节点更换执行 Agent、模型、账号或 Runtime Adapter，节点语义保持不变。

```text
E5 教训复核
默认：Claude profile A
本次：Codex profile B
```

Contract 校验执行者能力、独立性和 allowlist。

#### B. Optional Node

启用 Contract 已经声明的可选节点，例如 integration 或 e2e。节点、位置和 Gate 已在 Contract 中发布。

#### C. Hook + Action

用于周报、通知、索引、统计等旁路处理：

```text
S3 某批完成 -> 写进行中周报
E13 销户完成 -> 写完成周报
attention.opened -> 通知用户
```

Hook 不允许省略、提前完成或替代主路径节点。跨项目写入通过 durable outbox 执行。

#### D. Blocking Extension Slot

用于必须影响主路径的特殊处理，例如安全扫描、额外人工确认、特定项目的强制验收。

Workflow Contract 需要先声明允许插入的 slot、允许节点类型、输入输出和失败语义。示例：

```text
S3 施工结束
  -> [slot: before_closeout_review]
  -> E0 / E1 / E2...
```

AI planner 只能把已注册节点绑定到已声明 slot。未声明位置的插入请求会被拒绝。

V1 建议先实现 Assignment Override、Optional Node 和 Hook。Blocking Extension Slot 只保留 Contract 与 Compiler 能力，等第一个真实阻断型需求出现后再发布具体 slot，避免提前造一套任意插图系统。

### 7.3 何时需要新 playbook 或新 Contract

- 某个特殊组合会反复使用：发布命名 playbook；
- 特殊节点需要所有 DevHarness 标准任务强制经过：发布新的 DevHarness Contract 版本；
- 特殊节点只做一次且已有合法 slot：本次 extension binding 即可；
- 没有合法 slot：当前 run 不允许临时越过边界。

## 8. 受控图模型与 Codex、Grok 争议

### 8.1 Codex 的有效部分

Codex 的两层模型保留：

- 内层使用发布版流程合同保护必经质量路径；
- 外层组合任务流程、周报、归档和通知；
- 跨项目 effect 使用 outbox；
- dev-harness 改版后发布新版本。

### 8.2 Grok 补出的缺口

只检查“出现的节点是否合法”和“effect 是否在授权子集内”，无法证明必经节点已经出现，也无法证明外部动作位于正确的质量闸之后。

坏图示例：

```text
写周报 -> 归档 -> 完成
```

全部节点都可能来自白名单，任务卡流程却完全没有运行。

### 8.3 最终受控图

最终方案采用：

```text
Workflow Contract 冻结硬节点、硬边、Gate、slot 和 effect 边界
AI planner 填参数、选 optional、做 assignment override、绑定 hook
Workflow Compiler 生成完整 ResolvedPlan
Authority Snapshot 冻结 Contract、参数、扩展、effect 和 hash
Relay Core 只执行已通过编译与授权的 ResolvedPlan
```

对于 DevHarness，完整性检查由 `dev-harness/task-standard@1` 提供。对于 `relay/basic-agent-task@1`，使用另一套更轻的完成条件。Core 不写死“每张卡必须被 DevHarness 宏覆盖”这一领域规则。

### 8.4 周报例子

```text
DevHarness 主路径：S0 -> S1 -> S2 -> S3 -> E0 ... -> E13
                                  |                  |
                                  +-> 进行中周报      +-> 完成周报
```

进行中周报和完成周报是 outbox action。它们不能替代 E2、E4、E5、E11、E12、E13，也不能把任务提前标记完成。

## 9. Herdr 与工作流状态

### 9.1 两套状态分开

Herdr 状态属于宿主观测：

```text
idle / working / blocked / done / unknown
```

Relay 状态属于运行调度：

```text
launching
running
attention_required
awaiting_result
succeeded
failed
interrupted_unknown
```

DevHarness 状态属于领域真相，例如 DevPlan 的未开始、进行中、待验收、已完成和已取消。

三者不能互相覆盖。

| Herdr 观测 | Relay 处理 |
|---|---|
| `working` | 节点保持 running，刷新活性证据 |
| `blocked` | 创建 Attention，节点进入 attention_required |
| `done` | 节点进入 awaiting_result；缺合法 result 时禁止完成 |
| `idle` | 结合阶段、最近事件、pane、result 和进程对账 |
| `unknown` | 启动 snapshot、进程对账和超时规则 |
| pane 或进程消失 | 缺合法 result 时进入 interrupted_unknown |

### 9.2 事件快路与对账慢路

Herdr Adapter 同时使用：

1. 事件订阅：快速接收状态和 pane 变化；
2. 周期对账：读取 snapshot、pane 和进程事实，修复断线与漏事件。

每个 run 记录 Herdr 版本、API 能力、Agent kind、pane 句柄和能力 hash。

### 9.3 已知盲区

- 启动信任弹窗可能显示为 idle；
- 状态检测规则随 Herdr 版本变化；
- 宿主事件可能漏掉进程退出；
- `done` 只说明 Agent 停止工作；
- 当前 Linux 机器证仍需补齐。

这些风险通过启动期限、版本冻结、进程对账、result 契约和双平台 dogfood 处理。

## 11. Gate Adapter 与领域对账

### 11.1 Gate Adapter 的职责

DevHarness Gate Adapter 负责调用冻结版本的机器工具，返回结构化结果：

```json
{
  "protocol": "relay.gate-result/v1",
  "gate_id": "dev-harness/e1",
  "outcome": "pass",
  "reason_codes": [],
  "evidence_refs": [],
  "source_digest": "sha256:..."
}
```

短期可以通过固定 wrapper 调用现有 Node 工具。长期应提供稳定 JSON 输出，避免 Go 解析面向人的终端文本。

### 11.2 对账时机

至少在以下时机调用领域对账：

- run 创建前；
- 每个承重节点 launch 前；
- authority 或目标仓关键工件变化后；
- E11 approval request 生成前；
- E12 finalizer 执行前；
- E13 销户后；
- run 恢复时。

### 11.3 冲突处理

出现以下情况时 fail-closed：

- Relay 认为节点完成，仓内必需工件缺失；
- DevPlan、brief 或 review 的版本与 authority snapshot 不符；
- Gate bundle digest 变化；
- review 独立性记录不满足 Contract；
- releasePacket hash 与用户确认 receipt 不匹配；
- E12 计划 effect 超出 E11 授权集合；
- Relay 运行状态与仓内销户事实矛盾。

冲突进入 Attention，保留现场和证据，不自动篡改任一权威账本。

## 12. Approval 与 E11/E12/E13

E11 建模为通用 approval gate，DevHarness Contract 提供领域语义。

approval request 至少冻结：

```text
workflow_id
run_id
task_id
release_packet_hash
allowed_effects
excluded_effects
evidence_refs
expires_at
```

approval receipt 至少包含：

```text
request_id
request_hash
answer
captured_at
provider
host_evidence_refs
```

当前 P2 可以继续使用 Agent 窗口中的确认原文和宿主截图，属于已接受的弱身份方案。Herdr 的 blocked 只负责提醒，不负责证明用户身份。未来 agent-console 可以提供更强的本地确认界面，Contract 和 Core 协议无需改变。

E12/E13 只能执行 approval request 中已经展示并授权的精确本地效果。push、deploy、环境操作、生产数据和下一张卡开工继续需要独立授权。

## 13. Outbox 与跨项目动作

周报、通知、索引更新和项目状态同步通过本机 durable outbox：

```text
<run>/
  outbox/
    requests/<action_request_id>.json
    attempts/<action_request_id>/<attempt>.json
    results/<action_request_id>.json
  action-state.json
```

规则：

- request 不可变；
- action id 由 run、hook、来源事件和 occurrence 唯一确定；
- consumer 接收 idempotency key；
- 状态至少有 pending、running、succeeded、failed、dead_letter；
- 默认 best_effort 不阻断 DevHarness 主路径；
- 强依赖 action 只能由发布版 Contract 或 playbook 声明；
- 目标项目拥有业务写入程序和检查器；
- action 成功不能冒充源任务验收成功。

## 14. 与 agent-console 的边界

agent-console 可以：

- 发现 dh-relay、Herdr、Workflow Contract 和 Gate bundle 版本；
- 列出 run，读取 ResolvedPlan、RunState、Event、Attention、HostObservation 和 ActionState；
- 展示 DevHarness 节点名称、必经节点、可选节点和 extension slot；
- 显示 Agent 正在工作、等待用户、已停下或宿主失联；
- 选择发布版 workflow/playbook；
- 配置允许的 profile、assignment override、optional 和 hook；
- 发起 start、resume、stop、reply、approval 等窄请求；
- 聚焦 Herdr pane 和打开证据。

agent-console 不能：

- 直接修改 Relay Store、DevPlan、review 或 verify 记录；
- 内置 DevHarness 节点规则；
- 将 Herdr done 解释成任务成功；
- 删除 Contract 的硬节点和硬边；
- 执行未审 UI 图；
- 管理 Agent CLI 凭据值。

V1 先提供 CLI 和 JSON：

```text
relay contracts --json
relay list --json
relay status <run_id> --json
relay inspect <run_id> --json
relay validate <request.json> --json
relay start --request <request.json>
relay control --request <control.json>
relay export <run_id> --output <dir>
```

需要实时体验时，再在同一 schema 上增加 Windows named pipe、Linux Unix domain socket 和 JSON Lines 事件订阅。
