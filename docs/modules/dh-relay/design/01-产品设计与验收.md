## 1. 人话版目标

### 1.1 我们在做什么

我理解你要的是：在 Design 与 DevPlan 已由独立 agent 讨论、审核并经用户确认后，不再让一个长期驻留的 AI 主控负责派活、巡检和收口；改由一次性编排 agent 先设计接力计划，再由确定性的 Runner 按文件状态依次或并行拉起可见、可交互的 agent 终端。每个 agent 只完成一棒，交出结构化结果；Runner 只验证身份、交接完整性和合法状态转换，不替施工或复核 agent 判断代码质量。

这个模块的第一阶段不是直接造完整生产编排器，而是用一个最小 PoC 验证最难、最容易出错的接力边界：前置任务阻塞后的重新编排、需要人类决策时的原会话挂起、异常退出时的 fail-closed，以及旧会话结果不得污染 fresh 会话。

### 1.2 为什么另建模块

- `dh-crew` 的既有阶段接力仍以阶段主控 / 任务主控为中心；`dh-relay` 验证的是“没有常驻 AI 主控，Runner 按状态接棒”。
- 两个模块同仓并存，但设计输入、DevPlan、运行状态和 workspace 隔离；本方案不迁移、不替代、不修改 `dh-crew` 的在途任务。
- `dh-crew` 既有阶段退出、精确 session、原子状态与 fail-closed 经验可作为安全原则参考，但不是 `dh-relay` 的正式设计输入，也不能让新模块消费旧模块的 active state。

### 1.3 关键决策（动这些要重新讨论）

1. **编排 agent 一次性运行**：只评估/生成 RelayPlan 或处理一次重编排，写完候选计划即退出，不承担持续监控。
2. **Runner 确定性优先**：清晰状态走规则；只有 `dependency_blocked` 等需语义判断的分支才拉起一次性诊断/重编排 agent。
3. **Runner 不负责代码质量**：worker 的 `succeeded` 只代表当前阶段可以交棒；review 才能形成质量结论，Runner 不把 `succeeded` 直接投影为任务完成。
4. **终端与业务状态分维**：Runner/终端宿主观察终端生命周期；worker 或可信宿主事件报告本棒业务结果，两者不得混成一个状态。
5. **交棒先于退出**：正常退出必须先完成交接包、结果提交和 Runner ack；进程先消失且无可信结果时只能停在 `interrupted_unknown`。
6. **不同阻塞采用不同会话策略**：需要人类决策时，worker 写非终态 checkpoint 后在原会话等待；用户在该 agent session 回答后，agent 自然继续，Runner 不读取、不转发回答，也不发 resume。Runner 只冻结依赖该节点的后续节点，无依赖的并行节点继续。需要新增前置任务、重新编排时交接后退出，前置完成后拉 fresh agent 恢复。复核快速返工时保留并恢复原施工会话属于目标形态，P1 不验证。
7. **PoC 终端后端固定为 `psmux`**：Runner 必须自动打开为用户可见、可交互的界面，并能精确探测、挂起和回收唯一 session；仅后台建 session 不算通过。

### 1.4 范围与分期

**P1 · 最小 PoC（本设计与当前 DevPlan 的范围）**：

- 固化 RelayPlan、authority、launch receipt、result、handoff、event 与双维状态契约。
- 实现最小 Runner 与 fake terminal adapter，确定性回放正常、阻塞、挂起、迟到结果、半写和异常退出。
- 接入一个真实 `psmux` 可见交互终端，跑通一次 dependency-blocked 重编排接力，并演示 decision-required 挂起。

人话版效果——跑完 P1 你能亲眼看到一场完整演示：

1. 编排 agent 写出计划，Runner 自动弹出一个你能看见、能打字的 worker A 窗口；
2. A 发现缺前置任务 B：交接、退出，重编排 agent 补出 v2 计划，B 跑完后全新的 A 带着交接包继续；
3. 旧 A 的迟到结果被拒收，不污染新 A；
4. 另一场演示：agent 停下来等你决策，你在原窗口回答一句，它接着干，Runner 全程不插手；
5. 崩溃、半写、探测失败等异常在 fake terminal adapter 上确定性重放，全部安全停住。

它证明的是一句话：没有常驻 AI 主控，靠文件状态接棒也能把最难的几个边界走通。它不交付完整的施工→复核→返工流水、多任务 DAG 调度与生产可用性——那些属于下方目标形态。

**目标形态（后续另行 A/B，不属于 P1 验收）**：

- workspace agent → 施工 agent → review lead → 并行 reviewer → 原施工 agent 返工的完整流水。
- 按 RelayPlan DAG 串行或并行执行多任务。
- 更多终端后端、自动决策、跨机器运行与统一 UI。

### 1.5 核心决策清单

| 决策点 | 选了什么 | 备选与取舍 | 不可逆程度 |
|---|---|---|---|
| 模块边界 | 同仓独立模块 `dh-relay`，代码候选根 `tools/` | 改造 `dh-crew` 会把试验风险带入现有编排 | 中；正式接线前仍可调整代码目录 |
| 控制结构 | 一次性编排 agent + 确定性 Runner（按规则调度的程序，非 AI） | 常驻 AI 主控更灵活，但需要轮询、占上下文且用户难看见真正施工现场 | 高 |
| 状态模型 | 终端状态与业务结果分维 | 单状态简单，但无法区分“进程停了”和“任务为何停” | 高 |
| 权威链 | 三重锁：active-plan CAS（生效计划切换前先核对版本，防并发改写与旧版覆盖）+ authority generation（届次编号，换届后旧届动作整体作废）+ immutable launch receipt（不可改的启动派工单，无单的 agent 一律不认） | 只看 DONE/result 文件无法拒绝旧 attempt（尝试轮次）的迟到结果 | 高 |
| 人工决策 | `decision_required`（等人决策）是原 session（会话）内的非终态 checkpoint（进度快照，非最终结果）；用户回答后 agent 自然继续，Runner 只冻结依赖节点 | 让 Runner 捕获、转发或确认回答会重复介入已经继续运转的会话，并增加不必要的控制面 | 高 |
| 前置阻塞 | 交接后退出，重编排补前置，fresh agent（全新拉起、不带旧会话上下文）恢复 | 长期保留旧会话会占资源且上下文可能过时 | 中 |
| PoC 终端 | `psmux`，可见交互 + 精确 session 身份 | Windows Terminal 普通 tab 更直接，但当前不能证明准确退出；2026-08-15 用户定：DHR_03 开工前按 A7 同一判据对 orca（仅作纯终端宿主候选）做一次 preflight 实测再定后端，psmux 为默认；若改选 orca 须先修订本决策 | 中 |

## 2. 全局地图与角色边界

### 2.1 运行地图

```text
已确认 Design + DevPlan
          │
          ▼
一次性编排 agent ──写──> RelayPlan proposal v1 ──Runner CAS 晋级──> active plan
                                                                    │
                                                                    ▼
                                           自动打开可见 psmux worker A
                                                                    │
                         ┌────────────── succeeded ──────────────────┤
                         │                                          │
                         ▼                                          ▼
                    下一阶段 / review                     dependency_blocked
                                                            交接 + ack + 退出
                                                                    │
                                                                    ▼
                                                一次性重编排 agent 写 proposal v2
                                                                    │
                                                   Runner 校验/CAS 晋级并先跑 B
                                                                    │
                                                                    ▼
                                                       B 完成后 fresh A 恢复
```

图中"proposal → Runner CAS 晋级 → active plan"的读法：

- **proposal（提案）**：编排/重编排 agent 写出的计划只是候选，写完不等于生效。
- **CAS 晋级（compare-and-swap，比较后交换）**：Runner 让计划生效时，先核对"当前生效的版本/届次是不是我预期的那个"，对得上才原子切换 active-plan 指针，对不上就拒绝。作用类似改共享文档前先看版本号：防止两个流程同时改，也防止过期的旧计划覆盖新计划；生效永远是一次原子动作，不存在"改了一半"的中间态。

### 2.2 角色边界

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户 | 确认 Design/DevPlan；处理 `decision_required`；做人验与 verify 确认 | 不负责轮询 agent 状态或搬运普通交接信息 |
| 编排 agent | 根据已确认输入生成一版 RelayPlan proposal；解释依赖、串并行、角色与恢复点 | 不常驻、不监控、不施工、不直接改 active plan |
| 重编排 agent | 判断阻塞是否成立，提出最小计划修订 | 不绕过人闸，不改变已确认目标/验收，不直接激活计划 |
| 诊断 agent（一次性·只读） | `interrupted_unknown` 等异常后由用户显式触发，读取现场并追加诊断结论/建议事件（见 §4.4） | 不常驻、不写 active state、不改计划、不重启会话；P1 不自动拉起 |
| Runner | 管 authority、session 身份、文件校验、原子晋级、合法转换、依赖冻结、拉起/回收 | 不读代码作质量判断，不替 review，不替用户决策，也不读取、转发或恢复原 session 内的人工回答 |
| 施工 worker | 按 brief 施工、测试、写结果和完整交接 | 不改 active plan，不改 Runner 状态，不把自评当复核 |
| review lead（目标形态） | 汇总独立 reviewer 结论，决定是否请求返工 | P1 PoC 暂不实现；不替用户签收 |

## 3. 状态、权威与文件契约

术语速览（人话对照，正式定义以下文各节为准）：

| 术语 | 人话 | 正式定义 |
|---|---|---|
| RelayPlan | 接力计划表：谁先跑、谁后跑、谁依赖谁、每棒什么角色 | §3.2、§3.3 |
| authority | 当前"届次"凭证：现在生效的是第几版计划、第几届授权，旧届动作一律作废 | §3.2 |
| launch receipt | 启动回执：Runner 每拉起一个 agent 前先写一张不可改的"派工单"，没有回执对应的 agent 一律不认 | §3.2 |
| result | 每一棒交出的结构化结果文件（`result.json`） | §3.1、§3.3 |
| handoff | 交接包：下一棒不翻旧会话、只读它就能继续 | §3.3 |
| event | 只追加的事件流水账（`events.jsonl`），不可变历史 | §3.3、§3.4 |
| 双维状态 | 终端维（进程/窗口是活是死）+ 业务维（任务干到哪了）分开记录，用于区分"进程停了"和"任务为什么停" | §3.1 |
| CAS 晋级 | 计划生效前先核对当前版本是否符合预期，对不上就拒绝；生效是一次原子切换，防并发覆盖与旧版回写 | §3.2 |

### 3.1 两个状态维度

`terminal_state` 由 Runner 或终端宿主观察，v1 固定枚举：

| 值 | 含义 |
|---|---|
| `launching` | 已有启动意图和 receipt，session 尚未确认可用 |
| `running` | agent 当前回合正在执行 |
| `idle` | 当前回合完成，session 仍可交互，允许同上下文恢复 |
| `stopped` | 执行被可信停止事件中止，session 是否仍在由 session 探针确认 |
| `exited` | 精确 session 已确认不存在 |
| `unknown` | 宿主探测失败，Runner 不得猜测或推进 |

`result_status` 是 Runner 对当前 attempt 最新有效 checkpoint 或 final result 的业务投影，v1 固定枚举：

| 值 | 含义 | Runner 默认动作 |
|---|---|---|
| `working` | 尚未交棒 | 保持当前节点 |
| `succeeded` | 当前阶段交付完成，可进入 `next_action` | 校验后进入 review/下一阶段；不标任务完成 |
| `dependency_blocked` | 需要先完成其他任务 | 完整交接、ack、退出，暂停并拉重编排 agent |
| `decision_required` | 同一 attempt 需要用户选择或授权的非终态 checkpoint | 保持原 session 可交互；冻结依赖节点，无依赖并行节点继续 |
| `quota_exhausted` | 主通道为宿主/Runner 侧识别（CLI 退出码、错误特征）或可信宿主事件；worker 自报仅作补充——额度真正耗尽时 worker 通常已无法自行写出结果 | P1 降级：不实现识别与恢复通道，运行中额度耗尽一律按 `interrupted_unknown` 兜底；本枚举为目标形态预留 |
| `interrupted_unknown` | 进程消失或停住但没有可信原因/完整结果 | fail-closed，保存可得现场并等待诊断/人工处理 |

补充约束：

- `stopped_by_user` 是可信停止事件的 `interruption_reason`，不另占 `result_status`。
- task overall state 与当前 attempt result 分离。P1 Runner 只允许保持 `active` 或投影为 `paused`，不定义或写入任务完成/失败；`succeeded + next_action=review` 时任务仍为 `active`，后续 review/验收体系才有权改变质量结论。
- `decision_required` 不是 final result，不结束 attempt，也不要求可信人工响应事件。用户回答发生在原 session 内；Runner 只接受同一 authority/launch/session/attempt 后续写出的有效 checkpoint 或 final result，不读取或判断回答内容。
- attempt 的 final `result.json` 只在本棒实际交接或结束时写入，一旦原子晋级即不可改写。`decision_required` 只写 checkpoint，不得为了暂停而提前生成 final result。
- “停滞/卡住”不设枚举值：它不是可直接观测的事实，而是监控判断——终端仍在 `running/idle`、业务持续 `working`、且长时间无新 checkpoint/事件时，由 probe 策略按阈值识别并按 A6 fail-closed 处理（阈值随 DHR_01 契约参数冻结）。日常运维视角由此简化为两类需要关注的现场：已停下的终端（`idle/stopped/exited/unknown` 且无结果）与运行时长超阈值的终端；`running` 且未超阈值的默认无需关注。

P1 合法转换必须由 DHR_01 落成机器可读矩阵并逐项生成正反例；未列举转换一律拒绝。设计层固定最小规则：

- `terminal_state`：`launching` 只可到 `running/exited/unknown`；`running` 只可到 `idle/stopped/exited/unknown`；`idle` 只可由精确 session 宿主观测到新回合而转 `running`（包括人工回答后的自然继续，不需要 Runner 发 resume），或由 stop/probe 转 `stopped/exited/unknown`；`stopped` 只可经可信 resume 到 `running`，或经精确 probe 到 `exited/unknown`；`exited` 为当前 session 终态；`unknown` 不得自动推进业务，只能由可信诊断/probe 解析为观测到的终端状态。
- `result_status`：`working` 可写出 `decision_required` checkpoint，或形成四种结束/暂停结果；`decision_required` 只可由同一 authority/launch/session/attempt 的有效 `working` checkpoint 覆盖回 `working`，或由同一身份链的 final result 转到其终态；连续 probe 无法确认 session 时转 `interrupted_unknown`。上述路径均不需要人工响应事件；`quota_exhausted` 只可经当前 authority/session 绑定的可信恢复事件回到 `working`（目标形态规则；P1 不实现该通道）；`succeeded/dependency_blocked/interrupted_unknown` 结束当前 attempt，后续动作必须创建新 attempt 或进入计划中的下一节点。DHR_01 只能把这些规则展开为矩阵和收紧触发条件，不得新增出口。
- 终端转换与业务转换分别校验；任一维非法、缺事件或身份链不完整时整体 fail-closed，不允许另一维单独推进。
- 未列出的自环同样非法；心跳/probe 是只追加的观测事件，不制造状态转换。`running → idle` 只有在当前回合已闭合且没有待晋级的 result/handoff 写入时成立。

### 3.2 唯一权威链

每次执行都必须绑定以下身份：

```text
plan_version + plan_hash
authority_generation
node_id + attempt_id
launch_id + session_id
```

编号速查（每层各拒收一类"冒牌货"；正式规则以下方条款与 §3.3/§3.4 为准）：

| 层级 | 编号 | 回答什么问题 | 什么时候变 | 对应身份链/文档位置 |
|---|---|---|---|---|
| 0 | `run_id` | 这是哪一场接力 | 每从头跑一场新接力换一个 | 不在身份链内；§3.3 运行现场目录根 |
| 1 | `plan_version` + `plan_hash` | 按哪版计划干活（hash=内容指纹，防篡改） | 每次（重）编排产出新提案 +1 | 身份链第 1 行；§3.3 `plans/`、`active-plan.json` |
| 2 | `authority_generation` | 现在是第几届授权 | 新计划 CAS 晋级生效即换届，旧届整体作废 | 身份链第 2 行；§3.3 `authority.json` |
| 3 | `node_id` + `attempt_id` | 计划里哪个任务节点、第几次尝试 | node 随计划定死；同一节点每次重新开工 attempt +1 | 身份链第 3 行；§3.3 `attempts/<node_id>/<attempt_id>/` |
| 4 | `launch_id` + `session_id` | Runner 的哪张派工单、终端的哪个会话 | 每次实际拉起 agent 发一张派工单，会话句柄随之绑定 | 身份链第 4 行；§3.3 `launches/`、§3.4 宿主观测 |
| 另 | `nonce` | 控制事件的一次性编号，防同一指令被重放 | 每条控制事件一个 | 不在身份链内；§3.4 |

规则如下：

1. 编排 agent 只写不可变 `relay-plan.vN.proposal.json`。
2. Runner 校验 schema、hash、依赖无环和权限边界后，用 `expected_generation + plan_hash` CAS 晋级唯一 active-plan pointer。
3. Runner 在 spawn 前写不可变 launch receipt；receipt 成功后才能启动 agent。
4. `result.json` 与 handoff 必须交叉绑定完整身份链。
5. 迟到、重复、错版本或错 session 的结果只能追加 `stale/rejected` 事件，不得推进 active plan，也不得关闭当前 session。
6. probe error、CAS 冲突、半写、坏 JSON、身份不一致一律 fail-closed。

### 3.3 文件所有权与提交顺序

运行现场由 canonical runtime layout 为 `dh-relay` 解析独立模块命名空间；概念结构如下：

```text
.dh-runtime/<dh-relay-canonical-namespace>/<run_id>/   # 一次接力运行的完整档案袋
├─ plans/relay-plan.vN.proposal.json   # 候选计划（各版本只增不改，未晋级不可执行）
├─ active-plan.json                    # 指针：当前生效的是哪版计划
├─ authority.json                      # 当前届次凭证（generation）
├─ launches/<launch_id>.json           # 启动回执：每次拉起 agent 的不可变派工单
├─ attempts/<node_id>/<attempt_id>/    # 每个任务节点、每次尝试各一套工作档案
│  ├─ handoff.md                       # 交接包：下一棒只读它即可继续
│  ├─ session-tail.txt                 # 终端输出尾部，先脱敏再限长，仅辅助证据
│  ├─ checkpoint.json                  # 本次尝试的非终态进度快照（含 decision_required）
│  ├─ result.json.tmp                  # 结果草稿（worker 写）
│  └─ result.json                      # 结果定稿（宿主原子晋级后不可改写）
├─ relay-state.json                    # Runner 的全局状态快照
└─ events.jsonl                        # 只追加的事件流水账（不可变历史）
```

| 工件 | 唯一写者 | 权威性 |
|---|---|---|
| RelayPlan proposal | 编排/重编排 agent | 候选；未被 Runner 晋级前不可执行 |
| active plan / authority / receipt / relay-state / events | Runner | 运行权威 |
| checkpoint / handoff / session tail / result tmp | 当前 attempt worker | checkpoint 是同一 attempt 的非终态进度；其余为 result 前置材料；session tail 仅辅助证据 |
| final result | 宿主侧原子晋级 | 当前 attempt 的业务结果，仍须经过身份与转换校验 |

正常交棒顺序固定为：先写自足 `handoff.md`、脱敏限长的 session 尾部、changed paths/tests/Git snapshot，再写 `result.json.tmp`；宿主校验后原子晋级 final，Runner 记录 ack，最后才按结果挂起或回收精确 session。`decision_required` 只原子替换当前 attempt 的 `checkpoint.json`，不走 final result 或交棒顺序。

`checkpoint.json` 只保存当前 attempt 的最新投影；每个被接受或拒绝的 checkpoint 都必须在全局 `events.jsonl` 留下身份链、状态、摘要和原因，作为不可变历史。DHR_01 还必须冻结 `session_tail_max_bytes` 的默认值、合法覆盖入口和“先脱敏、再限长”的顺序；超长与含凭据 fixture 必须分别证明不会把原值带入 final 工件。

### 3.4 可信控制事件与会话内回答边界

DHR_01 必须冻结 Runner 控制事件的 actor、source、nonce、occurred_at、plan/attempt/session 绑定和防重放规则（P1 降级：nonce/防重放仅冻结字段定义，不做逐项重放攻击测试，随目标形态补齐——单机单人场景该威胁极低）：

- 普通人工回答属于原 agent session 的交互，不是 Runner 控制事件。Runner 不捕获输入、不解析 transcript/stdout、不保存回答或摘要、不转发输入，也不调用 resume；agent 在同一 session 收到回答后自然进入下一回合。
- Runner 只消费当前 authority/launch/session/attempt 写出的 checkpoint、final result 与宿主 session 观测。后续有效 `working` checkpoint 或 final result证明该 attempt 已继续；Runner 不需要、也不得补造“用户已回答”事件。
- 可信控制事件只覆盖外部 stop、额度恢复等 Runner 级动作；旧 generation、错 session、重复 nonce 的控制事件全部拒绝并留事件账。
- `quota_exhausted` 主通道是宿主/Runner 侧识别（CLI 退出码、stderr 错误特征）与可信宿主事件；worker 自报（绑定结果）仅作可遇不可求的补充。无法证实时归 `interrupted_unknown`，不得猜测。P1 降级：整条识别与恢复通道不实现，一律走 `interrupted_unknown` 兜底。

## 4. 固定流转

### 4.1 正常完成与复核返工

- worker 写 `succeeded` 表示本棒可交付，不表示代码质量通过。
- Runner 根据 RelayPlan 的 `next_action` 拉起 review 或下一阶段。
- 目标形态允许 review 后保留并恢复原施工 session，但 P1 不实现或验收这条恢复路径。
- P1 只锁住 `succeeded` 不得直接完成任务；完整 review lead、并行 reviewer 与 review 返工恢复留后续阶段。

### 4.2 需要人类决策

- worker 写 `decision_required`、问题、已尝试内容、选项与风险，然后结束当前回合但不退出 session。
- Runner 将 session 观测为可交互等待，不启动 replanner、不推进依赖该决定的节点；无依赖的并行节点照常运行。
- 用户在同一 session 回答后，agent 自然继续当前 attempt。Runner 不介入这次问答；它只等待同一身份链上的后续 checkpoint 或 final result，再按依赖与结果调度。

典型场景：删除文件或破坏性 Git 操作、A/B 方案选择、多轮修改仍失败且要换方向、权限或目标边界不清、人机多轮配合操作（如在测试服务器上由人代为执行命令并回贴输出，多轮往返直至该阶段完成）。

多轮配合场景的语义补充：worker 在进入需要人配合的阶段时写一次 `decision_required` checkpoint 即可；其后的多轮往返都是原 session 内的普通交互，Runner 不感知、不计数，直到 agent 写出后续 `working` checkpoint 或 final result 才恢复对该节点的调度。期间依赖该节点的后续节点持续冻结，属预期行为，不另设枚举或事件。

### 4.3 前置任务阻塞与重新编排

1. A worker 写 `dependency_blocked` 和完整交接包。
2. Runner 校验并 ack 后，回收 A 的精确 session。
3. Runner 自动打开一次性重编排 agent；它判断阻塞是否真实并写 v2 proposal。
4. 只有“不改变已确认目标/验收、仅新增无环前置节点、恢复条件明确”的 proposal 才可自动 CAS 晋级。
5. 涉及方案选择、删除/权限、目标或验收变化、依赖成环/多解时转 `decision_required`。
6. Runner 拉 fresh B worker；B 完成后再拉 fresh A attempt，注入 A 的交接包与 B 结果。
7. 旧 A 的任何迟到结果均标 stale，不得影响 fresh A。

### 4.4 外部停止、OOM、额度和窗口消失

- agent 活着时可以知道自己准备停止并先交棒；agent 已被外部停止后不能自行补写结果。
- Runner 只有跟踪精确 launch/session，才能观察 session 是否消失；无法可靠推断消失原因。
- 人手动停止若未经过 Runner/可信宿主事件，不能写 `stopped_by_user`，只能进入 `interrupted_unknown`。
- Runner 保存可得的 session tail 与 Git 现场并暂停；P1 不自动拉诊断 agent，只允许用户显式触发一次性只读诊断。诊断结果只能追加事件/建议，不得写 active state。
- `quota_exhausted` 需要可信额度恢复事件；`decision_required` 不设 Runner 解闸事件，由同一 session 内 agent 的后续 checkpoint/final result自然覆盖暂停投影。若额度结果提交时精确 session 仍存在，Runner 保持该 session `idle`；若 session 已退出，只保留暂停事实，恢复时创建 fresh attempt，不伪造原 session 可恢复。P1 降级（2026-08-15 用户确认）：quota 识别与恢复通道不实现，运行中额度耗尽一律按 `interrupted_unknown` 兜底；本段恢复语义属目标形态，且任何阶段都不故意消耗真实额度。
- `decision_required` 挂起期间 Runner 继续按有界策略 probe 精确 session；连续 probe 无法确认 session 存活时，终端转 `unknown`、业务转 `interrupted_unknown`，不得继续宣称原 session 可恢复。具体间隔与次数由 DHR_01 契约参数冻结，不在设计层写死秒数。

## 5. P1 最小 PoC 操作剧本

1. 给定已确认的 fixture Design/DevPlan，Runner 自动打开一次性编排 agent，产生 RelayPlan v1 后退出。
2. Runner 自动打开可见、可交互的 `psmux` A worker。
3. A 报告缺少前置 B，写完整交接包；Runner ack 后确认旧 A session 已退出。
4. Runner 自动打开重编排 agent，产生 v2：`B → fresh A`。
5. B worker 完成；Runner 启动 A attempt 2，并把 A attempt 1 的交接与 B 结果作为输入。
6. 注入 A attempt 1 的迟到 result，证明只产生 stale event，active state 不变。
7. 另跑一个带依赖与无依赖并行节点的 `decision_required` fixture：原 session 保持可交互，依赖节点冻结、无依赖节点继续；用户在原 session 回答后 agent 自然继续，Runner 不读取回答、不调用 resume，只凭同一身份链的后续 checkpoint/final result 继续调度。
8. 用户查看终端时间线、状态快照、事件账和截图，判断接力体验是否比常驻主控巡检更清楚；5 分钟仅是展示时长建议，不是验收阈值。

## 8. 边界

- **不做**：P1 不实现完整 workspace→施工→并行 review→返工生产流水。
- **不做**：P1 不验证 review 返工时保留/恢复原施工 session；该能力随完整 review 流水另行 A/B。
- **不做**：P1 不做通用多任务 DAG 调度、跨机器、统一终端 UI、只读归档 tab。
- **不做**：不让 agent 自动替用户批准删除、权限、方案或目标/验收变化。
- **禁改**：现有 `dh-crew` controller/loop 协议、active state、DevPlan、workspace 与用户在途 WIP。
- **禁混**：`dh-relay` 不读取 `dh-crew` 的运行状态；通用终端原语只能通过明确 adapter 边界复用。
- **凭据**：任何账号、token、key 或凭据值不得进入计划、交接、session tail、事件、测试和提交。
- **验收表述**：P1 通过只能称“状态接力 PoC 通过”，不能宣称完整生产编排完成。
