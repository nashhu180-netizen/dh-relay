# P6 身份与额度治理契约调整

## 1. 目标与边界

### 目标

在不读取或记录凭据值的前提下，让一次启动与一次 fallback Attempt 都能证明其冻结的执行身份；无合法 fallback 时安全停在既有人工等待语义，并留下持久、可追溯的 Attention。

### 非目标

- 不做自由账号切换、自动登录、账号配置写入、凭据管理或读取凭据值。
- 不新增核心 `paused` 枚举；“已暂停等待处理”只是用户可见文案。
- 不修改历史 `design/02`；若候选获批，改以新的当前有效 P6 补充设计承接。
- 不让控制客户端的切换改变既有 Attempt / Result 的执行身份。

## 2. 冻结决策

### D1 · 版本化 Receipt 身份快照

真正承载 Attempt / checkpoint / Result 身份链的 Attempt Receipt 新增版本化合同（候选名 `relay.attempt-receipt/v1`），由 `workflow-driver` 的 `openAttempt()` 在**开立 Attempt 时**冻结以下脱敏身份对象及其有序 fallback 路由快照：

```json
{
  "executor_identity": {
    "executor_profile_id": "herdr.codex.<approved-alias>",
    "account_alias": "<approved-redacted-alias>",
    "config_fingerprint": "<sha256>",
    "executor_capability_hash": "<sha256>"
  },
  "fallback_profile_snapshots": [
    {"executor_profile_id":"herdr.codex.<approved-alias>","account_alias":"<approved-redacted-alias>","config_fingerprint":"<sha256>","executor_capability_hash":"<sha256>"}
  ]
}
```

- 只允许 profile registry 的已登记字段派生；`account_alias` 是已批准的脱敏别名，两个 hash 不得由凭据值或完整敏感环境计算。
- 原 `relay.launch-receipt/v2` 仍只表达 start/control 操作回执，保持可读且不承载 Attempt 身份；不得仅升级它而遗漏真正的 Attempt 链。
- `fallback_profile_snapshots` 是源 profile 的 `fallback_profile_ids` 按 routing-priority 顺序解析后的唯一完整身份快照（可为空）；其 Receipt schema、持久化和重放输入**复用** D2 容量约束：最多 6 项，`executor_profile_id` 为 ASCII `[A-Za-z0-9._-]{1,96}`、`account_alias` 为 ASCII `[A-Za-z0-9._-]{1,48}`、hash 为 64 位小写 hex。自动 fallback 和 pause 的人工可选列表只能从这份 Receipt 快照派生，重启或 registry 变更不得重新计算或扩大它。Attempt Receipt 的 schema 校验、Store 持久化/重放和 checkpoint/result 的当前身份校验必须消费同一份快照。此决定是协议变更，必须由前置契约卡拥有 `contracts/**`、`workflow-driver`、Store 与必要测试路径；DHR_34 不越界承接它。
- `config_fingerprint` 固定为 `config-fingerprint/v1`：前置卡将 `config_fingerprint_rule.fields` 从字符串数组升为唯一、按现役 `CANONICALIZATION.md` 的 UTF-16 code-unit 升序的 `{pointer, classification:"nonsecret"}` 数组；每个 Pointer 均须显式标为 `nonsecret`。哈希输入固定为 `{algorithm, executor_profile_id, path_template, fields:{pointer:value}}` 的 RFC 8785 规范化 JSON；任何 Pointer 缺失、未标 `nonsecret` 或命中敏感字段均拒绝签发。Receipt 只保存 hash，不保存投影值。
- `executor_capability_hash` 固定为 `executor-capability/v1`：哈希输入为 `{algorithm, executor_profile_id, capabilities, supported_platforms, headless_supported}` 的 RFC 8785 规范化 JSON，其中数组先去重并按现役 `CANONICALIZATION.md` 的 UTF-16 code-unit 升序。不得混用 Runtime/Host handshake capability hash。

### D2 · 无 fallback 的等待语义

当 quota 分类为高置信、但没有可用且预登记的 fallback 时：

1. 不签发新的 Attempt，不切换账号，不产生终态 Result；
2. **一次原子暂停事实**：前置卡扩展既有 `relay.event/v2`（不另起无接收方的事件信封），加入 `kind=fallback_pause_created`，并规定该 kind 必须有非空 `node_id`、`attempt_id`、`reason=E_FALLBACK_UNAVAILABLE`，且 `event.at == raised_at`。其 `detail` 保持现有 string 类型，但值**必须是** `relay.fallback-pause/v1` 的 RFC 8785 canonical JSON UTF-8 文本；前置卡同时提供 payload schema 与“解析 detail 后校验”的语义 validator，禁止把对象塞进现有 string 字段或用自由文本替代。payload 字段固定为 `{pause_id, run_id, node_id, attempt_id, receipt_id, reason_code, raised_at, fence, attention, manual_retry_profiles}`，其中 `reason_code=E_FALLBACK_UNAVAILABLE`，`pause_id=sha256("fallback-pause/v1\n" + run_id + "\n" + node_id + "\n" + attempt_id + "\n" + receipt_id + "\n" + reason_code)`。`manual_retry_profiles` 从 Receipt 的 `fallback_profile_snapshots` 按原序筛选得到，元素为 `{executor_profile_id, account_alias, config_fingerprint, executor_capability_hash}`（可为空）；它只供人工显式选择，不表示曾满足自动切换条件。profile registry schema/validator 必须限制源 fallback 列表及每个脱敏字段的长度，并在注册时按最长合法 ID、时间戳和六个 snapshot 构造此 JCS payload，拒绝任一可能超过现役 `event.detail.maxLength=4096` 的配置；因此合法 registry 的安全 pause 永远可落账，不能在 quota 发生时才因尺寸失败。它在一条已有事件信封、可重放的记录中同时承载下列两个规范对象，禁止拆成多次非原子 append：
    - **容量约束**：profile registry schema 固定 `fallback_profile_ids.maxItems=6`、`executor_profile_id` 为 ASCII `[A-Za-z0-9._-]{1,96}`、`account_alias` 为 ASCII `[A-Za-z0-9._-]{1,48}`，两个 hash 均为 64 位小写 hex。validator 在注册时以 relay.common 各 ID 的 schema 最大合法 UTF-8 代表、RFC3339 毫秒时间戳最大代表及六个 snapshot 构造 JCS payload，必须证明 `Buffer.byteLength(detail,"utf8") <= 4096`，否则拒绝 registry。任何放宽上述 ID/时间戳 schema 的变更必须同时重跑该容量证明并在失败时拒绝发布；因此合法 registry 的安全 pause 永远可落账，不能在 quota 发生时才因尺寸失败。
    - `fence` 为 `relay.attempt-fence/v1`，字段 `{fence_id, attempt_id, receipt_id, reason_code, fenced_at}`；`fence_id=sha256("attempt-fence/v1\n" + run_id + "\n" + node_id + "\n" + attempt_id + "\n" + receipt_id + "\n" + reason_code)`。重放建立 fenced `(attempt_id, receipt_id)` 集合；`appendCheckpoint` 与 `appendResult` 必须在当前 Receipt 判定**之前**检查该集合并以 `E_ATTEMPT_FENCED` 拒绝。
   - `attention` 为 `relay.attention/v1`，字段 `{attention_id, run_id, node_id, attempt_id, receipt_id, reason_code, state:"open", raised_at}`；`attention_id=sha256("attention/v1\n" + run_id + "\n" + node_id + "\n" + attempt_id + "\n" + receipt_id + "\n" + reason_code)`。
    Store 必须以 `pause_id` 唯一索引实现 `appendFallbackPause`：首次调用在同一持久化提交中写入该**唯一**事件及索引；同一 `pause_id` 且完整 canonical `detail` 完全相同，返回既存 event/seq 而不追加新 seq；任一字段、嵌套 ID、时间戳或 canonical 字节不同则 `E_FALLBACK_PAUSE_CONFLICT`。所有 pause/retry 多文件变更都必须经 `relay.store-mutation/v1`，其唯一耐久顺序与恢复规则以下方“journal 更正”为准；在 mutation 恢复完成前该 Run 一律拒绝读写/订阅，任一 journal/blob 缺失、摘要不符或无法补全均为 `E_STORE_MUTATION_RECOVERY_FAILED` 并 fail-closed。`raised_at == event.at == fence.fenced_at == attention.raised_at` 且三个派生 ID 必须逐字复算匹配，否则 `E_FALLBACK_PAUSE_INVALID`。一次成功重放必须同时导出 fence、节点 `waiting_human` 与 open Attention；三者缺一、事件截断或损坏均为坏账并 fail-closed，不允许继续该 Run。物理宿主停止请求可另行执行，但不得以是否已退出作为 fence 生效条件；
    - **journal 更正**：`relay.store-mutation/v1` 的提交顺序固定为：先完整写入 immutable staging blob、fsync blob 并原子发布/同步其目录；再写入引用该已发布 blob 的 `prepared` journal、fsync journal 并同步其目录；随后写目标，最后原子写 `committed` marker。journal 含事务 ID、幂等键、事件 seq、每个目标的版本前置条件/hash；blob 保存该目标完整 canonical 内容与 sha256。恢复 `prepared` 时逐目标判定：目标已等于 staging hash 则视为已应用；否则仅当仍等于版本前置 hash 才从 staging 重写并校验；两者皆非才 fail-closed。全部目标成为 staging hash 后才标 `committed`。journal/blob 任一缺失、摘要不符或无法补全均为 `E_STORE_MUTATION_RECOVERY_FAILED` 并 fail-closed；二者只含既可进入 Receipt/事件的脱敏对象，成功后按审计保留规则回收。
  3. 当前节点进入既有 `waiting_human`，Run 投影为 `waiting_human` / `needs_you`；
4. 用户选择**兼容旧客户端**：现有 `relay.rpc/v1` endpoint、其握手/descriptor capability hash、全部既有参数和成功 payload 冻结不变；旧二进制客户端无需新增参数即可继续连接。前置卡新增固定地址、独立于 v1 的 `relay.rpc-bootstrap/v1` endpoint；新客户端向该 endpoint 发 `{protocol:"relay.rpc-bootstrap/v1"}`，成功返回有 schema 的 `{protocol:"relay.rpc-descriptor/v2", endpoint, capability_hash, methods_schema, read_model_versions:["v1","v2"]}`，再连接独立 `relay.rpc/v2` endpoint。v2 的 request/response/stream envelopes 与 `listRuns`、`inspectRun`、`subscribe`、`retry-with-profile` 方法 schema 都在该卡冻结；v2 客户端才显式传 `read_model_version=v1|v2` 并取得 `relay.client-read-model/v2`。bootstrap 或 v2 不存在时，新客户端可按既有 v1 降级。旧 v1 客户端在没有 open Attention 的 Run 上行为与字节形态保持不变；它请求的列表或目标若含 open Attention，则使用既有 v1 标准 RPC error 形态返回 `E_ATTENTION_REQUIRES_READ_MODEL_V2`，绝不筛掉项目。v1 `subscribe` 建立时有 open Attention 同样拒绝；若订阅后才在一个 mutation 中创建 Attention，持久化的仅是该 Attention 账本事实而非连接资格：对仍存活的 v1 连接，publisher 在 mutation commit 后、发布该 mutation 的 `fallback_pause_created` / `run_state_changed` 前，以既有 v1 stream-close/error 语义强制关闭并移除；进程崩溃会天然断开所有连接，恢复后依据持久化 open Attention 拒绝新 v1 subscribe，不尝试重建连接或 ineligible 集。v2 才可收到 `open_attentions[]` 和前置卡新定义的 `relay.subscription-terminal/v1` `{code, run_id, caused_by_seq}`。服务不得静默省略字段；
5. 只有人工明确 `retry-with-profile` 才可创建新 Attempt：仅 v2 RPC 参数固定为 `{run_id, node_id, pause_id, executor_profile_id, retry_request_id}`，其中 `retry_request_id` 为调用方生成的 sha256 格式幂等键。UI 只展示 pause 中已冻结 profile 的脱敏 `account_alias` 供选择。Store 以 `(pause_id, retry_request_id)` 唯一索引，在一个持久化事务内验证 pause 仍 open、`executor_profile_id` 存在于 `manual_retry_profiles`、当前 registry 的该 profile 仍与冻结 `{executor_profile_id, config_fingerprint, executor_capability_hash}` 全等且其非敏感配置规则仍通过；然后追加一个 `relay.event/v2:fallback_pause_resolved`（其 `detail` 是有 schema 的 canonical `relay.fallback-pause-resolution/v1`，含 `pause_id`、`attention_id`、`executor_profile_id`、`retry_request_id`、`resolved_at`、新 `attempt_id` 与 `receipt_id`）并开立新 Attempt Receipt。相同幂等键必须返回同一 resolution/new Attempt；不同键重试已关闭 pause 返回冲突。任一校验、事件追加或开立失败则全部不做。重放该 resolution 才会关闭 Attention；旧 Attempt 永远保持 fenced，`resume` 不得复活它。UI 可将上述组合显示为“已暂停等待处理”。

`paused` 不成为新的 Store/Run 枚举。`relay.attention/v1`、旧 Attempt 的 fence 与 `E_FALLBACK_UNAVAILABLE` 是本调整的正式协议责任，不得用自由文本或仅有页面文案替代。

### D3 · fallback 必须是 fresh Attempt

只有 quota 高置信且目标 fallback 为**合格的预登记条目**时，才允许开立新 Receipt + 新 Attempt。`fallback_profile_ids` 是唯一且有序的 routing-priority 列表，前置 registry schema 与 validator 一并拒绝重复/未知/无序编码和不能保证 pause detail 容量的条目；选择规则是“按 Receipt 的 `fallback_profile_snapshots` 原序的第一个合格项”。合格 = 目标 snapshot 存在、当前 registry 的对应 profile 与 snapshot 全等、平台匹配、其 `config_fingerprint_rule` 全部通过且 registry 校验通过；实际启动失败不得被解释为再次自动切换。暂停后的人工选择只能使用 pause 创建时冻结的 `manual_retry_profiles`，且必须再次通过上述“全等快照 + 非敏感配置”校验；事后 registry 变更不扩大原 pause 的选择集。

新 Attempt 不得复用旧 `attempt_id`、`receipt_id` 或旧身份快照；旧 Attempt 只保留历史，不得再接受成功/失败/检查点写入。

普通、权限、网络或不可分类错误均不触发 fallback；`registry unavailable` 与 `fallback unavailable` 必须是两个独立负例。

## 4. 拟议计划调整（尚未生效）

1. B-adjust 发一个新的、独立的前置契约卡（ID 由 DevPlan 当次唯一发放），负责 D1/D2 的 Attempt Receipt（含 fallback routing snapshot）、`relay.event/v2` 两种 fallback 事件及其 canonical-detail validators、detail 容量上界 validator、可恢复 Store mutation journal、pause/retry 幂等索引与事务、fence、Attention 及 resolution 折叠、冻结 `relay.rpc/v1`、固定地址的 bootstrap/v2 envelopes/method schemas 与 subscription publish barrier、registry 非敏感字段与 fallback 顺序校验、兼容性与定向测试；任务类型/档位由 B 审核冻结，预期为标准档。
2. DHR_34 改为依赖该卡，仅保留 D3 的 quota 分类、fallback 编排与回归；允许路径不包含 `contracts/**`、签发服务或 Store。
3. DHR_35 继续依赖 DHR_34 的已冻结身份链，不因本调整提前开工。

## 5. 反例与止损

- 不能以 `event.detail` 的自由文本替代 Receipt 身份快照。
- 不能用“页面看起来暂停”掩盖不存在的持久等待状态或 Attention。
- 不能只记录 fence/Attention 文本：缺少所列协议字段、幂等键、重放或拒收规则时一律未满足。
- 不能把 `registry unavailable` 误判成“没有 fallback”并自动切换。
- 若 v3、Attention 稳定原因码或旧 v2 兼容任一项无法在前置契约卡范围内证明，停止并新开设计调整；不得把协议债转嫁给 DHR_34。
