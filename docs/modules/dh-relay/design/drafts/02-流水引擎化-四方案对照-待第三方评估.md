## 第一部分：你需要知道的背景

### dh-relay 是什么

一套**接力执行**系统。一张开发任务卡（来自 dev-harness 方法论）由多个 AI agent 接力跑完，**中间没有常驻 AI 主控**，人只在该出手时出手（落户确认、决策、收口确认）。

每张卡今天固定跑 **11 棒**：

| 棒 | 干什么 | 谁跑 |
|---|---|---|
| 1 | workspace 落户（建任务树 + 8 件套文档） | agent |
| 2 | 施工 | agent |
| 3 | 机器闸（跑 `dh <模块>` + 该卡测试） | **脚本**，宿主执行 |
| 4 | 代码复核 R1（fresh，只读） | agent |
| 5 | 代码复核 R2（fresh，可读 R1） | agent |
| 6 | 汇合出 verdict | agent |
| 7a | 集成/端到端（**可选**，开关 `integration=true`）——含本地合 test、e2e 脚本、条件远端 push、人机多轮取证 | agent + 人 |
| 7b | 需求与一致性复核 | agent |
| 7c | 教训复核 | agent |
| 8 | 收口备料（manifest、as-built、交付汇报、证据展示） | agent |
| 8' | finalizer（squash + verify + 快进 master） | **脚本**，Runner 签发 |

外加 run 级两个：棒 0（接力计划生成，一 run 一次）、run 尾（archive 归档）。

### 今天的授权模型（关键，四个方案都得跟它兼容）

```
用户在对话里授权
   → 主会话落 authorization-request（只是请求）
   → 宿主校验后原子生成 authority-snapshot.json（不可变，唯一授权真源）
   → planner agent 按固定模板实例化，只填槽位
   → Runner 晋级前拿 snapshot 校验 planner 输出「语义等价」，不符即拒
```

snapshot 冻结的东西：卡集合、每张卡的 DevPlan 行与目标/验收/变更范围、所依据文件的 Git blob 哈希（两级：整文件 + 逐卡片段）。

**注意 snapshot 今天不冻结什么**：图拓扑、宏列表、边、触发条件、开关。

### 现状进度

- 代码只实现到 P1：角色枚举只有 `worker/reviewer/replanner`，plan 是一份手写 JSON 的 nodes 数组。
- P2（十八张卡 `DHR_04`~`DHR_21`）：`DHR_04` **进行中**，`DHR_05`~`DHR_21` 全部**未开始**。
- `tools/` 下的 `templates/`、`cli/`、`finalizer/`、`archive/`、`oracle/` 目录**都还不存在**。
- 另有 P3（`DHR_22`~`DHR_24`，终端后端可配置化），未开始，与本议题基本正交。

## 第二部分：用户的原始诉求（逐字，未经改写）

> 「我想做成可编排的流程引擎」

追问目的时的回答：

> 「dev-harness 可以和其他流程拼接。比如：做完一个任务更新周报。未来的dev-harness修改.」

**已拍板的三项**：
- 外部动作失败**不阻断**原任务，走 outbox（卡照常收口，外部动作有自己的成功/失败/重试状态）
- 周报写**另一个仓**
- 周报仓的消费链**不进本次增量**（本次只做本机不可变 outbox + 反伪造）

**未拍板**：外层到底要多自由（本文要评的核心）；`dev_harness_card@v1` 是否必须等于今天的 11 棒。

## 第三部分：已经被否掉的第零版（供理解洞在哪）

**第零版**：撤掉模板等价校验，改用一张 5 条红线的**不变量校验器**——planner 交任意图都行，Runner 只静态校验红线未被破。

**被 codex（gpt-5.6-sol / xhigh）判 P0 不通过**，核心理由：

> **红线清单 ≠ 授权清单。** 模板不只是形状检查，它**同时框死了 planner 能发起的动作集合**。撤掉模板后 planner 从「填表人」变成事实上的**权限授予者**——可以选用户从未授权的 prompt、脚本、外部动作。卡号合法 ≠ 动作合法。

安全公式应为 `计划的副作用 ⊆ 授权的许可`。codex 并指出：若坚持全动态图，**16 条不变量缺一不可**（授权集合闭包、策略版本冻结、逐卡支配关系、当前候选绑定、变更失效传播、执行者真实性……）。

原 5 条里**三条语义本身就错**：
- 「≥2 个不同 `profile_id` 的复核」——正式口径是「账号可同、**会话必不同**」（`design/02:59`）；`profile_id` 只是注册表标签，两个 profile 可指同一账号 → 既误放又误杀
- 「每卡恰好一个 finalizer」——与「closeout 前取消的卡走 cancelled-exempt」冲突（`design/02:68`）
- 「`lesson_review` 必须存在」——要的是真 launch + result + 三终态（`design/02:278`）；**图里有节点 ≠ 它真跑过**

## 第四部分：四个候选方案

### 方案 A · 自由外层 DAG + 内层冻结宏（两层模型）

codex 建议方向，主会话据此写成草案。

- **外层**：DAG 自由拼「流程宏」——`dev_harness_card@v1`、`weekly_report@v1`、`archive@v1`、`human_verify@v1`
- **内层**：每个宏内部**固定**。`dev_harness_card@v1` 仍是 11 棒、仍走模板等价校验，一条断言不放宽
- **演化**：改卡内流程 → 发 `@v2`。snapshot 冻结版本号，老 run 绑老版本不受影响
- **外部效果**：relay 只 append 不可变事件，另一条独立授权的链去消费

**⚠️ 已被 claude-grok 判 P0 不通过**：

> C3 只管「多写了什么」，不管「**少跑了什么**」。少跑 R1/R2/lesson_review/收口确认**不产生额外写入**，子集关系仍成立。**越权从卡内挪到了卡间。**

**能过全部验收的绕过场景**：
1. 用户授权卡 `FOO` + 周报目的地；确认窗口显示宏集合 `{dev_harness_card@v1, emit_event@v1, archive@v1}`
2. planner 交图：`emit_event`（`depends_on=[]`）→ `archive`，**卡宏根本不实例化**
3. 副作用仍 ⊆ 用户批的摘要；「每节点须有合法 owner」只查**已存在**的节点；无依赖的 `emit_event` 是**第二源点**、不是孤儿（与现役 fixture `plan-v1-chain.json:13` 的节点 E 同形）
4. 周报被更新成「任务完成」，而质量棒**一次都没跑**

**补洞的代价**（grok 估）：必须同时做「整图冻结（节点+边+参数+触发谓词）+ 省略闸 + 参数面划线 + run 级 grant 字段定义」，工作量**接近被否的那条策略引擎**，只是粒度粗一层。

---

### 方案 B · 终态 hook + 单流水版本化 ← grok 首选

- 11 棒原样冻结为 `standard-pipeline@v1`
- 卡/run 到达终态时 append 一条 outbox 事件
- dev-harness 要改 → 发 `@v2`
- **不引入外层图**

**优点**：P0 **无从产生**（没有组图权就没有卡间越权）。用户两个诉求都满足：拼接靠 hook，演化靠版本发布。改动面最小。

**代价**：不能把宏插到任意位置。但用户举的场景「合并到 test 后登录服务器验证」**本来就在棒 7a**，不需要任意位置。

---

### 方案 C · 已发布 playbook（点选式）← grok 次选

- 预先审过并注册 2～3 条图：`card-only@v1`、`card-then-report@v1`、`card-then-human_verify-then-report@v1`
- 用户在建 run 窗口**点选**一条
- snapshot 冻结 `playbook_id + version + content_hash`；planner 只填槽

**关键性质**：**谁授权这张图 = 用户点的那条 playbook。** 编排权在用户手里，不在 planner 手里。

**代价**：新拼法要发 playbook 版本，不能即兴连线。

---

### 方案 D · 先把 P2 十八张按现行设计做完，引擎另开 A

`DHR_04` 已开工，后面 17 张未动。现在改写 B1/B3/B8/B9/B10/B12/B14/B15 等于**在第一张卡中途重开 A**。

**优点**：风险最低。**代价**：周报能力推后。

## 第六部分：请第三方评估者回答

1. **grok 那个 P0 成立吗？** 「子集公式对省略无解」这个论证对不对？方案 A 补洞的代价估计（≈ 策略引擎）是否夸大？
2. **四个方案里哪个最配用户那两句原话？** 请特别判断「过冲」这个指控——用户说「可编排的流程引擎」，他要的是 planner 的组图权，还是自己点选的编排权？
3. **方案 B 有没有被低估的缺陷？** 「终态 hook」够不够表达「做完 A 卡再做 B 卡然后一起发周报」这类需求？
4. **方案 C 的 playbook 数量会不会失控？** 每种拼法一条 playbook，长期是不是退化成方案 A 的手工版？
5. **有没有第五个方案？**
6. **`dev_harness_card@v1` 是否必须等于今天的 11 棒？** 背景：已知 relay 的 11 棒相对 dev-harness 方法论的 18 节点有**至少 9 处偏差**（代码复核轮 1 该前移进施工批次却放在施工后、收口棒把 5 个节点压成一棒、E4/E5 该并行却串行、人闸②被 closer 吞掉「自己备料自己索权」、尾巴分流缺失等）。保 v1 = 保「零退化」这条硬验收，但也意味着这些偏差要留到 v2。
