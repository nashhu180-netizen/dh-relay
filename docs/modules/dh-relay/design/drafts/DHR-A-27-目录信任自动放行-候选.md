## 1. 目标、边界与决定

### 1.1 白话说明：这在解决什么

你派活给 Codex / Claude Code 时，产品自己会弹一个「你信任这个目录里的内容吗」。今天（DHR_68 之后）relay 的行为是：**看见了、记一条"在等你"、停下来等你去按**。你要的是：**别停，直接替我按"信任"。**

做完之后你手里有什么：新目录第一次派活不用再去点那一下；每次自动放行都有一条可查的账；出问题有一个总开关能关掉，关掉后行为退回 DHR_68 的人工暂停。

### 1.2 这道闸实际拦的是什么（事实，不是措辞）

产品问的虽然是"目录"，但答"信任"之后放开的是**该目录内自带的 agent 配置对 agent 的指挥权**：

- Claude Code：`.claude/settings.json`（其中 hooks 可执行 shell）、`CLAUDE.md`、项目级 MCP 声明。
- Codex：`.codex/config.toml`、`AGENTS.md`。

所以「自动信任任何目录」在语义上等于：**relay 替你预先同意"它拿到的任何仓库，都可以指挥 agent，包括跑命令"。**

这与用户「目录是用户自己开的」的前提**部分成立、部分不成立**：今天路径确实由用户手打；但 `AGENTS.md` 冻结的产品定位是「relay 是给**任意业务仓**用的通用工具，它操作的一直是**别人的仓**」，到 P7 跑真实任务卡时 `work_dir_root` 来自 RelayPlan / 项目注册表，不必然是用户刚点开的那个。**本条只作事实登记，不改变用户裁决。**

### 1.3 冻结决定（来自用户对话裁决）

1. **授权范围 = 任何目录**。不做路径白名单、不限于 relay 自建的临时 fixture 根、不区分仓内仓外。用户明文裁决，已知代价见 §1.2。
2. **审计保留**。每次自动放行必须留下可查的结构化记录。用户未反对；理由是它不牺牲任何便利。
3. **撤销保留**。必须有一个总开关能关掉自动放行；关掉后行为**逐字**退回 DHR_68 的「一次持久 Attention + 人工确认」。用户未反对；同上。
4. **只放行"目录信任"这一类框**。工具执行审批、权限升级、危险命令确认、账号/登录相关的任何对话框，**一律不代答**，继续走人工暂停。这是本设计的硬边界，不随 §1.3.1 放宽。（用户理解对齐时明确：「产品弹的**所有目录**都信任」——限定词是"目录"，不是"所有框"。）
5. **覆盖时点 = 会话全程，不限启动期**。产品在**任何时刻**弹出目录信任框都放行，包括：agent 中途进入嵌套仓、切到另一个目录、或产品因版本升级重新询问。DHR_68 只处理了启动期 `launch_blocked`；本设计要求同一套判定同时挂在轮询期的 `blocked` 分支上。
6. **DHR_68 的安全暂停路径不下线**，它是本机制的兜底与回退目标。

### 1.4 非目标

- 不读取、不上传、不记录任何凭据、token、cookie、账号状态。
- 不代做除目录信任外的任何产品审批（见 §1.3.4）。
- 不改 Receipt / Result / Store / RPC / contracts 的既有语义，不改 driver 的 Result 判定。
- 不新增网络端口、跨主机授权、自动登录。
- 不承诺覆盖未来任意产品版本的 UI 变化（不可证，见 §5 反例）。
- 不碰 Linux / SSH（仍按 `B-22` ① 延后）。

## 2. 机制：两条候选路线（**本节含待决策项**）

产品不提供绕过该框的命令行参数——DHR_35 已实测 Codex 的 `--sandbox` / `--ask-for-approval` 均不绕过，`backlog DHR-BL-2` 亦记载 `--dangerously-skip-permissions` **不覆盖**该框。故只剩两条路。

### 路线 A · 启动前幂等预置（写产品自己的信任表）

launch 前把 `work_dir_root` 写进该 profile 的产品配置：Claude 是 `~/.claude*.json` 的 `projects["<path>"].hasTrustDialogAccepted=true`；Codex 是 `~/.codex/` 下的等价项（**格式待实测确认，本草案不假设**）。

- **已知可行性**：`backlog DHR-BL-2` 记载 2026-08-16 DHR_04 首跑时，主控手工往三份 `.claude.json` 写该字段后配一次 `send-keys Enter` 解开，**后续两棒未再撞**。
- **优点**：框根本不出现；无屏幕解析、无按键落错的可能；可直接断言"配置里有这条"，机器证干净。
- **代价**：①**要写用户级产品配置**——这是 P6 全程守住的一条硬边界（`B-22` ② 明确"禁止读取/写入产品配置值"），本路线要求用户显式松绑；②格式是产品私有、无文档、随版本变；③**并发写危险**——`DHR-BL-2` 已记载 CLI 退出时会回写同一份 `.claude.json`，预置必须容忍被覆盖且可重入，写坏用户配置是真实风险。

### 路线 B · 观测到 blocked 后代答（不碰任何配置）

复用 DHR_68 刚建好的 `launch_blocked` 缝：观测到启动期 `blocked` → 读 pane 文本 → 匹配已登记的信任框特征 → **导航到肯定项** → 发回车。

- **已知可行性**：DHR_35 的 `bootstrap-fixture-trust.ps1` 已在本机对 **Codex 与 Claude Code 两个产品**各成功执行过，并做到幂等（已信任则识别为 `already-trusted`、不重复发键）。
- **优点**：**一个字节的产品配置都不碰**，P6 既有边界不动；失败模式安全——文本不匹配就一个键都不发，直接回落 DHR_68 的人工暂停。
- **代价**：屏幕解析，产品改 UI 就失效（但失效方向是安全的）；**代答落错选项有前科**——`backlog` 已登记「不能让 relay 据此自动作答，IHSR_05 RB-3 有代答落错选项的先例」。
- **必须的护栏**（DHR_35 已验证有效，本设计原样继承）：
  - 只有 pane 文本命中已登记的**信任框**特征才动作；命中其它任何框 → 零按键。
  - **禁止盲发回车**——Claude 的默认选中项是 `No, exit`，盲发回车等于选"退出"。必须解析选中标记（`^\s*[›❯]\s*(?<label>…)`）、导航到肯定项、确认当前选中的就是肯定项之后才发回车。
  - 每个 Attempt 的自动放行**次数有上限**，超限 → 回落人工暂停（防 UI 变化导致的无限按键循环）。

### 待决策 D-1：路线 A / B / A+B

<!-- dh:pending-decision:v1 id=A27-D1 -->

**主控倾向 = 路线 B**，理由：
1. **【理解对齐后新增，且是决定性的】路线 A 在语义上覆盖不了用户的诉求。** 预置只能预置 relay **已经知道的那个** `work_dir_root`；而用户要的是「产品弹的**所有目录**都信任」，包括 agent 中途进入的嵌套仓、切过去的别的目录——那些路径 relay 在 launch 时**根本不知道**，无从预置。要靠预置覆盖，就得预先把机器上所有可能路径都写进产品信任表，这既做不到也比自动放行危险得多。**路线 A 单独使用已不满足冻结决定 §1.3.5。**
2. 路线 A 的坏失败是**写坏用户的产品配置**（并发回写 + 无文档格式 + 跨版本漂移）；路线 B 的坏失败只是**没按成、退回人工暂停**。两者失败代价不对称。
3. 路线 B 已被本项目本月在**两个产品上各跑通一次**，路线 A 只在 Claude 上手工验证过一次、Codex 侧格式未实测。
4. 路线 B 不要求松绑 `B-22` ② 的产品配置边界，改动面小。

> **⚠️ 以下收窄论证已被审核部分推翻。** 主控回查本机实测后确认：「父目录信任不向嵌套仓传递」对 **Codex** 是实测事实（`workspace/DHR_35/evidence/f3508-root-cause/probe-results.json` 的 `nested-git-repo-inside-trusted-dir` → `blocked / agent_not_ready`），但对 **Claude Code 未实测**，而审核者引用的 Claude 文档称父目录 trust 可扩展到子目录。原草案的缺陷是**把只对 Codex 实测过的结论写成跨产品一般事实、且正文未挂证据**。**D-1 恢复 A / B / A+B 三选项**，裁定前置 = 两产品 × {父目录 / 嵌套仓 / 中途切目录} 的只读能力矩阵。详见 [evidence/31 §3](../evidence/31-A27-目录信任自动放行-交叉审核记录.md)。

**（以下为整改前原文，保留作形成史）D-1 仍标为待决策**，但选项已从「A / B / A+B」收窄为：
- **B 单用**（主控倾向）；
- **A+B 混合**——对已知的 `work_dir_root` 预置以减少弹框次数，其余时刻仍靠 B 兜底。混合的代价是同时背上路线 A 的配置写入风险，收益只是"少弹几次框"，而 B 本来就不需要人参与，**收益存疑**。

`IHSR_05 RB-3` 的代答前科正对着路线 B，这是选 B 必须靠 §2 路线 B 的三条护栏（fail-closed 匹配、禁止盲发回车、次数上限）来对冲的已知风险，请 fresh 审核重点攻击这三条护栏是否足够。最终由用户裁决。**在 D-1 裁定前，本文件不得被当作已定方案。**

## 3. 审计与撤销

### 3.1 审计

每次自动放行写一条结构化记录（新增事件种类 `directory_trust_granted`，字段闭集）：

| 字段 | 内容 | 说明 |
|---|---|---|
| `at` | ISO 时间 | |
| `node_id` / `attempt_id` / `executor_ref` | 既有标识 | 与现役事件账同口径 |
| `work_dir_root` | 被放行的目录 | |
| `product` | `codex` / `claude-code` | |
| `matcher_id` | 命中的信任框特征登记 ID | 便于事后判断"是不是认错了框" |
| `mechanism` | `preseed` / `answered` | D-1 定案后可能只剩一种 |

**明令不入账**：pane 文本原文、产品配置正文、任何凭据形态串。（`AGENTS.md` 宪章 #6 密钥红线。）

可查渠道：既有 `relay inspect / events` 即可读出，不新增查询面。

### 3.2 撤销（总开关）

- 单一 relay 级开关，关闭后**零按键、零预置**，行为与 DHR_68 完全一致。
- **默认值 = 开**（按用户"任何目录都信"的诉求），但受 D-2 的作用域限制（见下）。
- 关闭为**即时生效**：已在跑的 Attempt 不追溯，但其后的每一次放行判断都读当前值。

### D-2 已裁决：默认开，但只对本机已登记的 executor profile 生效

<!-- dh:pending-decision:v1 id=A27-D2-REASK -->

> **⚠️ 本节已被审核推翻，D-2 退回待决策。** 两名 fresh 审核独立判定选项②是**安慰剂**：现役 driver 本来就要求 profile 可解析才能执行，故「已登记 profile」只排除了本来也跑不起来的机器。主控当初把②表述为「默认安全」是错的，用户是基于该错误框架做的选择。**须重问，见 [evidence/31 §4](../evidence/31-A27-目录信任自动放行-交叉审核记录.md)。** 以下原文保留作形成史。

**用户 2026-08-31 对话明文裁决：「那就对我 0 差别好了」= 选项 ②。**

含义与边界：

- 自动放行**默认开**，但**仅当**本次 Attempt 使用的 executor profile 是**本机 registry 里已登记的**那一份时才生效。
- 用户本人零操作差别——他的 profile 本来就都在 registry 里。
- 代码被别人 clone 走、或在没有已登记 profile 的机器上跑 → 自动放行**不生效**，行为等同 DHR_68 的人工暂停。**这是"默认安全"而不是"默认放行"**。
- 该判定与 §3.2 的总开关是**与**关系：开关关掉 → 一律不放行；开关开着但 profile 未登记 → 也不放行。
- **不因此新增任何 registry 字段或配置面**：判定复用现役的「profile 是否解析得到」这一既有事实，不引入新的授权表（新增授权表等于变相白名单，与 §1.3.1「不做白名单」冲突）。

> **留给审核的问题**：这条"仅本机已登记 profile"的判定，是否真的构成有意义的安全边界？考虑到 registry 本身也是跟着用户走的文件——如果攻击面是"别人拿到这份仓"，那他多半也拿得到 registry。请独立评估它是**真边界**还是**安慰剂**；若判为安慰剂，请直说，主控会带着这个结论回去问用户是否还要保留。

## 5. 反例与止损

- 产品的**其它**审批框被误认为信任框而代答——A27-M1 的负例必须覆盖；判定不可证时停止，不得放宽匹配。
- 盲发回车导致选中 `No, exit`——A27-M2 硬拦。
- 预置写坏用户产品配置（并发回写、字段丢失）——路线 A 的一票否决项；不可证即不选 A。
- 把"自动信任"外溢成"自动同意一切"——§1.3.4 硬边界，任何实现越过它即停止。
- 声称"覆盖任意未来产品版本"——不可证，禁止写入任何结论。
- 机制失效表现为静默挂死而非回落人工暂停——A27-M7 硬拦。

## 6. 拟议 B-adjust（**尚未生效**）

D-1 / D-2 裁定且用户整版确认后，预计拆一张 `standard/heavy` 卡承接：允许路径限于 `relay-core/runtime/executors/herdr/**`、`workflow-driver.mjs` 的信任事件路径、相关测试与 fake、契约中新增的 `directory_trust_granted` 事件种类，以及其工作区。**本草案不发 ID、不授权开工。**

## 7. 与既有冻结件的关系
