# 通用节点与运行中计划续接：交叉审核记录

> 状态：A-full事件`DHR-A-23`已完成新版fresh审核、理解确认与用户整版确认，并原子晋升正式`design/10`。P7/P8、DHR_53工作现场和PlanHome仍未切换；本记录不授权B-adjust、开发、清理worktree、初始化/启用PlanHome、提交或推送。

## 1. 原始需求与候选边界

用户在连续讨论后确认：dh-relay 保持 orchestrator、monitor、executor 三类逻辑角色；施工、复核、回归、决策只是不同 RelayPlan 节点中的 Executor 工作，不是 Core 业务 `node_type`。节点工作由 Plan 指向的 workspace/指令决定，账号、模型、推理强度、fresh 与权限由节点执行绑定决定。DevHarness 不通过 runtime Adapter 与 Core 强耦合，而由人工/编排 Agent 把已拆好的步骤写入 Plan。

复核发现问题时才追加“返修并定向回归 → fresh 定向复核 → fresh 全面复核”。三轮仍未闭合时，由 fresh 决策 Executor 只读分析并在提交 Result/Handoff 后关闭；用户决定后，编排 Agent更新原 Plan，程序只校验、解析和激活新 generation，另一次显式 `continue` 才启动新增节点。

用户进一步明确：“以最新的为准，DHR53施工的内容不符合矛盾的话可以清楚重做。”主会话最初按“清除重做”理解为先保留 Git、review 和 workspace 审计锚点，再从 master 重建；新版 fresh review 已将该口径收紧为“登记精确 master SHA、archive ref 与 tree/file manifest 后重建”，不得使用会漂移的 `latest master` 或 destructive reset 抹掉历史。

## 4. 当时的用户理解确认（后续澄清已推翻）

- 理解问题：决策 Executor 建议拆成多个任务时，是把原 Run 以 `cancelled/replanned_as_new_tasks` 关闭，并为每个新任务创建新的 `task_id`、RelayPlan 和 Run；还是让原 Run 永久停在等待状态。
- 用户当时回答“可以”，主会话据此采用“原 Run 关闭、子任务分别新建 Plan/Run”的解释。
- 用户随后明确指出该解释不对：`task_id` 是业务计划中的任务卡；“拆两个新任务”是业务计划拆任务；RelayPlan 本来就可以承载多个任务，而且可以跨计划、跨项目。用户进一步明确由决策 Executor把拆分结论回传给编排 Agent，后者执行 B-adjust、决定新任务加入或不加入当前 RelayPlan，并继续不受阻塞的任务。
- 因此，前述 `cancelled/replanned_as_new_tasks`、每任务强制独立 Plan/Run、Core `split_from` 回链等结论全部失效；原审核的 `approved` 只属于旧候选，不能为新版背书。新版必须重新 fresh review、重新理解确认和整版确认。

## 5. 后续澄清形成的新版原始需求

用户后续原话和含义形成以下纠偏输入：

1. “task_id 怎么理解？……拆两个新任务，一般是指业务上的计划拆两个任务。”——`task_id` 是所属 DevPlan 的业务任务卡 ID，不是 RelayPlan 或 Run。
2. “决策agent确定拆分业务任务。信息回传到编排agent。”——Decision 仍是 Executor 节点；它提交结论并关闭，不能直接修改 DevPlan/RelayPlan。
3. “编排agent负责处理：包括 b-adjust 调整、更新接力计划（可以加入也可以不加入）、如果不加入，选取调整计划，选取接力计划中不阻塞的任务继续。”——业务计划调整、是否纳入当前 RelayPlan、继续哪个 Ready 节点是三个显式动作。
4. “接力计划是可以承载多个任务而且是可以是跨计划甚至是跨项目的。”——单 `task_id` Run 根、repo-local PlanHome 与 P8 禁止跨仓 Run 均需替换。

## 9. 新版用户理解确认

- 理解问题：Decision Executor 的 durable“确定拆分”结论，是只作为编排 Agent发起 DevHarness B-adjust 的依据，仍需用户或项目既有 Authority 确认；还是结论本身就自动授权修改业务 DevPlan。
- 主会话建议前者，因为 B-adjust 会实质改变业务任务权威，且一份 RelayPlan 可能跨多个项目，Decision 的模型结论不能自行取得各项目写权限。
- 用户回答：“确认。”据此冻结：Decision Executor只提交并落账拆分结论后关闭；结论不自动授权 B-adjust。编排 Agent须先取得相应项目 DevHarness 要求的用户确认或既有 Authority，随后才可执行 B-adjust、选择新任务是否加入当前 RelayPlan、激活 generation，并显式 `continue` 不受影响的 Ready 节点。
- 该答案与 reviewer 已复审通过的 fail-closed 候选一致，只把待决策状态改为已确认，不改变目标、范围、验收、权限或失败语义，因此无需再次定向复审。新版 A23 可以进入整版确认；整版确认仍不授权后续 B-adjust 或开发。
