## 第一部分：背景（给不读仓的评估者）

- dh-relay：接力执行系统，多 AI agent 接力跑完一张 dev-harness 任务卡，中间无常驻 AI 主控，人只在落户/决策/收口时出手。现役 P1（PowerShell + psmux）跑通；旧 P2/P3 已冻结。

## 第三部分：「把 DSH 换成 pi」可行吗

### 3.1 pi 是什么（本轮核对的事实）

- `earendil-works/pi`（原 `badlogic/pi-mono`），92k stars，v0.84.2（2026-08-14），100+ tag，提交活跃（08-17 仍有 push）。自述"AI agent toolkit: unified LLM API, agent loop, TUI, coding agent CLI"。
- 产品形态：**终端 TUI 编码 agent**（`pi`），单进程单会话。**没有 Web UI**（早期 pi-mono 里的 `web-ui` 包在当前包列表中已不存在；`pi-chat` 是 Slack 集成）。
- 扩展系统（`packages/coding-agent/docs/extensions.md`）：单文件 TypeScript，放 `~/.pi/agent/extensions/` 或 `.pi/extensions/` 自动发现，`/reload` 热重载；能注册工具、命令、事件拦截（含阻断工具调用）、`ctx.ui`（select/confirm/input/notify）、TUI 自定义组件/widget/overlay、`pi.appendEntry()` 把状态写进会话持久化；可通过 npm/git 分发为 pi package。官方 examples 有 80 多个（含 `subagent`、`structured-output`、`permission-gate`、`plan-mode`、`handoff`、`sandbox` 等）。
- 会话（`docs/sessions.md`）：JSONL 树，`~/.pi/agent/sessions/`，`-c` 续接、`--fork`、`/tree`、`/clone`。
- **RPC 模式**（`docs/rpc.md`）：`pi --mode rpc`，stdin/stdout **JSONL**，命令带 `id` 关联；`prompt` 支持 `steer`/`followUp` 排队；事件流有 `agent_start/turn/message/tool_execution_*/agent_end`；扩展的 `ctx.ui` 对话框通过 **Extension UI Protocol** 走 JSON 让宿主代答。文档建议 Node 宿主直接用 `AgentSession` 类而不是子进程。另有 `--mode json`（纯事件流）和 `-p`（一次性）。
- 新增 `server / protocol / client` 包：Unix socket + CBOR 帧的会话服务协议，README 明写 **"Experimental… may change or be removed without notice"**；不提供独立 CLI 服务，也没提 Windows Named Pipe。
- Windows（`docs/windows.md`）：**需要 bash**（Git Bash 即可）；正式支持，但门槛是"有 bash"。
- 权限：**没有内置权限系统**（README 明写），靠扩展 gate 或容器/沙箱。
- 稳定性对比：pi 是 0.x 但版本序列长、扩展 API 有大量范例在用；DSH 是 rc.7、只有一个 tag。**但 pi 的"服务/协议"面（server/protocol）比 DSH 的插件平台还年轻，且自标实验性。**

### 3.2 关键判断：pi 和 DSH 不是同一类东西

用户选 DSH 的理由（design/05 §1、§3.1）是**要一个专属工作台**：多页面 Web UI、Run 图、Attention/Approval 页面、跨项目首页、插件平台、Workspace/Session。DSH 提供的是"平台外壳"，dh-relay 往里插。

pi 提供的是"**一个很好的 agent + 极易写的扩展**"，UI 是终端。用 pi 1:1 替换 DSH，意味着：

| 05 想从外壳拿到的 | DSH | pi |
|---|---|---|
| Web 多页面工作台、Run 图、跨项目首页 | 有（Client Plugin + UI Slot） | **无**；TUI overlay/widget 能做单会话内的面板，做不了多项目仪表盘 |
| 树外插件 | 有，但 Client 侧配方未文档化（P4-1） | 有，单文件 TS，无构建、热重载，**远比 Cordis 轻** |
| 插件生态 / 范例 | 起步 | 80+ 官方范例 + npm/git 包 |
| Approval / User Questions | 内置 | 扩展 `ctx.ui.confirm/select`（RPC 下走 Extension UI Protocol） |
| Subagent / Jobs | 内置 | 扩展范例 `subagent`，非平台级 |
| 被外部程序驱动（当执行器） | Codex/Claude Provider one-shot；SDK 面向驱动 DSH agent | **`--mode rpc` 一等公民**：JSONL、steer、事件流、UI 代答、会话续接 |
| 平台无关服务协议 | 无（Bridge 自建） | server/protocol 包，**实验性**、Unix socket |
| Windows | 已装、已起（rc.6） | 需 Git Bash（本机有） |
| 权限系统 | 有 | 无 |

结论：**"pi 替代 DSH"是换掉了产品目标，不是换掉了实现。** 如果用户要的仍是 Web 工作台，pi 给不了；如果用户愿意接受"终端工作台"，那么 pi 是可行的、而且**更便宜**，但那实质上是回到"独立 Relay Runtime + 一个控制台"的 04 路线，只是控制台从 agent-console 换成 pi 扩展。

### 3.3 pi 真正强的位置：当执行器，不是当外壳

pi 有一处能**直接补上 P5-1 那个空洞**：Relay Runtime 每个节点 spawn 一个 `pi --mode rpc`（或 Node 内 `AgentSession`），子进程与任何 UI 进程无关、JSONL 双向、事件可入账、`ctx.ui` 提问经 Extension UI Protocol 直接映射成 Relay Attention、会话文件可续接（`--session`）。这比"Herdr 观察 Codex CLI 的 pane 文本"（P6 的 working/blocked/done 对账、盲区进 Attention）**观测面干净一个数量级**，也比 DSH one-shot Provider（无续接、无审批路径）能力强。

**代价与未知**：
- pi 用的是**你自己的 provider 凭据/API**（pi-ai 多 provider）。用户目前的 Codex/Claude Code 多账号（`codex / codex-ninth / claude / claude-grok / claude5`）很可能是订阅制额度，Herdr + CLI 路线的价值之一是花订阅额度。pi 能否走这些订阅账号，我**未核实**（pi 支持 Anthropic 等登录方式的具体口径要看 `docs/providers.md`，本轮未读）。这一条决定 pi 执行器是"替代 Herdr"还是"并列一个 API 计费的执行器"。
- pi 无内置权限系统 → 只读诊断（P8 DHR_43 "机器可证明只读"）得靠扩展 gate + 沙箱，不如 DSH 原生工具白名单可证。
- 会话文件在 `~/.pi/agent/sessions/`（按 cwd 组织），Relay 需要把 session 路径入 Receipt（`--session-dir` 可指到 `.dh-relay/<run_id>/`）。

### 3.4 建议

**不建议 1:1 替换。建议按"外壳与执行器分开评估"改写问题：**

1. **外壳**：维持 evidence/06 的裁决——DSH 当外壳，但**P4 Pilot 的判否分支加一条**："若 P4 判否，候选外壳按 (a) pi 扩展 TUI 控制台、(b) agent-console 两个方向重评"，不要只写"恢复 agent-console 评估"（`P4:175-179`）。这样 pi 有明确落点，也不打断当前主线。
2. **执行器**：在 **P6** 增加一张（或把 DHR_35 拆出一条）"`pi.rpc.<profile>` 执行器 spike"：Relay 用 `--mode rpc` 跑一个节点，验证事件入账、Attention 映射、`--session` 续接、Windows 子进程树清理。若成立，P7 的 S1/S2 brief/task-plan、E5/E6/E7 这些"DSH Native Agent"节点可路由到 pi 执行器，**从而绕开 P5-1 的宿主归属问题**（Runtime 直接 spawn，不经 DSH 进程）。前提：先查清 3.3 第一条（订阅账号 vs API 计费）。
3. **如果用户的真实优先级是"稳定 + 生态"而非"Web 工作台"**：那么诚实的最小路线是 **Relay Runtime（P5）+ pi 扩展当控制台 + pi RPC 当执行器**，P4 的 DSH Pilot 可以直接跳过、把 2～3 天用在 pi 扩展 Pilot 上（单文件 TS、无构建、当天可见）。这不是 DSH 路线的补丁，是**换路线**——需要用户明说，evidence/06 才该改。

### 3.5 一句话给用户

pi "更稳、生态好"是真的，但它稳的是**编码 agent 本体和扩展 API**，不是"工作台平台"——那一面（server/protocol）比 DSH 还新且自标实验。**要 Web 工作台就留 DSH；要省事、能接受终端就换 pi；不管哪种，pi 的 RPC 模式都值得当执行器接进来。**
