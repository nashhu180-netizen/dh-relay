## 1. 用户方向

- 用户要求解释并正式补足“Herdr 已拉起 Agent、但 Agent 没有实际推进”的处理。
- 用户提出：启动时限内应有持久 `node_started`，运行中应有可验证 checkpoint；Monitor 只报告停滞而不裁决质量；超时后撤权、停止旧 Pair、以新 Attempt/Ticket 恢复；下游不得提前启动，Review Batch 只恢复卡住路径。
- 用户补充：Herdr 可以监控 Agent 状态，停止时应获取信息；英文术语要有中文说明，YAML 要逐字段中文讲解。

## 2. fresh-context 复核与裁决

复核发现并要求闭合的风险如下，主会话均已采纳：

| 级别 | 问题 | 已采纳的正式口径 |
|---|---|---|
| Blocker | 把 Workflow Engine 写成直接持久化，违反 HostSessionActor 单写者边界 | Engine 仅生成带 guard 的 recovery command；Actor 以 CAS 原子落 Attention、撤权和 `recovery_pending` |
| Blocker | Result 与恢复并发、重复恢复、旧 Pair 未关闭会造成双写或双实例 | 冻结 expected generation/state、`recovery_request_id`、单一 CAS winner、旧 Pair 关闭与 `capacity_wait` 条件 |
| High | 把 Herdr prompt 夸大为目标身份原子 compare-and-send | 只表述为 Host 的 prompt 请求；身份在投递前后校验，替换竞态返回 `delivery_uncertain` |
| High | 角色解析可能跨 Run/Session 或依赖焦点、Pane 顺序 | 使用 Sender Context 的完整身份链、唯一 live agent name 与 Pane 回读校验；零/多/错范围一律拒绝 |
| High | `target_busy` 被误写为稳定事实 | 定义为前检查观察忙碌、因此本次未调用 prompt；检查后发生变化统一按竞态处理 |
| High | Host 不可达、probe error、Pane 缺席与真正退出混淆 | 仅 Pane 与进程均消失才记 `exited`；其他分别记录 `host_unavailable`/`probe_error` |
| High | 人等状态会被 checkpoint deadline 误恢复 | `blocked`、`awaiting_input`、`decision_required` 只短提醒并暂停自动恢复 |
| High | 诊断快照可能泄漏屏幕中的凭据 | 只存白名单字段，先脱敏再 UTF-8 限长；任一步失败零原文落盘 |
| Medium | 新状态、工件与反例没有 Schema/身份/幂等要求 | A29 要求实现卡先冻结 Schema、身份链、digest、幂等键和完整反例矩阵 |

复核结论：上述修订后无开放 Blocker/High/Medium；正式设计可晋升。该结论不代表实现已完成。

## 3. 理解确认与授权边界

面向用户解释并确认的场景是：终端拉起并不等于 Agent 已接单；`node_started` 证明接单、checkpoint 证明可恢复进展、Result/Handoff 才能关闭节点。Herdr 状态和末段输出仅作为经过脱敏的诊断输入，绝不替代业务结果。用户随后明确要求“先把文档更新下”，授权本次正式设计更新及必要的审核留痕。

该授权不包含 B-adjust、开发、运行时启用、提交、推送、部署或环境操作。

## 6. Role Relay 忙碌投递定向复核

用户明确决定：目标 Agent 处于工作中不再构成普通消息的拒绝条件；Role Relay 删除 `target_busy`，对 `working`、`idle`、`blocked` 都直接尝试 prompt。复核结论：该调整不改变业务边界——聊天仍不能撤销 Ticket、替换 Attempt、变更任务合同或启动下游；身份替换竞态仍以 `delivery_uncertain` 暴露。验收同步要求三种生命周期均发起 prompt，且不存在 `target_busy` 返回。

## 7. Role Relay 忙碌投递的用户决策

用户说明“一般不用考虑这个情况，直接发即可；有时候就是想要打断、给他新的指令”。据此，普通新指令直接尝试投递；真正停止或替换当前执行仍需显式控制面，避免聊天绕过身份撤权与结果竞态保护。该确认只更新设计，不授权实现或运行时启用。
