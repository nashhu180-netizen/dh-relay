##### 1. 方案问题

**P0 · 验收回链语义越界（H1 / H4）** · `P4 §1`、`DHR_25` 验收口径、`§5` 覆盖表  
- 问题：卡片把产出挂到 design/06 **H1 / H4** 全称命题，但交付物远小于命题原文。  
- 独立事实：design/06 §11 H1 =「DSH 未安装或完全停止时，**Relay Runtime** 可以启动、查询、运行和恢复」；H4 =「客户端断开、DSH 插件卸载和 SSH 断开均不隐式取消 **Run**」。P4 明文非目标「不实现 Relay Runtime」，现场只有 fixture / 一次性 CLI。  
- 「SSH 断开不改变 fixture」对只读文件几乎恒真，不能证明「不断开 Run」。  
- 影响：B 覆盖关失真——看起来盖了 H1/H4，实际未盖；后续 P5/P9 易被误以为 H1/H4 已在 P4 卸责。  
- 建议：验收只挂 **P4-CM*** 本地命题；对 design/06 写清「本阶段仅覆盖子命题 X，全称 H1/H4 延后到 P5/P9」，禁止把全称 H-ID 写成已承接。

**P0 · H9 虚盖** · `P4 §5` 覆盖表 vs `DHR_25/26/27` 验收口径  
- 问题：§5 写「H1/H3/H4/**H9** 的 fixture 级子命题由 DHR_25/27 承接」，但三张卡验收口径**均未引用 H9**。  
- 独立事实：H9 =「Linux 无 GUI、仅 SSH 时，可以运行 **Runtime、CLI、Herdr 和一条代表性工作流**」。P4 只有 SSH 下读 fixture 的 CLI，无 Runtime / Herdr / 工作流。design/06 §10 P4 原文只要求「同一 fake/v1 Read Model 可由通用 CLI 在 Windows 和 SSH 读取」——这不等于 H9。  
- 影响：覆盖表与任务卡自相矛盾，属拆计划覆盖关不合格。  
- 建议：§5 删除 H9；SSH 只回链 design/06 §10「P4」+ P4-CM2。

**P0 · DSH 判否时 P4-CM4 可空转却仍解锁 P5** · `§4.1 P4-CM4`、`§4.5`、`DHR_27` 依赖「通过或已落判否证据」  
- 问题：CM4 =「CLI 和任何增强客户端均消费同一 Read Model」。DHR_26 `stopped-by-pilot` 后不存在第二客户端，CM4 可被读成空集通过，从而在「跨客户端一致性」未证时仍满足「P4-CM 全部通过 ∧ 进入 P5」。  
- 对照：§0.1 / DHR_27 目标强调 CLI↔DSH 对证；空转通过会拆掉 Pilot 的核心证明之一。  
- 建议：显式二分——（a）DSH 通过：CM4 要求跨客户端 JSON/字段一致；（b）DSH 判否：CM4 标 `N/A（无第二客户端）` 且**不得**计入「CM 全绿」，改由「CM1/2/3/5/6 全绿 + DM=stopped + 报告诚实」解锁，或要求至少一种非 DSH 第二投影（例如只读 JSON 文件对拍）才能算跨客户端一致。

**P1 · H3 在 DHR_25 上过早挂靠** · `DHR_25` 验收  
- H3 要求 DSH、Pi 与 CLI 读同一 Read Model。DHR_25 只有 CLI，最多证明「CLI 只渲染 Read Model」；跨客户端一致属于 DHR_27（且依赖 DSH 是否存在）。  
- 建议：DHR_25 去掉 H3 回链，改挂 P4-CM1/CM2/CM5。

**P1 · 「基线轨必须过 / 增强轨可判否」与用户口径：不构成产品硬冲突，但计划措辞仍有残留** · `§0.1`、`§4`、`README`「P4 的特殊阶段闸」、对照用户口径与 design/06 §1  
- **判断**：阶段闸不对称 **≠** 把 CLI 定位成保底/应急/回退。design/06 §1 本就规定 CLI = **必须存在的参考客户端**，DSH = **可替换、可缺席的首选桌面工作台**；README 硬约束#1 已改为「并行、可配置替换」。Pilot 里「CLI 不过则主线不立、DSH 可判否」对齐的是「必备 vs 可缺席」，不是「CLI 是差一等的退路」。  
- 仍有问题：通篇「基线轨 / 增强轨」+「DSH 优先」容易让人读成 CLI=保底、DSH=正式；与用户刚纠正的口径摩擦。§4.5「DSH 判否时 P5 以 Relay CLI 为默认」作为**阶段默认控制面**可接受，但不得在讲解里说成「CLI 顶上」。  
- 建议：对外/白话统一「必备参考控制面（CLI）∥ 首选桌面控制面（DSH，可判否）」；少用「增强轨」指 DSH。

**P1 · DHR_25 定轻档偏松** · `DHR_25` 档位  
- 形式：仓外、只读、不接线、不动 `tools/` → 按 dev-harness 可不进高危五类，轻档合法。  
- 实质：§0.1 / 实施提示称 Read Model「P5 正式内核直接沿用 / 可进入 P5 协议」——这是跨阶段契约冻结；轻档无两轮复核、无人判 schema 签收。  
- 建议：升**标准档**，或保持轻档但增加人判「最小字段是否够 P5 沿用」并由用户对话确认后才允许写进 P5 输入。

**P1 · 2~3 有效开发日 vs 串行三卡（含两张标准档）不匹配** · `§1` 批次、`§4.4` 止损、`DHR_26/27`

- 建议：预算改为「DHR_25 ≤1 日；DHR_26 单独预算并与阶段总预算脱钩」或砍 DHR_26 到「加载 Host + 静态面板」更小闭环；标准档复核时间必须计入。

**P1 · §0.1 白话与正文不一致 / 夸大** · `§0.1` vs `§1`/`DHR_25` 实施提示 / `§4.5`

##### 2. 用户理解风险

**P1** · 读完以为 **H1/H4/H9 已在 P4 验收掉**，Linux Headless 正式路径已经成立；实际只证明「SSH 里能打印同一份假数据」。  
**P1** · 「基线 / 增强」叙事 +「DSH 判否也不挡 P5」→ 以为 **CLI 是正式产品里的保底通道**；与你刚定的「并行可替换、CLI 不是保底」口径相反。正确读法：CLI 是**必须先证明存在的参考控制面**；DSH 是**想用但允许证明失败的桌面控制面**。

### 二、用户理解风险

1. **「拆成两张 = 不确定性消失」**  
   实际：Host/Client 未知被隔离了，但 **DHR_49 仍是「配方 + 两屏 + 装卸」一大包**；不确定性从「一张卡里爆炸」变成「集中在 49」。更准的说法：失败时能诚实停在 Client，且不抹掉 Host。

2. **「三态归人判 = 中间两张卡不用验收」**  
   实际：26/49 仍按标准档进待验收（装卸证据、截图、配方全文等）；人判的只是最后贴 `passed / 带约束 / 停`。更准：机器记账，人贴标签。

   实际：它是 DHR_25 Pilot 产物 + 你口头「暂时够了」；design 白名单正文没有字段级定义。更准：Pilot 暂定真源，P5 才定合同——除非你选先补 A′。

4. **「换机也要过才算可复现」vs「换机失败只带约束」**  
   实际：称 **pass** 要两条都过；只有清净失败才强制止损。若你心里「换机不过 = 整条 DSH 轨停」，需要明说，否则会按「带约束继续」走。

5. **「CLI 是保底」残留语感**  
   计划已改「必备控制面 / 桌面控制面可判否」，§4.5 也写了「阶段默认 ≠ 回退」。但白话若再提「2~3 天小实验证明 CLI 够不够」，仍可能听成 CLI 在替 DSH 托底。对齐你的口径：两条并行、可配置替换。

### 二、增量 B 审核（列表屏中途闸 · 新条款）

核过位置：`P4` DHR_49:172–176（验收）、:180（实施提示）；对照 §4.4:237–243、DM3:168、DHR_27 人判:192–193；来源叙述 §0.2:58–59、`evidence/09` §17.8:823–827 / §18:829+。

**1. 拆分二分是否穷尽且互斥**  
**否，未穷尽；条文也未声明可双命中。**  
- 骑墙场景：**「分组/分堆在面板里看不清、找不到目标 run」**——既可归 (i)（DSH 表格/折叠/样式不可控，渲染能力），又可归 (ii)（`group` 词表或排序语义不合用，信息组织）。现文写「必须拆成两类、**不得混谈**」，易被读成强制单选互斥；未写「一条评价可同时落入两类」。  
- 第三类缺口：**纯控制面偏好**（「字段都对、也渲染得出，但我就是更习惯 CLI / 键盘流」）——既非渲染机制失败，也非契约字段问题；现二分装不下，却仍会被「不如 CLI 好用」触发闸。

**2. 谁来拆**  
条文把**提案权**给主会话、把**确认权**给用户（:176「拆分结果经用户确认后」）。这比「AI 单方裁定」好，但：  
- 拆错不对称仍在：错判成 (ii) → 本该止损的 DSH 轨继续；错判成 (i) → 本该改契约的问题误触/误导向止损。  
- 「确认」若只是对主会话整包分类点头，仍可能被框架带跑。  
**现有「经用户确认」必要但偏软**——应升级为：主会话只提候选归属表，**由用户逐条点选 (i)/(ii)/双属/其他**；未点选不得当作已拆完。

**3. 闸与止损的关系**  
存在路径打架风险。  
- 中途闸：只暂停、不自动终止；拆完后仍由用户选「照做 / 改后做 / 不做」。  
- 同时：(i)「命中 §4.4 条件时触发止损」（:173），而 §4.4:237 命中即「停止 DSH 桌面控制面轨扩张」。  
当 **(i) ∩ §4.4** 时，一边已进入止损收口，一边闸仍摆出「照做」选项——**谁优先未写死**。  
正确关系应是：**闸负责停下来分类；一旦分类确认命中 §4.4，改走 §4.4 止损收口，不再提供「照做」**。未命中 §4.4 的 (i) 仅作 DM 事实登记，再回到三选一——此路径现文可成立，但未写清。

**4. 不空转条款**  
**字面与「暂停扩张」矛盾，且「未表态」无判据。**  
- :172「首次渲染成功即**暂停扩张**」vs :176「用户未表态时默认按原计划继续做详情屏，不因等待而空转」。  
- 未定义：提过一次无人答？用户说「回头再说」？会话中断多久？  
若把「未表态」理解成「问过即算可续」，则「暂停」退化成一次性通知；若理解成「必须等到表态」，则与「不空转默认续做」直接冲突。缺操作判据。

**5. 与 DM3 的关系**  
部分覆盖。DM3:168 已有「详情屏未完成记 N/A，不得因列表屏已绿宣称 DM3 全过」，语义上可吃下「中途闸选不做」。但触发语是「**中途止损时**分屏登记」——中途闸用户选「不做」**不是止损**。口径差一截，记账时可能被抠字眼。

**6. 是否引入新的人判负担**  
会增加一轮拍板，但与 DHR_27 四项人判 + 三态收敛**主题不同**（闸=列表屏后是否扩张；27=整轨终态与 P5 默认面），不必然冲突。风险在于：用户在闸上已表达「DSH 不如 CLI」，DHR_27 H2/三态若再以近似问题重问，造成疲劳或结论漂移。现文未声明「中途闸登记是 DHR_27 的输入事实，不得在无新证据时要求用户推翻重裁」。属负担/冲突护栏缺失，非逻辑自毁。

**7. 是否需要回链设计验收 ID**  
**不需要，不构成第 1 轮 P0 同类白名单问题。**  
中途闸是 Pilot **过程人判/止损前分流**，来源为理解问答（§0.2:58–59），并不宣称关闭 design/05·06 某条 H/B 全称。与「把无白名单正文的契约写成已承接」不是一类。
