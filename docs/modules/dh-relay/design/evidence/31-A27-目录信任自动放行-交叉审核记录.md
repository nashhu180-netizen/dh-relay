## 3. R-08 的主控反查（唯一部分采纳项）

审核者用 Claude 官方文档「父目录 trust 可扩展到子目录」反驳主控"嵌套仓无从预置"的论证。主控**不直接采信外部引用**，回查本项目的本机实测：

`workspace/DHR_35/evidence/f3508-root-cause/probe-results.json`（分支 `wt/DHR_35`，2026-08-31 实测，**Codex**）：

| case | exit | agent_status | error_code |
|---|---|---|---|
| `control-already-trusted-dir` | 0 | idle | — |
| `nested-git-repo-inside-trusted-dir` | 1 | **blocked** | `agent_not_ready` |

该文件的原文结论：**"Trust is keyed to the exact project path and is not inherited from a trusted parent directory."**

**裁决**：
- 对 **Codex**，"父目录信任不向嵌套仓传递"是**本机实测事实**，审核者的反例不适用。
- 对 **Claude Code**，本项目**没有实测**；审核者的文档引用可能成立。
- 因此原草案的真实缺陷是：**把一个只对 Codex 实测过的结论写成了跨产品的一般事实，且正文未挂任何证据**。
- **改法**：§2 D-1 的论证改为挂 DHR_35 实测证据、限定为 Codex；Claude 侧标为**未实测**，并把"两产品 × {父目录 / 嵌套仓 / 中途切目录}"的只读能力矩阵列为 **D-1 裁定的前置**。
- **D-1 因此维持待决策**，选项恢复为 A / B / A+B 三项——审核者在这点上是对的：现有证据不足以排除 A。

## 4. 须用户重新决定的问题

<!-- dh:pending-decision:v1 id=A27-D2-REASK -->

**D-2 需要重问，因为主控给出的选项框架有错。**

主控当时把选项②表述为「默认开、但只对本机已登记的 executor profile 生效……工具被别人拿去用时不会静默放行」，用户据此选了②并说「那就对我 0 差别好了」。

**两名审核独立判定②是安慰剂**，rev2 的论证决定性：**现役 driver 本来就要求 profile 可解析才能跑**，所以"已登记 profile"这一条只排除了那些**本来就跑不起来**的机器；任何一台正常配置过的机器都满足它，照样静默默认开。**②并不提供它所声称的隔离。**

剩下两个真选项：

| | 含义 | 对用户的差别 |
|---|---|---|
| ① 全局默认开 | 完全按用户字面。任何人在任何配置好的机器上跑这份 relay，都自动信任任何目录 | 零操作 |
| ③ 默认关 + 本机显式开一次 | 用户在自己机器上打开一次（一条命令 / 一个本机标记），之后零操作；别人 clone 走默认是关的 | **一次性一步**，之后零差别 |

**主控倾向 ③**：它对用户的成本是**一次**，换来的是"这个安全默认不会跟着代码传播给未来任何使用者"。两名审核也都推荐 ③ 或等价的"安装者显式授权"。
