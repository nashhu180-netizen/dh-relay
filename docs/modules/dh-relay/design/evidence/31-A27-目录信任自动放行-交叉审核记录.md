**D-2 需要重问，因为主控给出的选项框架有错。**

主控当时把选项②表述为「默认开、但只对本机已登记的 executor profile 生效……工具被别人拿去用时不会静默放行」，用户据此选了②并说「那就对我 0 差别好了」。

剩下两个真选项：

| | 含义 | 对用户的差别 |
|---|---|---|
| ① 全局默认开 | 完全按用户字面。任何人在任何配置好的机器上跑这份 relay，都自动信任任何目录 | 零操作 |

**主控倾向 ③**：它对用户的成本是**一次**，换来的是「这个安全默认不会跟着代码传播给未来任何使用者」。两名审核也都推荐 ③ 或等价的「安装者显式授权」。

## 6. R-01 modal provenance 只读实测（主控，2026-08-31）

> 形态：只读查 herdr 0.8.2 的 API 面与本机既有 agent，**未拉起任何真实产品实例**，未写任何文件。

### 6.1 herdr 能给 relay 的全部信号

| 来源 | 内容 | 能否作为对话框身份 |
|---|---|---|
| `AgentStatus` 枚举（API schema 实测） | **只有五个值**：`idle` / `working` / `blocked` / `done` / `unknown` | ❌ 无对话框类型、无选项集合、无提示种类 |
| `agent read --source detection` | 实测就是**另一份屏幕文本快照**，与 `recent-unwrapped` 同类 | ❌ 仍是可被普通输出伪造的文本 |
| `state_labels`（`pane_agent_status_changed` 事件里的自由形态 `{string:string}`） | schema 里存在；但对本机真实 agent 跑 `agent get` 返回**缺省（None）** | ⚠️ 未观测到承载对话框信息；要确证需在真实 blocked 态下再观测一次 |
| 事件种类清单（32 种，实测枚举） | 全是 pane/agent 生命周期与布局事件 | ❌ **没有任何一种是"对话框/审批/提示"事件** |

**结论 6.1**：**herdr 不提供对话框身份。** relay 手上只有「五值状态 + 原始文本」，这正是两名审核判定不足的那个输入面。

### 6.2 但存在一层**进程级** provenance（新发现，审核双方均未提及）

`herdr pane process-info --pane <id>` 实测返回前台进程的 `argv` / `argv0` / `cmdline` / `pid` / **实时 `cwd`**：

```
{"foreground_processes":[{"argv":["C:\...\@anthropic-ai\claude-code\bin\claude.exe"],
  "cwd":"D:\MyFiles\ai-workflow\dh-relay\","name":"claude.exe","pid":36088}], "shell_pid":12924}
```

这是**agent 打印的文本伪造不了**的信号（进程表不由 pane 输出决定）。可用来构成合取式身份：

> （前台进程确实是本次启动的那个二进制，按 **pid** 比对）∧（`agent_status == blocked`）∧（文本命中版本化 matcher）∧（`process-info` 的**实时 cwd** 即目标目录）

**这比"纯文本匹配"严格更强**，且顺带解决 **R-03**：审计该记的「实际被信任的目录」可以取 `process-info` 的**实时 cwd**，而不是 launch 时固定的 `work_dir_root`——后者正是审核指出会记错的那个字段。

### 6.3 残余风险（诚实结论：R-01 **没有被完全解决**）

进程级身份能证明**"是哪个产品、在哪个目录"**，但**证明不了"弹的是哪一个框"**——同一个 `claude.exe` 在同一个 cwd 下弹「信任此目录吗」和弹「要执行 rm -rf，确认吗」，在进程层面**完全同形**，区分二者的信息**只存在于文本里**。

因此两名审核指出的核心风险——**把另一个审批框误认成目录信任框**——**依然存在**，只是被压缩到"同产品、同目录、同 blocked 态下的框间混淆"这一更窄的面。

**与 D-2 终裁的叠加效应必须显式登记**：用户已裁定①全局默认开，即**不做任何作用域收敛**。「认不出是哪个框」× 「所有机器所有目录都开」= 误答面取到最大。这不是反对用户的裁决，是把它的代价写清楚。

### 6.4 这把 D-1 推向哪里

- **路线 B 不再是"不可实施"**，但它的安全性上限被 6.3 钉死：**只能做到"同产品同目录下的框间区分靠文本"**。要不要接受这个上限，是产品决策，不是技术决策。
- **路线 A（预置产品信任表）在这一点上有结构性优势**：框根本不出现，就没有"认错框"的问题。它的代价转成"写用户产品配置"（须松绑 `B-22`②）与"覆盖不了未预置路径"（对 Codex 已实测成立，对 Claude 未测，见 §3）。
- 因此 **D-1 的真实取舍**是：**「认错框的残余风险」（B） vs 「写坏产品配置的风险 + 覆盖不全」（A）**，而不是主控原草案写的"A 覆盖不了所以排除 A"。原论证已作废，本节取代之。
