## 第一部分：你需要知道的背景

### dh-relay 是什么、现在做到哪

- 一套**接力执行**系统：一张 dev-harness 方法论下的开发任务卡由多个 AI agent 接力跑完，中间**没有常驻 AI 主控**，人只在落户确认 / 决策 / 收口确认时出手。
- **现役实现（P1）**：PowerShell 7 脚本 + Markdown 工件，终端后端 psmux（`tools/runner/`、`tools/host/`、`tools/adapters/`、`tools/contracts/`）。运行真相在业务仓 `.dh-runtime/relay/`（v1）。
- **P2 完整流水**（`dev_plan/P2-完整流水-开发方案.md:78-105`）：19 张标准卡，只有 `DHR_04`（前置机器护栏）已完成，其余 18 张未开工。其中和本文强相关的未开工卡：`DHR_05` 冻结 relay/v2 身份链、`DHR_08` 用户级执行 profile 与 quota fallback、`DHR_09` 控制台 + detached 宿主、`DHR_12` 授权 request/snapshot、`DHR_14` 诊断 agent、`DHR_18` 重编排。
- **P3 Herdr 底座**（`dev_plan/P3-...md:87-91`）：3 张卡（可配置后端 → herdr 适配器 → 真卡实战），未开工。
- **04 技术方案**（`design/04`）：建议 Go 重写 Core、Herdr 首选宿主、Workflow Contract + 受控图、agent-console 当外部控制台。**待确认，未开工**。

### 05 方案说了什么（一段话版）

DSH（DeepSeek Harness）当个人工作台外壳，dh-relay 做成 DSH 里的持久工作流服务；第一阶段走**方案 C**：DSH Bridge 插件（Host + Client）↔ `relay.rpc/v1`（Named Pipe / UDS，JSON-RPC）↔ 独立 Relay Runtime。DevHarness 仍以 Workflow Contract + Gate 接入；施工主力仍是 Herdr + Codex/Claude Code；DSH 原生 Agent 负责规划 / 接力计划实例化 / 重编排 / 诊断 / 汇总；DSH one-shot Codex/Claude Provider 负责 fresh review。Go vs TypeScript 的决定推迟到 Pilot 后。给了 POC-0～7 验证计划、W/R/X/A/D/P 六组验收命题和 10 条停止条件。

## 第二部分：对 05 的评估

### 2.1 总判断

**方向可以试，方案 C 是对的选择，保护原则也对。但 05 不该整份"确认进白名单"——只该批一个很窄、限时的 Pilot（POC-0～2），其余等证据再决定。**

### 2.2 站得住的部分（已独立核对）

| 05 的判断 | 核对结果 |
|---|---|
| §4.1 DSH workflow seam 无检查点、重启不能恢复、无后台脱离收集、运行不由服务跟踪 | ✅ 官方 `packages/workflow/workflow/README.zh.md`「已知限制与暂缓事项」逐条对应：*仅支持前台收集 / 没有日志化或恢复 / 没有已保存或嵌套工作流 / 运行由持有方负责不由服务跟踪* |
| §4.3 Codex Provider 每次新进程 + 临时线程、只回最终文本、无续接、无人工审批路径 | ✅ 官方 `packages/subagent/subagent-codex/README.zh.md`「已知限制」原文：*每次运行均新建一个进程、一个线程和一个轮次，不支持续接、恢复、池化、进度流…；没有人工审批路径，已知的无人值守审批请求会被拒绝；产品载荷仅包含最终文本* |
| §3.1 仅有 RC 标签、开发者预览 | ✅ 仓库 tags 列表只有 `dsh-v0.1.0-rc.7` |
| §4.4 E11 授权不交给 DSH 一次性 approval；§4.5 动态包不承重核心；§6.1 三类真相分层 | ✅ 逻辑正确，是必须守住的红线 |
| §10.3 冻结 agent-console、§13.3 Go 决策后移 | ✅ 实际上是**减负**，值得肯定 |
| §17 给了停止条件、§16 给了验收命题 | ✅ 比 04 直接定 Go 更稳 |

### 2.3 担心的地方（按重要度排）

**C1. 计划堆叠、交付为零。（最大风险）**
现状：P1 跑通；P2 19 卡完成 1 张；P3 未开工；04 未开工。05 再叠一层：POC-0～7、三个新插件包（`dsh-relay-host / client / devharness`）、一套 Named Pipe JSON-RPC、一个新的 `dsh-agent` 执行器种类、Executor Profile 体系。每份文档单看都合理，叠在一起就是"永远在设计"。05 §18 自己也说"确认后 P2 要 B-adjust"——即 18 张未开工卡要重排一次。
→ 既然用户已倾向 DSH 为主体，那**该做的是尽快让这条路线产出第一个可运行的东西，而不是先把 05 全文当规范**。

**C2. POC-2 的前置条件被低估。**
05 §7.1 / POC-2 要求 `relay contracts / profiles / list / status / inspect --json`。但 *Workflow Contract* 与 *Executor Profile* 是 04/P2 里**尚不存在**的概念（对应 `DHR_05 / DHR_08 / DHR_12` 未开工）；现役 relay 只有 v1 存储和 runner/replay 脚本，没有 `contracts`、`profiles` 子命令。POC-2 不是"接一下现有 CLI"，而是隐含要先做一截 P2。文档写成了纯桥接。

**C3. DSH 路线买到的主要是"工作台 UI"，而当前最缺的是流水本身。**
DSH 的收益集中在页面、会话、模型配置、插件管理这些外壳能力；dh-relay 真正缺的是 P2 那 18 张卡描述的持久流水。流水不通，UI 无物可展。这不否定 DSH 路线，但决定了**Pilot 里 UI 只需证明"能接、能活过重启"，不必做全 §10.2 那三个页面**。

**C4. 05 漏掉一个可能改变 §13 天平的事实：DSH 可继续子 Agent 已有会话持久化与冷恢复。**
05 §4.2 说"DSH Jobs 和 Terminal 以进程生命周期为边界"——对 workflow / Jobs / Terminal 成立；但官方 `packages/subagent/subagent/README.zh.md` 明确写了 **continuable 子 agent 有持久化 header、冷恢复（cold recovery）、`list_agents` 把仅存于存储的子 agent 映射为可恢复的 `ready` 状态**。即 DSH 原生 Agent 会话层的耐久性比 05 描述的强，方案 B（原生 TS Relay Service）与方案 C 的差距没那么大。**结论不变**（编排层的检查点/恢复仍没有），但 §13 "Go vs TS" 在 Pilot 后评估时必须把这条算进去。

**C5. Windows 是用户主平台，DSH 在 Windows 上只验证过"装得起来"，没验证过"插件树外接得进去"。**
用户已在 Windows 上安装过 DSH（未深入使用），所以"能否安装、能否启动"这一关**大概率已过**。但 05 真正压重的是**树外 Host + Client 插件、Profile 安装、Named Pipe、子进程树清理**这些在 Windows 上的表现，这些仍未实测，应是 POC-0/1 第一件事。

**C6. 外部 Client UI 插件是最可能被 rc 升级打碎的一层。**
05 §14.4 已承认。补充：目前**只有一个 rc tag**，没有版本序列可以观察 API 稳定趋势，"兼容层能否收束"眼下无法预判，只能靠 Pilot 期间实际经历一次升级来看。

**C7. 两份"待确认"文档并存，主线不清。**
04 说定 Go，05 说 Go 后移；04 让 agent-console 当控制台，05 让 DSH 当。两份都未进白名单，容易让后续 agent 拿错基线。既然倾向 DSH，建议**明确一句：04 的 Workflow Contract / 受控图 / Gate Adapter / 三类真相继续有效，04 的 Go 与 agent-console 两条被 05 取代**，写进 04 状态栏，别让两份并列。

### 2.4 建议

1. **不把 05 整份加进 `designInputs`。** 用一张**轻档、限时（2～3 天）、在 dh-relay 仓外的实验目录**跑 POC-0～1：独立 `$DSH_HOME`、装 rc.7、树外写最小 Host + Client 插件、在 **Windows** 上让 UI 出现一个面板并渲染一条 fake run。只回答 W1 / W2 / W6 三个命题 + C5。
2. **POC-2 改口径**：先读现有 v1 `.dh-runtime/relay/` 存储 + 一条 fake run，**不等** Contract / Profile。
3. **无论 DSH 成不成，`DHR_05`（冻结 relay/v2 JSON 身份链）都先做**——它是 DSH 桥接、agent-console、Herdr 三条路共同的前提，不会浪费。
4. Pilot 通过 → 05 进白名单，P2 做 B-adjust，同时按 C7 更新 04 状态；Pilot 不通过 → 05 降级为实验记录归档，P2/P3 原路走。
5. **既然倾向 DSH 为主体**，Pilot 里额外多验一件事：DSH 原生 Agent 能否作为**棒 0（接力计划实例化）**的执行器跑通一次——这是 DSH 路线里最先能替换掉现有实现、又不碰 E11 授权红线的节点。
