## 1. 起因与需求理解

DHR_35 的 E-3568~E-3571 证明：production driver 与外围 runner 是两个 prompt 写入者；Herdr request accepted、`idle/state_change_seq` 与 `--wait` 都不能证明目标 turn 已收到或 settled。独立诊断又纠正了两项过强表述：仓内没有首样本绝对时间，不能说它必然晚于 delayed Enter；同形官方复现只能证明假阴性风险，不能证明本次就是假阴性。

主控最初提出“投递不确定就撤销旧 Attempt/Pair 后新建 Attempt”。用户认为这对实际发生率而言过度，原话为：“**是不是有点过度但有了。我基本没遇到过你担忧的问题。不然就重发好了。不会重复做的**。”主控据此把方向改为：单一内容 owner、同一 Agent 原样补发一次、第二次后停止，不以重启作为常规路径。

理解问题进一步收窄为：常规无进展时重发一次；只有身份变化或发送中崩溃导致次数不可证时才停人。用户回复“可以”。这形成审核输入，不使设计生效。

## 2. fresh-context 初审

审核实例：`/root/single_prompt_design_review`。fresh、只读、未参与起草；读取仓根 `AGENTS.md`、正式 `design/README.md`、`design/10`、`design/12`、现役 `workflow-driver.mjs` 与 `herdr-executor.mjs`；未写文件、未启动 Agent/Relay run、未读取凭据。

结论：P0=0，P1=4，P2=2，`CHANGES_REQUESTED`。

| # | 发现 | 主控裁决与调整 |
|---|---|---|
| R1 | 现役启动、恢复、解除 blocked 三处仍会独立发送 completion instruction，与“一份完整 prompt”冲突。 | 采纳。A-full 明确用 startup dispatch 取代三处发送；外围 runner/Role Relay 第二 sender 归零。 |
| R2 | 现役 `sendToHerdrAgent` 只按 agent name 调 prompt，不能证明补发仍绑定同一 terminal instance。 | 采纳。每次发送前后核 Host generation、agent instance 与 terminal-derived `host_ref`；不可证/变化则消耗 slot、`delivery_uncertain`、不补第三次。 |
| R3 | “最多一次补发”没有发送后、落账前崩溃的线性化规则。 | 采纳。Actor 在物理发送前 CAS 占用 ordinal 1/2 不可回收 slot；异常/崩溃也消耗，恢复不猜测。 |
| R4 | 只存 digest 未定义如何跨恢复逐字重建相同 prompt。 | 采纳。冻结 versioned formatter、字段闭集与全部确定性输入；digest 不同即拒绝。 |
| R5 | “一次完整 prompt”易被理解为一次物理投递。 | 采纳。正式名称和承诺固定为“单一内容、最多两次物理投递”，不承诺 exactly-once execution。 |
| R6 | 用户“不会重复做”不能升级为系统安全保证；Result 幂等不覆盖文件、命令或外部副作用。 | 采纳。重复 prompt 固定要求从持久事实续做，并在正文与验收显式保留副作用边界。 |

## 3. 第一轮定向复审

同一审核实例只读复核 R1~R4 的调整，并引用用户对有限重发与不确定场景 stop 的确认。结论：R1/R2/R3 PASS；R4 OPEN，P0=0、P1=1，`CHANGES_REQUESTED`。

剩余问题是安全存储：若保存展开的 workspace/instruction 内容可能违反密钥红线，只存 digest 又可能无法跨源变动重建。审核要求不能把选择留给施工期。

主控采纳并冻结：startup dispatch 不复制 workspace 正文；私有 ignored runtime 只存版本化白名单结构字段，Receipt 只在 `design/12` 已批准范围出现；prompt body 不持久化，只由模板版本和冻结字段确定性重建；敏感/未知字段、来源漂移、模板缺失或 digest 不同一律拒绝 ordinal 2 并 `waiting_human`。

## 4. 第二轮窄复审

同一审核实例只读复核安全重建补丁，确认结构化 source、私有存储、确定性 formatter 与 fail-closed 规则闭合 R4；未新增 P0/P1，最终 `PASS`。

主控裁决：全部 P0/P1 已采纳并进入正式正文；P2 均已通过准确命名、状态词和副作用边界闭合。用户已裁决唯一产品取舍，不再存在必须由主控代拍的问题。

## 5. 用户理解对齐与整版确认

面向用户的整版说明覆盖：唯一逻辑/物理 owner、完整内容来源、最多两次投递、两枚不可回收 slot、同一身份补发、崩溃/身份不明停人、私有结构重建、Result 唯一完成真相及机器/人验边界。

用户先于 2026-09-07 对取舍回复“可以”，随后在整版确认口明确回复“确认”。该确认只授权将 `DHR-A-31` 正文、README 白名单、候选形成史与本审核记录原子晋升；不授权 B-adjust、DevPlan/任务卡、代码、真实 Agent、DHR_35/P6 收口、Linux、verify、合并、推送或部署。
