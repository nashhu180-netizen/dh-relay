## 1. 本 session 讨论过程

### 1.1 从“主控派活”转向“接力执行”

用户提出：“对 dh crew 换种形式……我想改成接力的形式。”初始设想是 Design/DevPlan 先讨论定稿，正式开工后按 dev-harness 阶段逐棒运行：一个 agent 建 workspace 后结束，另一个施工，之后由复核 agent 组织并行 review；有问题再回施工 agent。

讨论确认：旧模式的痛点不只是 agent 数量，而是常驻主控拉外部 agent 后要定期巡检、在主会话刷屏，且人不容易直接看见真正施工 agent 的现场。新模式应让真实可交互终端成为第一等对象，人可以随时切换查看。

### 1.2 编排 agent 与 Runner 分开

用户明确：“这个编排只是负责设计评估接力计划，完成就关了。”据此分成：

- 一次性编排 agent：把已经确认的计划转为 RelayPlan，或在阻塞时提出一版修订。
- Runner：规则式 while/if/loop，读取文件状态、验证身份和状态转换、自动拉起下一 agent。
- 施工/review agent：对业务内容和代码质量负责；Runner 不负责质量判断。

用户允许 Runner 在规则无法判断时拉起 agent 辅助诊断，但不把 Runner 变成长驻 AI 主控。

### 1.3 两个状态维度

用户提出终端生命状态与业务状态必须拆开：终端可能“进行中、完成、停止、退出”，业务则可能完成、需要决策、发现前置阻塞、额度耗尽或未知中断。

讨论进一步澄清：

- agent 活着时可以先写交接、声明交棒；已经被外部停止后不能再自行补交。
- Runner 若跟踪准确 session，可以知道进程/会话是否消失，但不一定知道消失原因。
- `stopped_by_user` 只有停止经过 Runner 控件或可信宿主事件时才能精确记录；否则只能记未知中断。
- 普通终端不存在天然“进程退出但只读 tab 永久保留”的统一语义。本模块采用“挂起=session 保留可继续；退出=session 关闭、后续 fresh agent 读工件恢复”。

### 1.4 三类停止的最终取舍

用户确认以下分界：

1. **需要人类决策**：挂起，不退出；人在原 session 回答。
2. **复核后可能马上返工**：施工 agent 可以挂起，方便回到原上下文。
3. **发现前置任务阻塞、需要重新编排**：写完整交接包后退出；阻塞项完成后拉 fresh agent 恢复原任务。

完整交接包至少包含结构化 result、可独立阅读的 handoff、changed paths/tests/Git 现场、恢复条件，以及 best-effort、脱敏、限长的最后回复/session tail。session tail 只帮助回看，不是权威状态。

### 1.5 落文档与最小 PoC

用户要求新建独立模块，`design` 中保留本 session 讨论过程与正式设计方案，并建立 DevPlan 做最小 PoC。主会话按 dev-harness 解释：两份实质文档之外还需要一个机械 manifest `design/README.md`；讨论过程进入 `design/evidence/`，不参与 B 拆计划。

PoC 被收窄到最难闭环：阻塞重编排 + fresh 恢复、decision 挂起、旧结果 stale、异常 fail-closed，以及一次真实可见终端演示。完整 review 扇出留到后续 A/B。

### 3.1 面向用户讲解

- **全局地图**：已确认 Design/DevPlan → 一次性编排 agent 写候选 RelayPlan → Runner CAS 激活 → 自动打开真实 agent → result/handoff 驱动下一棒。

- 问题：首个 PoC 的真实终端后端，选择可精确追踪/回收、同时必须自动打开为可见交互界面的 `psmux`，还是只保证弹窗直观但不能证明精确退出的普通 Windows Terminal？

### 6.3 用户否决二次操作后的调整

> 历史方案：本节描述的输入桥已被 §10.1 全部作废，仅保留为过程记录，不代表当前设计。

- 用户回答：2026-08-14，“不符合，会增加我的负担”。该回答否决“在 agent session 回答后，再去 Runner 控件提交一次”的方案。
- 主会话裁决：用户正常路径只能操作一次。改为 launch-scoped 可信输入桥在终端输入边界捕获真实 `user_submit`，先提交绑定 nonce/authority/session 且只含输入摘要的事件，再把同一缓冲输入恰好一次转发给 worker；Runner 只认同时证明 event committed 与 input forwarded 的 bridge receipt。
- 安全边界：禁止从 transcript/stdout/worker 回复/工具输出推断用户输入；任一半提交保持 `decision_required` 并自动补齐未完成侧，不要求用户重复操作。后端做不到真实输入边界捕获时 A4 失败，不得降级成二次 Runner 操作后宣称 PoC 通过。
- 正式落点：设计 §1.3、决策表、§3.4、§4.2、§5、A4/H1；DevPlan DHR_01/02/03。
- fresh Fable 5 xhigh 定向复审：一次回答方向、A1～A8/H1～H2 覆盖、三卡依赖/状态与禁改边界保持；无新增产品取舍。要求补齐半失败重试上限、event/forward 摘要一致、桥信任锚、恰好一次持久 journal 与两个半失败恢复正例。
- 主会话裁决：全部采纳但收紧顺序为 `captured→event_committed→input_forwarded→receipt_acked`。event-only 可补 forward；event+forward/ack-missing 只补 receipt；forward-without-event 属不变量破坏，转 `interrupted_unknown`，不允许事后补造事件。桥由 Runner 启动并拥有、通过认证 IPC 回传，原始输入只在 host-only 临时缓冲存在，ack 后清除。
- 返工确认：同一 reviewer 重读后确认五项全部 closed，无新 P0/P1、无新增产品取舍；正常路径与 event-only/ack-missing 两类可恢复半失败的人工动作数均为 1，forward-without-event 保持 fail-closed。

## 10. 用户确认 Runner 不介入原会话回答

### 10.1 对过度设计的纠正

- 用户追问：2026-08-14，“如果人类回答了，继续运转了，为啥runner还要介入呢。”该问题指出此前方案把“Runner 管依赖调度”误写成了“Runner 还要恢复会话”。
- 主会话裁决：此前的 launch-scoped 输入桥、bridge receipt、输入缓冲、journal、转发补偿和重试设计全部作废，不进入正式 P1 契约。保留这些段落仅用于记录方案如何被用户否决，不代表当前设计。
- 当前边界：`decision_required` 是同一 attempt 的非终态 checkpoint。用户在原 session 回答后 agent 自然继续；Runner 不读取、转发或确认回答，不调用 resume，也不生成“用户已回答”控制事件。
- Runner 的唯一相关职责：看到 checkpoint 后冻结依赖当前节点的后续节点，无依赖的并行节点继续；随后只接受同一 authority/launch/session/attempt 的有效后续 checkpoint 或 final result。session 消失或 probe 无法确认时仍按 `interrupted_unknown` fail-closed。

### 10.2 理解确认与计划联动

- 理解问题：`decision_required` 期间，Runner 只冻结依赖当前节点的后续工作；与它无依赖的并行节点仍可继续——这是否符合预期？
- 用户回答：2026-08-14，“可以”。
- 联动范围：正式设计 §1.3、§3.1、§3.3、§3.4、§4.2、§5、A4/H1、§9；DevPlan §0 与 DHR_01/02/03。三卡、状态、依赖、批次和禁改边界均不变。
- 授权边界：该回答确认产品行为，不授权 DHR_01 开工、建 worktree、提交或 verify。

### 10.3 fresh Fable 5 xhigh 定向复审

- 审核实例：`claude-fable-5`、账号 `claude5`、effort=`xhigh`，fresh 只读调用；第一次调用在 124 秒命令时限内无输出并被终止，第二次收窄审阅范围后返回，均未修改仓库。
- 结论：**可开工**，P0=0。正式 design/devplan 已一致排除 Runner 介入原 session 回答；历史 bridge 方案仅在 evidence 中保留且已明确作废。
- 采纳的最小澄清：①在 §3.1 明列 `idle → running/unknown`、`decision_required → working/final/interrupted_unknown` 的触发边界，DHR_01 不得新增出口；②P1 Runner 只保持 `active/paused` 投影，不定义完成/失败；③checkpoint 历史统一进入全局 `events.jsonl`；④DHR_01 冻结 `session_tail_max_bytes` 与先脱敏后限长；⑤DHR_03 第一动作设 psmux backend preflight；⑥DHR_02 明确编排 proposal 使用 fixture。
