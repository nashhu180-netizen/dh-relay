## 2. 首轮审核结论

结论：`changes-requested`；Blocker 0、High 2、Medium 2、Low 1。

### 方案问题

1. **High · `continue` request/Receipt 漏冻结**：正式设计要求承重实现前冻结，但候选初稿让 DHR_55 直接实现，可能造成授权/幂等合同漂移。建议归入 DHR_54，DHR_55 只消费。
2. **High · 旧 P7 Gate 未重映射**：旧 `P7-M1~M9` 仍挂在拟取消的 DHR_36~40；若只取消卡，P8 解锁条件会悬空。建议保留历史并建立新的 active P7 Gate。
3. **Medium · active A 集合写得过宽**：DHR_60 初稿写“重放 A1~A31”，会把已 superseded 的 A20/A22 带回。建议只重放 active 集合，A20/A22 仅作历史反例。
4. **Medium · Orchestrator Lease 无归属**：正式设计要求 Runner-issued run-scoped Lease；候选只验证“有效 Lease”，未写 schema 和生命周期责任。建议 DHR_54 冻结、DHR_55 实现签发/续期/撤销/过期。
5. **Low · Oracle 边界易混**：DHR_60 排除 P8 Oracle，同时又写独立 E2E oracle。建议明确排除的是 P8 cross-card/archive Oracle，本卡单卡独立 oracle 仍必做。

### 用户理解风险

- 新 `DHR_55/DHR_56` 虽已改为窄卡，仍可能被误解为沿用旧候选同号范围；需明确不继承。
- DHR_56 只形成“单步骤安全接力”的中间成果，不等于 P7 完成；完整交付仍依赖 DHR_57~60。
- 七张 heavy、一张 normal 的配方合理；DHR_57 若触及身份/权限合同必须停下由用户重定类，不能施工方自升级。

### 需要用户决定的问题

- 是否接受旧 P7 M1~M9 只保留历史，并改由新 P7-M10~M17 解锁 P8。
- 是否接受把 `continue` Receipt 与 Orchestrator Lease 合同/生命周期分别前移到 DHR_54/DHR_55。
- 是否确认 DHR_60 只重放 active A 集合，A20/A22 仅作 superseded 反例。
