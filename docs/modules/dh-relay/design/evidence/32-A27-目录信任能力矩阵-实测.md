## 1. 主矩阵：5 种目录形态 × 2 产品

「起来」= `agent start` 成功且屏幕无信任框；「**信任框**」= 屏幕上确有目录信任对话框。

| # | 目录形态 | Codex | Claude Code |
|---|---|---|---|
| 1 | 已信任仓根（对照） | 起来（4.7 s） | 起来（4.8 s） |
| 2 | 已信任仓的**普通子目录**（无 `.git`） | 起来（5.0 s） | 起来（5.2 s） |
| 3 | 已信任仓内的**嵌套 git 仓** | **信任框**（`agent_not_ready`） | **信任框**（`agent_not_ready`） |
| 4 | 已信任仓的 **git worktree**（仓内 `.dh-worktrees/`） | 起来（8.2 s） | 起来（4.9 s） |
| 5 | **全新 git worktree，建在仓外 `%TEMP%`**（F1） | 起来 | 起来 |
| 6 | 完全外部的**非仓目录**（同一个 `%TEMP%` 下） | **信任框**（`agent_not_ready`） | **信任框** |

### 结论

**C-1｜两个产品在这六种形态上行为完全一致。** 原草案「Codex 与 Claude 的信任模型可能不同」的假设**不成立**；审核 R-08 引用 Claude 文档提出的「父目录 trust 可扩展到子目录」，在本机实测下与 Codex 表现相同，没有产生跨产品差异。

**C-2｜信任的单位是「git 项目根」，无 git 时是 cwd 本身。** 第 2 行（子目录通过）不是"父目录信任向下传递"，而是 **git 根解析**——它解析到了已信任的仓根；第 3 行（嵌套仓弹框）正是同一规则的反面：嵌套仓自己就是 git 根，且未被信任过。

**C-3｜git worktree 继承主仓的信任。** 决定性证据是第 5 行对第 6 行：全新 worktree 建在 `%TEMP%` 下（与仓根**无任何路径前缀关系**），两产品都直接起来；而**同一个 `%TEMP%` 下**的普通新目录，两产品都弹框。唯一变量就是那个 `.git` 文件。这条同时排除了第 4 行的替代解释（"`.dh-worktrees/DHR_35` 是以前被单独答应过"）。

**C-4｜信任闸不被任何权限/沙箱参数绕过，本轮用最强的旁路参数复证。** 本机 `codex` 壳固定注入 `--dangerously-bypass-approvals-and-sandbox`，第 3、6 行**照样弹信任框**。这把 DHR_35 的旧结论（`--sandbox` / `--ask-for-approval` 不绕过）推到了上限。

## 2. 新发现：herdr 对 Claude 的启动期 blocked **报不出来**

第 6 行 `claude / outside` 的三个信号互相矛盾：

| 信号 | 值 |
|---|---|
| `herdr agent start` 退出码 | **0（成功）** |
| `agent get` 的 `agent_status` | **idle** |
| `pane get` 的 `agent_status` | **blocked** |
| 屏幕文本 | **就是目录信任框** |

同批实验里 `agent get` 与 `pane get` 本来就会因采样时刻不同而短暂不一致（`codex/root` 是 working vs idle，`codex/subdir` 是 idle vs working），所以**不能**拿这两者的差异单独下结论。但本行的方向是明确的：**`agent start` 已经返回"启动成功且可交互"，而产品实际正卡在信任框上。**

**对 DHR_68 的影响（登记为新 finding，不在本次范围内修）**：DHR_68 缺陷 C 的启动期 blocked 检测**只认 `agent_not_ready` 错误码**。该判据对 **Codex 成立**（第 3、6 行都是 exit 1 + `agent_not_ready`），**对 Claude 不成立**——Claude 走的是"start 报成功"的路径，`launch_blocked` 不会被置位，relay 会把一个卡在信任框上的 agent 当成就绪 agent，然后把提交指令发进去。

> 这条与 A-27 是**独立缺陷**：即使 A-27 一行代码不做，DHR_68 的 Claude 侧仍有这个盲区。建议单独立卡。

## 3. 会话中途新增目录（路线 A 覆盖面的关键格）

**测得**：Claude 会话中途对一个**从未被信任过的仓外目录**执行 `/add-dir`：

```
❯ /add-dir C:\Users\nash\AppData\Local\Temp\A27mid
  ⎿  Added C:\Users\nash\AppData\Local\Temp\A27mid as a working
     directory for this session · /permissions to manage
```

→ **没有任何信任框**，直接加入。

**如实登记的混淆项**：该实例处于 auto mode。同批实验已证明"权限模式不抑制信任闸"（§1 C-4：codex 全程 bypass 参数仍弹信任框），因此倾向认为 `/add-dir` 本身就不过信任闸；但**未在 manual mode 下复测**，故本格标 **「部分测得」**，不作为已闭合结论。

## 4. R-01 可区分性实测：同产品的信任框 vs 非信任审批框

审核 R-01 的核心担忧是「文本匹配无法证明这就是目录信任框，可能把别的审批框认成它」。本轮实拍了三个框。

**Claude · 目录信任框**
```
Quick safety check: Is this a project you created or one you trust? (Like your own
code, a well-known open source project, or work from your team). If not, take a
moment to review what's in this folder first.
❯ No, exit
  Yes, I trust this folder
Enter to confirm · Esc to cancel
```

**Claude · 命令审批框**（同产品、同目录、同为 blocked 态）
```
Bash command
   ls /c/Windows | head -3
   List first 3 entries in C:\Windows
Do you want to proceed?
❯ 1. Yes
   2. Yes, allow reading from /c/Windows from this project
   3. Yes, and switch to auto mode
   4. No
Esc to cancel · Tab to amend · ctrl+e to explain
```

**Codex · 目录信任框**
```
Do you trust the contents of this directory? Working with untrusted contents comes
with higher risk of prompt injection. Trusting the directory allows project-local
config, hooks, and exec policies to load.
› 1. Yes, continue
  2. No, quit
Press enter to continue
```

### 判定 4-A：可区分性**比审核假设的好**，但没归零

Claude 的两个框在**三处同时不同**：标题句（`Quick safety check` vs `Do you want to proceed?`）、选项标签（`Yes, I trust this folder` vs `Yes / allow reading from …`）、页脚指令（`Enter to confirm · Esc to cancel` vs `Esc to cancel · Tab to amend · ctrl+e to explain`）。三处合取的匹配器误命中概率远低于 R-01 假设的"只能靠模糊文本猜"。

**但仍未归零**：这是**版本快照**，不是契约。产品改文案即失效——这正是草案里「版本化 matcher + 未命中即回退到人工」那条约束存在的理由，本实测**加强**它、不取消它。

### 判定 4-B（本轮最重要的一条硬约束）：**默认高亮项方向相反，禁止盲按回车**

| 框 | 默认高亮（`❯` / `›`）落在 |
|---|---|
| Claude 目录信任框 | **`No, exit`** |
| Claude 命令审批框 | `1. Yes` |
| Codex 目录信任框 | `1. Yes, continue` |

所以任何"盲按回车"式的自动放行实现：**在 Claude 信任框上会直接退出会话**，**在 Claude 命令审批框上会批准任意命令**。

> **对 A-27 草案的硬约束（必须写进正文）**：路线 B 的按键动作必须**按选项标签文本定位并逐步导航**，禁止按位置、禁止盲按回车、禁止复用另一个产品的键序。且导航后、确认前必须复验高亮行文本确实是目标选项。

### 未测：Codex 的非信任审批框

本机 `codex` 壳固定注入 bypass 参数；绕壳直调真二进制并加 `--sandbox read-only --ask-for-approval on-request` 后，只读命令与仓外写命令**都没有触发审批框**（推测配置层仍是 `never`）。因此 **Codex 侧的可区分性未测得**，判定 4-A 目前**只对 Claude 成立**。

## 5. 对 D-1 的影响：覆盖面账被改小了

路线 A（启动前预置产品信任表）需要覆盖的目录集合，由 §1 的结论收窄为：

- **每个 git 项目根**（无 git 时为 cwd 本身）——不是每个路径，也不是每个子目录；
- **worktree 不需要单独预置**（C-3）；
- 会话中途 `/add-dir` **不过信任闸**（§3，部分测得），故它对路线 A **不构成缺口**。

这与原草案「路线 A 覆盖不全所以排除 A」的论证方向相反：**缺口比原先设想的小得多**。原论证在 [31 §6.4](31-A27-目录信任自动放行-交叉审核记录.md) 已作废，本节进一步给出正向证据。

路线 B 这一侧，本轮的净效果是：**残余风险降低**（判定 4-A）**但新增一条硬约束**（判定 4-B）。

**D-1 仍待用户裁定**，本文只交事实，不替用户选。
