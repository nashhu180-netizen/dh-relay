## 一、方案问题（复核者原文摘要 + 主控裁决）

### R-01 · P1 · 缺陷 C 的目标与用户原始需求没有闭合

- **问题**：草案把启动期 trust `blocked` 改为 `waiting_human`，同时把"代产品做信任决定"列为非目标。
- **依据**：用户原话「这要做成固定的程序，以后不要用户自己按」「就是以后开新的项目，也能支持」。
- **影响**：新项目仍会停在需人工处理的产品信任框，只是从"报启动失败"变成"持久 Attention"，**不等于**"不要用户自己按"。
- **建议**：讲解前让用户明确选择——接受「安全暂停 + 人工确认信任」作为新项目语义，或要求「受控自动化信任」；后者新增信任授权、白名单、审计与撤销的产品安全语义，**应先走 A-full**。
- **主控裁决**：**采纳**。这是本轮最重要的发现——主控起草时确实把缺陷 C 当成了用户诉求的完整答案，实际只解决了一半。该取舍属产品决定，主控不代裁，转入 §三 交用户。草案对"用户诉求承接"的表述须改写。

### R-02 · P1 · 缺陷 C 的验收在当前实现下不成立，且允许路径不足

- **问题**：草案称"driver 按既有 `HERDR_STATUS_MAPPING.blocked` 产生 `waiting_human` + `human_input_requested`"，但现役 driver 并不消费该映射。
- **依据**：`herdr-executor.mjs` 确有该映射；但 `workflow-driver.mjs` 未导入或消费它。启动返回 `ready_observation=blocked` 后，driver 先发 completion instruction，随后把 `lastStatus` 初始化为 `blocked`，而轮询的 blocked 分支仅在 `lastStatus !== 'blocked'` 时才写 `human_input_requested`——因此**不会**写出草案所称的 blocked Attention；`blind` 分支至多写一个无 blocked 语义的泛 Attention，且 instruction 失败会先写 `E_EXECUTOR_HOST_LOST`。
- **影响**：无法证明"启动期 blocked 保留 handle 后按既有语义进入 Attention"；可能产生错误的 host-lost 归因，或缺少带 blocked 上下文的 Attention。
- **建议**：把 `workflow-driver.mjs` 与相应 driver 测试纳入 DHR_68 允许路径，删除"不得改 workflow driver"的非目标；若坚持禁改 driver，验收 C 必须降级为 adapter 局部事实。
- **主控裁决**：**采纳**。复核者给出了可复核的具体机制（`lastStatus` 初始化 + 分支条件），主控起草时未核到这一层。按建议扩允许路径并删除该非目标，验收 C 改写为可证的事件序列命题。

### R-03 · P2 · 缺陷 A 的"可配置且默认足以覆盖"不可证，配置边界未定义

- **依据**：`makeHerdrCli({ timeoutMs = 10_000 })` 把同一默认超时用于**所有** CLI 命令；DHR_35 只证明 6 次采样最大 29482 ms、3/6 超限，不能证明未来任意启动都在 60 秒内完成。
- **影响**：全局调到 60 秒会同时拖慢查询/关闭类命令的故障发现；只给 `agent start` 加时限，则草案未定义值从哪注入、谁可配置。
- **建议**：验收改为可证命题（启动专用默认值 + 现有 29482 ms 真实样本完成 + fake 覆盖"超时后 agent 存在/不存在"两支 + 其余命令超时语义不变）；默认取值与是否暴露配置面留给用户。
- **主控裁决**：**采纳**。原草案 §4 已自陈时限取值待用户定，但确实把"默认足以覆盖"写成了可验收命题，属不可证承诺，按建议改写。

### R-04 · P2 · DHR_67 的历史状态与依赖图需更精确

- **依据**：P6 现行计划已写明 DHR_67 只满足启动前置；其 frozen test 的 `paneRun` fake 默认返回 `{ ok: true, value: {} }`，与实测的 exit 0 + 空 stdout 不同。
- **影响**：只保留"已完成"而不补限定，易被读成"Windows Claude 已真实启动通过"；把 DHR_35 的全部既有前置机械串成 DHR_68 前置，会虚增第一个端到端 demo 的等待链。
- **建议**：限定说明须落在 **P6 任务表备注**（不能只写在新卡草案里）；DHR_68 只列实际所需依赖并说明理由。
- **主控裁决**：**采纳**。草案原写法把限定放在了新卡草案 §2.2，落盘后会消失在 drafts 里；改为直接改 P6 任务表 DHR_67 行的备注列。依赖图同步收窄。

### R-05 · P2 · "不触发 A-full"的主张需限定条件，且 A4 引用有误

- **依据**：design/12 的 `P6-RI-A4` 是 Windows 真实 `Receipt→checkpoint→submission→Result` **完整闭环**命题，不是"启动前置"；design/06 已要求无人客户端时需人类输入必须形成持久 Attention。
- **影响**：把 A4 写成启动前置会错误扩张 DHR_68 对既有验收的覆盖声明；若改为自动接受产品信任，则实质改变安全/交互语义。
- **建议**：只有在"修实现以兑现既有安全暂停语义、且不改稳定 ID / Result / Attempt 语义"时才维持不触发 A-full；若采纳自动信任，结论反转，先走 A-full。
- **主控裁决**：**采纳**。DHR_68 不再声称承接 A4，改为「A4 的启动前置条件」+ 承接 design/06 H1/H5 的 Attention 语义。是否触发 A-full 的结论**挂在 R-01 的用户裁决上**。

## 二、用户理解风险（复核者原文）

1. 用户最可能把"启动期 blocked 返回 handle 并进入 waiting_human"理解成"新项目以后会自动完成目录信任、无需再按确认"。按草案当前非目标，这两件事**并不相同**：前者只是把失败变为可见的人工暂停，仍可能需要用户处理产品信任框。
2. 另一个风险是把 DHR_67 的"已完成"理解成 Windows Claude 已经真实启动通过；现有主计划并不作此承诺，真实反例恰是 DHR_68 的触发原因。

## 三、需要用户决定的问题（复核者原文，转呈用户）

1. 对未信任的新项目选哪种语义：**安全暂停并由人确认**，还是**在明确限定的路径与条件下自动确认产品信任**？若选自动确认，允许哪些路径、谁授权、如何审计与撤销，须先进入 **A-full**。
2. 若保留自动化启动修复，启动专用默认时限取多少、是否允许配置、配置面是否面向所有项目；草案建议 60 秒只是基于当前最大 29.482 秒样本的**建议，不是已证事实**。
3. DHR_67 的正式历史表述是否按「保持已完成 + P6 表内明确 fake 覆盖局限、真实反例由 DHR_68 承接」落账；这不推翻既有 verify，但决定阶段闸面对该卡的可读含义。
