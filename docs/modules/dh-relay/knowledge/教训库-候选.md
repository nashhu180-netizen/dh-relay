# dh-relay · 教训库候选区（待裁决）

> **它是什么**：miner 自动抽出、还没人裁决的教训候选。**不是正册**——正册 `教训库.md` 只进人裁决过的。
> **怎么用**：① miner 收口往「候选清单」append，状态「待裁决」；② 人裁决——挑中 → 编 L-NNN 搬进正册、本行改标「已入册 L-00X」；弃 → 本行改标「弃 + 一句理由」（留着防 miner 下次又抽同一条），**不直接删**。

### 候选-1 · 判定函数的每个 reason 码 / 分支都要有断言钉住，并用静态守卫兜底（人肉小审逮不干净）
触发场景：写校验器 / 身份链裁决 / 状态机这类"多分支返回原因码"的契约代码，或复核此类代码 · 建议分类：编码陷阱 + 行为流程 · 来源：DHR_01 findings F-002(批A node 级)/F-005(批B stale-plan、wrong-node)/F-016(轮2 launch_id)/F-017(FreezeSet 只 1 跳)/F-020(系统性)/F-021(守卫精度)；吸收 lesson_candidates L-002
疑似重复：无（dh-relay 正册为空；与 dh-crew 教训库 L-001/L-010 同属"全绿掩盖"家族，但不是同一条）
- 现象：同一类缺口在三批施工里三次复发——某个 reason 分支删掉整段代码套件照样全绿；每轮换人复核各逮一条，直到轮 2 才立系统性守卫；守卫首版又被复验发现"修了没锁"（全变量插值 reason 静默漏抓、注释里出现码就算覆盖）。
- 反思：TDD 只保证"写了的断言"是红过的，不保证"每个分支都有断言"；靠人眼在几百行 diff 里数分支必漏。守卫本身也是代码，同样会有精度盲区，须用变异探针证明它真会红。
- 建议后续动作：① 契约/判定类任务的 task_plan 验收项写死"每个原因码 ≥1 条断言"；② 保留并沿用 `tools/tests/relay-contract-reason-coverage.ps1` 模式（源码原因码集合 vs 断言行原因码集合，差集非空即红；非字面 reason 直接 fail-closed）；③ 新守卫加完必做两个探针（注入未覆盖码→红；码只在注释→红）才算"锁住"，不能只看 ALL PASS。
状态：待裁决

### 候选-2 · 穷举 / 矩阵测试的期望值不能来自被测数据本身（自证循环）——测试里独立硬编码设计文档的 oracle
触发场景：给状态转换矩阵、枚举表、白名单等"数据即规则"的东西写穷举测试 · 建议分类：编码陷阱 · 来源：DHR_01 findings F-011（轮1 批B~D 小审探针 3a）
疑似重复：无
- 现象：transitions 套件 72 组合穷举以 `transition-matrix.json` 自己为期望：删掉 `running→idle` 合法边 84 断言照样全绿，错加设计未列的边也放行；只有 4 类特殊边有独立锚。
- 反思：把数据文件当 oracle 等于"用答案对答案"，穷举规模再大也证明不了矩阵和 design §3.1 一致，只证明代码读得懂自己的 json。
- 建议后续动作：测试里独立硬编码设计文档的合法边集合，先断言"矩阵边集合 == oracle"（多一条 / 少一条都红），再拿 oracle 做穷举期望；收口前用"删一条合法边"变异探针验一次真红（本卡 E-009 做法）。
状态：待裁决

### 候选-3 · 验收口径写"多类工件任一残留即失败"时，每类工件要有真实形态的夹具，不得同一字符串换标签循环冒充多类覆盖
触发场景：脱敏 / 清洗 / 校验类需求写"对 N 类工件都生效"，或复核此类测试 · 建议分类：编码陷阱 + 行为流程 · 来源：DHR_01 findings F-006（E4 需求复核）；吸收 lesson_candidates L-003
疑似重复：无
- 现象：A8 要求 handoff/result/event/session-tail 四类 final 工件零残留，redaction 套件却是同一段文本贴四个标签循环断言，实际走完整脱敏链路的只有 session tail；`Test-RelayArtifactClean` 还靠 `hunter` 关键字启发式判 kind，是贴着夹具写的。
- 反思：把"N 类"退化成"1 类 × N 个标签"能让断言数好看、但没有覆盖各类工件的字段位置 / 格式差异；这类假覆盖 TDD 自己发现不了，只有从需求角度反查才露馅。
- 建议后续动作：需求条目里凡出现"多类 / 任一 / 各自"字样，验收表就按类拆行、每类一份该形态的最小夹具（含凭据的 handoff 头、result summary 字段、event reason 字段…）；确实只做通用函数不接线的，review 明写"本卡只证通用函数、接线归下游卡"，别用循环冒充。
状态：待裁决

### 候选-4 · 主控预写 task_plan / brief 里的"见下方 XX 表 / 见 §X"内部引用，派活前先机械核一遍目标真实存在
触发场景：主控（或任何人）预写施工计划、给 worker 派活前的自检 · 建议分类：行为流程 · 来源：DHR_01 findings F-000（P1）+ progress "主控失误补录"；吸收 lesson_candidates L-001
疑似重复：疑似与 dh-crew 教训库 L-013（派活前"钉死 brief"）同族——本条是它的一个具体子项：引用完整性
- 现象：task_plan A2 写"字段表见下方【schema 冻结表】"，表根本没写；codex 首派读完即 blocked（拒绝自行发明 fail-closed 白名单），主控补表后续派，白耗一轮派活。
- 反思：主控写计划时"表我待会补"的意图没有落地，也没有一步机械检查把悬空引用挡在派活前；worker 侧行为其实是对的（escalate 而不是猜），问题全在主控。
- 建议后续动作：派活前对 brief/task_plan 跑一遍"引用目标存在性"检查（正则抓"见下方 / 见 § / 详见【】"→ 在同文件或引用文件里能定位到）；可作为 dh-check 或 controller-brief 校验器的一条静态规则；契约类任务尤其要在派活前把字段白名单本体给全，不给"稍后补"。
状态：待裁决

### 候选-5 · PowerShell 默认比较大小写不敏感（`-in/-eq/-ne/-notin`），冻结枚举必须用 `-cin/-ceq/-cne` 或 Ordinal 比对，且修一处要全库 grep 同类算子
触发场景：用 PowerShell 写枚举校验、状态快照判定、任何"精确字面匹配"的 fail-closed 逻辑；返工修同类 bug 时 · 建议分类：编码陷阱 · 来源：DHR_01 findings F-001（批A 小审 P2）+ F-008（E4 复核发现修复未覆盖 relay-transitions.ps1）
疑似重复：无
- 现象：`Test-RelayEnumValue` 用 `-notin`，`"role":"Worker"` 等大小写变体过校验，冻结枚举 fail-closed 形同虚设；批A 修成 Ordinal 后，同仓 `Get-RelayStallVerdict` 的 `-in @('running','idle')`、`Get-RelayExitWithoutResultVerdict` 的 `-ne 'exited'` 仍是不敏感比较，被下一轮复核再逮一次。
- 反思：PS 的大小写不敏感是语言默认、写的时候没有痛感；同一个坑往往散落在多个文件，"修一处"只修了被指出的那处。
- 建议后续动作：契约层枚举/字面比对一律 `-c` 前缀算子或 `[string]::Equals(...,Ordinal)`，并给每个枚举补一条大小写变体反例断言；修此类 finding 时的返工动作固定包含"`rg '\-(in|notin|eq|ne) '` 全库扫同类算子"一步，而不是只改被点名的行。
状态：待裁决

### 候选-6 · 钉边界的断言必须配变异对照，「测试全绿」不等于「断言在咬」
触发场景：写契约测试 / 校验器 / 任何「守住某条边界」的断言，或复核此类代码 · 建议分类：编码陷阱 · 来源：DHR_26 review 轮2 P2 + 施工者自查
疑似重复：无（候选-1 讲的是「每个分支都要有断言」，本条讲的是「已写的断言可能根本不咬」）
- 现象：DHR_26 两次栽在同一件事上——第一次测试只跑自造 fixture、接上真数据整棵插件树灭掉；第二次新写的契约断言里词边界符被写成字面退格字符 0x08，正则匹配不到任何东西，违规文件照样全绿。
- 反思：断言的存在性和有效性是两回事，人肉读正则读不出 0x08 这种非打印字符；只有"故意写一份违规输入看它红不红"能证明断言在工作。
- 建议后续动作：把变异做成可复跑的 harness（本卡两个：`contract-mutation-check.mjs` / `transcript-mutation-check.mjs`），每条断言配一条对应的变异体，收口证据里附 harness 输出而不是"测试通过"。
状态：待裁决

### 候选-7 · 校验器不能拿被校验对象当期望来源，重建 oracle 也不能复用被测代码
触发场景：写"对拍 / 校验 / 一致性检查"类脚本，或复核此类脚本 · 建议分类：编码陷阱 · 来源：DHR_26 review 轮2 P1 + 两次收敛复检
疑似重复：**疑似与候选-2 同源**（候选-2 是"穷举测试的期望值不能来自被测数据"）；本条是同一根因在**校验器**上的形态，裁决时可考虑合并为一条通用条目
- 现象：`verify-transcript.mjs` 前两版从转录自己声明的字段推出待核清单，于是"把 details 全删掉"也判 IDENTICAL；改成外部清单后仍有大量字段不参与裁决，篡改 schema / 诊断 / 信封照样 IDENTICAL。
- 反思：期望必须由调用方独立给出、并从原始数据重建；重建时若复用被测代码的加载器，oracle 会与 bug 同步。
- 建议后续动作：校验器一律「外部期望 + 从源数据独立重建 + 键集封闭（多一个字段就红）」三件套，并配变异对照。
状态：待裁决

### 候选-8 · 「禁用后不存在」不等于「卸载后被清理」，探针不能和被卸载对象同生共死
触发场景：验证插件 / 服务 / 组件的生命周期清理 · 建议分类：领域知识 · 来源：DHR_26 review 轮2 P1
疑似重复：无
- 现象：`disabled: true` 启动时插件的 `apply()` 根本没执行，那份 `present:false` 只证明「从未注册」；而包内探针在 `plugin remove` 后自己也没了，报 `Cannot find package`，removed 态只剩配置树行数当证据。
- 反思：清理证据要求"先真的注册、再卸、再观测"，观测者必须活过被观测对象的消失。
- 建议后续动作：把探针放到被卸载对象**之外**（独立包/独立进程），并另做一次"注册→dispose→断言消失"的框架内复现；两条角度都留转录。
状态：待裁决

### 候选-9 · 把正确性押在安装拓扑上迟早会咬
触发场景：写插件 / 扩展包，决定"依赖谁提供、怎么解析" · 建议分类：领域知识 · 来源：DHR_26 findings §12d/§12e
疑似重复：无
- 现象：「不打包 Cordis、靠宿主 profile 的 module fallback 解析」只在包被物理拷贝进 profile 树时成立；目录（`link:`）安装下 Node 按软链真实路径向上找 `node_modules`，必然 `Cannot find package`。
- 反思：这个设计把正确性押在了"用户用哪种装法"上，而这个前提从未被任何测试或文档保证过，是靠 tgz 装法碰巧满足的。
- 建议后续动作：根因修法是让运行时零外部依赖（用宿主注入的公开 API，如 `ctx.provide`），而不是在文档里禁掉一种装法；并用契约测试钉死"零 bare import"。
状态：待裁决

### 候选-10 · 文档纠错要 append + 原处加 superseded，不要偷改历史结论
触发场景：后续轮次推翻了早前批次的结论 / 证据 README · 建议分类：行为流程 · 来源：DHR_26 review 轮2 P1-D
疑似重复：无
- 现象：目录安装被证伪后改用 tgz，后来根因修掉、两种装法都成立；但证据总索引与批内 README 仍在教人"必须装 tgz"，读者按它操作会走回头路。
- 反思：证据目录是按时间分批的，读者可能绕过总索引直接读某一批；只在总索引上纠错不够。
- 建议后续动作：被推翻的批次**顶部加醒目 superseded 提示**、原文保留作根因记录；progress 这类 append-only 账本追加纠错条（明说哪句不实），不改旧句。
状态：待裁决

### 候选-11 · 补丁只治好被指出的那个实例，不代表同类全部实例都被治好——机制的覆盖面要按"同类目标清单"逐项巡检
触发场景：给契约/协议演进中反复出现的机制（版本号判定、能力指纹、审计扫描范围、白名单登记）打补丁，且该机制天然对应"N 份同类文件 / N 个同类分支" · 建议分类：编码陷阱 · 来源：DHR_28 findings F-049（未知版本 reason 码只对 7 份协议里的 1 份兑现）/ F-075（`capability_hash` 先漏共享定义模块，是 F-033 缺口 A「能力不同却算出同一指纹」的第五次复发）；review.md 里 capability 覆盖面"裸名字→`{id,digest}`→含共享模块"走了三步，每步都被复核逼出来
疑似重复：与 DHR_28 L-009 同源（"改 bug 的手本身是新 bug 高发区"）但角度不同——L-009 讲的是新写条件要在极端输入上重测，本条讲的是补丁要覆盖机制对应的全部同类目标清单，不是新代码本身的边界值。裁决时可考虑是否合并为 L-009 的具体子款
- 现象：F-043 修好了 `relay.rpc/v1` 一份协议的未知版本判定，其余 6 份协议的判别字段没有同步映射到 `E_UNSUPPORTED_VERSION`，直到复核逐条实测才发现 1/7；`capability_hash` 第一次修复只把"裸名字"升级成 `{id,digest}` 覆盖了 7 份顶层协议，但共享定义模块 `relay.common/v1` 完全不在覆盖范围内，locator 全域约束的实际改动可以在指纹不变的情况下被篡改。
- 反思：这类机制补丁在写的当下容易只盯着"最初被举证的那一份"，而机制本身描述的是"对所有 N 份同类文件都要生效"；不主动列出 N 份清单逐一核对，遗漏的部分只能靠下一轮复核撞见。
- 建议后续动作：给这类机制打补丁时，先列出该机制理应覆盖的完整目标清单（如"7 份顶层协议 + 1 份共享定义模块"），补丁收口前逐项过一遍，而不是只验证最初报出的那个反例。
状态：待裁决

### 候选-12 · 证据只覆盖论断的一部分（一种形态 / 一个合取项），结论却写成整条已兑现——本卡收敛阶段被同一复核者一次性揪出的七条共同病灶
触发场景：验收口径 / 结论陈述包含多个合取项（"A 且 B"）或需要覆盖多种形态（"这条路径下所有情形"）时，只测了其中一部分就写"该条已兑现 / 该风险已消除" · 建议分类：编码陷阱 + 行为流程 · 来源：DHR_28 progress.md E-029（"从未跑过的 Run 报告成功完成"这个最坏答案不再可能——实际只堵住了空集合形态，非空全 `pending` 形态仍被放行，见 F-048）/ E-034→F-067（验收口径 2 是两个合取项，证据只覆盖第一项"不导入私有类型"，结论写成整条口径兑现）；review.md e2 代码复核轮 2 结论原话"新发现七条全部落在同一条缝上：声称的覆盖面 vs 实际覆盖面"（F-067/F-075/F-076/F-077/F-078/F-079 同源）
疑似重复：与 DHR_28 L-006（"可修的缺陷记成固有边界"）不同角度——L-006 讲的是缺陷被误判为边界，本条讲的是证据覆盖不全但结论被写成全称 / 整条已兑现；两条都属于"没做到写成结论"的家族，但触发条件不同，建议保留为独立条目
