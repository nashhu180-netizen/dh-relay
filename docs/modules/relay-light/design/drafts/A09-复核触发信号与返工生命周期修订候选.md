## 0. 人话目标与边界

### 0.1 一句话

现在「要拉复核，被复核的人必须先记终态 `done`」；而「记了 `done`，这个人就再也接不住返工」。本稿提议：**在送审方与判定方同处一个节点的场景里**，把判定方的触发条件从终态 `done` 换成一个**非终态的「待复核」信号**，让施工者在整个复核—返工循环里保持 live，判定方同样留活口，直到判定通过才双方依次封口。

### 0.2 用户已裁决的方向（只有这三句，不多不少）

用户 2026-09-15 裁决：

1. 复核类 agent 的 trigger 不再要求被依赖方处于终态；改为承认一个**非终态的「待复核」信号**，施工者在整个复核—返工循环中保持 live。
2. 复核方同样留活口——**不判 PASS 不记 `done`**；PASS 后再依次记双方终态，节点方可关闭。
3. 轮次上限沿用现有 `limits.rework_max_rounds=2`，超限仍走 strategist → 用户闸。

**裁决不含**：信号名、事件名、错误码位、判定角色与适用阶段的范围、验收编号、lint 是否拒旧写法、计数归属与停止时点。这些全部是本稿的提案，见 §9.2 的开放项。

### 0.3 不动的边界

- 不改产品方向、五阶段划分、公开子命令集合（仍只有 `add` / `status` / `lint`）、批次与任务卡数量。
- 不改 `roles.toml` 的角色表与模型绑定。
- 不改 `dh-mapping.toml` 的 `[stages]`、`[recipes.*]` 与 `limits` 的**键名与取值**。
- **不改 `status --json` 的冻结 schema**（A62 不动，见 §5.3）。
- **不改 R 阶段模板**，不改 R 的复核与收敛形态（§3.1）。
- **不豁免终态封口**：`done` / `agent_lost` / `cancelled` 之后同一 `(node, agent)` 仍不得再有任何事件。本稿改的是「什么时候才该进终态」，不是「终态还算不算数」。
- 本候选不授权修改正式 design、DevPlan、复核记录、workspace 合同、代码、worktree，不授权提交、verify、合并、推送或 D-start。

## 2. 信号名：两个候选与推荐

### 2.1 候选一（**推荐，前提是同时采纳 §3 的类型化合同**）：复用 `checkpoint` + 约定 token

- **账本事件不变**，仍写 `checkpoint`；`note` 加约定 token，提议 **`ready_for_review=<判定方 agent 名>`**。
- trigger 词表新增一个值，提议 **`on:review_ready:<名字>`**。

**优点**

1. **不动 19 词白名单**。事件层白名单是 19 个词，由 `HC-RL-A2` 逐字咬死；加词就得同批改 A2 的硬数字、A2 的单测、SKILL 词表段与账本样张。
2. **不动状态机迁移表**。`checkpoint` 的合法前驱已经是 `{agent_launch, checkpoint, resume}`（`relay_log.py:1821`），新信号落进现有迁移，`A60` 的迁移表一个字不改。
3. **与既有实践同构**。C2 的绕法本来就是「挂在 live 实例名下的 `checkpoint` + note 里的 token」，本候选把现场跑通的做法升格为合同。
4. `A102`（批内往返不加 attempt）在本候选下**成立的条件是**：待复核信号写成 `checkpoint` 且不伴随 `agent_launch`。这由 §3.5 保证，**不是自动继承**——需由 A145 的正例证明。

**缺点与已给的对冲**

| 缺点 | 对冲（§3 的合同条款） |
|---|---|
| `note` 承担语义的分量又重一层 | 三个 token 全部**写入时即校验**（A145 / A146），不再是自由文本 |
| `_note_tokens` 对重复同名 key 只保留第一次（`relay_log.py:2203`-`:2210`），多路无法在一条 note 里表达 | **一条 `checkpoint` 只携带一条 ready 信号**，出现第二个同名 token 直接退 2（§3.5） |
| 与 `A69` 的 helper token（`decider=` / `strategist=`）共用 note 空间 | 显式声明三个新 token **不是** helper token，不进 A69 的扫描集（A145 反例钉住） |
| `lint` 与 `status` 不会自然理解 note 里的语义 | lint 侧只管 trigger 词表（A150）；`status` 侧**本稿不提案暴露**，理由见 §5.3 |

### 2.2 候选二：新增事件名 `ready_for_review`

账本事件层从 19 词扩到 20 词；trigger 写 `on:ready_for_review:<名字>`。

**优点**：语义自带，不靠 note 解析；日后要给「待复核」加独立时序约束有地方挂。

**缺点**：`A2` 的「19 词」是硬数字，改它牵动验收原文、单测、SKILL 词表段、design §3.3 / §3.4 两处表与 §10.2 账本样张；新事件必须进状态机，`A60` 的迁移表要新增一行并回答「`ready_for_review` 之后还能不能 `blocked`」；已落盘账本（含 `rlt12-win-01` 这份 71 行）不含该词，跨版本判读多一条分支。

### 2.3 推荐与理由

**推荐候选一，且候选一只有在 §3 的三个 token 全部类型化、写入时校验之后才成立**——fresh 复核指出：不加这层合同，候选一等于把可执行语义塞进自由 note。§3 就是为此写的，attempt 2 已判该部分 CLOSED。

若用户更看重状态表达的干净，候选二仍在桌上，代价是上面那份完整改动半径。**本稿不代替用户定名**，见 §9.2 开放项 1。

## 3. 适用范围、配对与路由合同

### 3.1 适用范围：只管「送审方与判定方同处一个节点」（v3 收窄）

这条修法**天然只适用于送审方与判定方同在一个节点 agent 表内的形态**。按现行五阶段模板与本轮实跑计划逐一核过：

| 阶段模板 | 节点内 agent | 同节点有送审方吗 | 现行 trigger | 本修订是否适用 |
|---|---|---|---|---|
| W（`SKILL.md:44`-`:56`） | builder + plan-reviewer | **有**（builder） | plan-reviewer = `on:done:builder` | 结构上适用；**是否纳入见 §9.2 开放项 2** |
| C（`:57`-`:73`） | coder + checker + scribe + decider | **有**（coder） | coder / checker 均留空（A95） | **适用** |
| R（`:74`-`:88`） | reviewer 多路 + scribe | **没有** | reviewer 留空、scribe 留空 | **不适用，模板不动** |
| X（`:89`-`:104`） | coder + 被打回那路 reviewer + decider | **有**（coder） | reviewer = `on:done:coder` | **适用**（正是 C1 事故的同形硬闸所在） |

**R 阶段为什么不适用——三条可核证据**

1. **R 节点没有同节点送审方**。R 模板的 agent 只有多路 reviewer 与一个 scribe；本轮实跑计划的 R1 三行（`relay_plan.md` 第 65～67 行）分别是 `requirement` / `lesson` / `scribe`，**trigger 全部留空**，表里没有 coder。R 复核的是**上一节点（C2）的产出**。
2. **给 R 写新 trigger 会被现有硬约束直接拒**。`A59` 要求非豁免 agent 的名字必须在**本节点** agent 表中（`relay_log.py:1584`-`:1585`），`A71` 要求 trigger 只引用同节点 agent（`:591`-`:603`）。所以给 R 的 reviewer 写 `on:review_ready:coder` 会触发 A71，在 R 节点写 `checkpoint coder#1` 会触发 A59。**v2 的 R 示例确实落不了地，这是 v2 的实质错误，v3 已改正。**
3. **R 打回本来就有合法出口，不存在「无路可退」这个病**。R 的 reviewer 打回时写 `stage_result outcome=done` 附打回清单，由编排追加 X 节点。本轮实跑正是这么走的：账本 **seq 50** 的 `R#1` stage_result 列出 5 条 P1，**seq 52** 编排即开 `X#1`；追加规则由计划注释 6 冻结。

**收窄是落在用户三句裁决之内的**：三句说的是「复核类 agent 的 trigger 不再要求被依赖方处于终态」，而 R 的 reviewer 现行 trigger 本来就是空的、不要求任何人终态，**它不在这条裁决要修的病灶里**。收窄不缩减裁决，只是把修法用在真正有病的两个阶段。

> **收窄后的残留，需用户知情**：R 阶段判定方的 `done` 时机仍只由纪律约束，程序不管。本稿认为可接受，因为 R 的打回出口（追加 X 节点）合法且已实跑验证。见 §9.2 开放项 3。

### 3.2 配对键：按 `role` 判定，不看 `close`、不看 trigger

v1 曾用「`close` 列指向的 agent」当判定方，那不成立——R 的 `close=agent:scribe` 指的是收敛者，C 的 `close=agent:checker` 又与「checker 保持空 trigger」并存。计划 agent 表本来就有 `role` 列（`AgentSpec.role`，`relay_log.py:131`、`:446`），取值必须是 `roles.toml` 的键。提议冻结：

> **判定角色闭集 = `{plan-reviewer, checker, reviewer}`**（`roles.toml` 十一个角色中，只有这三个产出 PASS / FAIL 结论并可能打回；`scribe` 是收敛者、`decider` / `strategist` 是决策者，都不判定，均不在集内）。集合随 `roles.toml` 变化由未来 A 事件同步，不由施工者临场扩充（沿用 `A132` 的闭集写法）。

### 3.3 A146 的生效条件：有信号才设闸（v3 新增，使收窄自洽）

只按 `role` 判定会误伤 R——R 的 reviewer 也是判定角色，但它没有同节点送审方可绑。因此：

> **A146 的配对闸只在「本节点存在至少一条指向该判定方的 `ready_for_review=` 信号」时生效。** 没有任何信号 → 不设闸，该判定方按现行规则写 `done`。

这一条让适用范围**自洽且自动收窄**：

- **X 的 reviewer**：trigger 为 `on:review_ready:<S>`，按 A144 没有信号就根本拉不起来 → 信号必然存在 → 闸必然生效。**强制性由 trigger 保证。**
- **C 的 checker**：trigger 留空（A95 不变），信号由监工按纪律发；发了就受闸约束，封口顺序守得住。
- **R 的 reviewer**：从不会有指向它的信号 → 闸不生效 → **R 完全不受影响**。
- **一切旧计划**：从不会有信号 → 闸不生效 → **向后兼容有结构性保证**（这是 A148 要证的正例之一）。

> **残留，需用户知情**：C 的 checker 因 A95 保持空 trigger，程序**无法强制**「必须先有 ready 信号」——监工若跳过信号直接记 `done`，闸不生效。要让 C 也强制，就得改 A95 的「checker trigger 留空」，那会牵动「批内同时在场」的产品语义。**本稿不提案改 A95**，见 §9.2 开放项 4。

### 3.4 三个 token 的 wire format（提议冻结）

| token | 写在哪 | 写法 | 含义 |
|---|---|---|---|
| `ready_for_review=<Rv>` | 送审方 `checkpoint` 的 `note` | `<Rv>` = 本节点 agent 表中一个判定角色的 **agent 名**（不带 `#attempt`） | 「我这一轮产出可以给 `<Rv>` 看了」 |
| `reviewed=<S>#<a>` | 判定方 `done` 的 `note` | `<S>#<a>` = 被复核的**实例全名**（含 attempt） | 「我这条结论答的是 `<S>#<a>`」 |
| `ready_seq=<n>` | 判定方 `done` 的 `note` | `<n>` = 本条结论所答的那条 ready 信号的 `seq` | 「我答的是第 `<n>` 条信号」 |

三个 token **均不是** `A69` 的 helper token（helper token 只有 `decider=` / `strategist=` 两种，`relay_log.py:1676` 起），不参与决策归属校验。

### 3.5 送审信号的写入校验（A145）

写 `checkpoint` 时，若 `note` 含 `ready_for_review=`：

1. `note` 中以 `ready_for_review=` 开头的 token **恰好一个**；两个或更多直接退 2。理由是 `_note_tokens` 只保留第一次出现（`relay_log.py:2203`-`:2210`），多写会**静默丢失**——必须在写入时拒绝，不能靠 parser 侥幸。
2. `<Rv>` 必须在**本节点** agent 表中存在，且其 `role` ∈ 判定角色闭集；否则退 2。
3. 写入者本身**不得**是判定角色（判定方不给自己送审）。
4. 该 `checkpoint` 不伴随 `agent_launch`，attempt 不变（`A102` 在新模型下继续成立的依据，由 A145 的正例证明）。

**多路怎么表达**：**一条信号对一个判定方；N 路就写 N 条 `checkpoint`。** X 阶段两路复核的实际形态是 `ready_for_review=requirement` 与 `ready_for_review=lesson` 两条相邻的 `checkpoint`。

### 3.6 实例绑定与配对（A144 / A146，v3 按 P1-2 加固）

**问题**：`_latest_by_name` 只按**名字**跨 attempt 取最新行（`relay_log.py:1588`-`:1603`）。只要求「存在一条匹配的 ready 信号」，下面三种序列会被误放行——信号所描述的产出早已不是当前待复核的产出：

- `coder#1` 发了信号后 `agent_lost`，`coder#2` 重拉并 live，**旧信号**仍能拉起判定方；
- `coder#1` 发了信号后又写了一条普通 `checkpoint`（继续干活），旧信号仍能拉起判定方；
- `coder#1` 发了信号后写 `blocked`，旧信号仍能拉起判定方。

**拉起侧（A144，launch-time）**——写 `agent_launch <Rv>#<n>` 且其 trigger 为 `on:review_ready:<S>` 时，要求：

1. 本节点存在一条 `checkpoint`，其 `agent` 字段为某个完整实例 `<S>#<a>`，`note` 带 `ready_for_review=` 且值**恰等于 `<Rv>`**；
2. `<S>#<a>` 必须是 `<S>` 在本节点的**当前实例**（该名下最大 attempt）；
3. 该 `checkpoint` 必须是 `<S>#<a>` 这个**实例的最新 agent 事件**（按 `_latest_for_instance` 判，不用 `_latest_by_name`）；
4. 由 3 直接得出 `<S>#<a>` 未处于终态；仍显式声明，并对三种终态各留反例。

任一不成立退出 2 报 `HC-RL-A144`。**这同时解决了路由（token 指向谁谁才拉得起来）与新鲜度（信号必须描述当前实例的当前产出）。**

**封口侧（A146，done-write-time）**——写 `done <Rv>#<n>`，且本节点存在指向 `<Rv>` 的 ready 信号（§3.3 的生效条件）时，要求：

1. `note` 含 `reviewed=<S>#<a>` 与 `ready_seq=<n>`，缺任一退 2；
2. `ready_seq=<n>` 指向的那条事件必须是一条 `checkpoint`，其 `agent` 字段**逐字等于** `reviewed=` 里的 `<S>#<a>`，且其 `ready_for_review=` 值等于 `<Rv>`——**杜绝把旧实例的信号与新实例的 `reviewed=` 拼接**；
3. 该条必须是 `(node, <S>#<a>, <Rv>)` 组合下**最新**的一条 ready 信号（防止判定方引用旧轮次，冒充已复审最新产出）；
4. `<S>#<a>` 在本节点**已 `done`**，且其 `done` 的 `seq` **早于**本条；`<S>#<a>` 尚未终态时判定方写 `done` 直接退 2。

任一不成立退出 2 报 `HC-RL-A146`。**执行位点是 agent `done` 的语义校验**（现有 `_validate_runtime_event` / `_validate_event_semantics` 一线，`relay_log.py:1854`-`:1895`），**不是** `_validate_node_close`——后者只在关节点时兜底，实现不了即时拒绝。

**为什么顺序是「送审方先 done、判定方后 done」**：`scribe` 的 `on:done:coder` 到送审方封口这一刻才算命中（`monitor-C2.md` 第 7 条原文即此）；判定方在两者之间保持 live，是它「已判 PASS 但尚未封口」的唯一可观察形态。

**为什么不另设「已消费」标记**：attempt 2 已判该理由成立，此处保留——(a) 同名实例的重复 `agent_launch` 已被 `A58` 与 `A49` 两道现成闸拦住；(b) 第 2 轮起的复审由**同一个 live 判定实例**完成，根本不写 `agent_launch`，没有可供消费的时点；真正需要绑定「答的是哪一次」的是封口侧，已由 `ready_seq=` 加本节的实例逐字比对承担。

### 3.7 一轮完整的账本形态（X 阶段两路，第一路 FAIL 一轮后 PASS）

X 阶段的 agent 表是 coder + 两路 reviewer + decider（实跑计划 X1 第 68～71 行），送审方与判定方同节点，正是本修订的适用形态：

```text
node_start    X1        monitor#4
agent_launch  coder#1
checkpoint    coder#1   note=ready_for_review=requirement round=1      ← seq S1
checkpoint    coder#1   note=ready_for_review=lesson round=1           ← seq S2
agent_launch  requirement#1   （trigger=on:review_ready:coder）
agent_launch  lesson#1        （trigger=on:review_ready:coder）
checkpoint    requirement#1   note=routed_to=coder#1 P1-1 <一句话整改>  ← FAIL，判定方保持 live
checkpoint    coder#1   note=ready_for_review=requirement round=2      ← seq S3，送审方仍 live
   （同一个 requirement#1 实例复审，不重拉、不新增 agent_launch）
done          coder#1   note=<收工小结> commit=<sha>
done          requirement#1   note=reviewed=coder#1 ready_seq=S3 PASS p1=0 p2=<n>
done          lesson#1        note=reviewed=coder#1 ready_seq=S2 PASS p1=0 p2=<n>
node_close    X1        （A17 双判据照常；close=agent:<打回路>）
```

**并行两路互不干扰**：`lesson` 全程未被打回，`ready_seq` 停在 S2；`requirement` 走到 S3。两路各绑各的信号，一路 FAIL 不影响另一路封口。**C 阶段同形**，差别只在 checker 的 trigger 留空、且 scribe 在 coder `done` 之后由 `on:done:coder` 拉起。

## 4. A49 / A60 / A70 三条各自的处置

### 4.1 `HC-RL-A49`（attempt 按 `(node, agent 名)` 计数）—— **保持不变**

**处置：一字不改，也不豁免。**

理由：新方案的目的是让送审方**不进终态**，因此不需要重拉；整个复核—返工循环在同一个 `coder#1` 实例内用 `checkpoint` 往返完成，正是 `A102` 与 `A113` 已写死的形态。A49 在新模型下依然是那道「不许换人绕过复核」的护栏，并按 §3.6 兼任「拦住 ready 信号重放」的第一道闸。

### 4.2 `HC-RL-A60`（agent 事件状态机；终态后不得再有事件）—— **保持不变**

**处置：命题与迁移表都不改，不豁免。**

理由：终态封口是账本可判读性的地基——一旦开口子，`status` 的在场判定、`node_close` 双判据（A17 / A74）、写入者交接（A93）全部要重新定义。

新模型下 A60 从「意外的拦路虎」变成「正确的封口闸」：送审方在判定通过前压根不该有终态，撞不上 A60；一旦撞上，说明 `done` 记早了，报错本身就是正确行为。**同批补反例**（§6.2 反例 3）证明本次修订未削弱 A60。

### 4.3 `HC-RL-A70`（`on:done:<X>` 前置校验）—— **保号不变，另立新条承接新 trigger**

**处置：A70 保号，语义一字不改**，继续只管 `on:done:<X>`；新 trigger 的前置校验另立 `HC-RL-A144`。

| 做法 | 评价 |
|---|---|
| (a) 把 A70 扩写成「两种前置」 | 一条验收塞两个可独立失败的观察点，违反 `RLT-A-06` 立的原子化规则（A131～A134 的 `split-from` 先例） |
| (b) A70 保号 + 新增 A144（**推荐**） | 两条各自可独立失败；旧写法的回归证据不必重跑；向后兼容由「A70 保号且证据不变」直接给出 |

### 4.4 三条的一句话总结

## 5. 配套条款提案

### 5.1 判定方留活口

判定方在**判定 PASS 之前不得记 `done`**。FAIL 且有 P1 时，判定方保持 live，把每条 P1 落成挂在自己名下的 `checkpoint`（note 带路由信息），整改 prompt 发回同一个 live 送审方；送审方改完发新一条 ready 信号，由**同一个判定实例**复审，不重拉、不新增 `agent_launch`。程序侧的保证是 §3.6 的封口闸。

### 5.2 终态顺序

PASS 之后依次记：**先送审方、后判定方**。随后 `node_close` 按现行双判据（A17 / A74）照常判，`close` 列语义不变。

### 5.3 轮次上限：第三套计数，只投影不拒写

沿用 `dh-mapping.toml` 的 `[limits] rework_max_rounds = 2`，**不新增配置键、不改取值**。

`loss_stop()` 是**只读投影**，它从不拒绝任何写入（`relay_log.py:2563` 起）。第三套照抄这个形状：

| 项 | 定义 |
|---|---|
| 「一轮」 | **一条 `ready_for_review=<Rv>` 信号 = 一轮送审**，首轮计入 |
| 计数 | `review_rounds[(node, Rv)]` = 该组合下的 ready 信号条数 |
| 耗尽判据 | `count >= limits.rework_max_rounds` **且** `<Rv>` 在本节点仍无 `done` |
| 出口 | `LossStop.triggered` 为真 → 监工据此拉 strategist → `escalate` 作链首 → **永远交用户裁决**（A97 / A114 不变） |
| 写入侧 | **不拒绝**任何 ready 信号；A145 因此在 `add` 层「不设硬上限」，与 A147 不矛盾 |

**一条需要写进复核视野的事实**：`loss_stop()` 目前**没有**接进 `Status`，也不出现在 `status --json` 的十三个冻结顶层键里（`relay_log.py:2640` 起的 `status_document` 无相关键）。**现有两套计数同样只是可调用的只读函数，并无机械暴露通道**——第三套的处境与前两套完全一致。

因此本稿**不**把 ready 集合暴露进 `status`：(a) A62 是冻结 schema，为新条目单开一个前两套都没有的通道会造成不对称；(b)「三套计数要不要一并暴露」是独立命题，牵动 A62 与 A106，应单独立案；(c) 半暴露正是复核警告的「伪半实现」。attempt 2 已判该理由成立。见 §9.2 开放项 5。

### 5.4 向后兼容

**一句话：trigger 词表是扩集不是替换——`on:done:<X>` 的语义与 A70 一字不改，旧计划原样可跑，lint 不拒不强制迁移；只有 C / X（及待裁的 W）模板的默认值换成新 trigger，R 模板不动。**

展开（**均为待验证的目标命题，不是已成立的事实**）：

- 已落盘的计划与账本**不需要迁移**。已核实的现状：`rlt12-win-01` 原样 `lint: ok`（fresh 复核实跑输出）。这**只证明旧计划在当前实现下可跑**，不证明扩集实现后仍可跑——后者由 A148 的正例证明。
- 旧计划里没有任何 ready 信号，按 §3.3 的生效条件，A146 的闸**对它们不生效**；这是向后兼容的结构性保证，而不只是「lint 不拒」。
- 同一份计划里**混用**两种 trigger 应当合法。**混用场景目前既无实现也无测试**，A148 就是为钉它而立。
- `lint` **不**对 `on:done:<X>` 报错，也不报「建议迁移」——`lint` 只有 0 / 2 / 3 三个退出码，没有警告通道，硬塞会把旧计划判死。
- 残留风险：旧模板生成的新 C / X 计划仍会踩 C1 那条路。缓解手段是模板换默认值 + adapter 补原文（A149），**不是**程序强制。见 §9.2 开放项 6。

### 6.2 建议同批新增的反例（防回归）

1. `on:review_ready:` 引用的送审方**已 `done`** → 退 2 报 A144（防「先 done 再复核」的倒退写法）。
2. `on:review_ready:` 引用的送审方**从未发过匹配的 ready 信号** → 退 2 报 A144。
3. 送审方终态后再挂 `checkpoint` → **仍**退 2 报 **A60**（证明 A60 未被削弱）。
4. 送审方终态后再拉第二个同名实例 → **仍**退 2 报 **A49**（证明 A49 未被削弱）。
5. **旧 attempt 的 ready 信号**（`coder#1` 发信号后 lost、`coder#2` live）拉起判定方 → 退 2 报 A144。
6. **ready 被后续普通 `checkpoint` 覆盖**后拉起判定方 → 退 2 报 A144。
7. **ready 之后写了 `blocked`** 再拉起判定方 → 退 2 报 A144。
8. 封口时 `ready_seq` 指向 `coder#1` 的信号而 `reviewed=coder#2` → 退 2 报 A146。
9. 判定方 `done` 早于送审方 `done`，或送审方尚未终态 → 退 2 报 A146。
10. 一条 `checkpoint` 写两个 `ready_for_review=` → 退 2 报 A145。
11. 轮次超 `rework_max_rounds` 后再发 ready → **被接受**（A147 只投影不拒写），且 `LossStop.triggered` 为真。
12. 无 ready 信号的节点（R 形态、旧计划）判定方直接 `done` → **被接受**（A146 不生效，A148 正例）。
