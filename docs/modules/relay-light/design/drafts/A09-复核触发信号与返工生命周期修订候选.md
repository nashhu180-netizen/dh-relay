# RLT-A-09 共创草案 v1 — 复核触发条件改为非终态「待复核」信号

## 0. 人话目标与边界

### 0.1 一句话

现在「要拉复核，被复核的人必须先记终态 `done`」；而「记了 `done`，这个人就再也接不住返工」。本稿提议把复核类 agent 的触发条件从**终态 `done`** 换成一个**非终态的「待复核」信号**，让施工者在整个复核—返工循环里保持 live，复核方同样留活口，直到判定通过才双方依次封口。

### 0.2 用户已裁决的方向（只有这三句，不多不少）

用户 2026-09-15 裁决：

1. 复核类 agent 的 trigger 不再要求被依赖方处于终态；改为承认一个**非终态的「待复核」信号**，施工者在整个复核—返工循环中保持 live。
2. 复核方同样留活口——**不判 PASS 不记 `done`**；PASS 后再依次记双方终态，节点方可关闭。
3. 轮次上限沿用现有 `limits.rework_max_rounds=2`，超限仍走 strategist → 用户闸。

**裁决不含**：信号名、事件名、错误码位、验收编号、lint 是否拒旧写法、计数归属。这些全部是本稿的提案，等复核。

### 0.3 不动的边界

- 不改产品方向、五阶段划分、公开子命令集合（仍只有 `add` / `status` / `lint`）、批次与任务卡数量。
- 不改 `roles.toml` 的角色表与模型绑定。
- 不改 `dh-mapping.toml` 的 `[stages]`、`[recipes.*]` 与 `limits` 的**键名与取值**。
- **不豁免终态封口**：`done` / `agent_lost` / `cancelled` 之后同一 `(node, agent)` 仍不得再有任何事件。本稿改的是「什么时候才该进终态」，不是「终态还算不算数」。
- 本候选不授权修改正式 design、DevPlan、workspace 合同、代码、worktree，不授权提交、verify、合并、推送或 D-start。

### 1.1 三条规则互锁

### 1.2 实证：C1 节点

- 账本 `relay/rlt12-win-01/relay_log.jsonl`：**seq 16** `done coder#1`、**seq 19** `done scribe#1`、**seq 20** `done checker#1`——checker 的结论此刻才落下，是 **FAIL p1=3 p2=0**。

- 三条 P1 的原文在 `..\RLT_21\docs\modules\relay-light\workspace\RLT_21\check.C1.md` 的「P1（阻断）」三节。
- 复核侧独立判定：同树 `review.lesson.md` 的 **P1-1**「C1 的 `done` 时机堵死节点内返工，未进入候选」，判词是「**可迁移的协议级教训，不是本卡一次性事故**；`done` 是状态机终态，落账时机直接决定返工边是否仍存在」。

### 1.3 现有绕行办法及其失效点

C2 起编排冻结了「**PASS 前谁都不记 done**」的纪律，派单 `dispatch/monitor-C2.md` 第 7 条（「记 `done` 的时机与 FAIL 返工路由」）写死：checker 报 FAIL 时保持 live，把整改逐条落成挂在 **live checker 名下**的 `checkpoint`（note 带 `routed_to=coder#1`），整改 prompt 发回同一个 coder 的 pane，不新增 attempt、不新增 `agent_launch`；PASS 后才按 **coder 先、checker 后**的顺序记两条终态。

账本对应 **seq 25 / 26 / 27** 三条 `checkpoint checker#1`，note 分别带 `routed_to=coder#1 P1-1/P1-2/P1-3`；C2 因此在 **seq 29** 拿到 `check.C2.md PASS p1=0 p2=1`。

**这个绕法只对 trigger 留空的角色有效。** C 阶段的 checker trigger 本来就留空（design §11 A95），监工想什么时候拉就什么时候拉。但 R / X 阶段的 reviewer 走的是 `on:done:coder`——`relay_plan.md` agent 表 X1 两行 reviewer 的 trigger 列即为 `on:done:coder`——硬闸逼 coder 必须先 `done` 才拉得起复核。派单 `dispatch/monitor-X1.md` 第 3 条把这个矛盾称作「**一个硬闸 + 一条纪律**」，并在第 9 条写明兜底结论：「**coder 已 `done` 之后不存在节点内返工路径**（A49 / A60）。这是第 3 条硬闸的必然后果，**不是可以变通的地方**」。

本轮 X1 两路复核恰好都 PASS（账本 seq 59 / 60），返工边没被真正踩到；**若当时任一路 FAIL，会原样复现 C1 事故**。这一句是推论，不是实测。

本条即 `workspace/RLT_12/findings.md` 的 **F-008**，该条「处置」列已记录用户 2026-09-15 的三句方向裁决，并注明「裁决只含这三句，**未**裁决信号名、事件名与码位」「**落地须另起任务卡**——RLT_21 已收口，允许路径与验收已冻结」。本稿是该条的设计侧承接，**不替 RLT_21 补签任何验收**。

## 2. 信号名：两个候选与推荐

### 2.1 候选一（**推荐**）：复用 `checkpoint` + 约定 token

- **账本事件不变**，仍写 `checkpoint`；在 `note` 里加一个约定 token，提议 **`ready_for_review=<复核方 agent 名>`**。
- trigger 词表新增一个值，提议 **`on:review_ready:<名字>`**。
- 前置校验：写 `agent_launch` 时，被引用的 X 在本节点的**最新事件必须是一条带 `ready_for_review=` token 的 `checkpoint`**，且 X **未处于终态**。

**优点**

1. **不动 19 词白名单**。事件层白名单是 19 个词，由 `HC-RL-A2`（「19 词 fail closed」）逐字咬死；加词就得同批改 A2 的硬数字、A2 的单测、SKILL 词表段与账本样张。
2. **不动状态机迁移表**。`checkpoint` 的合法前驱已经是 `{agent_launch, checkpoint, resume}`（`relay_log.py:1821`），新信号自然落进现有迁移，`A60` 的迁移表一个字不改。
3. **与既有实践同构**。C2 的绕法本来就是「挂在 live 实例名下的 `checkpoint` + note 里的自由文本 token（`routed_to=`）」，本候选等于把现场已经跑通的做法升格为合同。
4. `A102`（批内往返不加 attempt）原样成立，不需要为新信号另立「不烧 attempt」的条款。

**缺点**

1. `note` 承担语义的分量又重了一层——`config_dir=` / `stage_id=` / `ref=` / `launch_fix=` / `amend=` / `nodes=` 之后再加一个。
2. `checkpoint` 从「纯记事」变成「部分带语义」，`status` 要能区分带 token 与不带 token 的 `checkpoint`。
3. token 与 `A69` 的 helper token（`decider=` / `strategist=`）在同一 note 空间里，需要显式声明 `ready_for_review=` **不是** helper token、不参与 `A69` 归属校验——否则会像派单 `monitor-X1.md` 第 3 条第 4 点警告 `routed_to=` 那样被 A69 误拒。

### 2.2 候选二：新增事件名 `ready_for_review`

- 账本事件层从 19 词扩到 20 词，新增 `ready_for_review`；trigger 写 `on:ready_for_review:<名字>`。

**优点**：语义自带，不靠 note 解析；`status` 投影直接读事件名；日后想给「待复核」加独立时序约束有地方挂。

**缺点**：

1. `A2` 的「19 词」是**硬数字**，改它牵动验收原文、单测、SKILL 词表段、design §3.3 / §3.4 两处表、§10.2 账本样张。
2. 新事件必须进状态机，`A60` 的迁移表要新增一行（合法前驱、合法后继各定一遍），并要回答「`ready_for_review` 之后还能不能 `blocked`」这类新问题。
3. 旧账本（含 `rlt12-win-01` 这份已落盘的 71 行）不含该词，跨版本读账本的判读基准会多一条分支。

### 2.3 推荐与理由

**推荐候选一。** 理由是改动半径：候选一只碰 trigger 词表与 `_require_trigger` 一处前置，白名单、状态机迁移表、账本样张全不动；候选二要动的是整个模块最底层的两张冻结表。本轮的目标是**补一条返工路径**，不是重做事件模型。

> **待复核**：token 拼法（`ready_for_review=` / `review_ready=` / 更短的写法）与 trigger 值拼法（`on:review_ready:` / `on:ready:`）均未定，本稿只给一组占位写法便于讨论。

## 3. A49 / A60 / A70 三条各自的处置

这是本稿必须正面回答的部分。

### 3.1 `HC-RL-A49`（attempt 按 `(node, agent 名)` 计数）—— **保持不变**

A49 现行原文：「attempt 按 `(node, agent 名)` 计数，每节点从 1 起，跨节点不累计」，其实现侧的重拉资格闸在 `relay_log.py:1806`-`:1811`（前一实例须为 `agent_lost` / `cancelled`，或本阶段已 `failed`）。

**处置：一字不改，也不豁免。**

理由：新方案的全部目的就是让施工者**根本不进终态**，因此**不需要重拉**。整个复核—返工循环在同一个 `coder#1` 实例内用 `checkpoint` 往返完成，这正是 `A102`（批内往返不加 attempt）与 `A113`（attempt 只因实例挂掉而增）已经写死的形态。A49 在新模型下依然是那道「不许换人绕过复核」的护栏——保留它，「批内不换人」才守得住。

**一个必须显式声明的推论**：新模型下，C1 那种「被复核方已终态、复核方报 FAIL」的局面**不应再出现**；万一仍出现（例如监工违纪抢记 `done`），A49 **仍然拒绝**重拉，处置仍是整建制推到下一节点或走 strategist 闸。**不为这种情况开后门**。

### 3.2 `HC-RL-A60`（agent 事件状态机；终态后不得再有事件）—— **保持不变**

A60 现行原文：「agent 事件状态机：单 `(node, agent)` 序列合法，终态后不得再有事件」。

**处置：命题与迁移表都不改，不豁免。**

理由：终态封口是账本可判读性的地基——「见终态即该实例已收口」这条语义一旦开口子，`status` 的在场判定、`node_close` 双判据（A17 / A74）、写入者交接（A93）全部要重新定义。本稿**不碰**它。

新模型下 A60 的角色从「意外的拦路虎」变成「正确的封口闸」：施工者在复核通过前压根不该有终态，所以撞不上 A60；一旦撞上，说明 `done` 记早了，报错本身就是正确行为。

**建议同批补一条反例**（见 §5.2 的反例 3）：coder 终态后再挂 `checkpoint` **仍**退 2 报 A60，用来证明本次修订**没有削弱** A60。

### 3.3 `HC-RL-A70`（`on:done:<X>` 前置校验）—— **保号不变，另立新条承接新 trigger**

A70 现行原文：「`on:done:<X>` 前置校验：X 在本节点无 `done` 则退出 2；X 为 `agent_lost` / `cancelled` 同样退出 2」。

**处置：A70 保号，语义一字不改**，继续只管 `on:done:<X>`。新 trigger 的前置校验**另立** `HC-RL-A144`。

**两个可选做法，本稿推荐后者**：

| 做法 | 说明 | 评价 |
|---|---|---|
| (a) A70 扩写 | 把 A70 改成「`on:done:` 与 `on:review_ready:` 两种前置」 | 一条验收塞两个可独立失败的观察点，违反 `RLT-A-06` 确立的原子化规则（见 A131～A134 的 `split-from` 先例） |
| (b) A70 保号 + 新增 A144（**推荐**） | A70 只管旧 trigger，A144 只管新 trigger | 两条各自可独立失败；旧写法的回归证据不必重跑；向后兼容天然成立 |

推荐 (b)。代价是验收表多一条，收益是**向后兼容由「A70 保号且证据不变」直接给出**，不需要额外论证。

### 3.4 三条的一句话总结

> **A49 不改、A60 不改、A70 保号不改**；本次修订全部落在「新增一条 trigger 前置（A144）+ 把 `done` 的落账时机写进合同（A146）」上。**没有任何一条现行硬约束被豁免或削弱。**

## 4. 配套条款提案

### 4.1 复核方留活口

复核方（reviewer / checker）在**判定 PASS 之前不得记 `done`**。FAIL 且有 P1 时，复核方保持 live，把每条 P1 落成挂在**自己名下**的 `checkpoint`（note 带路由信息），整改 prompt 发回同一个 live 施工者；施工者改完由**同一个复核实例**复审，不重拉、不新增 `agent_launch`。

### 4.2 终态顺序

PASS 之后依次记：**先被复核方、后复核方**（`done coder#1` → `done <reviewer>#1`）。顺序不是审美问题——`scribe` 的 `on:done:coder` 到施工者封口这一刻才算命中（`monitor-C2.md` 第 7 条原文即此）。随后 `node_close` 按现行双判据（A17 / A74）照常判。

### 4.3 轮次上限

沿用 `dh-mapping.toml` 的 `[limits] rework_max_rounds = 2`，**不新增配置键、不改取值**。超限仍走 strategist 链 → **永远交用户裁决**（design §9.3、A97、A114）。

**开放问题（本稿给推荐，但这是最需要复核的一处）**：节点内复核往返的轮次算在哪套计数里？

| 选项 | 说明 | 风险 |
|---|---|---|
| ① 不计数，只留纪律 | 维持现状（`monitor-C2.md` 第 7 条：「同一条 P1 往返 3 轮仍不收敛就拉 decider」），程序不管 | 与用户「轮次上限沿用 rework_max_rounds」的裁决对不上；死循环只靠监工自觉 |
| ② 复用同一配置键，作**独立第三套计数**（**推荐**） | 按 `(node, 复核方)` 数 FAIL 次数，达 `rework_max_rounds` 后拒绝第 N+1 条待复核信号，走 strategist 闸。`A107` 由「两套计数」扩为「三套计数、互不叠加、谁先到谁触发」 | A107 必须同批修订，其现有单测失效 |
| ③ 并入 X 阶段的 rework 计数 | 节点内往返与 X 阶段 `#k` 合并计数 | 两者颗粒度不同（节点 vs 阶段实例），合并后 `status` 的轮次读数会失去意义 |

推荐 ②。

### 4.4 向后兼容

**一句话：trigger 词表是扩集不是替换——`on:done:<X>` 的语义与 A70 一字不改，已有计划原样可跑，lint 不拒、不强制迁移；只有 SKILL 新模板的默认值换成新 trigger。**

展开：

- 已落盘的计划（含 `rlt12-win-01`）与已落盘的账本**不需要任何迁移**。
- 同一份计划里**混用**两种 trigger 合法：`scribe` 继续 `on:done:coder`（它本来就该等施工者封口），reviewer 改 `on:review_ready:coder`。
- `lint` **不**对 `on:done:<X>` 报错，也不报「建议迁移」——`lint` 只有 0 / 2 / 3 三个退出码，没有警告通道，硬塞会把旧计划判死。迁移压力放在 SKILL 模板与派单纪律层。
- 需要显式承认的残留风险：旧模板生成的新计划仍会踩 C1 那条路。缓解手段是模板换默认值（A149）+ adapter 监工模板补原文（A149 的结构检查），**不是**程序强制。这一点**待复核**。

### 5.1 新增条目（草案）

### 5.2 建议同批新增的反例（防回归，挂在上表各条下）

1. `on:review_ready:` 引用的施工者**已 `done`** → 退 2 报 A144（防「先 done 再复核」的倒退写法）。
2. `on:review_ready:` 引用的施工者**从未发过待复核信号** → 退 2 报 A144。
3. 施工者终态后再挂 `checkpoint` → **仍**退 2 报 **A60**（证明 A60 未被削弱）。
4. 施工者终态后再拉第二个同名实例 → **仍**退 2 报 **A49**（证明 A49 未被削弱）。
5. 复核方 `done` 早于施工者 `done` → 退 2 报 A146。
6. 节点内 FAIL 轮次超 `rework_max_rounds` 后再发信号 → 退 2 报 A147。
7. 旧写法 `on:done:coder` 的完整链路正例 → 通过（A148）。
