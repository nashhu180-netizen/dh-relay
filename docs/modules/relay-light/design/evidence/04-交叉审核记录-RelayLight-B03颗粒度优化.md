#### 方案问题

- **P1｜把 RLT_16 与 RLT_19 重新合并，回退了已裁决的原子性问题。**
  - **问题：** 候选把机制、卡内追加（H16）和新增任务卡追加阶段（H17）合回一个 heavy 卡（`drafts/RLT-B-03-颗粒度优化-调整候选.md:33-38,85`）。
  - **原始需求或独立事实：** B-01 的 fresh review 已判两者“不是一个验收单元”；用户已接受“拆两卡”，理由是验证动作、允许路径、用户判断点都不同（`design/evidence/02-交叉审核记录-RelayLight-B拆计划.md:81-84,148,152-154`；正式方案也以 RLT_16/RLT_19 分别承接 H16/H17，`dev_plan/P1-RelayLight-开发方案.md:611-612,648-651`）。正式输入更分别要求“当班监工接手卡内节点”与“新 W 阶段才拉监工、builder 建七件套”（`design/01-RelayLight-产品设计与验收.md:1227-1228`）。共用程序或同一次安装不是同一人判。
  - **影响：** H16 成功会掩盖 H17 的跨卡权限/时序失败，或反之；一次 heavy 的五路复核也不能恢复两次独立的用户判断与高危授权边界。
  - **建议：** 保留 RLT_09 的实现卡可讨论合并，但 H16/RLT_16 与 H17/RLT_19 必须恢复为两张高危 heavy 实跑卡、各自 task_plan、证据段和开工确认。若仍主张翻案，先向用户说明与 2026-09-09 已确认裁决相反的新增证据，再作明确 B-adjust 决定。

- **P1｜RLT_14/RLT_15 的合并并降为 light，同样回退了已确认的复核裁决。**
  - **问题：** 候选把 H6 的 auto/consult 决策链和 H15 的返工超限→strategist→用户裁决合为 RLT_14，并从两张 normal 降为 light（`drafts/RLT-B-03-颗粒度优化-调整候选.md:40-45,84`）。
  - **原始需求或独立事实：** 用户要求独立审核再晋级；AGENTS §5 冻结 light 为教训+一致性两路，不含需求复核，normal 有需求方向复核。B-01 已逐项裁决 RLT_12/13/14/15/17 至少 normal，且用户已确认当时“实跑卡按用户能一次判断的场景切，合并反而让人验签不动”（`AGENTS.md:24-25`; `design/evidence/02-交叉审核记录-RelayLight-B拆计划.md:81-83,152-154`）。H6 评估两种 decider 手感，H15 评估返工上限与 strategist 输入，正式输入本身即为不同问题（`design/01-RelayLight-产品设计与验收.md:1225-1226`）。
  - **影响：** 需求复核被取消，且一次故障链/账本隔离不能证明用户能分别判断自动决策与人闸；“保留两段证据”不能替代独立签收与必要 review。
  - **建议：** 至少恢复两个 normal 卡。若要保留一次受控运行以减少搭建成本，应只复用 fixture/公共准备，不合并验收、review、用户人判或高危授权。

- **P1｜四合一 RLT_03 不是可操作的单一验收单元。**
  - **问题：** 候选把 parser/lint、纯追加状态机、status/lifecycle、Recipe/config 四个原 heavy 卡合为一张，称同一文件与 unittest 足以守住边界（`drafts/RLT-B-03-颗粒度优化-调整候选.md:19-24,78`）。
  - **原始需求或独立事实：** B 的颗粒度关要求“每任务是一个验收单元”。正式方案将这些定义为可独立实现、证明、签收的解析、追加状态机、status 生命周期、配置 Recipe，并明确大量断言集中也不按单条碎卡（`dev_plan/P1-RelayLight-开发方案.md:648-651`）。机械映射显示候选 RLT_03 单独承接 60 余条机器验收，其中含互相独立的配置权威/Recipe（A91/A92/A99/A115-A117）、账本状态机、以及 status JSON/生命周期；五路仅是同一张卡的 review 次数，不会把 60 多条合同变成可复核的一个单元。
  - **影响：** D 开工无法写出可审的 task_plan 而不退化为“全绿”；任一子合同失败都会阻塞全部核心和 5 路复核，反而扩大返工半径，也无法尽早交付可用解析/账本结果。
  - **建议：** 不接受四合一。至少重切为两张可独立验收的 heavy 卡（例如按“plan/lint+账本写入合同”与“status/lifecycle+配置 Recipe 合同”重新核依赖），或保留正式方案的四张；每张列明其 ID 群、可单独运行的测试入口和下游依赖。先有此切法，才可重新计算路径节省。

- **P1｜RLT_12 在未登记全量测试入口前跑高危首个 demo，§2.5 的自洽性不足。**

  - **原始需求或独立事实：** 正式输入 §3.8 明定 Python 测试必须经 `tools/tests/relay-light-log.ps1` 登记到 `$suites`，再由 `run-relay-tests.ps1` 跑全量（`design/01-RelayLight-产品设计与验收.md:442-446`）；正式计划将 RLT_10 和 RLT_20 都放在 RLT_12 前，并令 RLT_20 在 RLT_07/08 后、RLT_12 前完成（`dev_plan/P1-RelayLight-开发方案.md:528-534`）。候选的“RLT_03 自身 unittest 已通过”并非已登记全量入口，也未定义 RLT_12 的等价准入证据。
  - **影响：** 用户会看到一次真实目录写入和真计划 demo，却未得到仓库标准回归的证据；A11/A16 与 H1 的失败定位被混在事后 RLT_10，违背尽早交付“可用且可验证”结果。
  - **建议：** 将测试薄壳/全量登记从 RLT_10 拆为首 demo 前的小卡或明确前置子交付，恢复为 RLT_12 依赖；把 A13 的退场核对与三条教训回流留在 demo 后。这样仍可合并后半段而不把验证闸后移。

#### 用户理解风险

- **P1｜“12 卡/42 路”容易被理解为等价地减少了流程，而实际取消了两类需求复核并合并了四个/三个独立签收。**
  - **问题：** 候选把路径下降作为核心收益（`drafts/RLT-B-03-颗粒度优化-调整候选.md:12-15,89`），但没有逐项向用户标出哪些是可安全复用的准备，哪些是被移除的独立审查/人判。
  - **原始需求或独立事实：** 用户问的是是否“过度设计”，不是授权降低需求复核或推翻其已确认的 H16/H17、RLT_14/15 裁决；AGENTS 的 light/normal/heavy 覆盖范围不同。
  - **影响：** 用户可能误以为只是删重复 worktree，实际接受了较少的需求方向复核和更大的失败半径。
  - **建议：** 面向用户的讲解须提供“原卡→候选卡→保留/合并/取消的 review 路径→仍独立的人判”对照表，并把任何降为 light 或合并 H16/H17 标成显式产品/风险取舍。

- **P2｜首 demo 的“可跑”与“已通过仓库回归”会被混同。**
  - **问题：** RLT_12 被表述为首个可演示闭环，同时 RLT_10 的全量入口延后。
  - **原始需求或独立事实：** §3.8 区分直接 Python 回归与登记进仓库 runner 的入口；两者跑同一测试文件，但证据意义不同（`design/01-RelayLight-产品设计与验收.md:442-446`）。
  - **影响：** 用户可能把 demo 的局部 unittest 绿误读成已完成 A11 的仓库级证明。
  - **建议：** 若保留候选方向，展示时明确写“demo 前仅何种测试；全量 runner 尚未完成”，并在用户确认前决定是否接受该风险；更好的默认仍是先恢复测试前置。

#### 需要用户决定的问题

- **P1｜是否明确推翻已确认的“按用户能一次判断的场景切卡”裁决，以换取 12 卡？**
  - **问题：** 候选的 RLT_16/19、RLT_14/15 合并与降档，已不是单纯去重。
  - **原始需求或独立事实：** 用户 2026-09-09 对“19 卡是否太多”的回答是确认保持，并接受 H16/H17 拆卡及实跑卡 normal 的裁决（`design/evidence/02-交叉审核记录-RelayLight-B拆计划.md:81-84,152-154`）。

  - **建议：** 默认选择“不推翻”：恢复上述四张独立卡/normal。若用户选择推翻，须逐项确认：H16/H17 是否允许同一签收、H6/H15 是否允许无需求复核、每个真实目录写入是否仍逐次单独授权；确认后再做定向复审。

- **P1｜首个真实 demo 是否必须在仓库全量测试入口已登记并通过后才允许开始？**
  - **问题：** 候选把此从正式方案的依赖关系改成了卡内 unittest 提示，属验证/风险边界改变。
  - **原始需求或独立事实：** §3.8 和 A11 已规定标准仓库入口；RLT_12 同时涉及真实用户目录写入与 Windows 真计划。
