一、方案问题

无 P0。

P1

- 正式输入的 Recipe 发生直接冲突 → §6.2 写 `normal` 含 `code-round2` 且使用 `[rework]`，§6.3 与 `HC-RL-A115` 则要求 normal 仅 requirement+lesson、配置使用 `[limits]`，并声明 §6.2 不应复述具体集合 → RLT_06 无法在不自行裁决正式输入的前提下开工 → 回 A 统一删除或修正 §6.2 的旧示例，再由 B 回填 RLT_06。

- RLT_16 不是一个验收单元，且路径范围失控 → 它同时承接可独立通过/失败的 `HC-RL-H16`（卡内追加）与 `HC-RL-H17`（跨卡新增），并写入 `workspace/**/task_plan.md`；这不是指定子树，而是任意卡的施工说明 → 既不能独立签收，也破坏逐条精确允许路径纪律 → B 应拆为两卡；跨卡卡还须由 A 明确“运行中新卡”怎样取得受限、可审计的路径授权，不能以通配整个 workspace 代替。

P2

二、用户理解风险

- “运行中可改计划”不是 agent 可任意改资料：仅限计划、DevPlan、task_plan；设计方案和验收 ID 必须交回用户。当前 RLT_16 的通配路径会把这个边界说宽。

## 四、面向用户讲解、理解问答与确认

### 讲解摘要

**全局地图（五批）**：第 1 批 RLT_01~RLT_08、RLT_10、RLT_12 —— 一致性对照打边界，做出 `relay_log.py` 的 plan 解析、账本追加、status 生命周期、配置 Recipe，写两侧同源 skill，接 AGENTS 与测试入口，**批末 RLT_12 跑出 Windows Claude 的第一份真计划闭环**，这是首个端到端 demo。第 2 批换 Codex 主控复跑并只改配置换协作，顺带回流教训与退场核对。第 3 批做运行中改计划机制与三组异常实跑（auto/consult、返工超限、卡内追加、新增卡追加阶段）。第 4 批到 ThinkPad 补 Linux 两组合，凑齐四组合矩阵。第 5 批做 `watch`。

**五问**：

1. **从哪里进入**——人拉规划 agent 出 `relay_plan.md`，人拉编排常驻；编排按计划开阶段、拉监工，监工拉其余 agent。
2. **状态与结果存在哪里**——计划与账本落 `docs/modules/<模块>/relay/<plan_id>/`，不放任务工作区（因为一份计划可跨多卡）；账本是只追加的 `relay_log.jsonl`，固定七字段。
3. **承诺什么**——程序**只记录不驱动**：节点关闭是固定双条件合取，`status` 只转述账本事实、不判产出合格；协作方式全在配置与模板里，改协作不改代码。
4. **如何独立验证**——119 条验收，机器 104 条走单测与静态检查，人验 15 条由用户看证据判断；`lint` 每条规则的编号就是验收项 ID。
5. **失败怎么办**——两套独立止损：节点内 attempt 上限 3、返工轮数上限 2，谁先到谁触发，出口相同（拉 strategist，永远交用户裁决）；监工挂了先关旧 pane 再重拉，编排挂了从 `status` 定位当前阶段续跑。

**三个理解风险**（承接审核第二段，已当面讲清）：运行中改计划只能碰计划、开发方案、任务卡，设计方案与验收 ID 一律交回用户；第 1 批只证明第一个闭环，四组合矩阵要到第 4 批；账本的 `done` 是监工读完产出的判断，与 Herdr 的 `done`（进程停下）不是一回事。

### 理解问题（一次一问）

**问**：新增任务卡这个场景里，新卡的工作区七件套由谁建、什么时候建？

**用户答**：「接力计划增加这张卡的节点，之后按正常任务跑。」

**判定：理解正确。** 用户说的「按正常任务跑」正是设计的落法——改计划实例只往开发方案加任务行、往 marker `cards` 加卡号、往 `relay_plan` 追加该卡的 W/C/R/F 阶段行；七件套（含 `task_plan.md`）由**该卡 W 阶段的 builder** 在编排开到新 W 阶段时照常建，改计划实例写它即判失败（HC-RL-A122）。这一条已固化进 §4.5.2 与 §4.5.3 第二种情况，并由 RLT_19 实跑验证。

### 用户另提出的问题

**用户问**：19 张卡是不是太多了？

**主会话解释**：19 张按性质分四类——**6 张实现卡**（RLT_03 解析、04 账本、05 status、06 配置、07 skill、09 改计划），**4 张基础设施卡**（RLT_01 两侧同源、02 一致性对照、08 AGENTS 接入、10 测试入口），**8 张实跑取证卡**（RLT_11~17、19，绝大多数是人验，用户要亲自看证据判断），**1 张 watch**（RLT_18）。真正写代码的只有 6 张，其余是取证与接线；实跑卡按「用户能一次判断的场景」切，合并反而让人验签不动。**建议保持 19 卡。用户确认。**

### 用户决定（2026-09-09）
