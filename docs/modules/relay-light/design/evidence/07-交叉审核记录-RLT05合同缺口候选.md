## 1. A06（RLT-A-06 共创草案 v1）复核结论

**VERDICT = REVISE｜P0=0 · P1=1 · P2=5 · P3=4**

### 1.1 方案问题

#### A06-P1-1｜H3 的五情形 resolver 与“安装器只有 `--all`、两侧总是同时安装”相冲突：H2 与 RLT_12 的无 flag 默认副本实跑按设计无法完成

- **问题**：A06 §4.2 规定：没给 `--config-dir` 时，只有一侧目录存在才自动选中；**两侧同时存在就退出 3**。A06 §4.2 末句又要求“§6.2.1、§3.1、A99 与 H2 的无 flag 默认安装副本实跑必须同步采用这一闭集”。但按正式合同，只要机器装过 skill，就一定两侧都有：
  - design/01 §8.1:877：“`--all` 从当前用户 home 派生两个固定目标，每次覆盖全部五文件”；
  - DevPlan RLT_01:118：“生产命令只提供 `--all`，从当前用户 home 派生 Claude/Codex 两个固定目标”；
  - A32（RLT_12 准入）要求“两个用户级目录的五文件分别与仓内源逐字节一致”，也就是两侧必须同时存在；
  - A125 要求四个用户级目录哈希全等。
- **原始需求 / 独立事实**：用户对 H3 的授权是“正式定义…默认目录判定”，而不是“取消默认目录”。H2（design/01:1241）写的是“至少一次不带 `--config-dir`、直接使用默认用户级安装副本”。DevPlan RLT_12:370 写“满足后直接使用默认 Claude 副本”，RLT_13:377/386 写“另跑一次不带 `--config-dir` 的默认 Codex 副本”。Fable D3 当初说“H2 依旧成立（单副本机器不传参可跑）”，但它依赖的“单副本机器”在现行安装器合同下不存在。另外，“当前平台”本身也有歧义：调用 `relay_log.py` 的是 orchestrator/monitor pane，而 roles.toml 把它们配成 `launch = "herdr:codex"`（design/01:772-778），即便主控是 Claude Code 也一样。所以“按调用者识别平台”也行不通，A06 禁止猜身份是对的。
- **影响**：一旦 A06 晋级，每台按合同安装过的机器上，不带 flag 调用都会退出 3。H2 这条人验在结构上做不到；RLT_12/13 的实施提示变成不可执行的指令；§8.1:879 的“否则读当前 CLI 的用户级 skill 目录”也和新规则冲突。缺陷要到 RLT_12/RLT_13 实跑时才会暴露，属于跨卡返工。A06 §7「AI 可证明 3」写的“H2 默认副本实跑没有互相矛盾”，从机械上看不成立。
- **建议**：晋级前必须由用户在以下方案中拍板（见 §1.3 A06-D1），并把选定方案同步写进 A06 §4、§6 和 B06 §3：
  - (a) **保留五情形 resolver，改写 H2**：adapter 总是把自己那一侧的默认安装副本路径作为 `--config-dir` 显式传入。H2 的命题从“不带 flag”改为“用默认安装副本、不用 fixture”。按协议二这属于语义变化，要退役 H2 并续发新 H 号，人验总数仍是 15。RLT_12/13 的提示同步改写。
  - (b) **引入宿主提示**：由 adapter 设置固定环境变量（例如 `RELAY_LIGHT_HOST=claude|codex`），或者给三个子命令都加 `--host` 可选参数。没有显式目录时按提示选侧；没有提示且两侧都存在时仍退出 3。H2 字面不变，但这是一条新的隐式或公开合同，需要进 §3.1、§6.2.1 和 adapter 验收（RLT_07 的 A26 或新 ID）。
  - (c) **安装器改为可以只装单侧**：这会推翻 A32、A124、A125 与“只提供 `--all`”，不建议。
  - 复核倾向 (a)：它不新增隐式合同，还彻底消除“谁是当前平台”的歧义。但这改变了用户可见的 H2 命题，只能由用户决定。

#### A06-P2-1｜H3 没有同步退出码表与错误编号：“配置失败退出 3”在 §3.1 冻结表里没有位置，错误 `<code>` 也没定

- **影响**：一致性路会判“退出码表与实现不闭合”；施工者要自己选错误编号，可能把配置错误报成已退役的 A91，或借用其他编号冒充。RLT_03 已验收的“3 的含义”被悄悄扩大，却没有留下记录。
- **建议**：§3.1 表中 add/status/lint 的 `3` 都补上“配置目录无法判定，或选中配置缺失、不可读、解析失败”。A06 冻结错误编号，建议：目录判定失败（双侧、零侧、显式目录不存在）用 `HC-RL-A99`（如采纳 A06-D2 则用 A135）；roles.toml 加载失败用 `HC-RL-A131`；dh-mapping.toml 加载失败用 `HC-RL-A92`。另写明“RLT_03 回归测试改为显式 `--config-dir` 属于 fixture 对齐，A5/A56 命题不变”。

#### A06-P2-3｜A132 的证法范围写错，“模型名”闭集也没定义，oracle 无法机械判定

- **问题**：A06 §3 表中 A132 的证法是“对 RLT_07 创建的 skill 五件做闭集静态检查”。但：
  1. 五件里的两份 TOML 由 RLT_05 创建（findings F-008；RLT_05 allowed-paths 含两份 TOML），RLT_07 并不创建五件；

  3. 产品承诺一栏写的是“skill 核心、adapter、五阶段模板与流程说明”，与证法的“五件”自相矛盾；
  4. 什么 token 算“模型名”，没有给闭集。
- **原始需求**：design/01 §2.3:170 写的是“**流程文档与模板**不写死模型，一律引用角色名”，指的是流程文档与模板，并不包括 roles.toml。

### 1.2 用户理解风险

1. **“Claude 主控读 Claude 目录”这句话不再成立。** 在 A06 的规则下，选哪一侧只看目录是否存在，与谁在当主控无关。而正常安装后两侧都存在，所以不带 flag 就会被拒。用户如果按原 §6.2.1 的直觉理解，会误以为 H2 仍可按原样实跑（见 A06-P1-1）。
2. **A99 号没变，但多了新的失败行为。** 用户可能以为 A99“只是补了说明”，实际上它新增了“双侧/零侧退出 3”等可独立失败的断言（见 A06-P2-5）。
3. **RLT_03 已验收的 CLI 行为会被 RLT_05 改变。** add/status 多了“配置不可用 → 退出 3”的来源，RLT_03 的测试都要显式带 `--config-dir`。命题不变，但用户可能误以为 RLT_03 完全不受影响（见 A06-P2-1）。
4. **checker 的“默认挂”只由 RLT_07 证明**（A133，而且与 A95 大量重合），RLT_05 只证“删掉也能用”（A134）。用户应该知道 RLT_05 收口时并不包含模板证据。

##### R2-A06-P2-3｜显式 `--config-dir ~/.claude/skills/relay-light/` 依赖 shell 展开 `~`，没有规定 resolver 是否 expanduser

- **问题**：A06 v2 §4.2:60 与 §4.4 要求 adapter 传 `~/.claude/skills/relay-light/`、`~/.codex/skills/relay-light/`。Python argparse 不展开 `~`；Windows 上经 PowerShell 或 Herdr `pane run` 转发给原生程序时，也不能保证展开。A06 只规定了默认候选按 home 判定，没有规定显式值要不要做 `expanduser`，也没说 `plan_loaded` 里的 `config_dir=` 记原样值还是展开值。
- **独立事实**：首个端到端 demo 在 Windows（RLT_12）；DevPlan 已有用 `%USERPROFILE%` 解析绝对路径的先例（RLT_12:370）。§6.2.1 样例 `config_dir=~/.claude/skills/relay-light`（design/01:717）使用 `~` 形态。

#### 7.2.1 方案问题

##### R3-A06-P2-1｜`config_dir=` 要求记录“规范化绝对路径”，但账本 note 按空白切分 key=value；Windows 用户目录中的空格会让路径在记录时被截断

- **问题**：A06 v3 §4.3:80 规定 `plan_loaded.note` 中的 `config_dir=` 统一记录“展开、规范化后的绝对路径”。§4.2:60 要求 adapter 传“当前用户 home 下…的绝对路径”。RLT_03 已实现并 verify 的 note 语法是按空白切分的 `key=value` 列表：`relay_log.py:596` 的 `_validate_plan_loaded_note` 与 `:560`、`:522` 都用 `note.split()`，design/01 §6.2.1:717 的样例也是空格分隔的键值对。A06 没有规定值中含空白时如何表示，也没有规定“规范化”具体用哪种变换（是否解析符号链接、Windows 分隔符写 `\` 还是 `/`）。
- **独立事实**：首个端到端 demo（RLT_12）与 H18（RLT_13）都在 Windows 上。Windows 用户目录含空格（例如 `C:\Users\First Last`）是常见情况，而本仓无法预知用户的实际 profile 名。
- **影响**：遇到这种目录时，`config_dir=C:\Users\First` 与 `Last\.claude\skills\relay-light` 会被拆成两个 token。A99 的“含 `config_dir=` 与 `plan=` 两个键”检查照样通过，但账本记录的路径是错的，而 H18、H10 恰恰要求用户凭账本的 `config_dir=` 判断“是否用了默认副本”，这就产生了一条会误导人验的证据。另外，“规范化”的口径不同，两台机器上同一目录的记录形态也会不同，影响跨机比对。
- **建议**（主控二选一冻结，写进 A06 §4.3 的 A135）：
  - (i) **编码**：`config_dir=` 的值 = 对显式值或默认候选依次做 `~` 展开 → `abspath` → `normpath`（**不**解析符号链接）→ 分隔符统一为 `/` → 空白按 `%20`、`%` 按 `%25` 百分号编码。A135 的测试补一例：伪造一个含空格的 HOME/USERPROFILE，断言记录值无空白且解码后等于实际目录。

- **全局地图**：A06 已把产品合同缺口写入唯一正式 design 输入；B06 只把新合同原子分账到 DevPlan 与 RLT_05 workspace，不改变任务集合、依赖、批次、档位、task_type 或 allowed-paths。
- **契约与状态**：RLT_05 仍为 25 条，但旧 A117/A91/A108 分别转移或退役，换入 A131/A134/A135；RLT_07 变为 20 条；全局为 111 A + 15 H = 126。B06 落盘本身不改变 RLT_05 的施工状态。
- **运行机制**：B06 正式同步后，工作区先进入 `blocked-by-D-start-authorization`；只有后续独立 D-start 才能把 RLT_05 改为进行中并开放 Batch 1。后续 Batch 仍逐批由主控派发。
- **独立验证**：fresh Opus 正式 B-review 后，v5 窄核结论为 `APPROVE`；机械闭集验证 owner、计数及任务状态/依赖/批次/task_type/allowed-paths 不漂移。落盘后再检查 DevPlan 活动 ID、25/20/126 计数与 workspace 旧 blocker 零活动命中。
- **失败处置**：合同、owner 或闭集不一致时不启动 worker；worker 遇到歧义只写 `BLOCKED` durable signal，不自行问用户、不越到下一 Batch。

### 12.2 理解问题与用户回答

- 主控提问：“B06 落盘后，DeepSeek 是自动开工，还是仍须独立 D-start 授权后才能开工？”

- 结论：理解通过。用户清楚 B06 确认与 D-start 是两道闸。

### 12.3 B06 正式落盘确认

用户的“后者，继续”按主控上一轮给出的精确语义，首先确认 B06 正式落盘：允许更新 DevPlan 活动事件、owner/计数/五张卡联动、design 顶部追踪句，以及 RLT_05 workspace 六件同步。该确认不授权 commit、push、PR、verify、merge、deploy 或清理。

### 12.4 独立 D-start 授权

同一句“后者，继续”在明确选择“仍须独立 D-start”后，又按主控上一轮明示的连续动作授权启动原施工。因此 B06 落盘完成后，独立 D-start 闸成立：RLT_05 可机械改为“进行中”，只开放 Batch 1，并按原定 OMP `opencode-go/deepseek-flash` worker 路由启动 `rlt05-build-deepseek`。后续 Batch、review、commit、push、PR、verify、merge、deploy 与清理仍各守原闸。
