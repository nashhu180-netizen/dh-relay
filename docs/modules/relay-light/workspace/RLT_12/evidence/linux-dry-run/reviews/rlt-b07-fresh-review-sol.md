1. **P1｜A112 与 A137 的活动 oracle 互相矛盾**：问题 → 新增 HC-RL-A137 要求节点未关时，带合法 `ref=` 的 `stage_result outcome=blocked/failed` 可接受；但仍处于活动清单的 HC-RL-A112 仍无条件规定 `stage_result` 早于末个 `node_close` 必须退出 2，DevPlan §6 又把两条都按“正好一次”映射。原始需求或独立事实 → 用户同意把预演发现“先转成对 SKILL.md 的修订卡（B-adjust）再跑正式”；独立核查现役 `relay_log.py:1979-1984` 也确认 A112 当前确实对所有 outcome 统一拒绝未关节点。影响 → 施工者无法同时让 A112 与 A137 全绿，RLT_21 的核心异常出口在合同层就不可判定。建议 → 原子修订 A112 为仅约束 `done/cancelled` 的前置，或在 A137 明列 `supersedes/clarifies A112` 并同步 A112 文本、证明方法及 RLT_05/RLT_21 owner 边界。

2. **P1｜`launch_fix` 分桶可无限刷新 attempt 止损**：问题 → A138 规定 `attempt_max` 按任意 `launch_fix=<token>` 值分别计数，却没有 token 闭集、可用分桶上限或必须绑定某次 `user_decision`；不断换 token 即可不断取得新的三次预算。原始需求或独立事实 → DR-F-002/003 的触发背景是消除 34 分钟静默和三次 NOT_RUN 后无合法出口；独立核查 §7.3 仍声明“两套止损谁先到上限即停”，现役 `loss_stop()` 也只按 `(node, agent 名)` 累计每条 `agent_launch`（`relay_log.py:2563-2584`），并不存在分桶。影响 → 新规则反而允许监工绕过止损，且 A138 把“第 4 条无 fix 拒”误称为 A113 上限，而活动 A113 只校验重拉前因、不定义上限。建议 → 冻结可执行预算，例如每次明确 `user_decision` 只授权一个新的 `launch_fix` 组、全节点最多 N 组；为授权引用和不同 token 逃逸各加反例，并校正 A113/A107 的引用关系。

3. **P1｜A140 把账本静默误写成终端与产出静默**：问题 → §7.3 的判定条件是 agent 处于 working 且“产出与终端均无变化”，A140 却要求 `status` 仅凭静默时长标 `silent_timeout`。原始需求或独立事实 → DR-F-002 记录的是 Herdr 进程存活、Connection lost、34 分钟无产出；独立核查现役 `derive_status()`/`AgentState` 只从账本最新事件 `last_ts` 计算 `idle_seconds`（`relay_log.py:2485-2502`），既不读取 Herdr working 状态，也不观察终端或产出文件。影响 → 活跃但未频繁写账的正常长任务会被误标挂死，随后模板要求中断并记 `agent_lost`，存在误杀与产出损坏风险。建议 → 把 status 字段明确命名/定义为 `ledger_silent_timeout` 提示；真正中断前由 adapter/监工同时核验 Herdr 状态、pane 与允许路径产出变化，并给“账本静默但终端仍更新不得中断”的反例。

4. **P2｜覆盖自查仍停在修订前计数**：问题 → DevPlan §6 尾注和 §8.1 仍写 `111+15=126`、126 个 ID、17 张卡、§14 七项；草案实际已是 `117+15=132`、132 个唯一映射、18 张卡、§14 八项。原始需求或独立事实 → 独立脚本限定 DevPlan §6 提取到 132 个唯一 ID、0 重复，其中 A=117、H=15；design §11 抬头也为 132。影响 → “正好一次”表本身目前成立，但自查证据自相矛盾，会让用户误以为新增六条尚未进入覆盖检查。建议 → 同步 §6 尾注与 §8.1 四个数字/项数，并保留机器提取结果作为审核证据。
